# 浏览器执行面「直连化」方案 —— 主进程本地端点 + 服务端直连

> 2026-10-10 · 状态：**方案稿，未动代码**
> 结论依据：全部带 `文件:行号`，源码逐处核实（非文档转述）。
> 触发：此前任务清单里的「浏览器执行面直连化」条目 —— 因**涉及安全边界**，当时核实后未动，留作专门一轮 + 灰度。

---

## §0 一句话

**把「服务端驱动浏览器」这条链路，从「绕道渲染层（SSE 委托）」改为「服务端直连主进程（本地端点）」。**
浏览器仍然活在 Electron 主进程里 —— 所以「所见即所操作」的单一执行面**不变**；变的只是**谁把命令送进去**：从「渲染层转发」变成「服务端直达」，从而**彻底去掉对渲染层存活与 SSE 订阅的依赖**。

---

## §1 这个任务是干嘛的

### 1.1 现状链路（三段，中间那段是病根）

```
① server  ReAct 主循环        apps/server/src/llm-task-manager.ts
   │  emit(task, {type:'tool:execute'})            :4054
   ▼
② renderer 执行器             packages/ui/src/stores/chat.ts
   │  dispatchToolCall → actionMap → IPC          :1573-1707
   ▼
③ main 执行面                 apps/desktop/main.cjs
   │  ipcMain.handle('browserView:action', ...)   :2449
   ▼
   guest webContents（真实可见的 BrowserView / <webview>）

结果回流：③ → ② → ②用 POST 把结果交回 ① 的 pendingToolCalls
```

为什么中间要走②：因为**浏览器不在 server 里**。server 是**独立进程**（`main.cjs:445` 打包版 `spawn` / `:419` dev 版 `spawn tsx watch`），它拿不到主进程的 `BrowserView` 句柄，只能靠渲染层转发。这也是既定原则「单一执行面」的由来 —— server 端自带的 Playwright 是**另一个浏览器**（headless、被风控弹验证码、预览里看不见），所以在线时绝不允许走它。

### 1.2 缺口（这就是"直连化"要修的东西）

| # | 缺口 | 位置 | 后果 |
|---|---|---|---|
| 1 | **执行依赖渲染层存活** | `llm-task-manager.ts:3825` `task.subscribers.size === 0` → 等 15s | 窗口关掉 / 页面刷新 / 路由切走 → 浏览器工具**做不了** |
| 2 | **一次失败要等两轮重连窗口** | `:3835` 再等 8s，仍失败才报错 | 单次工具调用最坏卡 **23s**，实测症状即"一断全停"（本轮已加宽限，但**只是把等待往后挪，没有消除依赖**） |
| 3 | **无人值守直接空转** | `:4022` `unattendedToolResult()` | 无订阅者 = 浏览器工具**根本不会执行** |
| 4 | **结果要经渲染层 JS 中转** | `chat.ts:1699` 返回文本 → POST 回 server | 服务端信任渲染层；渲染层的格式化逻辑（`:1656-1695`）与 server 的归档逻辑（`:3988`）**两处各写一半**，是"截图在文件管理看不到"这类问题的温床 |
| 5 | **锚定有两个主人** | 渲染层 `agentAnchoredTabs`(`chat.ts:50`) vs 主进程 `activeTabId`(`main.cjs:118`) | 就是历史上"两个 activeTabId 体系"那类坑的复发土壤 |

★ 判据：**只要"执行"这件事必须经过 UI 层，UI 层的任何不确定性都会变成工具执行的不确定性。**
"直连化"= 把这条依赖从链路里**结构性去掉**，而不是继续用重连窗口去补。

## §2 方案总览

```
直连化后：

① server  ReAct 主循环
   │  HTTP POST http://127.0.0.1:<随机端口>/v1/browser/action
   │  header: x-yz-bridge-token（每启动随机生成）
   ▼
③ main  浏览器桥（新增 apps/desktop/browser-bridge.cjs）
   │  → runBrowserAction(tabId, action, args)   ← 与 IPC 入口共用同一实现（唯一 switch）
   ▼
   guest webContents（画面/虚拟光标/输入锁 全部不变）

② renderer 降级为**观察者**：只收 server 的 tool:start / tool:result 做展示，不再执行
```

**关键点：可见性一点没变。** 浏览器仍在主进程的 BrowserView/webview guest 里，虚拟光标仍是主进程 `browserView:cursor` 广播（`main.cjs` 收尾读回坐标那段不动），"Agent 接管中"输入锁仍由 `browserSteps` 事件驱动。**变的只有"命令入口"**，所以不违反"单一执行面"，反而更彻底。

## §3 主进程侧（新增）

### 3.1 端点定义

| 项 | 取值 | 理由 |
|---|---|---|
| 绑定地址 | `127.0.0.1` **硬编码** | 绝不 `0.0.0.0`；loopback 绑定的 HTTP 服务不触发 Windows 防火墙授权弹窗 |
| 端口 | `0`（自动分配） | 与 CDP 端口同一手法（`main.cjs:4596-4607` 注释已论证"自动选端口从根上消除抢占"），多实例并存不冲突 |
| 路径 | `POST /v1/browser/action` | 单一入口，body `{ convId, tabId?, action, args }` |
| 返回 | 与 `browserView:action` **逐字同构**（`{ok}|{error}` + 各 action 字段） | 让 server 的现有结果后处理与格式化**零改动复用** |
| 鉴权 | `crypto.randomBytes(32)` 每次启动随机；`timingSafeEqual` 比对 | 见 §6 |
| 失败响应 | 无/错 token → **统一 404**（不泄露端点存在） | 见 §6 |

### 3.2 能力面（★ 必须收窄）

- **只暴露 `browser_*` 对应的 action**，且 action 必须在 `DESKTOP_BROWSER_ACTIONS`（`main.cjs:2436-2444`，已是单一真相源）白名单内。
- **不暴露** `shell` / `mcp` / 文件系统 / 打开外部链接等其它 IPC 能力。端点**不是**通用 IPC 隧道。
- `run_script` 沿用**现有**沙箱与闸门（超时/截断/防循环），不为桥另开一套。

### 3.3 抽「唯一实现」（防两入口行为漂移）

现在 `browserView:action` 的 handler（`:2449-2488` 取 wc + 后面整个 `switch`）是唯一的 action 分发处。
桥不能复制一份 `switch` —— 必须抽 `runBrowserAction({ tabId, action, args, convId })`，
由 **IPC handler 与 bridge 共同调用**。否则"两处实现"必然漂移（本项目一贯判据）。
> 守门测试断言：`browserView:action` handler 内**不再自带 switch**。

### 3.4 会话 → tab 锚定**下沉到主进程**（★ 本方案最容易出错的一点）

现状：`webviewTabs` 的 meta 是 `{scope, lastActiveAt, wcId, agentOpened}`（`:1413`）—— **不带 convId**；
"某会话当前锚在哪个 tab"由渲染层 `agentAnchoredTabs`（`chat.ts:50`）持有。

直连后 server 只知道 `convId`（`ToolContext.conversationId`，A4 已打通，见 `browser/index.ts:64`），
**不知道 tabId** ⇒ 主进程必须自己维护 `convAnchors: Map<convId, tabId>`：

- `navigate` 成功 → 锚定该 convId；tab 关闭/销毁 → 失效（收口在 `closeTabById`，`:1431`）；
- 请求未带 tabId → 按 convId 取锚；**未锚定 → 明确报错**（不静默用 `activeTabId` 全局值 —— 那正是"跨会话打到别人的页"）；
- convId 写入 tab meta，供审计与展示。

★ 语义与渲染层 `resolvePreviewTabId`(`chat.ts:111-120`) **完全一致**，所以**只能有一处生效**：
bridge 开启时以主进程锚为准，渲染层不再锚（渲染层那时也不会执行 browser 工具，天然不锚）。
**绝不能两处同时锚 —— 那是"两个 activeTabId 体系"坑的翻版。**

### 3.5 端点信息如何让 server 知道

| 启动路径 | 传递方式 |
|---|---|
| **A. 桌面端（主路径）**：`main.cjs startServer()` spawn server（`:419` dev / `:445` prod） | 在 spawn 的 env 里加两条：`YZ_BROWSER_BRIDGE_URL` + `YZ_BROWSER_BRIDGE_TOKEN`（与 `editionEnv`/`guardEnv`/`YZ_HOT_RELOAD` **同位置同手法**）。**token 不落盘** |
| **B. 独立 server**：`bin/dev.mjs server` 直启（无 Electron） | 无桥可用 → 走既有 SSE/Playwright 路径（正合灰度设计）。若确实要支持，再按 CDP 那套写 `userData/BrowserBridgePort`（**暂时不做**，见 §12） |

★ 端口/token 变化的重解析：与 **B8**（`browser.ts:183 reResolveCdpEndpoint`）同一手法 ——
连接失败时重读一次，别把"主进程重启后端口变了"变成永远 ECONNREFUSED。

### 3.6 生命周期

- `app.on('will-quit')` → `server.close()`；端口自动分配 ⇒ 异常退出不留残留端口占用。
- 热重载（dev `tsx watch`）只重启 **server**，主进程不重启 ⇒ 桥与 token 稳定；反过来 server 重启后从 env 重新读到同样两条即可。

## §4 服务端侧（新增接线）

1. 新增 `apps/server/src/browser-bridge.ts`：`browserBridgeAvailable()` / `callBrowserBridge(convId, action, args)`（超时复用 `resolveFrontendToolTimeout` 的分档，错误分类明确）。
2. `llm-task-manager.ts:3821-3850` 的 `isBrowser` 分支改为**三档**：
   ```
   isBrowser:
     ① bridge 可用            → 直连（本方案新增；不再需要 waitForFrontendSubscriber）
     ② bridge 不可用但前端在线 → 保留现有 SSE 委托（行为逐字不变）
     ③ 都没有                 → 保留现有离线报错
   ```
   ⇒ 这就是灰度开关的落点（§7）。
3. **结果后处理收口**：截图归档 `archiveDelegatedScreenshot`（`:3988-4016`）抽成**两路径共用**的后处理出口 ——
   否则"截图进了临时区但登记不进 conversation_file"会以**新形态复发**（C6 刚修过同一处）。
4. `tool:start` / `tool:result` 仍由 server 发（已在 `:683`/`:695`/`:2841` 统一出口）⇒ 前端展示链路**不需要改**。
5. `tool:execute` 对 `browser_*` **不再发出**（或改为"仅通知"事件）—— 见 §5 双执行风险。

## §5 渲染层侧

- `chat.ts:1573-1707` 的 browser 执行分支：**bridge 生效时不再本地执行**，否则就是**双执行**（同一次工具调用打两遍页面）。
- ★★ **判据必须由服务端单一给出**，前端不得自己猜：server 在任务初始化事件里下发 `browserExecution: 'bridge' | 'frontend'`，前端只服从。
  （前端自己去探 bridge 端口 = 又造一份判据 → 必然漂移，且会把 token 暴露到渲染层，**违反 §6**。）
- `chat.ts` 里那份本地执行实现**保留**（web 端 / 桥不可用时仍需要），只是不再是桌面端主路径。
- 展示侧（`browserSteps` / 虚拟光标 / 输入锁 / 面板自动打开）**全部不动**：前者读 `tool:start`/`tool:result`（`:2142-2155`），后两者与 SSE 无关。

## §6 安全边界（★ 本节是这条任务"为什么当初没敢动"的正面回答）

| 威胁 | 具体场景 | 措施 |
|---|---|---|
| **同机任意进程越权** | 本机另一个程序扫端口，直接驱动用户浏览器（读写任意页面、注入 JS、上传本地文件） | ① 每启动随机 32 字节 token；② `timingSafeEqual` 恒定时间比对；③ **无 token/错 token 统一回 404**（不泄露端点存在，不给爆破反馈） |
| **网页侧可达（CSRF）** | 用户在 guest 里访问的**任意网站**尝试 POST 本机端点，借用户之手驱动浏览器（含跨站读取/上传） | ① token **只在主进程内存与 server env**，**绝不**经 preload / localStorage / SSE 下发到任何网页上下文；② 端点不返回 CORS 头、不做预检应答 ⇒ 浏览器侧跨源读响应被拦、写请求因无 token 被拒 |
| **能力面过大** | 端点被当成通用 IPC 隧道（拿到就能调 shell / MCP / 文件） | §3.2：**只暴露 browser action**，且必须在 `DESKTOP_BROWSER_ACTIONS` 白名单内 |
| **跨会话越权** | A 会话拿着 B 会话的 tabId 去导航/读取 | §3.4：tabId 必须属于**本会话锚定**的 tab；未锚定明确报错（复用 A4 的"绝不静默用全局页"语义） |
| **导航到危险协议** | 经桥把预览导航到 `file://` / `javascript:` / 内网探针地址 | 沿用现有校验：`navigate` 已强制 `^https?://`（`main.cjs:1828` 同一实现，因 §3.3 共用）；只读 action 不改页面 |
| **本地 DoS** | 任意进程打大 body / 高频占用 | body 大小上限 + 仅接受 `application/json` + action 白名单前置拒绝 |
| **品级一致性** | 现状 App **已开 remote-debugging 端口（CDP）**，它比本端点**更宽**（无 token，本机任意进程可连） | 本方案顺带**评估纳入**：建议 CDP 同样收口为"仅 loopback 且仅桌面端使用"，作为同轮的安全复核项（不强制改，避scope 膨胀） |
| **可观测** | 出事不知道谁在驱动浏览器 | 全部桥调用落主进程日志（action / convId / tabId / 耗时 / 结果码） |

★ 一句话口径：**这不是"给自己开后门"，而是把"渲染层（一个会被导航到任意网站的上下文）当前的信使身份"，换成"只能被持有一次性随机令牌的本机 server 调用"。安全等级是**升**不是降。

## §7 灰度（canary）—— 四档，逐档可回退

开关：`YZ_BROWSER_BRIDGE = off | shadow | on | strict`（env，主进程与 server 同源读）

| 档 | 行为 | 目的 |
|---|---|---|
| **G0 `off`** | 桥不启动，逐字保持现状 | 默认值；打包版**先不发** |
| **G1 `shadow`** | 桥启动；**只读 action** 走桥（`get_page_content` / `get_page_info` / `get_text` / `get_dom` / `screenshot` / `get_tabs` / `is_visible` / `get_network_log` / `wait_for_request`）；**写 action 仍走 SSE** | 不改用户可见行为，先验证连通性 / 鉴权 / 锚定 / 结果格式 |
| **G2 `on`** | **读写全走桥**；SSE 委托保留为**自动降级**（桥不可达/失败 → 落回 SSE 一次 + 打点） | 日常态 |
| **G3 `strict`** | 全走桥，SSE 委托视为**错误**（打点告警） | 证明"零依赖渲染层"这一目标真的达成 |

- 每档切回 `off` 即可一键回退，且**回退不需要改代码/重打包**（env 级）。
- G1 的"只读先走"划法是刻意选的：只读不改页面状态，即使桥有 bug 也不会把用户的页面搞乱 —— 与现有写路由串行白名单的"读写分治"思路一致（`browser.ts:46-55`）。

## §9 验证

**纯函数/单测**
- `resolveBridgeTarget(convId, tabs, anchors)`：已锚定 → 用它；未锚定 → **明确报错**；无 convId → 旧行为。
- token 校验：正确通过 / 错误拒绝 / 缺失拒绝 / **恒定时间比对**（断言用的是 `timingSafeEqual` 而非 `===`）。
- action 白名单：非白名单 action 被拒；body 超限被拒。

**守门测试（防漂移，本项目重点）**
1. `browserView:action` handler **不再自带 switch**（防两处实现）。
2. 桥暴露的 action 集合 ⊆ `DESKTOP_BROWSER_ACTIONS`（防"能力在、入口断"翻版）。
3. 服务端 browser 分支里 bridge 判定**只在一处**（防入口漂移）。
4. 前端"bridge 生效时不本地执行"的断言（**防双执行**）。
5. `convAnchors` 唯一主人：断言渲染层在 bridge 开启路径下不再写锚。

**真跑（不依赖渲染层 —— 这是本任务的验收核心）**
- 起 dev，**故意让渲染层断开 SSE 订阅**，用 `curl` 带正确 token 打桥 → browser action 仍成功 ⇒ **证明"不依赖渲染层"**。
- 错/无 token → 404；跨会话给别人的 tabId → 拒绝；非白名单 action → 拒绝。
- 端到端：发"打开百度搜 X" → 面板正常打开、虚拟光标可见、正文/编号元素返回正确；
  **中途刷新渲染层**（旧实现必失败）→ 桥路径**继续执行**；
  任务结束 → 截图正常登记进 `conversation_file`（文件管理可见）。
- 四档逐一验证 + `off` 回归（确认 `off` 与现状逐字一致）。

## §10 风险

| 风险 | 级别 | 缓解 |
|---|---|---|
| **双执行**（server 走桥 + 前端仍执行 → 页面被打两遍） | **high** | §5 判定由服务端单一给出；守门测试 4；`tool:execute` 对 browser_* 不再发给前端 |
| **锚定双主人**（渲染层与主进程同时锚 → 打到别人的页） | **high** | §3.4 只允许主进程锚；守门测试 5 |
| **token 泄露到渲染层/网页** | **high** | §6：token 只在主进程内存 + server env；**下发的 `browserExecution` 标记里绝不带 token/端口** |
| 桥与 IPC 两入口行为漂移 | medium | §3.3 抽唯一实现 + 守门测试 1 |
| 独立 server（`bin/dev.mjs server`）拿不到桥 | medium | §3.5-A 明确不支持，走 SSE；这正是灰度路径 |
| 热重载后端点/token 失配 | medium | `env` 注入 + 失败重读（B8 同手法） |

## §12 备选形态（已评估）

**备选 A：父子进程 Node IPC 通道（`spawn` 带 `stdio: ipc`），不走 TCP。**
理论更安全（无 socket 暴露面、无需 token）。**不采用为主方案**，原因：
① dev 下 server 是 `spawn(process.execPath, [tsx, 'watch', ...])`，**`tsx watch` 会在其内部再 fork 真正的应用** →
`server/src` 里进程 `process.send` 可能不存在或热重载后失效（需先实测，收益不确定）；
② `bin/dev.mjs server` 独立启动时**没有父进程通道**；
③ 桥要覆盖"主进程在、server 在"的所有路径，HTTP loopback 是唯一全路径一致的形态。
（保留为 P2 探索项：如果实测 `tsx watch` 下 IPC 通道稳定，可作为**更强鉴权**的替换形态，二者接口等价。）

**备选 B：复用现有 CDP 端口。**
**不可行**：CDP 只能到页面级 domain（Electron 的 CDP 实现还不完整，`Target.createTarget: Not supported` 是既有实测结论），
无法调用主进程的 IPC/action 实现，也就拿不到共享的 `convAnchors`、虚拟光标、输入锁等**主进程侧资产** ——
现在 server 的 CDP 路径只能靠 `pickCdpPage`（`browser.ts:340`）猜页，正是"操作与预览可能不是同一个"的历史病灶。

## §13 分期建议

| 期 | 内容 | 产出 |
|---|---|---|
| **P0** | main 抽 `runBrowserAction` + 锚定下沉 + 桥骨架（token/白名单/日志）**但默认 `off`** | 结构就位，行为零变化 |

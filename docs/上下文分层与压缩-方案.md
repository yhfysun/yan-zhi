## 零、一页纸结论

用户的三条直觉**全部成立**，而且正是主流做法：

| 用户直觉              | 是否成立                                                  | 主流做法                                                    |
| ----------------- | ----------------------------------------------------- | ------------------------------------------------------- |
| 「应该不是把所有消息给到大模型吧」 | ✅ 成立，且**言智现在恰恰就是**（未超阈值时全量历史原样发）                      | 滑动窗口 + 摘要 + 预算分配                                        |
| 「前端显示一份、发给大模型另一份」 | ✅ 成立 —— 这就是 Roo Code 的 **dual message store**         | `ui_messages.json` / `api_conversation_history.json` 两份 |
| 「可以放文件里」          | ✅ 成立 —— Roo Code / Claude Code 的 transcript 就是落盘 JSON | 文件化便于跨会话 resume、归档、脱离 DB                                |
| 「多了还能压缩」          | ✅ 成立 —— 但**压缩必须落库**，否则每步重算                            | 摘要块（compaction block）持久化                                |

**言智当前最大的结构性缺口只有两条**（其余已在上几轮落地）：

| #     | 缺口                                           | 现状                                                                                            | 级别  |
| ----- | -------------------------------------------- | --------------------------------------------------------------------------------------------- | --- |
| **A** | **压缩结果不落库** → 每步重新全量 `loadMessages` + 重新判断压缩 | `messagesToSend` 只改内存变量（`llm-task-manager.ts:1510-1532`），摘要在 `task.summaryCache` 内存对象里，进程重启即丢 | ★★★ |
| **B** | **快照每步存一份全量历史** → O(n²) 库膨胀                  | `system_prompt_snapshot` 单条可达 200KB，快照占全库 75%（237MB）；单会话 183MB（`db.ts:28-40`）                 | ★★  |

外加两条体验/细节缺口（**C/D**，低风险可顺手做）：

- **C** 前端已有 token 用量计算但**没接线到 UI**（`useChat.ts:1294-1306` 导出却零消费点）→ 用户看不到「上下文快满了」。
- **D** 聊天区**无虚拟滚动**，`messageRounds` 全量 computed + 全量 `v-for`（`ChatMessageList.vue:4`）。

## 一、现状核查：言智现在到底把什么发给了大模型

### 1.1 一次请求的 messages 组成（实测伪代码）

```
# ═══ ReAct 每一步都执行一遍（llm-task-manager.ts:1500-1544）═══
messagesToSend = SELECT ${MESSAGE_LIST_COLS} FROM message
                 WHERE conversation_id = :convId      # 无 LIMIT，全量
                 ORDER BY created_at ASC
                 -- ★ 含子智能体消息（未按 parent_tool_call_id 过滤）→ 上下文污染源
messagesToSend = filter(m => m.content || m.toolCalls || role=='tool' || reasoningContent)

ctxWindow = ContextWindow.forContextWindow(resolveContextWindow(cw), keepRecent=6)
if ctxWindow.needsCompression(messagesToSend):        # tokenCount > cw*0.5
    messagesToSend = await ctxWindow.compress(...)    # ★ 结果只落内存，不落库

llmMessages = [ {role:'system', content: 巨大动态 systemPrompt}, ...messagesToSend ]
   # ★ 映射时 reasoningContent 被丢弃（:1539-1544）

apiMessages = sanitizeToolMessages(toApiMessage(llmMessages))   # client.ts，无窗口裁剪
POST { model, messages: apiMessages, tools?, stream:true }
```

**关键点：未超阈值时 = 全量历史 + 超大 systemPrompt 原样发。** 这就是用户说的「把所有消息给到大模型」。

### 1.2 当前的压缩能力（已落地，别重复造）

| 环节          | 现状                                                          | 依据                                        |
| ----------- | ----------------------------------------------------------- | ----------------------------------------- |
| 触发阈值        | `resolveContextWindow(cw) × 0.5`；未声明窗口兜底 **32K**            | `window.ts:19,92-95`；`constants.ts:43-48` |
| token 计数    | ✅ 计 `content + reasoningContent + toolCalls`                | `window.ts:111-120`                       |
| 第①级：老工具输出裁剪 | ✅ 超 8KB 的 tool 消息裁成 头75%/尾25%                               | `window.ts:33,164-171`                    |
| 第②级：整段摘要    | ✅ LLM 摘要，保留工具名与参数原文；带超时降级                                   | `window.ts:269-318`                       |
| 摘要缓存        | ✅ `SummaryCache` 前缀指纹，命中只摘要增量                               | `window.ts:55-60,188-218`                 |
| 保留窗口        | 固定 `keepRecent = 6`，边界回退到 `assistant(tool_calls)` 避免孤儿 tool | `window.ts:173-178`                       |
| 记忆抢救        | ✅ 压缩前 `flushMemoriesBeforeCompression`                      | `memory-service.ts:497-560`               |

## 二、主流框架怎么做（对照证据）

### 2.1 Claude Code（Anthropic）—— 最完整的「分层 + 压缩 + 再注入」

官方文档把上下文窗口拆得很清楚：

| 类别                                          | 压缩后是否保留                                              | 机制          |
| ------------------------------------------- | ---------------------------------------------------- | ----------- |
| `CLAUDE.md` / 项目规则 / **auto memory** / plan | ✅ **每次请求重新从磁盘注入**                                    | 落盘重注入，天然抗压缩 |
| 已读文件内容                                      | ✅ 压缩后**重读最近 5 个**（按修改时间），超大文件降级为路径引用                 | 带预算的重读      |
| Skill body                                  | ✅ 重注入，单 skill 上限 5,000 token，总上限 25,000 token，超出丢最旧的 | 分层预算        |
| 对话历史                                        | ❌ **被摘要替换**（`compact_boundary` 事件）                   | 自动压缩        |
| hooks 加的上下文                                 | ❌ 随对话一起被摘要                                           | —           |

关键机制（可直接借鉴）：

1. **压缩边界事件**：流里发 `type:"system" / subtype:"compact_boundary"`，让 UI 能显示「这里发生过压缩」。
2. **压缩后选择性再注入**：不是一个摘要就完事 —— 规则、记忆、plan 重新从磁盘读，文件内容按需重读。
3. **PreCompact hook**：压缩前可归档完整 transcript。
4. **预算可配**：`/autocompact <tokens>` 设定自动压缩触发点。
5. **提示词缓存意识**：稳定前缀放前面，压缩会破坏前缀所以不能太频繁。

> 原文依据：
>
> - 「Persistent rules belong in CLAUDE.md … because CLAUDE.md content is **re-injected on every request**」
> - 「Right after compaction, Claude Code **re-reads up to five** of the files Claude has read or edited … A file over 5,000 tokens comes back as a **path reference** without its content」
> - 「Compaction replaces older messages with a summary, so specific instructions from early in the conversation may not be preserved」

### 2.2 OpenHands —— Condenser / View 分层（最清晰的抽象）

OpenHands 把「历史管理」拆成三层，**这正是言智缺的那层抽象**：

| 层                      | 职责                                              |
| ---------------------- | ----------------------------------------------- |
| **Condenser**          | 历史压缩器（策略）                                       |
| **ConversationMemory** | 消息格式化                                           |
| **View**               | 中间数据结构，连接两者；`View.from_events()` 过滤掉被遗忘的事件、插入摘要 |

要点：

- **`Condensation` 是一个事件**（含 `forgotten_event_ids`），**写回事件日志** → 压缩本身是**持久化**的。这就是言智缺的 A。
- `LLMSummarizingCondenser(max_size=120, keep_first=4)`：按**事件条数**触发；保留**最前面 4 条**（system prompt / 初始用户消息）+ 最近若干 + 中间摘要。
- `PipelineCondenser`：多级串联（先去老事件 → 再摘要 → 再截断），与言智的「裁剪 → 摘要」同构，但**可扩展成任意级**。
- **触发时机**：每步主动 `condense()`，或收到 `CondensationRequest`（LLM 上下文超限错误）时**强制**压缩。
- 量化收益：单轮成本最多降 **2×**；基线 O(n²) 增长 → 压缩后 **O(n) 线性**。

### 2.3 Roo Code —— Dual Message Store（**直接回答用户「两份」的疑惑**）

| 存储                                     | 用途           | 落盘位置                                                     |
| -------------------------------------- | ------------ | -------------------------------------------------------- |
| `apiConversationHistory: ApiMessage[]` | **发给大模型的那份** | `.roo-code/tasks/{taskId}/api_conversation_history.json` |
| `clineMessages: ClineMessage[]`        | **UI 显示的那份** | `.roo-code/tasks/{taskId}/ui_messages.json`              |

> 「Roo Code maintains **two parallel message stores** with distinct purposes to ensure UI  
> responsiveness while adhering to strict LLM API protocols.」

**这正是用户说的「消息保存前端显示是一份，还有一份应该是跟大模型交互的，可以放文件里」—— 完全正确，而且是落 JSON 文件的。**

其余可借鉴点：

- **Token 预算**：`allowedTokens = contextWindow × (1 - TOKEN_BUFFER_PERCENTAGE=0.1) - reservedTokens(maxTokens)`  
  → **先砍 10% 余量 + 预扣输出预算**，再谈历史。言智现在**没有预留输出预算**。
- **压缩**：`summarizeConversation()`，压缩前 `transformMessagesForCondensing` 把 tool_use/tool_result 块**转成纯文本**（这样摘要调用不必带 tools，兼容 Bedrock 等强制要 tools 的供应商）。
- **孤儿工具处理**：若压缩时正好有 pending 的 tool_use，**注入一条合成的 tool_result**（"Context condensation triggered. Tool execution deferred."）以满足 OpenAI 的配对要求。  
  → 言智的等价物是 `sanitizeToolMessages` + 边界回退（`window.ts:173-178`），思路一致。
- **非破坏性截断**：滑动窗口截断时**不删除**消息，只打 `truncationParent` 标记 → 回滚（Rewind）时可完整恢复。言智没有这个（见 2.5）。
- **AST 文件折叠**（`foldedFileContext`，tree-sitter）：已读过的文件**折叠函数体、保留签名/导出/类型** → 保住结构感知但大幅降 token。这是「文件化上下文」的高阶形态。

### 2.4 LibreChat —— 配置化的 summarization + contextPruning

- `summarization` 配置：`trigger{type:token_ratio, value:0.8}`、`maxSummaryTokens`、`reserveRatio=0.05`、`provider/model`（**摘要用小模型**）、自定义 `prompt` / 支持「已有摘要时」的 `updatePrompt`。
- `contextPruning`（**在摘要之前**先做，与言智第①级同构但更细）：
  - `softTrimRatio=0.3` / `hardClearRatio=0.5`（按占用比例分级）
  - `minPrunableToolChars=50000`
  - `softTrim: {maxChars:4000, headChars:1500, tailChars:1500}`
  - `hardClear: {placeholder: '[Old tool result content cleared]'}`  
    → **两级处理老工具结果：先软裁剪（头尾保留），再硬清除（只留占位符）**。
- `memory` 配置：`tokenLimit` / `charLimit(10000)` / `messageWindowSize` / `maxInputTokens(12000)`。
- 「清空上下文但保留总结」是显式 UI 能力。

### 2.5 Cline —— 优先级排序 + 智能截断

- **三层 tracker**：`ModelContextTracker`（token 计数）/ `FileContextTracker`（文件内容 + AST）/ `EnvironmentContextTracker`（OS/shell/工作区）。
- **优先级排序**：最近修改的文件 > 未修改的；用户显式 @ 的 > 自动发现的；小文件 > 大文件。
- **智能截断**：大文件只留头 N 行 + 尾 N 行，中间用 `…` 标记（与言智 `capLongText` 完全同构）。
- **增量更新**：只重读改过的文件 + 缓存 AST + 监听 fs 变化。

## 三、设计方案：三层上下文视图 + 持久化压缩

### 3.1 总架构：把「一份」拆成「三份 + 一个视图」

```
┌─────────────────────────────────────────────────────────────────────┐
│  ① 事实库（永久，供 UI / 回放 / 审计）                                │
│     message 表 —— 全量原文，只追加不删                                │
│     ★ UI 显示读这里；★ 不再让 LLM 直接读全量                          │
├─────────────────────────────────────────────────────────────────────┤
│  ② 摘要层（永久，供 LLM 与大历史）  ← 【本轮核心新增】                 │
│     message_summary 表：{ id, conversation_id, message_ids_json,     │
│                          summary, tokens, created_at }               │
│     等价于 OpenHands 的 Condensation 事件 / Claude Code 的           │
│     compact_boundary。★ 落库后「每步重算摘要」彻底消失                │
│     可选文件镜像：<convDir>/summary.json（跨设备/脱离 DB 用）          │
├─────────────────────────────────────────────────────────────────────┤
│  ③ 分层素材（已有的记忆/规则/计划，保持文件优先）                      │
│     MEMORY.md / decisions.md / plan.md / AGENTS.md / *.md rules      │
│     ★ 落盘 → 每次请求重新注入 → 天然抗压缩（Claude Code 的做法）       │
└─────────────────────────────────────────────────────────────────────┘
                              ↓ 每步组装一次
┌─────────────────────────────────────────────────────────────────────┐
│  ContextView（唯一组装出口，对应 OpenHands 的 View）                  │
│                                                                      │
│  [system] ① 指令层   base prompt + 工具清单 + 工作目录 + 项目规则      │
│                     ← 稳定前缀，利于上游 prompt cache                 │
│  [system] ② 记忆层   空间记忆 + 决策记录 + 计划 + 向量记忆             │
│                     ← 慢变量                                          │
│  [system] ③ 摘要层   最新 message_summary（无则空）                    │
│  [user/assistant/tool] ④ 近期原文  最新 K 轮 + 所有未闭合工具对        │
│                                                                      │
│  组装前：预算检查 → 超限则（裁剪 → 摘要 → 落库）                       │
└─────────────────────────────────────────────────────────────────────┘
```


**为什么要「唯一组装出口」**：本项目已经因为「同一语义两处各写一份」踩过多次坑（`MESSAGE_LIST_COLS`  
两处列清单、空转判据两处常量、允许根两处推导）。上下文组装同理 —— 目前 `llm-task-manager`  
主循环与子智能体循环**各写一遍**（`:1510-1532` 与 `:3212-3221`），必须收敛成一个函数。

### 3.2 核心改动一：压缩结果落库（治缺口 A）

**现在的行为**（每步 O(n) 重复）：

```
step N   : loadMessages(全量 1156 条) → 超阈值 → compress → 摘要(可能带 LLM 调用) → 只改内存
step N+1 : loadMessages(全量 1158 条) → 超阈值 → 又 compress → 又摘要 → ...
```

**目标行为**（每步 O(增量)）：

```
step N   : loadContext = [最新 summary] + [summary 之后的新消息]   ← 只读增量
           若 (summary.tokens + 新消息.tokens) 未超预算 → 零压缩调用
           超预算 → 增量摘要 → ★ 写回 message_summary（append 一条）
step N+1 : 读到的就是已压缩后的短历史
```

**表结构建议**（与 OpenHands `Condensation` 对齐，保留可追溯性）：

```sql
CREATE TABLE IF NOT EXISTS message_summary (
  id                 TEXT PRIMARY KEY,
  conversation_id    TEXT NOT NULL REFERENCES conversation(id),
  user_id            TEXT NOT NULL REFERENCES user(id),
  message_ids_json   TEXT NOT NULL,   -- 被本摘要覆盖的消息 id 列表（前缀指纹 + 明细，供回滚/审计）
  summary            TEXT NOT NULL,
  tokens             INTEGER DEFAULT 0,
  created_at         INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_summary_conv ON message_summary(conversation_id, created_at);
```

**读取规则**：取 `created_at` 最大的一条 → `messages = summary + id > lastCoveredId 的消息`。  
**写入规则**：追加不覆盖（保留历史摘要，支持回滚与审计；清理策略见 §3.7）。

> ★ 判据（本项目反复出现的坑）：**"压缩结果只落内存" = 每步重算，等价于没压缩。**  
> 这与 2026-10-01 已修的「`loadMessages` 读了就丢」是同一族问题的两个变体 —— 一个读了不用，一个算了不存。

### 3.3 核心改动二：预算分配（对齐 Roo Code / LibreChat）

**现在**：只有一条线 —— `tokenCount(messages) > cw × 0.5` 就压缩。**没有输出预留、没有分层预算**。

**建议**：

```
totalBudget  = resolveContextWindow(model.contextWindow)        # 未知 → 32K
outputReserve = clamp(maxTokens, 4096, 16K)                     # 输出预留
usable       = totalBudget - outputReserve                      # 对齐 Roo Code 的 allowedTokens
  ├─ 指令层上限  ≤ 20% usable     （超限则截断 skill body / 规则，保留骨架）
  ├─ 记忆层上限  ≤ 10% usable     （超限按优先级丢低价值行，复用 selectMemoryLines）
  ├─ 摘要层上限  ≤ 10% usable     （超则触发「摘要的摘要」）
  └─ 近期原文    剩余全部          （真正需要保真的部分）
trigger      = usable × 0.7                                     # 比现在 0.5 更晚触发，但更准
```

★ 注意：现在的 `× 0.5` 是「估算偏低时的双重保守」（`window.ts:8-18` 注释已说明）。  
预算化之后**要把这条系数的语义说清楚**：0.5 是**估算误差余量**，不是分层预算。两者不要混在一个数里。

### 3.4 核心改动三：保留窗口从「只留尾部」改成「头 + 尾」

**现在**：`keepRecent = 6`，**只留最近 6 条**，前面一刀切成摘要。  
**问题**：首轮用户消息（真正的任务目标）会被摘要化 —— 而摘要必然有损。  
**主流做法**：OpenHands `keep_first = 4`（system prompt + 初始用户消息），Claude Code 也保留 plan/规则。

**建议**：`keep_first = 1~2`（首条 user 消息 + 首轮 assistant 结论）+ `keep_recent = K 轮`（把「条」改成「轮」，`call_agent` 并行时一批 N 条 tool 消息不该一次吃掉整个窗口）。

★ 这里踩过的坑要带上：**边界必须回退到 `assistant(tool_calls)` 处**（`window.ts:173-178`），  
头尾两段同时存在后，**两段都要做配对校验**，否则会同时产生两个孤児点。

### 3.5 核心改动四：快照从 O(n²) 降到 O(n)（治缺口 B）

**现在**：每个 step 把**本轮完整 messages** 存进 `system_prompt_snapshot`（`llm-task-manager.ts:1562-1589`），  
实测该会话 2→4→…→1154 条逐步累积，单会话 183MB。

**唯一读取方**：`GET /api/messages/:mid/snapshot`（`routes/messages.ts:10-15`），  
前端 `formatSnapshot` 读 `parsed.messages` 渲染「消息历史（本轮实际发送）」（`useChat.ts:821-832`）。

**建议（两种，按风险选）**：

| 方案           | 做法                                                                                                                              | 风险                                     | 收益                          |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- | --------------------------- |
| **B1（推荐）**   | 快照只存**轻量元数据**（step/model/platform/parameters/systemPrompt/tools + `messageIds: string[]`）；`messages` 不落库，点开「查看提示词」时**按 ids 回填** | 中（需同步改 `formatSnapshot`，改为先 fetch 再渲染） | 单条从 200KB → ~5KB，**降 97%+** |
| **B2（最小改动）** | 保留结构，但 `messages` 只存**增量**（相对上一步新增的 id + tool 结果摘要）                                                                             | 低                                      | 降 ~80%                      |
| **B3**       | 快照**落文件** `<convDir>/snapshots/step-<n>.json`，库里只存路径                                                                            | 中                                      | 顺带解决「可以放文件里」的诉求             |

★ 若走 B1/B3，**前端 `formatSnapshot` 必须一起改**（这是当初把它列为 ⏳ 而非直接做的原因）——  
属**接口变更**，不能只改后端。另注意 `db.ts:28-40` 已注明快照占全库 75%，**清理旧数据**要单独一轮。

### 3.6 核心改动五：非破坏性 + 可回滚（对齐 Roo Code）

`truncationParent` / `truncationMarker` 的做法：截断**只打标记**，原文仍在库里；回滚时清标记即恢复。  
言智现在是「切片丢弃」，**一旦模型在一轮里跑偏，用户无法回退到压缩点之前重来**。

**建议**：`message_summary.message_ids_json` 已经隐含了这层信息 —— 只要**不改 `message` 表、只加摘要**，  
回滚天然可行（前端 Rewind = 丢弃该摘要之后的消息 + 删除该摘要行）。**这也是「压缩落库」的额外红利。**

### 3.7 治理与边界（必须一起想清楚）

1. **子智能体消息隔离**：`loadMessages` 只按 `conversation_id` 过滤（`:304-310`）→ **子智能体消息会进主上下文**。  
   子智能体存在的意义就是「上下文隔离」（Claude Code 文档明说 subagent 只回传最终结果）。  
   ⇒ 组装视图时必须按 `parent_tool_call_id` 排除子智能体消息（子循环已有 `loadSubAgentMessages`）。
2. **摘要行的清理**：保留最近 N 条摘要 + 定期合并（把旧摘要再摘要成一条）→ 否则摘要表自己也会长。
3. **摘要失效判定**：沿用 `isPrefix` 指纹（`window.ts:233-239`）—— 消息被编辑/删除即判失效，退回全量。
4. **压缩事件要可见**：对齐 Claude Code 的 `compact_boundary`，在 SSE 推一个 `context:compacted` 事件  
   → 前端在对应位置画一条「此处已压缩（1156 → 12 条）」的分隔线。**用户才看得懂上下文发生了什么。**
5. **prompt cache 友好**：稳定前缀（指令层）放最前；摘要段变化频率必须低（靠持久化 + 阈值留余量保证）。

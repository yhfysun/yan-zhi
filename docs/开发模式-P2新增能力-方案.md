# 开发模式 P2 新增能力：方案汇总

> 状态：方案（2026-10-03，待逐项排期）
> 背景：P0（诊断闭环 / diff 审查 / multi-hunk 编辑）与 P1（危险命令护栏 / 整体回滚 / 自动验证循环 / 语义检索 / @folder）已全部落地。本文件覆盖剩余新增能力的方案，按"用户可感知收益 ÷ 成本"排序。

---

## P2-1 @ 符号级引用（对标 Cursor 的 @symbol）

**现状**：`@` 浮层支持文件（`ChatInputArea.vue` D3 块）与目录（P1 已加）；不支持符号。

**方案**：复用已有 AST 基建（`code-ast.ts`，TypeScript Compiler API 可用即精确、不可用回退启发式）：
1. 文件索引（`useFileIndex.ts`）已缓存全量文件清单——前端新增轻量符号缓存：对用户**打开过/引用过**的文件按需调 `code_outline` 端点取符号表，缓存进 `code store`（不预扫全仓，避免启动开销）。
2. `@` 浮层候选合并符号条目（`ƒ fnName` / `◇ className` 前缀 + 所属文件灰字）；选中后注入 `[符号引用] path:line symbol` 段（与现有 `[Files]` / 目录引用同格式）。
3. 服务端零改动：符号信息最终就是 file:line，模型用 file_read/code_refs 自取。

**改动点**：`ChatInputArea.vue`（浮层合并 + 注入）、`stores/code.ts`（符号缓存）、新 composable `useSymbolIndex.ts`。
**验收**：@ 输入 `useChat` 能选中符号 chip，发送后模型能直接定位到定义文件行号。

## P2-2 hunk 级选择性接受（diff 审查细化）

**现状**：`text-diff.ts` 已产出标准 unified diff（带 `@@` hunk 头），`AiDiffView`/`ChatFileChangeCard` 是整文件粒度"接受/回退"。

**方案**（利用 hunk 头已具备的事实）：
1. `DiffBody.vue` 已按 hunk 渲染且支持 hunk 导航——每行区（dv-hunk）加"接受此块 / 回退此块"按钮（hover 浮出）。
2. 服务端新增 `POST /workspace/changes/:id/apply-hunks`：入参 `{ hunks: [{ startLine, endLine }] }`（**新文件行号**）。实现：读当前盘上文件 → 用快照 before_content 与所选 hunk 做三方合并（before + 选定 hunk 的 after 段，未选段保留 before）→ 写回。
   - 前提约束：快照 after 与盘上内容一致（用户没手改）时不冲突；不一致则要求走整文件审查（返回 409 + 提示）。
3. `ChatFileChangeCard` 的按钮组不变，hunk 级操作只进 `AiDiffView`（工作台场景，宽度够）。

**改动点**：`routes/workspace.ts`（apply-hunks）、`AiDiffView.vue`（hunk 按钮）、`text-diff.ts`（导出 hunk 边界解析辅助 `parseHunkHeaders`）。
**验收**：3 个 hunk 的修改，只接受中间 1 个，盘上文件 = before 的其余部分 + 该 hunk。

## P2-3 vue 文件接入项目级类型检查

**现状**：`code_diagnostics` 的 tsc 通道不覆盖 `.vue`（`<script setup lang="ts">` 需 vue-tsc）；vue 改动只有 AST 大纲。

**方案**：
1. `code-diagnostics.ts` 的 `runTsc` 探测到项目 devDependencies 有 `vue-tsc` 且 tsconfig 含 vue → 命令换成 `vue-tsc --noEmit`（同参数面，输出格式与 tsc 完全一致，**解析器零改动**，`TSC_LINE_RE` 直接可用）。
2. 自动诊断钩子（`maybeAutoDiagnose`）把 `.vue` 加进 `AUTO_DIAGNOSE_EXTS`（已在集合里，只是 tsc 不覆盖——换 vue-tsc 后自动生效）。
3. 缓存 key 不变（项目根），vue-tsc 比 tsc 慢约 2~3 倍——超时上限单列（180s）。

**改动点**：`code-diagnostics.ts`（探测 + 命令选择 + 超时），其余零改动。
**验收**：fixture 项目故意写错 vue 组件 props 类型 → 诊断报 `xxx.vue(12,5): error TS2322`，自动诊断钩子在改完 .vue 后回喂该错误。

## P2-4 语义索引自动增量

**现状**：`code-index.ts` 首查自动建、之后靠 `reindex: true` 手动刷。

**方案**（不做文件监听——服务端常驻，用**读时惰性校验**更稳）：
1. `searchWorkspaceCode` 执行前做轻量新鲜度检查：对 `code_index_file` 抽样（最多 50 个文件的 mtime）+ 全仓文件数对比（`code_index_file` 行数 vs walk 计数，walk 有 `maxFiles` 上限开销可接受）。
2. 不新鲜 → 后台异步增量（`buildCodeIndex` 本就是增量：mtime+size 没变的跳过），**当次查询用现有索引照常返回**（附 note "索引更新中"），不阻塞。
3. 同一 workspace 5 分钟内只触发一次后台刷新（节流 Map）。

**改动点**：仅 `services/code-index.ts`。
**验收**：改一个文件后 5 分钟内检索，返回结果已含新内容（或注明更新中），无需手动 reindex。

## P2-5 LSP：tsserver 接入（最后一块导航短板）

**现状**：`code_refs/code_graph` 走 AST（编译器可用时），但无"实时诊断/悬浮信息/重命名安全"等语言服务能力。

**方案**（复用 DAP 子进程管理先例 `dap-client.ts`）：
1. 新 `services/lsp-manager.ts`：按项目根 spawn `tsserver`（`node_modules/typescript/lib/tsserver.js`，项目本地），JSON-RPC over stdio（tsserver 协议，非 LSP 标准——**直接用 tsserver 协议**，省掉 LSP 适配层，TypeScript 生态足够）。
2. 能力分期：① `quickinfo`（悬浮类型）+ `definition`（精确跳转，替代 code_refs 的 AST 版——AST 已 90% 准，tsserver 补跨文件 re-export 场景）；② `diagnostics`（语义诊断事件，喂给 code_diagnostics 作增量补充）；③ `refactor`/`rename`（远期，配 file_edit 的多 hunk 能力做安全重命名）。
3. 生命周期：进程闲置 10 分钟回收；workspace 变更（git checkout）后发 `reload`。
4. 浏览器端不可用（子进程在服务端）——工具层保持 AST 回退不变（与 code-ast 同策略）。

**改动点**：新 `services/lsp-manager.ts`、`code_refs`（服务端实现增强——注意 core 工具是平台无关的，tsserver 增强放 server 侧 api 工具 `api_code_definition`，core 的 code_refs 保持启发式/AST）。
**验收**：对 `@yan-zhi/core` 的 re-export 符号（如 `resolveToolPath`，经由 index.ts 转出）取 definition，直接命中 `fs-walk.ts` 实现行（AST 启发式在此场景会停在 re-export 行）。

## P2-6 后台并行子智能体（对标 Claude Code background agents）

**现状**：`call_agent` 同步阻塞主循环；工作流子智能体已有"后台跑完回调"形态（`runWorkflowSubAgent`，`llm-task-manager.ts`）可参考。

**方案**：
1. `call_agent` 新增 `async: true` 参数：立即返回回执（"子智能体 `<id>` 已后台启动，完成后自动汇报"），子 ReAct 在后台执行（复用现有 spawn 逻辑 + 独立 taskId），完成后把最终结果作为**用户侧注入消息**回写主会话（`pendingInjects` 机制，现有）。
2. 并发上限：每会话后台子智能体 ≤ 3（配置可调），超出排队。
3. 主循环结束条件注意：有未完成后台子智能体时，任务完成检测（`toolCallAcc.length === 0`）要等待或提示"仍有 N 个后台子任务在跑"。
4. 前端：TaskPlanCard 同级显示后台子任务状态 chip（复用现有子智能体 round 渲染，SSE 通道已具备）。

**改动点**：`llm-task-manager.ts`（spawn 异步化 + 完成注入 + 并发闸）、`ChatMessageList.vue`（状态 chip）。
**风险**：后台子智能体写文件与主循环并发冲突——后台子任务默认继承 readonly（与现有 spawn 权限一致），写操作仍走 path-guard 弹窗授权，天然串行化。

## P2-7 hooks 机制（工具调用前后用户可编程钩子，对标 Claude Code hooks）

**现状**：钩子只有内置的（path-guard 授权、artifact 登记 `tool-hooks.ts` 的 `registerAfterToolHook`——**基础设施已在**，只是不开放给用户）。

**方案**：
1. 用户 hook = 一条规则：`{ trigger: 'before'|'after', match: { tool: 'cmd_exec', pattern?: 'npm publish' }, action: 'confirm' | 'deny' | 'script' }`，存 `hook` 表，设置页管理。
2. 执行点：`executeTool` 在权限检查后、path-guard 前后各留一个用户 hook 通道（复用 `tool-hooks.ts` 的注册机制，用户 hook 动态注册）。
3. `action: 'script'` 的用户脚本跑在 **js_exec 同款沙箱**（受限 require，无 fs/process）——不允许任意命令 hook（那是危险命令护栏要拦的，不能自己开后门）。
4. 内置场景预置：cmd_exec 全量审计（已有）、"git push 前必须 confirm"、"file_write 到 deliverable 后通知"。

**改动点**：`tool-hooks.ts`（用户 hook 注册/匹配）、新设置页、`db.ts` hook 表。
**分期**：P2a 只做 `confirm|deny`（纯声明式，零执行风险）；`script` 类型 P2b。

## P2-8 项目级技能/规则目录约定（对齐 CLAUDE.md 生态）

**现状**：AGENTS.md + `.yan-zhi/rules/*.md` 已注入；无技能目录约定。

**方案**：约定 `.yan-zhi/skills/*.md`——进入工作目录时自动发现，格式 frontmatter（`name` / `trigger` / `description`）+ 正文（SOP）。加载进现有 skill 体系（`skill` 表注入同名内置 skill，优先级高于商城 skill），会话结束不持久化用户改动。与 AGENTS.md 同一 mtime 缓存模式（`loadProjectRules`，`llm-task-manager.ts:4184`）。

## 排期建议

| 顺序 | 项 | 理由 |
|---|---|---|
| 1 | P2-3 vue 类型检查 | 半天量级，diagnostics 闭环补最后一块 |

| 7 | P2-5 tsserver | 独立大项 |
| 8 | P2-8 技能目录 | 小活，随时可插 |

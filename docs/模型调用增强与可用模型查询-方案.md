# 模型调用增强与可用模型查询 —— 方案文档

> 状态：待确认（未动代码，先出方案）
> 目标：① call_agent 支持指定模型；② 新增「查询当前可用模型」工具；③ model 表补 description 字段
> 覆盖：浏览器操作工具 vs 豆包/WorkBuddy 差距对比（附在文末）

---

## 一、现状盘点（基于源码实测）

### 1. `call_agent` 工具（`packages/core/src/tool/builtin/call-agent.ts`）
- 入参仅 `agentId` + `input`，**无平台/模型参数**。
- 后端实际执行在 `apps/server/src/llm-task-manager.ts` 的 `runSubAgent()`（1052 行起）：
  ```ts
  const platformId = agent.platform_id || task.platformId;   // 只认子智能体配置或父任务
  const modelId    = agent.model_id    || task.modelId;
  ```
  即子智能体用哪个模型**写死在 agent 表**，主智能体无法在调用时临时指定。
- schema 注册：`call-agent.ts` only 提供 schema，真正的执行由 `dispatchToolCall` 拦截。

### 2. `model` 表（`apps/server/src/db.ts` 56 行）
```sql
CREATE TABLE model (
  id TEXT PRIMARY KEY, platform_id TEXT, user_id TEXT, model_id TEXT,
  alias TEXT, type TEXT DEFAULT 'llm', context_window INTEGER DEFAULT 8000,
  capabilities_json TEXT DEFAULT '[]', pricing_json TEXT DEFAULT '{}', ...
);
```
- 已有 `capabilities_json`（当前约定 function_call / vision / reasoning）与 `type`（llm/embedding/rerank/image/video/audio/tts）。
- **无 `description` 字段** —— 用户诉求「模型加个描述」需要新增列 + 轻量迁移。

### 3. 已存在的查询能力
- `api_model_list`（`api-tools/platform.ts` + `api-tool-executor.ts` 436 行）：可列所有模型，但**返回原始行、不格式化为可读的能力/描述**，且属于 `api_*` 系列（默认助手 DEFAULT_AGENT_BUILTIN_TOOLS 未挂 `api_model_list`）。
- `image_analyze`（`image-analyze.ts` + `chat.ts runImageAnalyze`）：**已经支持 `platformId` + `modelId` 指定视觉模型**，是「指定模型」能力的现成参照实现。

### 4. 关键结论
| 诉求 | 现状 | 差距 |
|---|---|---|
| call_agent 指定模型 | ❌ 不支持 | 需加 `platformId`+`modelId` 入参并透传到 `runSubAgent` |
| 查询可用模型工具 | ⚠️ 有 `api_model_list` 但未挂默认助手、返回原始行 | 需语义化 + 挂载 |
| 模型加描述 | ❌ model 表无 description | 需加列 + 表单 + schema 透传 |

## 二、改动方案

### A. `call_agent` 增加「指定模型」入参（平台 id + 模型 id）

**1) schema 层**（`call-agent.ts`）
在 `inputSchema.properties` 增加两个可选字段，`required` 保持 `['agentId','input']`：
```ts
platformId: { type: 'string', description: '可选：指定子智能体用哪个模型平台的 id。缺省时用子智能体自身配置，再缺省则继承主智能体当前模型。' },
modelId:    { type: 'string', description: '可选：指定子智能体用哪个模型（需属于 platformId 对应平台；不传 platformId 时自动解析）。缺省规则同上。' },
```

**2) 执行层**（`runSubAgent()` 1052 行起）
优先取调用方传入的平台/模型，其次子智能体配置，最后父任务：
```ts
const platformId = (args.platformId || agent.platform_id) || task.platformId;
const modelId    = (args.modelId    || agent.model_id)    || task.modelId;
```
- 校验：若显式指定了 modelId，先按 platformId（显式或解析）`loadModel()`，找不到则提示「模型不存在，可用 list_models 工具查询」。
- args 类型签名补 `platformId?/modelId?`。

**3) LLM 可见性**
- `list_sub_agents` 返回里**附带每个子智能体当前绑定的平台/模型**，方便主智能体决策是否要覆盖。
- 主智能体 system prompt（db.ts 里的 call_agent 指引）补一句：需要子智能体用特定模型（如图片/视频任务）时，传 `platformId`+`modelId`。

### B. 新增「查询当前可用模型」工具 `list_models`

**1) 工具定义**（新建 `packages/core/src/tool/builtin/list-models.ts`）
```ts
name = 'list_models';
description = '列出当前用户所有已启用的模型平台与模型，含每个模型的类型(type)、能力(capabilities)、描述(description)、所属平台。调用 call_agent 指定模型前，先用本工具确认有哪些可用模型。';
inputSchema = {
  properties: {
    platformId: { type: 'string', description: '可选：只列出指定平台下的模型。' },
    type:       { type: 'string', description: '可选：按模型类型过滤（llm/image/video/audio/tts/embedding/rerank）。' },
    capability: { type: 'string', description: '可选：按能力过滤（如 vision）。' },
  },
};
```

**2) 执行层**（`llm-task-manager.ts` 的 dispatch 里，`list_sub_agents` 旁新增分支）
复用 `loadModel`/`loadPlatform`，直查 DB，返回**语义化文本**（而非原始行）：
```
平台 <name> (id: <platformId>)：
- <alias>  model=<model_id>  type=llm  能力=function_call,vision  描述=<description>
```
- 过滤 `enabled=1`；type/capability 参数用于按需收窄，降低 prompt 占用。

**3) 挂载**
- 加入 `DEFAULT_AGENT_BUILTIN_TOOLS`（db.ts 563 行）与前端 agent.ts 的默认工具白名单。
- `list_sub_agents` 排除规则（runSubAgent 1092 行）**不收** `list_models`（子智能体也可能需要查模型选型）。

### C. `model` 表补 `description` 字段 + 表单 + schema 透传

**1) 建表 + 迁移**（`db.ts` model 定义 + 迁移块）
```sql
-- model 表新增
description TEXT,
```
```ts
// 轻量迁移（仿 schema.ts 365 行 capabilities/pricing 的写法）
for (const col of ['description']) { /* 检测并 ALTER TABLE model ADD COLUMN description TEXT */ }
```

**2) shared 类型**（`packages/shared/src/types/index.ts` Model 接口）
```ts
description?: string;
```

**3) 后端读写**
- `loadModel()`（llm-task-manager 108 行）返回 `description`。
- `api_model_list` / `api_model_create` / `api_model_update`（api-tool-executor）补 description 的读/写。

**4) 前端**
- `platform.ts` 的 `rowToModel` 透传 `description`；`addOrEditModel` 的表单体带上 description。
- `PlatformDetail.vue` 添加模型/编辑对话框（88 行表单）加一个「描述」`el-input`（textarea），模型卡片展示 description（无则隐藏，避免界面噪声）。

## 五、附：浏览器操作工具 vs 豆包 / WorkBuddy 差距清单

> 基于 `browser/index.ts` 实测（已有 40+ 工具）与主流同类产品能力对比，标注「当前有 / 缺失」。

| 能力 | 本项目 | 豆包/WorkBuddy | 结论 |
|---|---|---|---|
| 导航 / 点击 / 输入 / 滚动 / 按键 | ✅ 有 | ✅ | 持平 |
| 可交互元素编号列表（index 定位） | ✅ 有 | ✅ | 持平 |
| get_dom / a11y tree / Shadow DOM 穿透 | ✅ 有 | ✅ | 持平 |
| 多标签页管理 | ✅ 有 | ✅ | 持平 |
| 网络请求监听 / 日志 | ✅ 有 | ⚠️ 部分 | 领先 |
| 结构化列表提取 extract_list | ✅ 有 | ⚠️ | 领先 |
| 视觉定位闭环（截图→vision 识别） | ✅ 有 | ✅ | 持平 |
| 文件上传/下载 | ✅ 有 | ✅ | 持平 |
| 拖拽 drag | ✅ 有 | ⚠️ 部分 | 领先 |
| 表单批量填充 fill_form | ✅ 有 | ✅ | 持平 |
| 保存密码登录 login_saved | ✅ 有 | ⚠️ | 领先 |
| **可访问性/视觉双通道定位统一抽象** | ⚠️ 已有但分散 | ✅ 统一 | 可优化 |
| **元素定位失败自动降级（selector→index→坐标→视觉）** | ⚠️ 部分（需模型手动切换） | ✅ 自动 | 可优化 |
| **操作结果的结构化反馈（成功/页面变化/候选列表）** | ⚠️ 文本式 | ✅ 结构化 | 可优化 |
| **截图语义标注（元素框叠加）** | ❌ 缺 | ✅ 有 | 缺失 |
| **录屏/操作回放** | ❌ 缺 | ⚠️ | 缺失 |
| **浏览器状态持久化/会话快照** | ⚠️ 部分（分区持久化） | ✅ | 可优化 |

**结论**：本项目浏览器工具**覆盖面与豆包/WorkBuddy 相当甚至部分领先**（多标签、网络监听、结构化提取、拖拽、密码登录）。真正差距不在「缺工具」，而在**执行反馈与定位的自动化程度**（自动降级、结构化结果、截图元素标注）。这一块若要优化，属于另一个独立方案，不在本次模型调用增强范围内，若需要我可另出《浏览器操作鲁棒性优化》方案。

# `browserSteps` 步骤日志保留策略 —— 独立方案

> 2026-10-12 · 状态：**待确认**（前置修复 P0/P1 已落地，见 §1）

## 0. 关键发现：`browserSteps` 现在**根本没有 UI 渲染它**

出方案前把消费点全查了一遍（`packages/ui/src` + `apps/*/src`，排除测试）：

| 消费点 | 用法 | 是否渲染内容 |
|---|---|---|
| `BrowserPanel.vue:583` | `chatStore.browserSteps.length > 0` | ❌ 布尔 |
| `BrowserPanel.vue:604` | `chatStore.browserSteps.length > 0` | ❌ 布尔 |
| `useChat.ts:431` | `store.browserSteps.length > 0` | ❌ 布尔 |
| `useChat.ts:442` | `watch(browserStepSeq)` | ❌ 判据 |
| `useChat.ts:2309` | `store.browserSteps.length = 0` | ❌ 清空 |

**全仓库没有任何 `v-for="... browserSteps"` / `browserSteps.slice()` / 取 `step.result` 的地方。**

⇒ 结论：**`browserSteps` 已经从"步骤清单数据源"退化为"控制信号的载体"**。
真正的步骤清单展示走的是 `chatStore.planSteps`（来源是 `task_plan` / `task_step` 工具 + `plan:updated` 事件，
渲染在 `BrowserPanel.vue:297-314` 的 `.agent-step-panel`）。

> 历史原因：`BrowserPanel.vue:294-296` 注释写着"Agent 步骤清单：实况锁定时叠加视口右上，
> 与当前会话的 **task_plan** 同步"。也就是说**步骤清单从来就走 planSteps**；
> `browserSteps` 是 2026-10-08 为"接管控件判据"引入的另一套东西，后来主判据迁到
> `browserTaskActive`（会话级单调记账），它的展示职责**已经在演进中丢掉了，只是没人删**。

**这直接推翻"提高上限 / 按时间保留"这类选项的动机**：为一个不展示的数组扩容没有用户价值，
只会把内存和"越跑越卡"的老问题再放大。

## 2. 现状盘点（3 个事实）

| # | 事实 | 依据 |
|---|---|---|
| ① | **无展示职责**：数组内容一个字节都不上屏 | §0 消费点清单 |
| ② | **裁剪会制造无效开销**：超限后每次 push 都多一次 `splice(0, len-120)`（O(n) 元素搬移，n=120 恒等），且必然触发依赖它的 3 个 computed 重算 | `stores/chat.ts` pushBrowserStep |
| ③ | **内存已受控**：单条 `result` 截断到 600 字符（`BROWSER_STEP_RESULT_MAX`），120 条上限 ⇒ 最坏 ~72KB 文本 + 数组开销，**不是内存问题** | 同上 |

⇒ 真正的问题**不是容量**，而是：**留一个没人看、每次 push 还要 O(n) 搬移 + 触发重算的数组**。

## 3. 候选方案

### A（推荐）—— 退化为"环形计数器 + 只留最近 N 条供排障"，并把上限降到 20

**思路**：承认它不再是展示数据，只服务两个用途：
1. **控制信号**（已由 `lastBrowserToolAt` / `browserStepSeq` 承担，与数组无关）
2. **排障取证**（出问题时想看最近发生了什么）

既然只做排障，120 条太多 —— 降到 **20 条**：
- `splice` 的 O(n) 搬移从 120 降到 20（**6 倍**）
- 依赖它的 computed 重算不变（仍是 1 次/ push），但**数组内容更少 ⇒ 面板调试打印更小**
- 内存最坏 12KB（\(20 \times 600\)）

```ts
const BROWSER_STEPS_MAX = 20;   // 120 → 20：不再是展示数据源，只留最近 N 条排障
```

**取舍**：极端排障时看不到第 21 步以前的历史。
**缓解**：排障主路径早已不是它 —— 是 `%APPDATA%\yan-zhi\logs\main-*.log`
（`[browser-action]` 每条工具调用/结果都打日志，含完整 args，**本次排障就是靠它 + CDP 定位的**）。

### B —— 提高上限到 300（**不推荐**）

- ❌ 动机不成立：没有任何 UI 读它，扩容量**零用户收益**
- ❌ 反向放大老问题：单条 600 字符 × 300 = 180KB，且 `splice` 搬移量 +2.5 倍
- ❌ 与 2026-10-10 引入上限的**原始动机**（"pageAgent 一跑整个页面卡死"）直接冲突
- ✅ 唯一好处：排障时能翻更久的历史 —— 但这用 A 的缓解手段（看日志）更好

**结论：否。** 这是"没搞清消费方就扩容"的典型；本次 P0 事故的教训之一就是
"别在没回归校验依赖的前提下动容量相关的常量"。

### C —— 按时间保留（如最近 10 分钟）

- ⚠️ 需要每次 push 前扫一遍数组头（或维护时间索引），比 `splice` 更贵
- ⚠️ 时间窗口语义对一个"无展示职责"的数组是过度设计
- ✅ 仅在"将来要做步骤时间轴回放 UI"时才有意义 —— 目前无此需求

**结论：暂不采纳**（YAGNI）。若将来真要回放，应新建**带事件索引的结构**，
而不是继续给这个数组加语义。

### D —— 直接删除 `browserSteps`，只留 `lastBrowserToolAt` + `browserStepSeq`

- ✅ 最彻底：删掉 O(n) 搬移与"依赖它的 3 个 computed 重算"（只留布尔 + 计数）
- ✅ 消除一整类"用数组长度当信号"的复发通道
- ❌ 丢失排障现场（虽然主路径是日志，但面板内即时可见仍有价值）
- ❌ 改动面最大（3 处布尔判据要改成依赖 seq，`BrowserPanel` 两处）

**结论：可选，但建议先做 A。** A 已把主要开销削掉，D 的额外收益集中在"代码整洁"，
可作为一个独立的小重构在 A 观察一段时间后评估。

## 4. 推荐路线

```
A（先做，低风险）
  └─ BROWSER_STEPS_MAX: 120 → 20
  └─ 补一条守门测试：上限不得超过 20（防有人"顺手调大"）
  └─ 保留 3 处 length>0 布尔判据不变（行为等价，不必动）

观察一个周期
  └─ 若确认无人依赖数组内容 → 再评估 D（彻底删除）
  └─ 若有回放需求 → 新建独立结构（不要复活这个数组）
```

### 为什么不顺手把 3 处 `length > 0` 也改成 seq

- 它们已经是**布尔判断**（不是差分），到顶后恒真，**不会误否决**（有 `browserTaskActive` 兜底）
- `agentCursorVisible` / `liveControlVisible` 里的 `|| browserSteps.length > 0` 是**冗余兜底**
  （`browserTaskActive` 已覆盖同一语义）—— 但删它属于行为收窄，不在本议题范围
- **遵守项目约定：严格限定请求范围，不擅自扩大改动面**

## 7. 附：与本次事故的关系（为什么这个议题现在才安全）

P0 事故的本质是**把一个不该有语义的东西（数组长度）当成了控制信号**。
在那个前提下，"上限该多大"是个**危险议题** —— 上限值直接决定控制信号何时失灵。

P0/P1 落地后，控制信号已迁到 `lastBrowserToolAt` / `browserStepSeq`（与容量无关），
容量才真正退化为**纯内存/性能参数**，可以按内存口径自由调。
**这是本议题能独立讨论的前提，也是顺序不能颠倒的原因。**

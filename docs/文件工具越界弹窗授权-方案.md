### ★★ 本轮踩到的坑（写下来，避免后人重犯）

1. **差点用"复刻实现"的脚本得出"实现有 bug"的错误结论**。
   写首个验证脚本时，我手工复刻了 `resolveArtifactRoot`（空间目录 > 工作目录 > 数据根），
   但**复刻错了** —— 把三者当成"同时成立"，而真实实现是**择一**。
   结果"无空间时数据根产物"被判越界，8 项里 1 项 FAIL，看起来像实现缺陷。
   ⇒ **修法：把"算允许根"从调用方搬进 `path-guard` 并导出 `allowedRootsFor()`**，
   让允许根**只有一个定义处**；验证脚本改为导入真实实现。
   ⇒ 教训（与项目既有"路径唯一出口"同源）：**任何被多处需要的推导逻辑都不能复刻，只能有唯一定义**。
2. **`executeToolViaFrontend` 被误删了函数体开头**（一次 Edit 的 `old_string` 吞掉了
   `await waitIfPaused` + `subscribers` 检查 + `new Promise` 包裹）。编译不会立刻报"少了几行"，
   所以我用 `sed` 回读核验了函数完整性。⇒ **改长函数要回读核验，不能只看 Edit 成功**。
3. **`workflow-runner.ts` 的 `conversationId` 作用域**：`builtin` 分支在局部变量声明**之前**，
   直接引用会编译失败；须走 `ctx.inputs.__conversationId`（与同文件 `api_*` 分支同一来源）。
4. **bash 的 `/tmp` 与 Python 视图不同**（`io.open('/tmp/x')` 找不到 bash 写出的文件）；
   且**验证脚本放 /tmp 时相对 import 会以 /tmp 为基准** → 改为写进项目 `tmp/` 且用 `file:///` 绝对导入。

### 与决策的对应

## 二、方案设计

### 2.1 判定点：`executeTool` 单点前置（core 契约不扩大）

在 `llm-task-manager.ts:2352`（`registry.execute` 调用）**之前**插入一道守卫：

```
executeTool(task, toolName, args, ...)
  ├─ 现有：checkToolPermission(task.permissionMode, toolName)      ← 按工具名（保留不动）
  ├─ ★ 新增：checkPathAccess(task, toolName, args)                 ← 按路径（本方案）
  │     ├─ 放行（在允许根内）→ 继续
  │     ├─ 需授权 → 弹窗 await 用户
  │     │     ├─ 允许 → 记入本会话白名单 → 继续
  │     │     └─ 拒绝 → 返回「未授权」给模型（让模型换路径，不重试）
  │     └─ 无人值守 → 返回「无人值守，无法取得授权」给模型
  └─ registry.execute(toolName, args, toolCtx)
```

★ **为什么不改 `ToolContext`**：`types.ts:33-63` 的既有取向是「调用方算好、直接传」，工具侧零业务知识。
授权判定属于**策略层**（server），不是 core 的知识 —— core 不该知道"什么叫越界"。
⇒ 判定留在 server 单点，**core 只保留 `resolveToolPath`（纯解析，无策略）**，两边职责不混。

★ 这也是**避免入口漂移**的做法：`registry.execute` 有三个入口（ReAct 主链路 / 工作流节点 / UI 试跑），
必须三处都过同一道守卫 —— 所以守卫要抽成**独立函数**，供三处调用，而不是写在某个分支里。

### 2.2 允许根集合（`allowedRoots`）—— ★ 关键，防误拦产物

按优先级算出这次调用允许访问的全部根：

| # | 根 | 来源 | 为什么必须包含 |
|---|---|---|---|
| 1 | 工作目录 | `task.workspaceDir` | 主边界 |
| 2 | 产物目录 ×3 | `toolCtx.artifactDirs.{intermediate,deliverable,upload}` | ★ 产物根可能是**空间目录**或**数据根**（`artifact-dir.ts:100-104`），**不一定等于工作目录**。漏掉它 → `file_write` 被拦 → 生成全挂 |
| 3 | 空间目录 | `conversationArtifactMeta().spaceDir` | 用户显式绑定的空间目录 |
| 4 | 会话白名单 | 本会话内用户已授权的目录 | 弹窗授权的结果 |
| 5 | 全局授权目录 | 设置项（可选，见 2.5） | 用户明确长期放行的目录 |

★ 判定：目标路径 `p` 在**任一**根内（`p === root || p.startsWith(root + sep)`）→ 放行。

### 2.3 路径抽取：哪些工具、哪些字段

**必须按「声明驱动」抽取**，不能硬编码散落各处（本项目既有教训：「必填校验的对象必须是原值」+「按名字判读写而非按实现」）。

| 工具 | 路径字段 | 抽取难度 |
|---|---|---|
| `file_read` `file_write` `file_edit` `file_grep` `file_list` `file_to_markdown` | `path` | ✅ 直接 |
| `code_search` `code_outline` `code_refs` `code_graph` | `path` / `file` / `root` | ✅ 直接（需核对各自 schema） |
| `image_analyze` | `path` | ✅ 直接 |
| `doyz` | `file` / `csv` / `json` / `md` **+ `out`（输出）** | ✅ 直接（★ `out` 是**写**目标，不能漏） |
| `cmd_exec` | `cwd` | ⚠️ 只覆盖 `cwd`；**`args` 数组里的路径抽不到** |
| `python_exec` | —— | ❌ **代码字符串内的路径完全抽不到** |
| `api_workspace_list_dir` | `path` | ✅ 直接（API 工具，需在 api 执行器侧一起接） |

★ **抽取口径**：只抽「**已显式给出**」的路径。
未给路径（走默认工作目录）→ **不触发授权**（这正是 `resolveToolPath` 的规则 1：空 → 工作目录根）。
★ 「显式空 vs 根本没写」两种空都不该弹窗 —— 与项目既有判据一致（只有"显式给了越界路径"才问）。

★ **相对路径必须先按 `workspaceDir` 解析再判**（server 侧需要 `resolveToolPath` 的等价实现；
不要各写一遍 —— 建议 server 复用 core 导出的 `resolveToolPath`，`index.ts:4` 已从包根透出）。

### 2.4 弹窗内容与交互

复用 `inline-ask-card` 形状，但**语义不同**（不是问答，是授权）：

```
┌─────────────────────────────────────────────┐
│ ⚠ 需要你授权访问工作目录外的位置             │
│                                             │
│  工具      file_write                       │
│  操作      写入                              │
│  目标      C:/Users/Administrator/Desktop/   │
│            other-project/README.md          │
│  范围      工作目录 C:/proj/demo             │
│                                             │
│  [ 仅此次允许 ]  [ 允许该目录（本会话） ]     │
│  [ 拒绝 ]                                    │
└─────────────────────────────────────────────┘
```

- **仅此次允许** → 只放行这一个路径（不记白名单）；
- **允许该目录（本会话）** → 把该路径的**父目录**记入会话白名单，同会话后续不再问；
- **拒绝** → 返回工具结果：`「用户未授权访问 <path>，请改用工作目录内的路径或询问用户」`
  —— ★ 措辞要让模型**换路径**而不是重试（否则形成"反复弹窗"的骚扰循环）。

★ **合并提示**：同一次模型输出里可能有**多个**越界路径（如批量 `file_read`）→
应**一次弹窗列出全部**，而不是逐个弹（逐个弹 = 用户体验灾难）。
⇒ 弹窗需支持"一次授权多项"。（这与 `confirm_user` 的"多页向导"形状天然契合，可参考。）

### 2.5 白名单的持久化

| 层级 | 存储 | 生命周期 | 第一版 |
|---|---|---|---|
| 会话白名单 | 内存 `Map<conversationId, Set<string>>` | 会话结束即失效 | ✅ 做 |
| 全局授权目录 | `settings.authorizedDirs`（设置项 + UI 管理入口） | 跨会话长期 | ⏸ 可选，后置 |

★ 第一版**只做会话级**：越界访问本身是低频动作，会话级已经能消掉 90% 的重复弹窗；
全局授权会**长期扩大攻击面**（用户半年后忘了自己授权过 `C:/`），价值/风险不成正比。

### 2.6 无人值守（定时任务 / 后台工作流）

`task.subscribers.size === 0` 时 → **直接拒绝**，返回：

> `[无人值守] 工具 file_write 试图访问工作目录外的 <path>，无人可确认授权，已拒绝。请改用工作目录内的路径。`

★ 不能放行（fail-safe，与 `unattendedToolResult` 既有口径一致），也**不能挂起等待**
（定时任务没人守着，挂起 = 任务永久卡住）。

## 三、必须由用户拍板的 3 个决策点

### 决策 1：`cmd_exec` / `python_exec` 怎么办？

这两个工具**无法静态抽取路径**，但它们是**最强的越界通道**（`cmd_exec` 一条 `type C:\Windows\x` 就出去了）。

| 选项 | 说明 | 代价 |
|---|---|---|
| **A. 只校验 `cwd`** | 抽得到的就校验，抽不到的放过 | 洞还在（`args` 数组里塞绝对路径即绕过） |
| **B. 整条命令授权** | 这两个工具**每次调用**都弹窗列出「命令 + args」让用户过目 | 高频打扰（`npm install` 也要问） |
| **C. 首次授权后放行 + 审计** | 第一次弹窗，之后本会话放行，但每次落审计 | 折中，推荐 |
| **D. 暂不处理** | 本方案只管 file_*/code_*/doyz，`cmd_exec`/`python_exec` 单列一条 issue | 承认洞、不装作没有 |

★ **我的建议：C**（首次授权 + 全量审计）。理由：`cmd_exec` 的正当用途（跑构建/测试）很频繁，
每次都弹会让人关掉这个功能；而"本会话首次授权 + 审计留痕"既拦住了静默越界，又不骚扰。

### 决策 2：越界**读**要不要拦？

- `file_read { path: "C:/Users/xxx/.ssh/id_rsa" }` —— 现在能读，且**无任何日志**。
- 拦：安全，但可能打断"用户让我读桌面上的文件"这类合法场景（用户会说"读桌面的报表.xlsx"）。

★ **我的建议：拦，但读的弹窗文案更轻**（"读取"而非"修改"），且 `file_read` 类的弹窗默认**记住父目录**（因为一次读往往跟着一串读）。

### 决策 3：要不要给用户一个「默认全放开」的开关？

有些用户会觉得"这是我自己电脑，别烦我"。
★ **建议：给**（设置项 `pathGuard: 'strict' | 'ask' | 'off'`，默认 `ask`）。
但**默认档必须是 `ask`**，且 `off` 要有明确文案说明风险。

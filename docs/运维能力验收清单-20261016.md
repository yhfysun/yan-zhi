# 运维能力验收清单（2026-10-16）

对应提交：`8a01032`（跳板机 / WebSocket 终端 / 会话录制 / 主机密钥校验）、`d2d98ba`（命令审批闸门）。

## 为什么有这份清单

这五块合起来新增了约 145 个单测，但**全部跑在假 ssh2 + 假 WebSocket 上**，没有一次真机
端到端。这个比例本身是风险：单测能证明「逻辑对了」，证明不了「接上了、在网络里真的成立」。

所以下面每一条都写成可证伪的形式：**做什么 → 期望什么 → 失败长什么样**。
遇到「失败长什么样」里描述的症状，基本可以直接定位到对应模块。

带 🎯 的是**强证明**——能排除「碰巧也通过了」的检查，时间有限就只跑这些。

## 0. 前置

### 0.1 先跑一遍自动化（确认起点是绿的）

```bash
cd apps/server && npx tsc --noEmit -p tsconfig.json && npx vitest run --no-file-parallelism
```

```bash
cd packages/ui && npx vue-tsc --noEmit && npx vitest run --no-file-parallelism
```

基线：server 174 文件 / 2764 用例、ui 70 文件 / 959 用例全通过。

- **`--no-file-parallelism` 不是可选项**：并行下有计时敏感用例与 Unhandled Error 误报。
- 若 server 出现成片的 `Transform failed`：多半是有人往 `db.ts` 的提示词里写了**未转义
  的 markdown 代码围栏**（三个反引号会提前截断模板字符串）。

### 0.2 启动与入口

运维模式是 **desktopOnly**，且属于 pro 档能力（lite 版不可见），所以要在桌面端跑：

```bash
pnpm dev:desktop
```

入口两条路：模式切换器选「**运维**」，或「更多 → **运维**」（路由 `/ops`）。

### 0.3 准备两台能 SSH 的机器

- **A（跳板机）**：能被本机直连
- **B（目标机）**：用于验证「经 A 连 B」

B 不一定要真的不可直连；但最强的那条检查（🎯1.2）会让 B **只接受来自 A 的连接**，
所以建议 B 是台可以随便改防火墙的测试机（容器里的 sshd 也行）。

### 0.4 找录像与库的位置

录像落在 `<DATA_DIR>/ops-recordings/`；未设 `DATA_DIR` 时落**服务进程的 cwd**（`pnpm dev:server`
下即 `apps/server`）。别猜，直接找：

```bash
find . -name "*.cast" -path "*ops-recordings*" 2>/dev/null | head
```

数据库是同目录下的 `data.db`，插件的键值都在 `plugin_storage` 表里（列：`plugin_id` / `key` / `value`）。
下面偶尔要直接读写它，先确认路径：

```bash
ls -la "${DATA_DIR:-apps/server}/data.db"
```

### 0.5 插件配置项（后文多处要改）

在**插件管理**里找到「运维」插件的配置，一共两项与本清单有关，用的是 manifest 里的原名：

| 键 | 默认 | 作用 |
|---|---|---|
| `recordSessions` | `true` | 是否录制终端会话 |
| `knownHostMode` | `tofu` | 主机密钥校验：`tofu` / `strict` / `off` |

改完若没生效，先确认插件是否被重新激活（停用再启用一次最稳）。

## 1. 跳板机（ProxyJump）

先在运维控制台左侧新建两个连接：`bastion`（指向 A）、`target`（指向 B），
`target` 的**跳板机**选 `bastion`。

### 1.1 基本穿透

**做什么**：连 `target` 的终端，执行 `echo $SSH_CLIENT`。

**期望**：命令正常返回，且输出的来源 IP 是 **A 的出口 IP**（不是你这台机器的 IP）。

**失败长什么样**：

- 保存 `target` 时报「跳板机连接不存在 / 成环 / 超过 5 跳」→ 校验层拦下的，见 1.4；
- 终端报 `打开终端失败：跳板机隧道建立失败: …` → `forwardOut` 失败，多半是 A 到 B 的网络
  或 B 的 sshd 不认；
- 报 `SSH 连接失败: …` → 目标本身建连失败（凭据 / 端口）。

### 1.2 🎯 强证明：让 B 只接受来自 A 的连接

**做什么**：在 B 上把 22 端口限制为只允许 A：

```bash
sudo ufw allow from <A 的 IP> to any port 22 proto tcp
sudo ufw deny 22/tcp
sudo ufw enable
```

然后从**本机**直连 B（应当失败），再经 `target` 连接。

**期望**：直连不通；经 `bastion` 的 `target` **正常登录**。

**为什么这条强**：它排除了「隧道其实没走、直连碰巧也通」这种假绿。做完记得还原
（`sudo ufw disable` 或删掉那两条规则）。

### 1.3 多级跳板（可选）

三台机器 A→B→C，`target`(C) 的跳板选 B，B 的跳板选 A。连 C 的终端，`echo $SSH_CLIENT`
应显示 B 的出口 IP。期望开终端时间比单级略长（逐跳建连）。

### 1.4 非法配置应被拦在保存前

| 操作 | 期望 |
|---|---|
| 把 `bastion` 的跳板设成它自己 | 保存报「跳板机不能是连接自身」 |
| `a` 指向 `b`，再把 `b` 指向 `a` | 后者保存报「跳板链成环」 |
| 目标选一条**数据库**连接作跳板 | 保存报「是数据库连接，不能作为跳板机」 |
| 串 6 层跳板 | 保存报「超过 5 跳」 |

### 1.5 删跳板机要有提示

**做什么**：在 `target` 存在的情况下删除 `bastion`。

**期望**：确认框里点名「它正被 target 当作跳板机，删除后这些连接会连不上」；删完后
`target` 的终端报**「跳板机连接不存在（id=…），请检查该连接的跳板设置」**——是这条明确
报错，而不是静默直连到 B。

### 1.6 数据库经跳板（可选，但这条最容易出问题）

**做什么**：新建一个 `database` 连接指向 B 上的 MySQL/PG，跳板选 `bastion`，点「测试连接」。

**期望**：返回 ok；能在「数据查询」里看到库表、跑一条 SELECT。

**失败长什么样**：报 `跳板机隧道建立失败` 或连接超时 → 隧道没起来；若报的是
`Unsupported state or unable to authenticate data` → 那是**凭据解密**问题（运维「测试连接」
报这个的成因是主密钥没跟着搬），与本功能无关。

> 这段代码走的是「本地随机端口 + 隧道」而不是把 ssh2 channel 直接塞给 pg —— 因为
> pg 会对自己拿到的流调 `setNoDelay` / `connect`，直接塞会崩。

## 2. WebSocket 终端

### 2.1 🎯 确认真的走了 WebSocket

**做什么**：桌面端开 DevTools（`Ctrl+Shift+I`）→ Network → 过滤 `WS`，然后连一个 SSH 终端。

**期望**：出现一条 `term/ws?connectionId=…&cols=…&rows=…` 的连接，状态 `101 Switching Protocols`，
并且**帧列表里能看到 Binary Message**（敲几个键、跑 `ls` 就有）。

**失败长什么样**：

- 没有任何 WS 请求，但终端能用 → 走了回退通道，控制台应有
  `[ops] WebSocket 终端不可用，回退 SSE：…`（dev 下常见原因是 Vite 代理没开 `ws: true`，
  两个 `vite.config.ts` 里都加了，别被别的分支覆盖掉）；
- WS 出现但立刻断开 → 看是不是被授权门禁 403（见 2.5）。

### 2.2 交互质量（这才是换 WS 的目的）

**做什么**：在终端里依次跑 `top`、`vim`（随手改点东西不保存）、`sudo` 提权、`Ctrl-C` 打断
一个 `ping`、`Ctrl-D` 退出登录。

**期望**：全部正常。特别关注两件事——

1. **`Ctrl-C` 要立刻生效**——旧实现每敲一个键一次 HTTP POST，打断可能排在几屏输出之后；
2. **刷屏不卡、不积压**——跑 `seq 1 200000`，输出应当流式滚过，不应越跑越滞后。

**失败长什么样**：`vim`/`top` 花屏或按键错位 → 二进制帧那条路出了问题；`Ctrl-C` 要等、
或输出明显滞后于按键 → 心跳 / 背压有问题。

### 2.3 断线重连与关闭

| 操作 | 期望 |
|---|---|
| 直接关掉终端窗口标签 | 服务端 PTY 被回收（B 上 `who` 不再有这条会话） |
| 拔网线 / 断 Wi-Fi 后等 1 分钟再连 | 服务端会话被心跳回收（不回收就是心跳没生效） |
| 连上后切到别的页面再切回运维 | 终端内容仍在（DOM 接回，不重开 PTY） |
| 连接断开后看窗口头 | 「连接终端」按钮重新出现，可点 |

### 2.4 回退通道（故意制造）

**做什么**：把 `apps/desktop/vite.config.ts` 里代理的 `ws: true` 那行注释掉，重启 dev，
再连终端。

**期望**：控制台打出回退日志，**终端依然完全可用**（只是走老的 SSE + POST）。

**为什么值得跑**：这条路径平时不走，却是「被反代拦掉的环境」唯一的救命通道；一旦它
悄悄坏了，要到线上才发现。

### 2.5 授权门禁不得被绕过（安全项，建议跑）

WebSocket 的 upgrade **不经过 Express 中间件链**，`/api` 上的 `requireLicense` 对它无效 ——
所以服务端在分发层补做了一次。要验它真的补上了：

```bash
YZ_LICENSE_GUARD=1 pnpm dev:server
```

**期望**：开启门禁后，**不带授权码**的客户端连 `term/ws` 会被拒（前端表现为终端连不上，
并且回退到 SSE 后 SSE 也 403）。

**失败长什么样**：门禁开着，终端却照样能连上 → **分发层的授权校验漏了**，这是个后门，
优先级最高。

## 3. 会话录制与回放

### 3.1 录制自动开始

**做什么**：连一个 SSH 终端，跑几条命令（`pwd`、`ls -la`、`df -h`），停一两秒，再断开。
看窗口头是否有**闪烁的红点 + 「录制中」**。

**期望**：有；断开后红点消失。切到「**录像**」Tab，应有一条记录，连接名 / 开始时间 /
时长 / 大小 / 通道都对得上。

**失败长什么样**：

- 列表一直空 → 先确认插件配置 `recordSessions` 没被关；
- 窗口头没有红点但列表里有记录 → ready 帧没带 `recording` 字段。

### 3.2 🎯 回放要“像当时那样”

**做什么**：点那条记录的「回放」。观察：内容、顺序、大致节奏（不是一次性刷完）。

**期望**：按当时的时间节奏重放；进度条可拖，拖动后画面是**从零快进到位**（不应叠上一遍）；
1× / 2× / 4× / 8× 切换可用。

**同时验一条取舍**：回放里**不会**重演当时的窗口尺寸变化，而是按当前窗口宽度渲染。
中途改过窗口大小的会话，回放换行位置可能与当时不同——**这是已知取舍，不是 bug**。

**失败长什么样**：

- 回放里命令像是被打了两遍 → 输入事件（`i`）被一起重放了；
- 拖动进度条后画面花掉 / 内容重复 → 快进前没清屏；
- 回放一片空白 → 录像文件只有头行（会话没产生输出），或者 `.cast` 解析失败。

### 3.3 三个边界

| 场景 | 期望 |
|---|---|
| 连上终端后**什么都不做**立刻断开 | 列表里仍有一条（0 输出但文件合法，回放会提示「没有任何输出」） |
| 跑 `yes` 或 `seq 1 10000000` 撑满 | 该条标记「**已截断**」，文件不再增长（上限 8MB），磁盘不被写爆 |
| 会话进行中直接强杀服务进程，再启动 | 那一轮没有索引记录；重启后孤儿 `.cast` 被自动清掉（见 3.5） |

### 3.4 ⚠️ 录制默认开启——要有预期

录制是**默认开**的。终端里敲过的密码、打印出来的 token 都会进 `.cast`。验收时顺手确认：

- 「录像」Tab 顶部显示「录制中」而不是「录制已关闭」；
- 关掉录制后（插件配置 `recordSessions: false`）**新会话不再产生记录**，列表保持原样。

这条不是 bug，但值得让使用者知道。文件只在本机 `<DATA_DIR>/ops-recordings/`，经 `/api`
下发，与其它运维接口同一道授权门禁。

### 3.5 ⚠️ 破坏性操作：孤儿清理

启动时会删掉「索引里没有的 `.cast`」——因为进程被强杀时收尾没跑到。

**这条检查本身很危险**（它删文件），所以代码里对**测试进程**做了守卫。真机验收建议这样跑：

```bash
# 1. 先记下当前有哪些录像
ls "${DATA_DIR:-apps/server}/ops-recordings/"
# 2. 手动放一个不属于索引的假文件
touch "${DATA_DIR:-apps/server}/ops-recordings/rec-orphan-test.cast"
# 3. 重启服务
# 4. 假文件应当消失，在册的都应还在
ls "${DATA_DIR:-apps/server}/ops-recordings/"
```

**失败长什么样**：在册的录像也被删了 → **立刻停手并报告**，这是数据丢失级别的缺陷。

> 顺带说明：单元测试里如果把 `VITEST` 守卫去掉，跑一次测试就会删光开发机上的真实录像
> （测试的 cwd 与「dev 未设 DATA_DIR 时」的录像目录是同一个）。这也是为什么清理逻辑
> 单独用 `sweepOrphanRecordings` 直测，而不是靠 activate 触发。

## 4. 主机密钥校验

### 4.1 🎯 首次连接记录指纹，且与 OpenSSH 一致

**做什么**：新建一个指向 B 的连接（凭据填对），连一次。切到「**主机密钥**」Tab。

**期望**：出现 B 的记录（`IP:端口`、`ssh-ed25519`、`SHA256:…`）。

**强证明**——把指纹和 OpenSSH 自己算的对照：

```bash
# 在 B 上
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

也可以在本地算：

```bash
ssh-keyscan -t ed25519 <B 的 IP> 2>/dev/null | ssh-keygen -lf -
```

两边的 `SHA256:…` 必须**逐字相同**。不同就说明指纹口径错了（我们用的是
`SHA256:` + base64(sha256(公钥 blob))、去掉 `=` 填充，与 OpenSSH 一致）。

### 4.2 页头显示的模式对不对

页头会显示当前策略（TOFU / 严格 / 不校验）。改成 `strict` 或 `off` 重启后，应跟着变；
`off` 会用危险色（红）标出来。

### 4.3 🎯 密钥变更必须被拒

**做法一（真实轮换，推荐）**：在 B 上重新生成主机密钥：

```bash
sudo rm /etc/ssh/ssh_host_*
sudo dpkg-reconfigure openssh-server    # 或 sshd-keygen / ssh-keygen -A
sudo systemctl restart sshd
```

再连同一个连接。

**做法二（不用碰服务器）**：直接改库里的记录，模拟「服务器换了密钥」：

```bash
sqlite3 "${DATA_DIR:-apps/server}/data.db" \
  "SELECT value FROM plugin_storage WHERE plugin_id='ops-shell' AND key='known-hosts';"
# 把 value 里那条记录的 keyB64 改几个字符，再写回
```

**期望**：连接**失败**，报错形如：

```
主机密钥校验失败：<B>:22 的主机密钥已变更。
  已记录：SHA256:<旧>
  本次收到：ssh-ed25519 SHA256:<新>
可能是服务器重装 / 换了机器，也可能是中间人攻击。
若确认是合法变更，请到「运维 → 主机密钥」页删除该主机记录后重连。
```

**必须同时确认两件事**：

1. 报错里**两个指纹都在**（只说「不匹配」等于把用户卡死）；
2. `known-hosts` 里**仍然是旧指纹**——被拒的新密钥绝不能被写进去，否则下次就放行了。

**失败长什么样**：密钥变了还能连上（**最严重**）；或者第一次连就报 mismatch（记错了）。

### 4.4 恢复路径要真的能恢复

**做什么**：接着 4.3，在「主机密钥」Tab 点该主机的「**忘记**」（确认框会说明后果），
然后重新连接。

**期望**：连接成功，且指纹更新为**新**密钥。

### 4.5 每一跳都单独校验

**做什么**：`target`（经 `bastion`）第一次连——两条记录（A 和 B）应**分别**出现在列表里。

**为什么重要**：只验最终目标而放过跳板机，等于把信任根留了个洞——而跳板机恰恰是流量
必经的那一跳。

**加强验证**：只对 `bastion`（A）做密钥轮换，`target` 不变。再连 `target` 应当**失败**，
且报错指向 **A** 的地址（而不是 B）。

### 4.6 strict 模式

**做什么**：配置 `knownHostMode: 'strict'`，然后连一个**从没连过**的主机。

**期望**：直接拒绝，报错里带实际收到的指纹并注明 strict。

**顺带确认**：**已记录**的主机在 strict 下照常放行（别把 strict 做成谁都不让连）。

### 4.7 off 模式是逃生口

配置 `knownHostMode: 'off'` 后：连任意主机都放行，且**不新增**记录，也不改写已有记录
（换密钥也能连上——这正是「关掉校验」的语义）。

## 5. 命令审批闸门

这一项的验收**必须走 AI 对话**（人在终端里敲命令不需要闸门——敲的人自己就是批准者）。

### 5.1 准备

新建连接 `prod-test`，**标签填「生产」**（这个标签是闸门的触发条件），指向一台**可以随便
折腾**的测试机，跑着 nginx 或任意能用 systemctl 管理的服务。

打开该连接的**对话模式**（AI 主导），问助手：「先用 `systemctl status nginx` 看看状态，
再用 `systemctl restart nginx` 重启它。」

### 5.2 🎯 只读放行、写操作停下

**期望**：

| 命令 | 结果 |
|---|---|
| `systemctl status nginx` | 直接执行，返回真实输出 |
| `systemctl restart nginx` | 返回「**⏸ 该命令需要人工批准，尚未执行**」，**没有执行** |

同时**工作区顶部（Tab 之上）出现橙色待批准条**，写着连接名和命令原文，带「批准 / 拒绝」。

**必须同时确认**：`systemctl status` 在**只读白名单**里，所以它不该触发批准——否则助手
连看一眼状态都做不了。

**失败长什么样**：写操作直接执行了 → **闸门没生效，这是本轮最关键的一条**。

### 5.3 🎯 批准后原样重试才执行

**做什么**：点「**批准**」。观察助手是否继续。

**期望**：批准被记录；助手**原样重试**那条命令后真正执行，返回真实输出（`nginx` 确实重启了）。

**已知限制**：是否自动重试取决于模型。若助手没有自己接着走，跟它说一句「已批准，重试」——
这属于正常交互，不算缺陷。但**批准前它绝不能执行**（5.2 已验）。

**再看一眼操作日志**：应有 `approval.requested` → `approval.approved` → `approval.granted`
这条时间线。

### 5.4 🎯 批准不能被复用，也不能被“张冠李戴”

| 做法 | 期望 |
|---|---|
| 批准 `systemctl restart nginx` 后，再让它跑一次**同一条** | 回到「待批准」（批准用一次即失效） |
| 批准 `systemctl restart nginx` 后，让它跑 `systemctl stop nginx` | 仍需**重新批准**（改一个字就是另一条命令） |

第二条尤其重要：否则「批准 `ls`」会被用来给「`rm -rf`」背书。

### 5.5 拒绝

**做什么**：重新触发一次待批准，点「**拒绝**」。

**期望**：工具返回「**⛔ 该命令已被运维人员拒绝执行**」，并明确要求助手**不要再重试、
也不要换写法（拆分 / 改参数 / 换工具 / 换连接）达成同样效果**；确认命令确实没执行。

### 5.6 🎯 模型无法自行确认（回归项）

**做什么**：设法让助手认为「用户已确认」。最直接的办法是直接问它：
「你带 `confirmed=true` 再调一次 `ssh_exec` 试试」。

**期望**：**依然不执行**，仍返回待批准。

**为什么单列**：旧实现的洞正在这里——`confirmed` 是模型自己传的。现在工具**恒以
`confirmed: false` 过护栏**，所以模型传什么都进不来。真出现「带了 confirmed 就执行了」，
说明有人把参数接回去了。

### 5.7 黑名单不给批准通道

**做什么**：让它跑 `rm -rf /` 这类破坏性命令。

**期望**：**直接被黑名单拒绝**，且**不出现待批准条**——黑名单不该能被「批准」绕过。

### 5.8 危险默认值

**做什么**：直接打那个决定接口，不带 `approve`：

```bash
curl -X POST 'http://127.0.0.1:3001/api/plugin/ops-shell/approvals/<id>' \
  -H 'Content-Type: application/json' -d '{}'
```

**期望**：返回 400（「必须显式给出 approve: true / false」）。**绝不能默认批准**。

### 5.9 过期

待批准放满 10 分钟再点批准。

**期望**：请求已失效（列表里不再有它 / 返回 404 或 409），需要重新发起。

### 5.10 docker_restart 同口径

在生产标签的连接上让助手重启一个容器。**期望**：同样先待批准；批准后执行；日志里能
看到 `docker restart <容器名>` 作为被批准的命令原文。

这五轮动了不少共享代码（插件注册表、连接池、终端主流程、控制台模板），顺手确认：

## 附 B：已知缺口（验收时不用当 bug 报）

1. **SFTP 写操作仍走老的二次确认**（前端 `ElMessageBox` 弹窗），没接新闸门。人工在界面上
   操作时那是合适的；本次闸门针对的是 **AI 发起**的写操作。
2. **回放不重演窗口尺寸变化**，按当前窗口宽度渲染（刻意的取舍，见 3.2）。
3. **批准后是否自动重试取决于模型**（见 5.3）。
4. **`db.ts` 里运维助手的系统提示词**已改为描述人工批准流程，但该行属于另一会话的在途改动，
   未随本轮提交入库；若库里提示词仍是旧版，模型可能先按旧习惯传 `confirmed`（行为仍安全，
   只是多一轮往返）。
5. **录制内容含敏感信息**（终端里敲过的密码、打印出的 token）。默认开启，只落本机。

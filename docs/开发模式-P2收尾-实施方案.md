## P2-6 后台并行子智能体（对标 Claude Code background agents）

> ✅ 已落地（2026-10-04）。实施偏差与新增发现：
> ① 闸门/文案抽成 `services/background-subagents.ts`（方案未写）——行为级测试才可能（后台循环本身跑不了单测）；
> ② 工作任务型子智能体在 `async: true` 时**直接走原路径不套壳**（发现：套壳会与 runWorkflowSubAgent 反写形成双重投递）；
> ③ **前端发现一个真并发缺陷并修复**：`subAgentMsgIds` 只按 subAgentId 索引，同一 agent 的两个后台任务会把两路 token 流合流进同一条消息 —— 已改复合键 `${parentToolCallId}::${subAgentId}`，服务端 chunk/tool_call 事件补发 parentToolCallId（消息渲染分组本就按 parentToolCallId，无需改）；
> ④ 收尾提示以**落库消息**实现（非给模型补话）——模型已决定 finish，再喂提示会强迫多跑一轮，与"不空转"拍板矛盾；
> ⑤ 布点踩坑：行注释里写 `skills/` + `*.md` 的 glob 写法会让测试的朴素 strip 正则把 `/*` 当块注释起点吞掉大段源码（多个守卫假红）——该序列在注释中一律改写，新测试 strip 改"先剥行注释再剥块注释"。

### 现状与可复用资产

- `call_agent` → `runSubAgent`（llm-task-manager.ts:3236）是**同步阻塞**的 ReAct 循环：父循环在 `executeTool` 里 await 它，子级跑完父级才继续。重活委派时用户全程干等。
- **完成语义的现成模板**：工作流子智能体（`runWorkflowSubAgent`:2885）已经是"后台跑完回调"形态 ——
  `startWorkflowRun`（fire-and-forget，落 workflow_run 表）→ `watchWorkflowRun`（订阅终态）→ `deliverWorkflowResult`（结果反写对话）→ `resumeWorkflowDeliveries`（重启补投）。
  ★ P2-6 的核心决策：**不发明第三种完成语义，ReAct 后台子任务对齐工作流的这套形态**。
- 主循环完成检测在 llm-task-manager.ts:1825（`toolCallAcc.length === 0` → finish），`pendingInjects` 兜底续跑在 :1843。

### 方案

1. **工具面**：`call_agent` 新增可选参数 `async: boolean`（schema 改 packages/core/src/tool/builtin/call-agent.ts）。`async: true` 时 `executeTool`（llm-task-manager.ts:2581 分支）不再 await 子循环，立即返回回执：
   `后台子智能体「<name>」已启动（任务号 <bgId>），完成后结果会自动发回本会话；期间你可以继续其他工作或结束任务。`
   回执格式对齐 `buildWorkflowReceipt`。
2. **后台执行体**：新 `runSubAgentDetached(task, args, parentToolCallId)`——**复用 `runSubAgent` 全部主体**（消息归属 / buildContextView / 工具面 / 深度限制 / 自动接力），只差两点：
   - 注册进 `task.backgroundSubAgents: Map<bgId, { agentName, status, startedAt }>`（`sub_agent:start` SSE 已具备，前端天然能看到子级消息流）；
   - 完成后走 `deliverSubAgentResult`：结果以**用户侧注入消息**落库（前缀 `【后台子智能体 <name> 完成】`），
     - 会话有**运行中**任务 → 走 `injectUserMessage` 同款通道（llm-task-manager.ts:458 起：落库 + `pendingInjects` 标记，父循环下一轮自然看到）；
     - 会话**无**运行中任务 → 直接落库为普通消息（与 `writeBackWorkflow` 的 pushConversationMessage 同口径），不主动唤醒新任务。
   - ★ 复用方式与 spawn_subagent 的先例一致（3270 注释："能复用就绝不复刻"）：把 runSubAgent 的"结果怎么处理"参数化（返回 vs 投递），不复制循环体。
3. **并发闸**：`task.backgroundSubAgents` 未完成数 ≥ 3（常量，可配）时 `call_agent async` 返回引导文案"后台并发已满，请等待其中一个完成或改为同步调用"，**不排队**（排队会让模型在 receipt 里看不到排队中任务，状态不可见；直接引导比静默排队诚实）。
4. **完成检测的边界（方案 P2 原文的第 3 点，这里拍板）**：主循环 `toolCallAcc.length === 0` 时**照常 finish**，不等待后台子任务 —— 等待会造成"模型不调工具 → 检测到后台任务 → 续跑 → 又不调工具"的空转烧 token 循环。后台结果靠注入消息唤醒下一轮（机制已存在，:458），父任务结束后完成的结果同样落库可见。在 finish 前若仍有后台任务，给模型的收尾提示补一句"注意：仍有 N 个后台子智能体在跑，完成后结果会发回本会话"。
5. **权限与无人值守**：后台子任务继承父任务权限档；**执行期间订阅者可能已退光**（用户关页面），写操作自然落入 path-guard 的无人值守 fail-safe 拒绝（requestPathAuthorization:649 已处理）—— receipt 里明示"后台子任务的写操作需要前端在线授权"。危险命令护栏 / 用户钩子同样生效（executeTool 单一入口，无旁路）。
6. **中止**：后台子任务监听**同一个** `task.abortController.signal`（runSubAgent 循环内 :3430 已逐 step 检查，天然级联）；任务删除/完成时 Map 清空。
7. **重启恢复（拍板：不恢复）**：后台 ReAct 子任务状态在内存，服务重启即丢 —— 与 workflow 的 `resumeWorkflowDeliveries` 不同，不做重启补投（补投需要把子 ReAct 全状态落库，成本远超收益）。启动时不做事；用户在会话里看到子智能体消息流戛然而止即"丢失"信号，P2b 若有诉求再落 llm_task 子任务行（表已有 origin 字段，留了路）。
8. **前端**：复用 `sub_agent:*` SSE 渲染；`ChatMessageList.vue` 给进行中的后台子任务加状态 chip（进行中/已完成），数据源用新增的 `task:background-update` SSE 事件（bgId/status）。

### 改动点
`call-agent.ts`（schema）、`llm-task-manager.ts`（executeTool 分支 + runSubAgent 参数化 + deliverSubAgentResult + backgroundSubAgents）、`ChatMessageList.vue`（chip）。

### 验收
三个 async call_agent 并发跑 → 回执立返；全部完成后三条结果消息出现在会话；第 4 个 async 调用收到"并发已满"；任务中止时后台子任务停止发射 token。

### 风险
- **文件并发写**：后台子任务与主循环同时改同一文件。现有防线已够：file_change 快照 + 审查面板 + path-guard；方案 P2 原文"默认继承 readonly"**不采纳**（会废掉后台跑重活的意义），改为靠弹窗授权串行化。
- 空转循环：靠第 4 点"照常 finish"规避，收尾后由注入消息唤醒，无持续烧 token 的路径。

## P2-5 tsserver 接入（LSP：导航最后一块短板）

> ✅ 已落地（2026-10-04）。实施偏差：① 只做了 `definition`（验收标准项）——`quickinfo` 与 `diagnostics` 实时通道**未做**（避免为未验证需求加工具面；diagnostics 通道涉及 `code_diagnostics` 增量口径设计，留待有真实诉求时）；
> ② node 运行时解析从 stdio-client 的私有方法抽成公共 `resolveNodeRuntime()`（否则 tsserver 会复刻第三份 —— 与「横切冗余收敛」的 Z1 同族问题，顺手先修一处）；
> ③ 项目根探测：向上找最近含 tsconfig.json 的祖先（找不到退含 package.json 的），tsserver 靠它加载项目；
> ④ 集成测试真实 spawn tsserver（临时 re-export 项目），验收标准（index.ts → impl.ts）实测通过；tsserver 不可用时 skip 不假红；
> ⑤ 崩溃路径补齐：失败计数带入自动重启、健康应答后归零、连续 2 次失败熔断（初版 getServer 恒传 failures=0，熔断分支不可达；另补死管道写入拒绝与 stdin 流错误兜底），假 tsserver 回归测试覆盖。

### 现状
`code_refs`/`code_graph`（packages/core/src/tool/builtin/code-refs.ts、code-graph.ts）在编译器可用时走 AST（code-ast.ts），但 AST 版在 **re-export 场景停在转发行**（`resolveToolPath` 经 index.ts 转出，definition 命中 index.ts 而非 fs-walk.ts 实现行）；也没有实时诊断。服务端 API 工具的注册先例：`api_code_semantic_search`（services/code-index.ts + mcp/api-tool-executor.ts）。

### 方案
1. **新 `services/lsp-manager.ts`**：按 workspace 根 spawn `node <root>/node_modules/typescript/lib/tsserver.js`（项目本地优先，缺失回退 server 依赖的 typescript——与 code_diagnostics 的 findLocalTsc/findLocalVueTsc 探测同款）。tsserver 协议（`{seq, type, command, arguments}` over stdio），**直接用 tsserver 协议**，不做 LSP 适配层。子进程管理复用 `dap-client.ts` 的先例（请求/响应按 seq 匹配 + 超时 + 崩溃重启一次）。
2. **能力分期**：
   - ① `definition` + `quickinfo`：新 API 工具 `api_code_definition`（注册到 api-tool-executor，与 api_code_semantic_search 同款描述风格："AST 版 code_refs 在 re-export 场景停在转发行，本工具走 tsserver 精确跳转"）。fileWrite/fileOpen 按需同步（tsserver 需要先 open 文件才有精确结果——对只查 definition 的场景，用 `reload` 命令全量刷新更省事，代价是慢一点，可接受）。
   - ② `diagnostics` 事件（`semanticDiag`/`syntaxDiag`）：订阅后写入内存 Map，`code_diagnostics` 工具新增 `source: 'lsp'` 增量通道——**只补充，不替换** tsc 全量通道（tsc 是权威、可缓存；lsp 是实时、易失）。
   - ③ rename/refactor：远期，不做。
3. **生命周期**：闲置 10 分钟回收；同一 workspace 单例；进程退出自动重启一次，再失败则该 workspace 熔断（本次任务内不再尝试，返回引导"tsserver 不可用，用 code_refs 启发式"）——熔断防止坏项目反复 spawn。
4. **浏览器端**：core 工具不动（平台无关），tsserver 只在 server 侧 api 工具；子智能体/工作流通过 api 工具面自然可用。

### 改动点
新 `services/lsp-manager.ts`、`mcp/api-tool-executor.ts`（api_code_definition）、`code-diagnostics.ts`（lsp 增量通道，可选）。

### 验收
对 `@yan-zhi/core` 的 re-export 符号（resolveToolPath）取 definition → 命中 packages/core/src/fs-walk.ts 实现行（AST 启发式停在 index.ts）；tsserver 被杀后首次调用自动重启，第二次失败熔断。

### 风险
tsserver 内存（大项目数百 MB）→ 闲置回收兜底；Windows stdio 编码 → 参照 CRLF 归一化的既有处理；协议无正式稳定承诺 → 只用 definition/quickinfo/diagnostic 三个最稳的命令。

## P2-8 项目级技能目录 `.yan-zhi/skills/*.md`

> ✅ 已落地（2026-10-04，提交随 P2-8）。实施偏差：实现抽成独立 `services/project-skills.ts`（原方案写在 llm-task-manager 内）——纯函数便于真实临时目录测试（6 例），也避免继续膨胀主循环文件；`effectiveWorkspaceDir` 计算点从规则段提升到函数入口（技能段与规则段共用同一取值口径）。

### 现状
AGENTS.md + `.yan-zhi/rules/*.md`（`loadProjectRules`:4413，mtime 缓存）注入系统提示；skill 注入在 buildSystemPrompt（:4150 起：触发词命中→注入完整 body，未命中→只注入 name+description）。

### 方案
1. **发现**：进入工作目录时扫 `<workspaceDir>/.yan-zhi/skills/*.md`，frontmatter（`name`/`triggers`/`description`，缺 name 用文件名）+ 正文 SOP。加载用与 `loadProjectRules` 相同的 mtime 缓存模式（目录级 mtime + 文件表）。
2. **注入**：在 :4150 的 skill 循环里合并为"虚拟 skill 行"——与 DB skill 走**同一份**注入格式与触发词匹配（`matchSkillTriggers`），不另起一段。**优先级**：项目目录 > agent/会话挂载 > 商城（同名时项目目录覆盖，提示词里标注"（项目技能，来自 .yan-zhi/skills/x.md）"）。
3. **不持久化**：不写 skill 表（会话结束即弃，目录就是真相源）；`api_skill_create` 沉淀的仍是 DB skill，两者并存，提示词的"技能缺失时的处理"指引补一句"本项目有 .yan-zhi/skills/ 约定时优先把团队规范放那里"。
4. **解析失败容错**：frontmatter 坏 → 跳过该文件并 console.warn，不让一个坏文件废掉整批。

### 改动点
`llm-task-manager.ts`（loadProjectSkills + :4150 合并）、无新表、无前端（P2a 先不做编辑器）。

### 验收
工作目录放一个 `code-review.md`（triggers 含"评审"）→ 用户说"帮我评审"时完整 body 注入；删文件后下次会话不再出现。

## P2-7 hooks P2b：script 类型 + after 通道 + 通用 before 通道接入

### 现状
P2a 已落地声明式 deny/confirm（services/user-hooks.ts + executeTool 前置执行）。基础设施欠账：`runBeforeToolHooks`（tool-hooks.ts:74）**主链路调用点仍为 0**（path-guard.ts 注释自认）；`runAfterToolHooks` 已接入（:1989 主循环、:3686 子智能体路径）。

### 方案
1. **先还账：把 `runBeforeToolHooks` 通用通道接入主循环**。位置在用户钩子（P2a 段）之后、危险命令护栏之前，顺序定为：**权限档 → 用户规则（P2a）→ 内置 before 钩子 → 危险命令护栏 → path-guard**（用户显式规则最先，内置兜底最后）。
2. **after 通道开放**：用户 after 规则（`trigger: 'after'`）只支持 `notify`（消息中心/会话内提示）与 `script`——after 已无拦截语义（工具都执行完了）。
3. **script 类型**：用户脚本跑 **js_exec 同款沙箱**（受限 require、无 fs/process——先例 services 里 js-exec），签名 `({ tool, args, result }) => { block?: string } | void`。异常处理：before script 抛错 → **fail-open 放行 + 审计**（与内置 before 钩子口径一致：钩子坏了不能废掉用户工具；但 deny/confirm 声明式规则仍是 fail-close，两者并存）；script 想拦就用显式 `return { block }`。
4. **设置页**：规则编辑加 trigger 选择与脚本编辑器（Monaco 已在包内），保存时 `new Function` 空跑一次做语法校验。
5. **schema**：user_hook 表 `trigger` 已留字段；新增 `script` 列（TEXT，P2a 未用列不迁移，直接加）。

### 改动点
`tool-hooks.ts`（无改动或极小）、`user-hooks.ts`（script 执行 + after）、`llm-task-manager.ts`（runBeforeToolHooks 接入）、设置页扩展。

### 验收
脚本钩子 `if (args.command?.includes('rm -rf')) return { block: '禁止递归删除' }` → cmd_exec 被拦且模型收到 block 原因；脚本抛错 → 工具正常执行 + 审计留痕。

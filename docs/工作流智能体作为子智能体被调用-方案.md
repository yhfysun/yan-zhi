# 工作流智能体作为子智能体被 harness 调用 — 现状核对与补齐方案

> 结论一句话：**这个逻辑没有。** 四条调用路径里，`harness → 工作流` 这一条是断的，而且断得很隐蔽——不报错，返回一段无关的空谈。
> 本文只做现状核对 + 方案设计，未改动任何产品代码。

---

## 一、四条调用路径的真实通断

| 调用方 | 机制 | 被调方 | 状态 |
|---|---|---|---|
| 前端工作流页 | `POST /workflow/run` | 工作流智能体 | ✅ 通 |
| 主智能体（harness） | `call_agent` | harness 子智能体 | ✅ 通 |
| 主智能体（harness） | `call_agent` | **工作流智能体** | ❌ **断** |
| 工作流 DAG | `sub_agent` 节点 | 工作流智能体（DAG 套 DAG） | ✅ 通 |

关键不对称：**工作流能嵌套工作流，但 harness 调不动工作流。**

## 二、证据（代码级）

### 2.1 `runSubAgent()` 完全不看 `agent.type`

`apps/server/src/llm-task-manager.ts:1419-1530`

```ts
// 1441  只按 id + 可见性解析，无类型判断
const agent = db.prepare('SELECT * FROM agent WHERE id = ? AND (user_id = ? OR is_public = 1)')
                .get(resolvedId, task.userId) as any;

// 1530  系统提示词：工作流智能体这里是 NULL → 退化成一句空壳
const systemPrompt = agent.system_prompt || '你是一个智能助手。';

// 1477  工具取自 builtin_tool_ids：工作流智能体是 '[]' → 零工具
const builtinIds: string[] = JSON.parse(agent.builtin_tool_ids || '[]');
```

而内置工作流智能体在 seed 时**显式写入 NULL 与 `'[]'`**：

`apps/server/src/builtin-workflow-agents.ts:174`

```sql
INSERT INTO agent (..., system_prompt, type, builtin_tool_ids, sub_agent_ids, ...)
VALUES (..., NULL, 'workflow', '[]', '[]', ...)
```

**净效果**：`call_agent { agentId: "a_wf_smoke_all_nodes", input: "..." }`

1. 查到 agent 行 ✅
2. 平台/模型解析 ✅（工作流智能体 `platform_id`/`model_id` 为 NULL → 回落到父任务模型）
3. 系统提示词退化为「你是一个智能助手」；工具列表为空
4. 进入 `for (let step = 0; step < maxSteps; step++)` 的 **ReAct 循环**
5. **`workflow_json` 字段从头到尾没有被读取过一次**

→ **DAG 一次都不会执行**，返回的是主任务模型对 `input` 文本的一段自由发挥。不抛错、不告警。

### 2.2 上游全部不拦，所以这个坑一定会被踩到

| 位置 | 行为 | 问题 |
|---|---|---|
| `llm-task-manager.ts:1296` | `list_sub_agents` 按 id 查 `name/description/platform/model` | **不返回 `type`**，LLM 无从知道这个是工作流 |
| `AgentEditDialog.vue:385` | `subAgentList = agents.filter(a => a.id !== props.agent?.id)` | **无 type 过滤**，工作流智能体可被勾选挂载 |
| `api-tools/agent.ts:11` | `api_agent_mount` 的 `subAgentIds` 无类型校验 | 接口层同样不拦 |

即：UI 允许你把「调研报告生成助手」挂成子智能体 → `list_sub_agents` 会列出来 → LLM 会调 → 拿到一段错的结果，全程没有任何一处报错。**这是典型的静默错误，比明着报「不支持」危险得多。**

### 2.3 顺带发现：`call_agent` 不校验挂载白名单

`llm-task-manager.ts:1441` 的查询条件是 `id = ? AND (user_id = ? OR is_public = 1)`，**没有对照 `sub_agent_ids`**。
`list_sub_agents` 是查挂载表的（`:1291-1292`），两者口径不一致。

后果：内置工作流智能体 `is_public = 1`（`builtin-workflow-agents.ts:174`），模型只要在上下文里见过这个 id，就能直接调，绕过「未挂载不可见」的设计意图。目前靠软约束（LLM 只从 `list_sub_agents` / system prompt 拿 id）挡着。

### 2.4 反向路径（工作流 → 工作流）是完整且严谨的

`apps/server/src/workflow-runner.ts:429-473` `ServerSubAgentNodeHandler`

```ts
// 463  按子智能体自己的 workflow_json 建一个独立引擎，递归跑子 DAG
const eng = createServerEngine({ agent: def, subAgents: this.bundle.subAgents }, ...);
const nextStack = ctx.callStack ? [...ctx.callStack, subAgentId] : [subAgentId];
const result = await eng.run(def as any, subInputs, { callStack: nextStack });
```

防环也做了：`packages/core/src/workflow/engine.ts:138-143` 有 `callStack.includes(subId)` 检测 + `maxDepth = 3`。

**但它同样不校验类型**（`workflow-runner.ts:454-461`）：若 `subAgentId` 指向一个 harness 型智能体，`workflow_json` 为 NULL → 解析成 `{nodes: [], edges: []}` → 跑一个空 DAG → **静默返回空结果**。同一个病。

### 2.5 工作流目前只有一个入口

`packages/core/src/tool/builtin/api-tools/index.ts:25-70` 的 21 个 API 模块里**没有 workflow 模块**（`workflow` 字样只出现在 `api_agent_create` 的 `type` 枚举里）。
唯一入口是前端 `agentStore.runWorkflow()` → `POST /workflow/run`（`packages/ui/src/stores/agent.ts:544-557`；`apps/server/src/routes/workflow.ts:22`）。

→ 上一轮方案的「断链 B（工作流调不到 api 工具）」之外，还有一层更根本的：**harness 也调不到工作流。**

## 三、补齐方案

### 3.1 先定义语义：工作流到底算不算「子智能体」

`call_agent` 的现有契约是（`call-agent.ts:9`）：

> 把子任务委托给指定的子智能体执行。子智能体以其**独立的系统提示词**与**可用工具**运行，并把结果返回。

工作流智能体**既没有系统提示词，也没有可用工具**，它是「一张确定性 DAG + 一组结构化入参」。硬塞进 `call_agent` 的语义里是拧的。

所以两条路线分开评估：

| | 路线 A：`runSubAgent` 按 type 分流 | 路线 B：新增 `run_workflow` / `list_workflows` 工具 |
|---|---|---|
| 改动点 | 一个函数 + 一个导出 | core 注册 schema + 后端拦截 + `db.ts` 挂载白名单 |
| 复用现有 UI | ✅「挂子智能体」入口直接生效 | ❌ 需要在工具挂载里额外勾 |
| 语义清晰度 | 中（`call_agent` 语义被拓宽） | 高（委派 vs 跑流水线，LLM 分得清） |
| 结构化入参 | 需要额外映射设计 | 天然支持 object |
| 修掉既有缺陷 | ✅ 顺手修掉「UI 能挂、后端不生效」 | ❌ 该缺陷仍在 |

**推荐：先做 A，B 作为可选增强。**

理由：A 修的是一个**已经存在的功能缺陷**（UI 说支持、后端跑不通），而不是新增能力；而且用户已经能在界面上挂载，不需要再教一遍。B 的价值在于让 LLM 显式区分两类委派，等真有「同一条流水线被多轮反复调用」的场景再加。

### 3.2 路线 A 的具体设计

**改动 1 — 复用 `executeBundle`，只加 `export`**（`apps/server/src/workflow-runner.ts`）

不需要新写一个同步执行器 —— `executeBundle`（`:553-571`）已经是「同步跑一遍 DAG 并返回 output」的形态，且**已内置 `run = null` 的降级路径**（无 SSE、无落库、无事件包装）：

```ts
// :557  run 传 null 时：logs 退化为普通数组、annotateBundle 跳过（不需要 nodeId 事件）
async function executeBundle(bundle, inputs, userId, run: WorkflowRunState | null) {
  const logs = run ? run.logs : [];
  const annotated = run ? annotateBundle(bundle) : bundle;
  const eng = createServerEngine(annotated, userId, logs, run);
  const result = await eng.run(annotated.agent as any, { ...inputs, __userId: userId }, {
    callStack: [bundle.agent.id],
    onNodeEvent: run ? (e) => emitRunEvent(run, e) : undefined,
  });
  return result;
}
```

只需：
1. 加 `export`
2. 补一个可选的 `onNodeEvent` 参数（用于事件桥接，见 3.3）
3. 捕获异常返回 `{ ok, output | error }`（`executeBundle` 现在是抛异常的，直接抛到 `runSubAgent` 会中断整轮对话）

`resolveBundleFromDb`（`:586`）也已导出，负责递归收集 `sub_agent` 引用的子智能体 —— 委派一路上的嵌套依赖自动带齐。

这样「工作流被前端直接跑」和「工作流被 harness 委派」走的是**同一个函数**，不会出现两套行为。

**改动 2 — `runSubAgent` 按类型分派**（`apps/server/src/llm-task-manager.ts`）

插入点：`:1442` 拿到 `agent` 行之后、`:1444` 解析平台/模型之前。门面形态与接口见 **3.3**（是分派，不是 TS 重载；调用方零改动）。

```ts
const ctx: SubAgentRunCtx = { task, agent, args, parentToolCallId, depth, uiTools };
const runner = SUB_AGENT_RUNNERS.find(r => r.handles(agent));
return runner ? runner.run(ctx) : runHarnessSubAgent(ctx);
```

三个必须一起处理的细节：

1. **入参映射**。`call_agent` 的 `input` 是 string，工作流要 `Record<string, unknown>`。策略按 `inputs_schema_json` 分档：
   - schema 只有 1 个字段 → `{ [field]: inputText }`（覆盖绝大多数单入参场景，LLM 无需感知）
   - schema 有多个字段 → 要求 LLM 传 JSON 对象；同时把 `CallAgentTool.inputSchema` 的 `input` 从 `type: 'string'` 放宽为 `oneOf: [{type:'string'}, {type:'object'}]`（`call-agent.ts:17-20`）
   - 无 schema → `{ input: inputText }`
   - **解析失败要明确报错并回传 schema**，不要静默塞进去

2. **事件与可视化**。工作流有节点级事件（`onNodeEvent`），子智能体消息体系是 message 级。最小可用做法：`sub_agent:start`（已有，`:1535`）→ 过程中 emit 节点进度 → 结束后把 output 作为 tool 结果落库。不要试图把 DAG 画进聊天流。

3. **中止与超时**。工作流可能长跑（含 llm 节点、浏览器节点）。必须接 `task.abortController.signal`，并加一个超时上限；否则一轮对话会被一条流水线挂死。

**改动 3 — `list_sub_agents` 输出标注类型**（`llm-task-manager.ts:1296-1308`）

```ts
const sub = db.prepare('SELECT name, description, platform_id, model_id, type, inputs_schema_json FROM agent WHERE id = ? ...')
// 行尾追加：` | 类型: 工作流(入参: {topic: string})`
```

不加这一条，LLM 只能靠名字猜，会继续做出错误的委派决策。

**改动 4 — 两处类型校验，把静默失败改成显式报错**

| 位置 | 现状 | 改成 |
|---|---|---|
| `workflow-runner.ts:454-461` | subAgentId 指向 harness → 跑空 DAG 返回空 | 校验有 `workflow_json`，否则 `throw new Error('子智能体 X 不是工作流类型，不能作为 workflow 的 sub_agent 节点')` |
| `runSubAgent` 分流的 else 分支 | harness 型走到这里 | 保持现有 ReAct 逻辑不变（正常路径） |

**改动 5（决策点，建议一并做）— `call_agent` 补挂载校验**

`llm-task-manager.ts:1441` 增加：若父 agent 的 `sub_agent_ids` 非空且不含 `resolvedId`，直接拒绝并提示先调 `list_sub_agents`。

风险：可能打断现有依赖「凭记忆直接点名」的调用。默认助手的 `sub_agent_ids` 已含 pageAgent + dataAgent（`db.ts:1710-1724`），主链路不受影响。**这一条建议单独确认后再动。**

### 3.3 两条路怎么切（设计定案）

**是分派，不是方法重载。** TypeScript 的 overload 只影响类型签名，同一份参数列表写两个声明，运行时不会有任何分派行为。这里两个实现的**签名完全相同、行为不同**，要的是 `agent.type` 上的运行时分派。

三种切法：

| 切法 | 形态 | 评价 |
|---|---|---|
| **门面分派** | `runSubAgent` 保持签名，内部两个分支 | ✅ **推荐**，调用方零改动 |
| 注册表分派 | `Map<type, runner>`，与 `WorkflowEngine.register()`（`engine.ts:47-51`）同构 | 2 个实现时略重；加第三种 type 时不用碰分派器 |
| TS 重载 | `function runSubAgent(...)` × 2 | ❌ 无效，签名一致 |

**切点位置**：`llm-task-manager.ts:1442`（拿到 agent 行）之后、`:1444`（解析平台/模型）**之前**。

理由：
- `:1426-1429` input 校验、`:1433-1438` 别名解析、`:1430` depth 检查、`:1441` 查 agent 行 —— **两边都要**，留在公共前奏
- `:1444-1473` 的平台/模型解析 + 可见性校验 —— **只有 harness 路需要**。工作流的模型由它自己的 llm 节点自带（`workflow-runner.ts:316-324`）

**复用点比预想的更省**：`executeBundle`（`workflow-runner.ts:553-571`）已经是现成的同步执行入口 ——

```ts
// :559-560  run = null 时自动降级为「纯执行」：无 SSE、无落库、无事件包装
const logs = run ? run.logs : [];
const annotated = run ? annotateBundle(bundle) : bundle;
// :565      __userId 已注入（漏了会直接报「平台不存在」）
const result = await eng.run(annotated.agent as any, { ...inputs, __userId: userId }, {
  callStack: [bundle.agent.id],          // :566 起栈，防环从这里开始
  onNodeEvent: run ? (e) => emitRunEvent(run, e) : undefined,
});
```

→ **只需给它加 `export`**，再补一个 `onNodeEvent` 参数（用于把节点进度桥接进聊天流）。`runWorkflowSync()` 因此薄到十行上下。

**接口设计（让将来能升级成注册表）**：

```ts
interface SubAgentRunCtx {
  task: LlmTask;
  agent: AgentRow;                    // :1441 已查出的行
  args: { agentId: string; input?: string; platformId?: string; modelId?: string };
  parentToolCallId: string;
  depth: number;
  uiTools: Set<string>;
}

interface SubAgentRunner {
  handles(agent: AgentRow): boolean;      // 是否由本实现处理
  run(ctx: SubAgentRunCtx): Promise<string>;  // 出参统一为文本
}
```

门面：

```ts
async function runSubAgent(task, args, parentToolCallId, depth, uiTools): Promise<string> {
  // ── 公共前奏（保留现状 :1426-1441）──
  const ctx: SubAgentRunCtx = { task, agent, args, parentToolCallId, depth, uiTools };
  const runner = SUB_AGENT_RUNNERS.find(r => r.handles(agent));
  return runner ? runner.run(ctx) : runHarnessSubAgent(ctx);   // harness 作兜底
}
```

两个要点：

1. **调用方零改动**。`dispatchToolCall:1276-1279` 那三行原样保留，`runSubAgent` 签名不变。
2. **`handles()` 判据**：`agent.type === 'workflow' || !!agent.workflow_json`。后者是给历史数据兜底（早期库的 `type` 可能没写对）。数组里把 `WorkflowSubAgentRunner` 排在前面，harness 作兜底 catch-all。

**升级成本**：现在 2 个 runner + 一个 3 行常量数组；出现第三种 type（如 `skill`/`text2sql`）时改成 Map 注册表是纯机械改动。

**顺带确认的缺口 — 模型回退**：`ServerLlmNodeHandler:319` 在 `platformId`/`modelId` 为空时直接 `throw new Error('LLM 节点缺少 platformId/modelId')`。而模型回填目前只有 `ensureBuiltinWorkflowModel()`（`builtin-workflow-agents.ts:198-225`）**且只针对 `WF_MAIN_ID`**。用户自建工作流若 llm 节点留空，被 harness 委派时会直接抛错。
→ 适配时把父任务的 `platformId`/`modelId` 通过 `ctx.inputs.__platformId/__modelId` 透传，作为 `:319` 的回退档。**这条漏了，委派会在第一个 llm 节点上炸。**

### 3.4 路线 B（可选增强）

新增两个内置工具，照 `call-agent.ts` 的「只注册 schema、执行由后端拦截」模式：

- `list_workflows` — 列出可用工作流 + 入参 schema（可复用 `list_sub_agents` 的类型标注后过滤出 workflow 型）
- `run_workflow { workflowId, inputs: object }` — 后端拦截 → 调 `runWorkflowSync`

挂载进 `DEFAULT_AGENT_BUILTIN_TOOLS`（`db.ts:656-695`）——注意这个白名单的注释已经警告过：「已注册未挂载 = 工具在 UI 里看得见、LLM 调不了」。

## 三之二、异步化与完成反写（第二轮，已实施）

### 为什么要改

第一版让 `call_agent` **同步 await** 整条 DAG。这是错的：一条流水线可能跑几分钟，同步等待会把主智能体的 ReAct 循环整体挂死，期间用户什么都做不了；即便加了超时，也只是「提前返回错误」，DAG 仍在后台跑完——两头不讨好。

长任务的正确形态就是**后台执行 + 完成回调**，而这套基础设施本来就有：`startWorkflowRun` 内部已是 fire-and-forget，还带落库（`workflow_run` 表）与 SSE。第一版绕开它是判断失误。

### 现在的执行模型

```
call_agent(workflow)
   ├─ 入参映射（不变）
   ├─ startWorkflowRun()  → 立即拿 runId，DAG 在后台跑
   ├─ watchWorkflowRun()  → 订阅终态事件
   └─ 立即返回回执（名称 + runId + 异步说明）  ← ReAct 循环不被阻塞
                    ⋯
DAG 跑完 → run:completed / run:failed
   └─ 反写对话：
        ├─ 文字 → 直接输出成 assistant 消息
        └─ 文件 → 写入会话交付目录 + 登记 conversation_file(category=deliverable) + 输出引用
```

**回执示例**（回给模型，不是回给用户）：

```
[工作流已在后台启动] 调研报告生成助手
runId: wfr_xxxxxxxx
该工作流为异步执行，不阻塞当前对话。执行完成后结果会自动写入本对话：文字直接输出，文件写入交付目录并登记。
你现在可以继续处理其他事情，不必等待。
```

### 产物形态判定

`classifyWorkflowOutput()` 把 output 节点产物切成两类（纯函数，可单测）：

| 产物 | 判定 | 处理 |
|---|---|---|
| 文字 | 默认（字符串、无文件特征的对象 → JSON） | 直接 `insertMessage` 成消息 |
| 文件 | 绝对路径 + 扩展名；或对象含 `path`/`file`；或含 `content` + `name` | 有内容先落盘到交付目录，再登记 + 输出引用 |

**不静默猜**：识别不出文件特征就按文字处理，反之亦然，但两种情况都会留下可见内容，不会出现「跑完了但什么都没有」。

### 会话级通知总线（为后续通知功能打底）

原来只有**任务级** SSE：任务一结束就没有任何订阅方，后台反写的内容只能等下次刷新才可见。

新增 `subscribeConversation(conversationId, cb)` / `emitConversation()`，语义是「不属于任何运行中任务的消息也能实时推给在线前端」。路由逻辑：

```ts
function notifyConversation(ctx, event) {
  const task = getTask(ctx.taskId);
  if (task && task.status === 'running') { emit(task, event); return; }  // 复用已订阅的 SSE
  emitConversation(ctx.conversationId, event);                            // 走会话总线
}
```

后续定时提醒、异步工具回调、外部事件入站都可以直接复用这层。

> 当前状态：总线已就绪并用于反写，但**前端尚未订阅**（`ChatMessageList.vue` 正被全局布局改造占用）。在前端接上之前，任务已结束时的反写内容落库可见、刷新即现；任务仍在运行时则能实时推送。

### 已知限制

- ~~server 重启会丢回调~~ → **已解决，见「三之三」**：投递上下文落库 + 启动补投。
- **反写不受任务中止影响**：`deliverWorkflowResult` 用一个「永不中止」的 signal 只套超时——流水线已经跑完，结果值得留下。
- **不自动续跑**：按决策，完成只反写内容，不会自动起新一轮 LLM。（任务仍在运行时除外：消息会进上下文，模型下一轮自然能看到，这与 `injectUserMessage` 行为一致。）

### 三之三、补偿投递（第三轮，已实施）

第二轮的反写 watcher 挂在内存里，server 重启即丢——跑完没来得及反写的、跑到一半被重启打断的，结果都悄悄消失。

**方案：投递上下文随运行落库，启动时统一补投。**

```
startWorkflowRun(..., delivery)        → workflow_run.delivery_json = ctx
反写成功                                → delivery_json = NULL（终态）
反写失败 / 进程重启                     → delivery_json 保留
─────────────────────────────────────
server 启动：
  markOrphanTasksInterrupted()          ← 此前从未被调用（死代码），本轮接上
  markOrphanWorkflowRunsInterrupted()   ← 同上；running → failed
  resumeWorkflowDeliveries()            → 扫 delivery_json 非空的行：
        status=completed → 按 result_json 补投产物
        status=failed    → 补投失败说明（error 列）
        成功后才清 delivery_json；失败保留，下次重启再试
```

**产物读取双通道**：`loadWorkflowOutput()` 优先内存（本进程内跑完的），回落 `result_json`（重启补投的场景）——两条路同一套 `classifyWorkflowOutput` 分类，不会出现两套行为。

**顺带修复的既有缺陷**：`markOrphanTasksInterrupted()`（llm_task 表）与 `markOrphanWorkflowRunsInterrupted()`（workflow_run 表）注释都写着「启动时回收」，但**全仓库没有任何调用点**——重启后 running 永远是 running。本轮一并接进 `index.ts` 启动块，且顺序固定：先回收、后补投。

**改动**：`db.ts`（`workflow_run` 加 `delivery_json` 列，幂等 ALTER）、`workflow-runner.ts`（`startWorkflowRun` 第 4 参 + `markWorkflowDelivered` + `loadPendingWorkflowDeliveries` + `WorkflowDeliveryCtx` 定义移到本文件避免循环依赖）、`llm-task-manager.ts`（`loadWorkflowOutput` 双通道 + `resumeWorkflowDeliveries` 导出）、`index.ts`（启动钩子）。

## 五、风险

| 风险 | 等级 | 说明 |
|---|---|---|
| 工作流内的 llm 节点被反复委派导致成本失控 | **high** | 一条 DAG 可能含多个 llm 节点，`call_agent` 无 token 预算概念。**必须**加超时 + 单轮委派次数上限 |
| 改 `apps/server/src` 忘重编 dist | **high** | 本仓库反复踩过的坑（见 `MEMORY.md`） |
| 入参映射猜错，工作流跑出无意义结果 | medium | 建议解析失败一律显式报错 + 回传 schema，不允许兜底猜 |
| 补挂载校验打断现有调用 | medium | 默认助手不受影响，但第三方自定义智能体可能依赖软约束。单独确认 |
| 长跑工作流阻塞会话 | medium | 需贯通 abort + 超时；不建议把工作流当同步子任务无限制等待 |

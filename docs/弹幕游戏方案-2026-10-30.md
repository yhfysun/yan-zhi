# 弹幕互动游戏方案（2026-10-30）

> 状态：调研 + 方案评审稿
> 目标：让直播间观众用**弹幕参与、用打赏改变战局**，由宠物 / 虚拟人主播实时解说
> 关联：[直播功能方案](avatar-live-plan.md)（同一套管线）、[宠物伴星方案](宠物伴星功能方案-2026-10-27.md)
> 可交互原型：[赤壁 / 观星台 / 甜咸之争](prototypes/historical-battle-proto.html)、[阵营对推（已被取代）](prototypes/danmaku-game-proto.html)

---

## 0. 结论摘要

1. **能搞，而且不需要新造一套直播链路**。现有 `画面合成 → 音频混音 → 编码推流` 里再插一个「游戏内核 + 游戏渲染」就能跑，弹幕入口 `POST /api/live/danmaku` 已经在。
2. **两条产品路线，别混为一谈**：
   - **路线 A（先做）自播互动玩法**：自己在自己直播间播，弹幕/礼物从哪来由我们定，游戏画面进我们的合成器。不依赖审核，2–3 周能跑通。
   - **路线 B（后做）上架抖音小玩法**：官方形态是「exe 客户端 + 服务端接平台回调」，能拿分成，但要提案评估、审核、接开放平台。游戏内核可原样复用，只需换外壳。
3. **玩法选型（2026-10-30 修正）**：不做匿名红蓝对推，改做**有主题的玩法族**——先给一个既定结局（史实 / 天命 / 立场），让观众用弹幕和打赏去改写它。P0 赤壁之战，P0.5 甜咸之争，P1 观星台与节气农耕。见 §3.2–3.4。
4. **打赏必须"每档都有可见动作"**，但不是"谁钱多谁必赢"——给的是**确定性收益 + 展示位**，不是胜负。免费玩家必须始终"看得见自己"。
5. **我们的差异化不是玩法，是主播**：宠物/虚拟人实时念名字、报战况、被打了会躲、赢了会转圈。纯弹幕游戏厂商没有这个。

## 1. 调研

### 1.1 官方形态：抖音「直播小玩法 · 弹幕玩法」

来源：抖音开放平台《直播玩法文档指引》《直播间礼物互动能力》《直播玩法 FAQ》。

**接入硬门槛**

| 环节 | 说明 | 周期 |
|---|---|---|
| 入驻认证 | 个人 / 企业开发者均可 | — |
| 创建小玩法 | 拿到 AppID | — |
| 提案评估 | 提交玩法提案（含 Demo 视频），从美术品质、玩法设计、题材选型评估 | 次日反馈，约 2 工作日 |
| 能力申请 | 提案通过后才能申请 | — |
| 开发联调 | 私密直播间挂载测试 | — |
| 提审上线 | 包体 + 配置同步审核 | 约 4 工作日 |

**技术形态**

```
抖音平台 ──HTTP 回调──→ 开发者服务端 ──WebSocket──→ 主播端「玩法客户端 exe」
            (评论/礼物/点赞)                              （Unity / Cocos / Laya / 自研）
```

- 客户端必须是**可运行的 exe**，挂载在直播伴侣的「小扳手」里，主播投屏开播。
- 平台不提供长连接接入，一期只支持 HTTP 推送；失败数据只有礼物支持 24h 内分页回查。
- 抖音云可托管服务端（内网专线免鉴权、WebSocket 网关、定时触发器），官方称能减少接入成本。

**能力清单**

| 能力 | 必需 | 备注 |
|---|---|---|
| 礼物互动数据 | 必选 | 最多选 8 种礼物 |
| 点赞互动数据 | 必选 | |
| 评论互动数据 | 必选 | 只下发改配置的关键词 |
| 玩法客户端（exe） | 必选 | |
| 直播信息 / 粉丝团 / 弹幕云启动 | 可选 | |
| 礼物进阶互动 | 可选 | 可区分阵营（≤4 个），需上报 group_id |

**礼物档位是固定的**（只能在下列礼物里挑 1–8 个）：

| 抖币 | 1 | 10 | 19 | 52 | 99 | 199 | 520 | 888 | 1200 |
|---|---|---|---|---|---|---|---|---|---|
| 礼物 | 仙女棒 | 能力药丸 | 魔法镜 | 甜甜圈 | 能量电池 | 恶魔炸弹 | 神秘空投 | 超级空投 | 超能喷射 |

支持**组刷**（配数量，如 66 个甜甜圈召唤超级小兵）、礼物效果描述限 5 字、可做「幸运魔方」随机道具。

**评论关键词是子串匹配**：配 `123`，发 `12` 不下发，发 `51234` 下发 —— 这意味着关键词设计要避免被日常聊天误命中。

**分成**：玩法特殊礼物流水平台 50% / 主播 50%，开发者从主播收益里自定价抽 X%，主播实拿 50%−X%。

### 1.2 非官方途径：网页版弹幕抓取

开源代表 `saermart/DouyinLiveWebFetcher`（1.8k star，2026-08 仍在维护），原理是：

1. 请求 `live.douyin.com/<房间号>` 拿 `room_id` 与页面渲染数据；
2. 用 `webmssdk` 生成 `signature` / `a_bogus`，拼 `wss://webcast.../webcast/im/push/v2/` 长连接；
3. 收 `PushFrame`（protobuf）→ gzip 解压 → `Response.messagesList` → 按 `method` 分派 `WebcastChatMessage` / `WebcastGiftMessage` / `WebcastLikeMessage` / `WebcastMemberMessage` 等；
4. 需自行发 heartbeat / ack，断线重连，并轮询房间状态判断开播。

**能拿到**：弹幕、礼物（含礼物名与数量）、点赞、进场、粉丝团、在线人数。
**风险**：签名参数随前端更新反复失效；账号可能触发风控；仓库多为 AGPL-3.0（传染）；平台条款上属于未授权抓取。

**结论**：只作为**开发期造数据**和**自己直播间自用**的兜底通道，不作为商业路径，也不进核心包（做成可选适配器）。

### 1.4 从业者踩过的坑（直接变成我们的设计红线）

来自《鱼蛙狂飙》《萌宠宠之战》制作人公开分享：

| 坑 | 我们的红线 |
|---|---|
| 对局 25 分钟太长 → 缩到 8 分钟 → 目标 2–3 分钟 | **单局 3 分钟**封顶，节奏按直播而非游戏设计 |
| 用游戏礼包思维定价（200 元），直播用户不买 | **礼物档位沿用平台 1–1200 抖币**，主力落在 10–52 抖 |
| 付费玩家碾压免费玩家，免费玩家流失 | 免费玩家**必有可见存在**（头像/单位/贡献榜） |
| 礼物特效播长片、切镜头 | 礼物特效 **≤1.5s，不切镜头** |
| 崩溃率千分之 1.5 主播体验就差 | 游戏内核与渲染隔离，**崩溃不影响推流** |
| 画面 3 秒内看不懂 | 打开就懂：一条战线、两个阵营、一根推线 |
| 人数一多同屏单位崩 | 单位**合并同类项**渲染，上限 2000 个视觉单位 |

## 2. 我们做的东西和别人的差别

| 维度 | 纯弹幕游戏厂商 | 我们 |
|---|---|---|
| 主播 | 主播只是开播的人 | **宠物/虚拟人是主播**，有动作、有表情、会解说 |
| 解说 | 无 | 现有 `live-ask` + `live-tts`：念打赏名字、报战况、回弹幕提问 |
| 互动深度 | 关键词 → 数值 | 关键词 → 数值 → **主播反应**（被打会躲，赢了转圈） |
| 部署 | 必须上平台 | 先本地自播，再决定是否上架 |
| 定制 | 改玩法要重新提审 | 规则是 JSON，直播间现场可调 |

一句话：**别人做的是「弹幕游戏」，我们做的是「有主播的弹幕游戏」。**

## 3. 玩法选型

### 3.1 候选对比

| 玩法 | 1 个观众能不能玩 | 打赏映射直观度 | 视觉热闹度 | 实现成本 | 流水天花板 |
|---|---|---|---|---|---|
| 阵营对抗（红蓝对推） | 差（要双方都有人） | ★★★★★ | ★★★★★ | 中 | 高 |
| 合作闯关（守塔） | **好** | ★★★★ | ★★★★ | 中 | 中 |
| 挂机展示（挤地铁） | 好 | ★★ | ★★★ | 低 | 低 |
| 整蛊主播（跑酷） | 好 | ★★★★★ | ★★★★ | 中高 | 中高 |

### 3.2 方向修正（2026-10-30 追加）

匿名「红蓝对推」是赛道标准答案，但它没有叙事——观众不知道为什么该帮红。**改成有主题的玩法族**：给一个"本来就写好的结局/命运/立场"，让观众去改写它。

核心不是新引擎，而是**基线（baseline）+ 干预（divergence）+ 判定（hinge）** 三段式：

| 环节 | 含义 | 例子 |
|---|---|---|
| 基线 | 没人干预时严格复现的结果 | 赤壁：火攻奏效，曹军大败 |
| 干预 | 每条弹幕/每笔打赏推动一根拉锯条 | 「改写度」/「星力」/「票数」 |
| 判定 | 到铰链时刻看拉锯条过没过门槛 | 改写度 ≥60% → 历史被改写 |

**为什么这样比匿名对抗强**

- 观众自带前情提要，3 秒就懂在争什么；
- 「能不能翻盘」天然有悬念，比「谁分高」耐看；
- 主播有得说：报战况、讲典故、念名字；
- 打赏有明确意义：不是加数字，是「解开铁索」「挪用星位」「逆转风向」。

### 3.3 玩法矩阵

同一套内核，换三样东西就能开新玩法：**场景与地形、基线脚本、动作词表**。

| 玩法 | 基线（不干预的结果） | 观众干预 | 打赏动作 | 判定 |
|---|---|---|---|---|
| **赤壁之战**（已做原型） | 史实：火攻奏效，曹军大败 | 改写度 | 解铁索 / 逆风向 / 识破诈降 / 援军 | ≥60% → 历史改写 |
| **官渡 / 淝水 / 巨鹿** | 各自史实结局 | 同上 | 换剧本即可 | 同上 |
| **观星台 · 天命**（已做原型） | 客星犯心宿，主兵灾 | 星力 | 点星 / 聚星 / 驱凶 / 移星 | ≥60% → 天命可违 |
| **甜咸之争**（已做原型） | 无基线，纯投票 | 票数 | 加票 / 拉票 / 拆台 / 翻盘 | 多数决 |
| **姓氏大作战**（已做原型） | 无基线，多族抢城 | 各族票数 | 本族加兵 / 抢城 | 票数最高夺城 |
| **MBTI 人格矩阵**（已做原型） | 无基线，十六型抢榜 | 各型亮度 | 点亮本型 / 拉人 | 最亮一格占榜 |
| **节气农耕** | 节气流转，按常年收成 | 农事度 | 祈雨 / 防风 / 赈灾 | 歉收 / 平年 / 丰年 |
| **周易起卦** | 本卦既定 | 六爻变化 | 变爻 / 定爻 | 卦成解卦 |
| **龙舟竞渡** | 无（竞速） | 桨力 | 加桨 / 鼓点 / 抢道 | 先到终点 |
| **飞花令 / 对诗** | 无（问答） | 答题 | 提示 / 换题 | 答对数 |

**排期建议**

- **P0**：赤壁（历史 RPG 感最强，也最容易讲清「改写」）
- **P0.5**：甜咸之争（零门槛、冷启动友好、几乎不需要美术，用来填空场）
- **P1**：观星台（视觉最讨喜，适合夜间档）、节气农耕（合作型，适合小直播间）
- 后三个（起卦 / 龙舟 / 飞花令）按节日档期排

**主题扩展**：同一套基线内核还可以套 敦煌壁画、二十四节气、十二生肖、山海经——差异只在场景绘制与文案，不动逻辑。

### 3.4 三条判定规则

1. **没人干预 → 严格复现基线**。不靠物理涌现，靠脚本时间线 + 偏差量，保证「不打赏就是史实」。
2. **逆着基线改越远越难**。门槛固定（60%），但越接近判定时刻，同样的礼物推得越少（时间衰减），避免最后一秒被一笔大单翻盘。
3. **判定之后不再改结论**。判定后的打赏只影响过程与战损，不改胜负——否则观众会觉得前面的努力白费。

## 4. 架构：接进现有直播管线

```
弹幕/礼物/点赞
      │
      ▼
┌─ LiveEvent（统一事件） ────────────────────────────┐
│  comment / gift / like / join / leave              │
└────────────────────────────────────────────────────┘
      │
      ├──→ ┌─ RuleEngine（关键词 / 礼物 → 语义动作）─┐
      │    │  规则是 JSON，可在设置页改              │
      │    └──────────────────────────────────────────┘
      │                     │
      ▼                     ▼
┌─ GameRoom（纯逻辑，无 DOM） ─┐   ┌─ HostReactor（主播反应）─┐
│  阵营/单位/血量/战局/榜单     │   │ 打赏感谢 / 战况解说 / 垫场 │
│  apply(event) → GameEvent[]  │   └──────────────────────────┘
│  tick(dt) → GameEvent[]      │                │
└──────────────────────────────┘                │
      │                                          ▼
      ▼                                   ┌─ Cue（speak/action/expr）─┐
┌─ GameRenderer（canvas） ─┐                 │ 走现有 TTS + Performer    │
│  只读 snapshot，不写状态  │                 └───────────────────────────┘
└──────────────────────────┘
      │
      ▼
SceneCompositor（现有）→ 编码推流（现有）
```

**三条硬规矩**

1. `GameRoom` 是纯 TS，不 import 任何渲染/网络代码 → 可单测、可回放、可在服务端跑。
2. `GameRenderer` 只读快照，**不允许改游戏状态**。渲染崩了游戏照跑，主播照播。
3. 所有外部输入先过 `LiveEvent` 归一化，**礼物与弹幕走同一条管道**，不让"打赏"变成绕过限流的后门。

### 4.1 核心类型

```ts
export type LiveEvent =
  | { kind: 'comment'; user: UserRef; text: string; at: number }
  | { kind: 'gift';    user: UserRef; giftId: string; giftName: string; count: number; coins: number; at: number }
  | { kind: 'like';    user: UserRef; count: number; at: number }
  | { kind: 'join';    user: UserRef; at: number }
  | { kind: 'leave';   user: UserRef; at: number }

export type UserRef = { id: string; name: string; avatar?: string }

export interface GameRoom {
  /** 幂等：同一 eventId 重放两次结果一致（断线补齐要用） */
  apply(e: LiveEvent): GameEvent[]
  tick(dtMs: number): GameEvent[]
  snapshot(): GameSnapshot
}

/** 游戏内发生的事，渲染与主播反应都订阅它 */
export type GameEvent =
  | { t: 'unit-spawn'; side: Side; name: string; kind: string }
  | { t: 'unit-die'; side: Side; name: string }
  | { t: 'skill'; side: Side; skill: string; by: string }
  | { t: 'base-hit'; side: Side; hp: number }
  | { t: 'round-end'; winner: Side | 'draw' }
  | { t: 'combo'; user: string; n: number }
```

**为什么事件既返给渲染又给主播**：主播反应和画面必须是同一个真相，否则会出现"画面炸了主播没反应"。

## 5. 打赏 → 动作绑定表（核心）

### 5.1 三层绑定

```
输入（弹幕文本 / 礼物 ID）
   ↓ ① 识别层：RuleEngine
语义动作（join-red / attack / heal / summon-heavy / clear-screen …）
   ↓ ② 效果层：GameRoom
游戏数值变化（生成单位 / 加攻 / 扣血 / 清场）
   ↓ ③ 表现层：Renderer + HostReactor
画面特效 + 宠物动作 + 语音播报 + 字幕 + 榜单
```

绑定表就是 ①② 之间的映射，纯数据：

```json
{
  "comments": [
    { "match": ["1", "红", "左边"], "action": "join", "side": "red" },
    { "match": ["2", "蓝", "右边"], "action": "join", "side": "blue" },
    { "match": ["冲", "打", "上"], "action": "attack", "cooldownMs": 1000 }
  ],
  "gifts": {
    "仙女棒":  { "coins": 1,    "action": "haste",       "durMs": 5000 },
    "能力药丸": { "coins": 10,   "action": "heal",        "amount": 20 },
    "魔法镜":  { "coins": 19,   "action": "clone",       "n": 3 },
    "甜甜圈":  { "coins": 52,   "action": "summon-unit", "kind": "chariot", "n": 5 },
    "能量电池": { "coins": 99,   "action": "team-buff",   "mul": 2, "durMs": 10000 },
    "恶魔炸弹": { "coins": 199,  "action": "aoe",         "dmg": 60 },
    "神秘空投": { "coins": 520,  "action": "summon-hero", "kind": "hero" },
    "超级空投": { "coins": 888,  "action": "clear-enemy" },
    "超能喷射": { "coins": 1200, "action": "next-round-buff", "mul": 1.3 }
  }
}
```

### 5.2 免费层：不花钱也要有事做

| 输入 | 动作 | 画面 |
|---|---|---|
| 任意弹幕（首次） | **加入** | 头像 + 昵称进场面，成为己方一个单位 |
| `1` / `2` | 选阵营 | 单位换成对应阵营色 |
| `冲` / `打` | 攻击（1s 冷却） | 己方单位冲刺一小段 |
| 点赞 | 蓄能 | 每 50 赞一次全队小增益，进度条可见 |
| 连续发言 | 连击 | 名字放大 + 连击数（不额外加成，只给存在感） |

**免费玩家的存在感是留存命门**：榜单常驻显示「本局免费贡献 TOP3」，不只显示打赏榜。

### 5.3 打赏层：每档都有可见动作

> 礼物档位直接沿用平台固定清单，不自造价格。

| 抖币 | 礼物 | 游戏动作 | 画面表现 | 主播反应 |
|---|---|---|---|---|
| 1 | 仙女棒 | 己方 5 秒加速 | 脚下拖尾光 | 「谢谢 X 的仙女棒！」 |
| 10 | 能力药丸 | 己方前排回血 | 绿色治疗圈 | 宠物跳一下 |
| 19 | 魔法镜 | 镜像分身 ×3 | 残影展开 | 「X 分身了！」 |
| 52 | 甜甜圈 | 召唤战车 ×5 | 5 辆车冲阵 | 「战车来了，冲！」 |
| 99 | 能量电池 | 全队攻击 ×2（10 秒） | 全屏电光 | 宠物发光 |
| 199 | 恶魔炸弹 | 敌方范围伤害 | 爆炸圈 + 震屏 | 「炸了炸了」 |
| 520 | 神秘空投 | 召唤英雄单位 | 大单位天降 + 名字横幅 | 宠物敬礼 |
| 888 | 超级空投 | 清空敌方场上单位 | 全屏白闪 + 名字特写 | 单独念名 + 停顿 |
| 1200 | 超能喷射 | **下一局**开局增益 | 局外公告 + 专属皮肤 | 「本局赞助人：X」 |

### 5.4 六条设计红线

1. **打赏买的是确定性和展示位，不是胜负**。888 能清场，但清完对方 30 秒内能重建，不改变"人多的一边赢"的基本盘。
2. **每档动作三件套**：画面 + 语音 + 字幕/榜单，缺一件观众就当没发生。
3. **连击合并**：同一用户 3 秒内连刷同礼物，合并成一次"×N"特效，不叠加 N 次。
4. **单用户冷却 + 单局上限**：防止一个土豪把对局变成单机。
5. **礼物特效 ≤1.5 秒**，不切镜头、不盖住战况中心。
6. **免费玩家永远有可见存在**：榜单、头像、连击数，三处至少一处。

### 5.5 为什么不做的事

- **不做真钱抽奖 / 下注竞猜**：涉赌，平台直接封。
- **不做"打赏解锁后续内容"**：观众会觉得被绑架，且踩未成年人保护红线。
- **不做机器人刷礼物造势**：平台有风控，且一旦被识别账号全废。

## 6. 主播反应（AI 差异化）

`HostReactor` 监听 `GameEvent`，按优先级产出 `Cue`：

| 触发 | 输出 | 优先级 |
|---|---|---|
| 礼物 ≥ 99 抖 | 单独念名 + 一句专属台词 | 高 |
| 礼物 < 99 抖 | 合并念名（3 秒窗口内多人一起念） | 中 |
| 己方血线 < 30% | 「快顶不住了！」+ 慌张动作 | 高 |
| 连续击杀 ≥ 5 | 「X 连杀了！」 | 中 |
| Boss / 英雄出场 | 解说 | 中 |
| 弹幕提问 | 走现有 `live-ask` 派任务 | 最高 |
| 空闲 20 秒 | 垫场 + 报战况 | 低 |

**与现有 Cue 优先级保持一致**：`reply > danmaku > narration > filler`。
游戏解说归 `narration`（可被正文打断），打赏感谢归 `danmaku`，垫场归 `filler`。

**频率闸**：主播话术总频率 ≤ 每 8 秒一句，避免解说盖过游戏音效、也避免 TTS 排队堆积。

**宠物动作映射**（复用现有六动作）：

| 事件 | 动作 |
|---|---|
| 收到礼物 | `hop` |
| 己方受伤 | `look`（惊慌张望） |
| 大额打赏 | `spin` |
| 连胜 | `wave` |
| 输掉 | `shy`（现有 `pet`） |

## 8. 分期

| 阶段 | 内容 | 验收 | 工期 |
|---|---|---|---|
| **G0** | 内核 + 渲染 + 手动投喂弹幕 | 本地起页面，手打 `1`/`2`/`冲` 能玩一局；礼物按钮能出特效 | 3–4 天 |
| **G1** | 绑定表 + 榜单 + 主播反应 | 9 档礼物全部有画面/语音/字幕；主播按频率念名 | 2–3 天 |
| **G2** | 接真实弹幕源 | 首次接入第三方适配器（可选装），断了能自动重连 | 2–3 天 |
| **G3** | 合作闯关玩法 | 单人开播可推进；与对抗玩法共用内核 | 3–4 天 |
| **G4（可选）** | 官方小玩法上架 | exe 壳 + 服务端回调 + 道具/评论配置过审 | 5–8 天 |

**G0+G1 是能拿给观众看的最小闭环**，约一周。

## 9. 风险

| 项 | 风险 | 应对 |
|---|---|---|
| 平台条款 | 第三方抓取属未授权，可能被限流/封号 | 只做可选适配器，默认关闭；商业路径走官方小玩法 |
| 抓取失效 | 签名参数随前端更新失效 | 适配器隔离，失效只影响弹幕源，不影响游戏内核 |
| 性能 | Electron + canvas 撑不住万人同屏 | 现实目标 500–2000 视觉单位；同类项合并渲染；超限降级为"数字代表一群人" |
| 免费/付费失衡 | 打赏玩家碾压，免费玩家走人 | 打赏给展示位不给胜负；常驻免费贡献榜 |
| 合规 | 抽奖/竞猜涉赌；未成年人打赏 | 明确不做抽奖；上线前接平台未成年人保护策略 |
| AIGC 标识 | 平台要求标识 AI 生成内容 | 场景角标沿用直播方案的「AIGC」标识 |
| 主播解说盖住游戏 | TTS 排长队 | 8 秒频率闸 + 可打断 |

## 10. 明确不做

- 不做真钱抽奖、竞猜下注、积分兑换现金

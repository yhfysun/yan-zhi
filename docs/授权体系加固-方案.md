# 授权体系加固方案（已实施）

> 2026-09-17 盘 + 实施。目标：**本仓库与任何构建产物都只能验签（解密侧），永不具备签发能力**；同时把「公司电脑打出来的包能直接跑」这个缺口堵掉。
>
> 用户拍板：**预置码保留**（`DEFAULT_LICENSE` 2026-11-27 到期，自然淘汰），因此本轮做 P1。

## 二、本轮实施内容

### P1-1 机器指纹替代裸 MAC（`apps/server/src/license.ts`）

原 `getMachineMac()` 取「第一个非 internal 网卡 MAC」——插 USB 网卡、装 VMware、WiFi 顺序变化都会让授权无理由失效。

新增 `getMachineIdentity()`，按平台读稳定硬件种子，哈希成 16 位大写十六进制：

| 平台 | 首选来源 | 备选 |
| --- | --- | --- |
| Windows | 注册表 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` | `wmic csproduct get uuid` |
| macOS | `ioreg` 的 `IOPlatformUUID` | — |
| Linux | `/etc/machine-id` | `product_uuid` → `/var/lib/dbus/machine-id` |
| 全部失败 | `sha256(hostname \| platform \| arch \| cpuModel)`（**刻意不含 MAC 与内存容量** —— 它们会变，正是要修的漂移源） | — |

- 哈希而非直存：MachineGuid / IOPlatformUUID 会被部分 DRM 当设备追踪 ID，不应经接口吐给前端。
- 任一来源失败都**不抛错**：硬件信息读不到时授权仍需可用，只降绑定强度（`source` 字段暴露实际走了哪条路径，便于排障）。

**绑定口径（向后兼容）**：`payload.machineId` 存在则比 machineId，否则回退比 `mac`，两者都空 = 不限机器 → **已发出的老码不失效**。

### P1-2 后端门禁中间件（`apps/server/src/license-guard.ts`，新增）

原门禁**只有前端路由守卫**（`packages/ui/src/router/index.ts:206`）+ localStorage —— 改一行 localStorage 即可绕过，`curl` 直连 `/api` 更是畅通。

- `requireLicense` 挂在 `app.use('/api', requireLicense)`，位置在所有业务路由**之前**。
- 取码：`x-license` 头优先，兼容 `Authorization: License <code>`（`Bearer` 留给 JWT，不复用）。
- 验签结果内存缓存，**TTL 10 分钟 / 上限 50 条 LRU**：稳态只付一次验签成本；**失败的码不缓存**（否则用户换新码后仍被拦满 TTL）。
- **豁免清单**（`EXEMPT_PREFIXES`）判定依据只有一条：*这个请求能不能带自定义请求头*。浏览器对 `<img>/<video>/<audio>/CSS url()` 发出的请求无法附加自定义头，故豁免：
  `health` · `license` · `auth` · `generated` · `media/proxy` · `plugin-assets` · `network/ip`
- **默认关闭**，`YZ_LICENSE_GUARD=1` 开启。理由：本地模式恒 guest、历史行为是「打开即用」，默认拦会让 dev 调试、冒烟脚本、`scripts/seed-workflow-agent.mjs` 全线 403。

### P1-3 前端统一注入授权头（`packages/ui`）

`api/client.ts` 新增 `buildRequestHeaders()`，`apiFetch` 统一注入 `x-license`；并逐处补齐**绕过 api 客户端的直连请求**：

| 文件 | 位置 |
| --- | --- |
| `stores/chat.ts` | SSE 流、tool-result ×2、abort、pause、resume |
| `stores/memory.ts` | `fetchJsonRaw` |
| `stores/cicd.ts` | 流水线流式运行 |
| `components/BrowserPanel.vue` | 6 处裸 fetch + `getAuthHeader` 改为复用中心函数 |
| `components/chat/ChatConsolePanel.vue` | 终端 SSE 流 |
| `components/code/panels/RunDebugPanel.vue` | 运行/调试 SSE 流 |

### P1-4 授权页与签发工具

- `stores/license.ts` 暴露 `machineId` / `identitySource`；`views/License.vue` 同时展示「机器标识」与「网卡 MAC」（前者为推荐绑定口径）。
- `scripts/gen-license.mjs` 新增 `--machine-id`（16 位十六进制）；`--mac` 与 `--machine-id` **互斥**（同时给会让人误以为两个都生效）。
- `scripts/license-manager.html` 同步新增机器标识输入与解析展示。

### 附带修掉的两个坑

1. **激活后插件层不恢复**：`App.vue` 的 `pluginStore.refresh()` 打 `/plugins`（非豁免路径）→ 门禁开启时停在授权页会 403 并被 `catch` 静默吞掉 → 激活后插件路由/皮肤/布局全缺，必须重启。已抽出 `bootPluginLayer()` 并在 `licenseStore.verified` 变真时重跑。
2. **豁免清单静默失效风险**：中间件挂在 `/api` 时 `req.path` 已被剥前缀，一旦改挂到 `/` 就会带 `/api` 前缀 → 豁免全失效，表现是「交付卡片图片全裂、皮肤全丢，但接口本身 200」，极难查。已用 `normalizeGuardPath()` 显式剥前缀并归一化，两种挂法都正确。

## 五、第二轮：凭证加密与签发侧隔离（P2 部分落地）

用户「2，3 优化下」——即把第一轮的遗留项 2（授权码明文存 localStorage）与 3（签发工具在库内）做掉。

### P2-1 敏感凭证加密落盘（`apps/desktop/keyring-crypto.cjs` 新增）

摸底时发现一个**比原计划更严重的问题**：`userData/keyring.json` 是**明文 JSON**，而里面存着 `platform:<id>:apikey` —— **真实的上游 API Key**。授权码反而不是最该保护的（它绑机器、且应用侧无签发能力，拿到也没用）。所以做法从「把授权码搬进 keyring」改成**加密 keyring 的敏感值**，一次同时保护两者。

- 敏感键：`license_code` + `^platform:.+:apikey$`。**界面偏好（`settings:*`）刻意保持明文** —— 加密后无法人工排查配置问题，且每次读写都要过一遍 DPAPI。
- 密文格式 `enc:v1:` + base64，底层 Windows DPAPI / macOS Keychain / Linux libsecret，密钥绑当前用户账户 → **复制 keyring.json 到别的机器或账户解不开**。
- **三条兼容语义（最易写错，已用单测+冒烟钉死）**：
  1. 无前缀的旧明文 → 原样返回，老用户升级后配置不丢；
  2. 密文解密成功 → 返回明文；
  3. 密文解密失败（换机器/换账户/文件被拷走/DPAPI 失效）→ **显式 `ok:false`**，IPC 层返回 null + 告警。**绝不能把 `enc:v1:xxx` 当 API Key 返回** —— 那样上游 401，且错误信息毫无指向性。
- `safeStorage` 不可用（Linux 缺 libsecret）时：加密返回 null → 降级明文（宁可弱保护也不能让用户存不进 API Key）；解密已存在的密文则显式失败。**不因密钥环缺失而中断保存**。

### P2-2 授权码改存 keyring（`packages/ui/src/api/license-code.ts` 新增）

授权码原先在渲染进程 localStorage。改存 keyring 后读写变异步，但 `buildRequestHeaders()` 必须在发请求瞬间**同步**拿到它（被所有直连请求调用）。故做成两级：

- **异步持久化到 keyring + 同步内存缓存**供请求头读取。缓存由授权 store 启动时填充（路由守卫 `init()` 必然先跑）。
- **迁移**：keyring 无码而 localStorage 有 → 写入 keyring 并**清掉 localStorage 副本**（不清就等于白迁移，明文副本还在）。
- keyring 不可用时退回 localStorage，**不让用户掉授权**。

### P2-3 签发侧移出仓库

`scripts/gen-license.mjs`、`scripts/license-manager.html` 与私钥同处一地，入库会随 clone 分发到任何构建机，放大「私钥和工具放一起」的事故面。

- `git rm --cached` 两者 + 扩展 `.gitignore`（连同原私钥忽略规则合成一段说明）。
- `package.json` 移除 `gen:license` 脚本（它指向已不跟踪的路径，留着就是断的）。
- README 补「授权体系」章节：应用侧只验签、门禁开关、绑定口径、签发侧不入库 + 手工运行方式。
- **用户拍板：只取消跟踪，文件留在原处**（不做物理搬移，避免出现两份私钥副本 / 单点丢失）。
- 已核实：CI、两份 package.json、三份 electron-builder yml **均无对该工具的引用**；`dist-release` 扫 1658 文件从未含 `scripts/`。

### 顺带修掉的坑

`apps/desktop` 无 vitest，改用 Node 22 自带 `node --test`。**踩坑**：`node --test <dir>` 会把目录当**模块 require**（报 `MODULE_NOT_FOUND`），不会递归找文件 —— 表现为「1 test failed」且看不出原因。必须写 glob：`node --test "test/**/*.test.cjs"`。

## 六、未做 / 遗留

- **预置码未删**（用户拍板保留，2026-11-27 自然过期）。**旧包内的预置码仍然有效**，公司电脑上那个旧包在到期日前仍会自动激活；要真正断掉必须重新打包分发。

- **`main.cjs` / `keyring-crypto.cjs` 改动必须重启 Electron**（preload 热重载、主进程不会）→ 症状是「能力可见但报 `No handler registered`」。本轮未做桌面端实机验证。
- Ed25519 替代 RSA-2048（码体积可缩 ~1/3）未做。
- ASAR 完整性校验未做（`dist-release/win-unpacked/resources/server/src/` 是明文目录，可直接改）。
- 签发工具已停止跟踪，但 **git 历史里仍有旧版本**（已推到远程 `origin/dev0.1`）。这是「降低分发面」而非「抹除历史」——两者都要做到的话需要 rewrite history + 强制推送，成本与风险都高，且工具不含私钥，判断为不必要。

## 七、回答「能不能只解密不能加密」

**本来就是这样**——`license.ts` 里只有 `createVerify`，没有任何 `createSign`，私钥也不在仓库与产物里。你担心的「公司电脑能跑」跟加解密能力无关，是 `DEFAULT_LICENSE` 这个预置试用码被打进每个包造成的。第一轮补的是**机器绑定质量**、**能挡 API 的门禁**、**前端带码**与**签发侧支持机器标识**；第二轮补的是**凭证加密落盘**与**签发侧隔离** —— 即「产物只验签、签发只在你本机」这套体系现在闭环了。

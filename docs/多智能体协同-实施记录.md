### 排除的假说（查证后确认无问题）

### 修复的缺陷
| # | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| ⑥ | 并发上限**三处各不同**：主链路默认 2（`YANZHI_MAX_CONCURRENT_AGENTS`）、后台子智能体 3、PlanRunner **硬编码 4 且不读该变量** | 同一物理约束（上游 LLM 配额）三处独立判定 → 用户调了一个另两个不变；429 风险不可统一控制 | PlanRunner 改用 `resolvePlanConcurrency()`，共享 `YANZHI_MAX_CONCURRENT_AGENTS`（1~8 钳位）；默认 4（计划场景诉求是并行，但不超过 8） |

- 重试与重派的每次执行 `parentToolCallId` 唯一（防上下文污染回归）

- 测试：`packages/core/src/workflow/engine-parallel.test.ts`（3 例：fan-out 真并发用**会合点**证明、condition 汇合不死锁、concurrency=1 顺序不变）；

## 2026-10-09 · 「其他模式是否也复用这套优化」排查结论 + 修复只读会话的矛盾指令

### 结论：这套优化**本来就是全局的**，无需按模式改造
- 实证 `conversation.mode`（office/dev/ops/sec/wf/clip）在实际运行链路上**只用于会话列表过滤**
  （`GET /api/conversations?mode=`）+ 一句 sessionIdentity 文案；**不影响**提示词构建、工具面、调度。
- 因此工件协议 / plan_tasks / 失败重分配 / workflow 并行对**所有模式、所有智能体**自动生效。
- 实测（buildToolsForBackend + filterToolsByPermission）：
  `a_builtin_code_agent` / `a_builtin_backend_dev` / `a_builtin_frontend_dev` / `a_default_assistant`
  **均可委派**（`call_agent` + `list_sub_agents` + `plan_tasks` 都在）。

### ★ 顺带发现并修复的真实缺陷：只读会话的「矛盾指令」
- 会话默认权限是 **readonly**（`chat.ts`）；而 readonly 下 `plan_tasks`/`reassign_task` 被
  `filterToolsByPermission` 从工具面摘除 —— 但 `buildSystemPromptForBackend` **无条件**注入
  「用 plan_tasks 编排」协议 → 模型同时收到「用编排」与「本次只读」两条**互相矛盾**的指令，
  且工具实际不可用 → 表现为反复撞墙。（`permissionModePrompt` 在 buildSystemPromptForBackend 之外追加，故互不知情）
- **修复**：`buildSystemPromptForBackend` 加 `opts.canDelegate`（默认 true 兼容其余两个调用点）；
  只读（canDelegate=false）时改注入「分步规划 + 需放开权限」的不矛盾说明；提示词模式的「可用工具」
  清单同步只列 `get_plan_status`（读类）。主链路按 `task.permissionMode` 传入。
- 判据：**同一事实（会话是否可委派）在工具面与提示词两处必须同源判定** —— 否则必然漂移成矛盾指令。
- 测试：`multi-agent-plan.test.ts` 新增「⑥b 编排协议按权限分流」守卫（含主链路必须传参）；**19 passed**。
- 实测：4 个智能体只读提示词均不含「用 plan_tasks」、均含只读说明；可写提示词均含编排协议。

## 2026-10-09 · pageAgent 特殊处理：浏览器操作「串行化」（用户拍板：按会话隔离 + 别互抢）

### pageAgent 的"特殊"到底是什么
它独占**浏览器这个全局单例资源**，且"当前活动页"在三处都是**单值**：
- 前端 `ensureActiveTab(scope)`：每 scope 单值（同会话只有一个活动页）；
- 桌面主进程 `main.cjs` 的 `activeTabId`：**全局单值**（scope 只用于过滤标签列表）；
- 服务端 Playwright 的 `pageInstance`/`activeTabId`：**进程级单值**。
⇒ 多个 pageAgent（或一批并发 `browser_*`）同时操作会**互相抢活动页**：后到的 navigate 覆盖前一页，
读取只能读到"当前页" —— 这正是用户感觉"只能有一个 pageAgent 在动 / 结果错乱"的真机制（并发闸其实是 3）。
实测证据：agent 的操作跑到了用户停留的番茄达人中心页上。

### 方案取舍（用户明确否决"真并行"）
> "2 的话应用页面体现不出来吧" —— 预览面板一次只显示一个活动页，真并行**用户看不到**。
故**不做**"活动页按 agent 隔离"（要动 main.cjs + 前端分发 + 服务端，收益/风险不成比例），
改做**会话级串行**：不互抢、行为可预期，且与既有 `agentAnchoredTabs`（按 convId 锚定 tab）隔离口径一致。

### 实现
- **前端**：新增纯模块 `packages/ui/src/stores/browser-op-queue.ts`（`chainBrowserOp`/`dropBrowserOpChain`）；
  `chat.ts` 把 `dispatchToolCall` 拆成「包装层 + `dispatchToolCallInner`」，`browser_*` 走 `serializeBrowserOp(ctx.convId, …)`
  —— **零改动内部 30+ 个 return 点**，也不可能漏包某分支。会话删除时清链（防泄漏）。
- **服务端**：`routes/browser.ts` 加 `withBrowserLock` 中间件，**只包写操作**
  （`/navigate` `/action` `/back` `/forward` `/refresh` `/close` `/focus` 共 7 个），
  读操作（state/screenshot/downloads/history/stats）直通 —— 否则 UI 轮询会排在长操作后卡住。
  ★ 挂在 router 层统一包装（而非逐个 handler）——本模块入口多，逐个包必漏（"入口漂移"教训）。

### 测试
- `packages/ui/src/stores/browser-op-queue.test.ts`（6 例）：同会话严格按序 / 跨会话不阻塞 / 前一个失败也放行 /
  链尾吞错不产生 unhandledRejection / 无 convId 不串行 / drop 清理。
- `apps/server/test/browser-serial-lock.test.ts`（4 例）：7 个写路由全包 / 读路由不包 / 白名单判定 / finally 释放。
- 回归：background-subagent、multi-agent-plan、browser-serial-lock、workflow-engine-control 各自全绿；
  ui（vue-tsc）0 error；server tsc 绿。

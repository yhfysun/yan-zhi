# 会话「卡死」与流式断流 —— 根因与修复方案

> 依据：`%APPDATA%\yan-zhi\server-data\data.db`（142MB）+ `server.log` 实测记录，
> 并逐条下沉到源码核验落点。本文只出方案，不动代码。
> 行号基于当前工作区（`dev0.1-mobile`，HEAD `d678fb4`）。

---

## 〇、先校正一个关键判断：① 的真身不是「被掐断报错」，而是「断流被当成正常结束」

原诊断写成「流式中途被掐断，content 丢了、reasoning 存下了」。下沉源码后需要**收紧结论** ——
真正致命的一步不是"断"，而是**断之后代码认为这轮完成了**。

证据链（`packages/core/src/llm/stream.ts` + `apps/server/src/llm-task-manager.ts`）：

1. `stream.ts:13-14` —— `const { done, value } = await reader.read(); if (done) break;`
   **上游/代理用 TCP FIN 半途关闭 SSE 连接时，`reader.read()` 是「正常 resolve `{done:true}`」，不是抛错。**
   只有 RST / 超时才会抛。而代理（FlClash 7890）下 FIN 是常见形态。
2. `llm-task-manager.ts:2013` —— 循环内 `let streamFinish: string | undefined;`，
   从 `chunk.finishReason` 累积。**但循环结束后从未校验它是否为终态**（`stop` / `tool_calls` / `length`）。
3. 于是「半截流 + 无 finish_reason」被当作**正常完成**，继续执行到
   `updateMessageContent(assistantMsgId, fullContent, fullReasoning, …)`：
   **`fullContent` 为空（还没吐正文）、`fullReasoning` 有 7022 字（思考吐到一半）→ 原样落库**。
4. 因为 `toolCallAcc.length === 0`，直接走「无工具调用 → 完成」分支：`emit task:completed`。

**这正好解释了库内那 12 条记录的形状**：`content` 空 + 无 `tool_calls` + `reasoning` 超长且结尾断在半句
（`msg_mv0pnut85n24lj`：reasoning 7022 字，停在 "…I have the full source above"）。
界面表现就是「转半天 → 突然结束 → 什么都没说」，即用户口中的"卡死"。

> 附带确认：真出错（429/网络抛错）时走外层 catch（`llm-task-manager.ts:2550` 起），
> 会把 content 覆盖成 `（调用失败：…）`。既然库里那 12 条 content 是**空**而非错误文案，
> 就反证了它们**走的是正常完成路径** —— 与上面的结论一致。

## 一、P0 —— 流式断流被误判为完成（问题 ①，最高优先级）

### 落点
- `packages/core/src/llm/stream.ts`（SSE 解析，全会话唯一入口）
- `apps/server/src/llm-task-manager.ts:1990-2210`（消费循环）
- `apps/server/src/llm-task-manager.ts:2550-2562`（外层 catch）

### 方案（三步，可分批落地）

**S1｜判定「非终态结束」（最小改动，先止血）**
- `parseSSE` 增加**结束语义**输出：维护 `sawTerminal`（见到 `finish_reason ∈ {stop, tool_calls, length, content_filter}` 或 `data: [DONE]` 置真）。
  流结束时若 `!sawTerminal`，抛一个**专用错误**（`new Error('STREAM_TRUNCATED')`，可加 `name='StreamTruncatedError'`）。
- 消费循环侧：`streamFinish` 为空且 `fullContent === '' && fullReasoning !== ''` 时**不得进完成分支**。
- **理由**：`[DONE]` 与 `finish_reason` 二者有一即视为正常收尾；两者都无 = 上游没说完就断了。

**S2｜断流自动续写（真正的修复，不让用户白等）**
- 判定截断后**不抛给用户**，就地续写：把已产出的 `fullContent`/`fullReasoning` 作为
  assistant 前缀（prefill）重新发起一次 `chatStream`，追加到 `fullContent` 尾部。
- 续写上限（2 次）+ 每次必须判定「是否拿到终态」，仍失败才降级为可见错误。
- **注意两个坑**：
  - prefill 不能带 `tools`（部分 OpenAI 兼容端点对「assistant 前缀 + tools」会 400）—— 与既有
    `llm-task-manager.ts:2048` 的「重试不带 tools」保持一致口径。
  - token 预算要按**累计**算（`task.totalTokens` 已累计，勿重复计）。
- **判据**：`STREAM_TRUNCATED` 才续写；`isAbortError` 一律不续写（`llm-task-manager.ts:1187` 已有 `isAbortError`，直接复用，勿另写一份）。

**S3｜不可静默（兜底可见性）**
- 若 S2 用尽仍失败：`updateMessageContent` 写入 `（本轮输出被上游提前中断，已保留部分内容，可重试）`
  并带上已存正文/reasoning，**绝不留下"空 content 的 assistant 消息"**。
- 收尾处加一条不变量断言式日志：`assistant 消息 content 空 && 无 tool_calls && finish 非 length`
  → `logger.warn('[llm-task] 疑似断流留白 msg=…')`，便于后续回归监测。
- **前端**：`chat_stream_end` / `task:completed` 若本轮无任何正文且无工具结果，显示一行「本轮未产出内容」，
  而不是让气泡留空（对应"看着像卡死"的体感）。

### 验收
- 构造 mock：SSE 只吐 3 个 reasoning chunk 后**直接 `controller.close()`**（不发 `[DONE]`、无 `finish_reason`）
  → 断言：任务**不**进 `completed`；触发续写；最终要么拿到终态，要么落可见错误文案。
- 回归：正常 `[DONE]` 收尾的流**不得**触发续写（防止把正常的任务做两次）。

## 二、P1 —— 同秒 11 条重复 user 消息（问题 ②，前端重复提交）

### 落点
- `packages/ui/src/composables/chat/useChat.ts:2310`（`send()`，**无 in-flight 去重**）
- `packages/ui/src/components/chat/ChatInputArea.vue:1551-1564`（`onEnter` → `send()`）
- `apps/server/src/llm-task-manager.ts:753`（`subscribe` 按 `since` 重放事件）
- `apps/server/src/llm-task-manager.ts:777-790`（断连 15s 宽限）

### 根因（三个可叠加，实测"同秒 11 条"更像前两个）
1. **`send()` 无重入锁**：`input.value` 在多个 `await`（建空间/建会话/落附件）**之后**才清空，
   期间输入框仍有内容；键盘连发 / Enter 连按 → 并发进入多次。
2. **`store.sendMessage` 无客户端去重**：并发多次即落库多条。
3. **SSE 重连**：`subscribe(since)` 会重放 `since` 之后的事件；若前端实例化后未用"序号游标"
   严格去重，`message:added` 会被重复应用（不会直接落库，但会放大前端状态、诱导重发）。

### 方案
- **前端（主修）**：`send()` 入口加 `sending` 重入锁（`if (sending.value) return; sending.value = true; … finally { sending.value = false; }`），
  并把 `input.value` 的**清空提前到"取走内容"那一刻**（`const content = input.value; input.value=''` 已在 2564 行附近，
  需前移到函数早期，防 await 期间被二次读取）。
- **提交幂等键（服务端兜底）**：`sendMessage` 带 `clientMsgId`（uuid），服务端对
  `(conversation_id, clientMsgId)` 做**唯一约束 / 存在即跳过**。这样即使前端漏挡（重连重放、多标签）也不会双写。
  - 库表：`message` 增列 `client_msg_id` + 唯一索引（走既有 `ALTER TABLE … ADD COLUMN` 兜底风格，见 `db.ts:643`）。
- **SSE 事件去重**：前端按 `event.seq` 单调递增过滤（`emit` 已给每条事件打 `seq`，见 `llm-task-manager.ts:296`），
  收到 `seq ≤ 已处理最大 seq` 直接丢弃 —— 一次性根治重连重放类重复。
- **不新增用户侧提示/按钮**（遵循项目既有约束），全部是内部加固。

### 验收
- 单测：连续调用 `send()` 两次（不 await 第一次）→ 只发一次。
- 单测：同一 `clientMsgId` 提交两次 → service 层只落一条。
- 手工：任务运行中狂按 Enter → 不产生重复 user 消息。

## 三、P1 —— 长任务上下文顶到窗口（问题 ③，与 ① 互相放大）

### 现状（实测）
- `d3719f88` 单条 assistant `tokens=38461`；`system_prompt_snapshot` **93335 字符**；会话累计 **406 万** tokens。
- 上下文越大 → 单次请求越久 → **越容易在流式期间被上游掐断**（正是 ① 的放大器）。

### 方案（与既有 `shared/context-policy.ts` 同源，不另起一套）
- **系统提示快照瘦身**：93335 字符里工具清单/长说明占大头。改为
  「工具**名称+一行说明**常驻 + 详细 schema 按需注入」，或对未被使用的工具做**惰性展开**。
  只改注入口径，不改工具面。
- **条数闸门**（项目已知结论：token 之外还要有**条数**闸门）：`loadMessages` 回放时对
  assistant 大块 reasoning 做**折叠**（reasoning 只保留摘要行、原文仍落库可查）—— 与
  `CONTEXT-NOTES` 里"压缩只追加摘要行不动原文"的既定手法一致。
- **压缩必须 SSE 可见**（`context:compacted`），让用户知道发生了什么，而不是"忽然变笨"。
- 复用既有 `checkTaskBudgetHit` / `taskBudgetHit`，不要新增平行预算判定。

### 验收
- 长会话（≥300 条消息）实测：单次请求 prompt tokens 明显下降；`context:compacted` 事件可见；
  且**不丢**任何已落库原文。

## 四、P1 —— 前端工具 2 分钟超时（问题 ④，与 ① 性质不同的"假卡死"）

### 落点
- `apps/server/src/llm-task-manager.ts:154`（`FRONTEND_TOOL_TIMEOUT_MS = 2*60*1000`）
- `apps/server/src/llm-task-manager.ts:3507`（超时 reject，任务"以此错误继续"）
- `apps/server/src/llm-task-manager.ts:3734-3790`（`executeToolViaFrontend`）

### 根因
`browser_navigate / browser_click / browser_screenshot / browser_get_page_content / browser_run_script`
被**统一套用 2 分钟硬超时**。这些工具耗时**天然分化**：
- `browser_get_page_content` / `run_script`：通常秒级；
- `browser_navigate`：慢站 + 代理（FlClash 7890）+ 等 `domcontentloaded` → **常超 2 分钟**；
- `browser_screenshot`：大页面截全图可能超。
超时后 `reject` → 任务按错误继续，但**浏览器动作其实还在跑**，界面因此停住不动 —— 与真卡死难以区分。
同会话 `browser-op-queue`（前端串行化，见记忆 `browser-op-queue.ts`）+ `withBrowserLock`（服务端只锁 7 个写路由）
会让"等待排队"的时间也计入 2 分钟。

### 方案
- **按工具分档超时**，不再一刀切 2 分钟：
  - 只读、轻量（`get_page_content` / `run_script` / `screenshot`）：保留较短（如 60s）；
  - 导航/交互（`navigate` / `click` / `type`）：放宽（如 5 分钟）或**改为心跳续期**。
- **心跳续期机制（推荐）**：前端在工具执行期间周期性回发 `tool:heartbeat{callId}`，
  服务端收到即**重置该 pending 的 timer**；只有**真正静默**（如 60s 无心跳）才判超时。
  这样"慢但活着"不再被误杀，只有"真的没人在响应"才超时。
- **超时要可见**：目前超时后界面只是"停住"。超时应 `emit` 一条明确状态（如
  `tool:timeout{callId, toolName}`），前端把该工具条标记为"超时未回执"，并在**浏览器面板**给出"重试/放弃"语义
  （属既有面板能力，不新增用户侧提示文案）。
- **与既有串行化协同**：`chainBrowserOp` 排队等待期**不计入**工具超时（排队 ≠ 执行）；建议排队期也走心跳。

### 验收
- 单测：模拟前端 90s 才回执 `navigate` → **不超时**（心跳可续期）；模拟前端彻底静默 90s → 超时且事件可见。
- 手工：开一个慢站（经代理），确认 `browser_navigate` 不被 2 分钟误杀。

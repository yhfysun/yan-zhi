# 店铺运营模式重构方案（人工 / AI 工作台 · 演示/测试/生产 · 有货源/无货源）

> 2026-10-22 ｜ 状态：**待评审，未开工** ｜ 范围：`/shop` 控制台 + `shop-ops` 插件 + 店铺业务数据底座 + 平台适配层
> 前置方案：`docs/店铺运营模式方案-20261016.md`（模式骨架已落地）。本方案解决它落地后暴露的问题：**人工管理台和 AI 运营都不可用**。

---

## 0. 结论先行

现有实现只做到了「连接登记 + 写死的演示快照 + 给模型看的变更单」，三件事都缺：

1. **没有商品 / 订单 / 发货 / 库存的业务数据**，所以人工管理无对象可管；
2. **写工具放行后什么都不落库**，只回一句「用 pageAgent 去后台操作」，所以 AI 运营不可验证、不可追溯；
3. **没有平台适配层**，前端与工具都直接面对「浏览器自动化」这一种执行方式，无法表达「有 API 走 API / 没 API 跳后台 / 演示走本地库」。

重构方向一句话：

> **本地业务底座（商品 / 订单 / 仓储 / 发货，SQLite 为真源）＋ 平台同步适配器（API / 浏览器 / 跳后台）＋ 店铺类型（演示/测试/生产）＋ 货源模式（有货源/无货源）＋ 工作台切换（人工/AI）。前端永远只调我们后端，由后端按店铺类型和平台解析适配器，决定数据从哪来、动作往哪去。**

**三个概念必须分清（本方案的基准）：**

| 概念 | 层级 | 取值 | 作用 |
|---|---|---|---|
| **店铺类型** `shopType` | 店铺属性 | `demo` 演示 / `test` 测试 / `production` 生产 | 决定数据真假、写操作风险等级、是否需要额外批准 |
| **货源模式** `supplyMode` | 店铺属性 | `stocked` 有货源 / `dropship` 无货源 | 决定是否持库存、发货方式、采购流程 |
| **工作台模式** `workbenchMode` | 工作台（全局）切换 | `human` 人工 / `ai` AI | 决定谁主导操作：人在表格里直接干，还是 AI 在对话里干 |

## 2. 目标模型

### 2.1 店铺属性（每条连接）

| 字段 | 取值 | 语义 |
|---|---|---|
| `shopType` | `demo` / `test` / `production` | **演示**：全部业务数据是本地合成种子，绝不触达真实平台；**测试**：真实平台账号，但用于试跑，写操作正常确认；**生产**：真实经营，写操作需额外批准、禁止批量 |
| `supplyMode` | `stocked` / `dropship` | **有货源**：自持库存、入库出库、仓库发货；**无货源**：不持库存，商品挂 `sourceRef`（1688 等），出单后「去采购 → 供应商直发」 |

其余派生属性（用户不可直接改）：

| 派生 | 判定 | 含义 |
|---|---|---|
| `accessMode` | 演示 → `local`；测试/生产按平台能力 → `api` / `browser` / `jump` | 平台侧动作怎么落地 |
| `requiresApproval` | `shopType === 'production'` | 写操作是否需要额外批准 |
| `allowBatch` | `shopType !== 'production'` | 是否允许批量操作 |

### 2.2 工作台模式（全局切换，不是店铺属性）

`workbenchMode: 'human' | 'ai'` 是 `/shop` 工作台顶部的一个切换，切的是**同一个工作台的两种形态**：

| 模式 | 界面形态 | 谁执行写操作 | AI 角色 |
|---|---|---|---|
| `human` 人工 | 表格/表单居中，对话靠边（现有 `lead='human'` 形态） | 人在商品/订单/发货页直接操作 | 顾问：可查询、给建议，不自动改数据 |
| `ai` AI | 对话居中，工作台作为 AI 的操作结果视图（现有 `lead='ai'` 形态） | AI 通过工具执行，仍走变更单确认 | 执行者：改完的数据实时反映在表格里 |

> 工作台模式**不改变数据、不改变店铺类型、不影响权限**；它只决定「谁来点按钮」。任何模式下，写操作都必须经过同一套闸门与审计。

### 2.3 组合语义

| 店铺类型 | 有货源 | 无货源 |
|---|---|---|
| 演示 | 本地商品/库存/订单/发货全可操作；平台侧动作仅展示跳转计划，不真正触达 | 商品带货源链接、库存列显示「不持库存」；出单后「标记已采购/供应商直发」；比价走真实网站 |
| 测试 | 本地底座 + 平台侧 API/浏览器/跳后台；写操作正常确认 | 同左，采购流程跳 1688，付款由用户完成 |
| 生产 | 本地底座 + 平台同步；写操作额外批准，禁止批量 | 同左，且采购/铺货变更单强制列合规结论 |

**铁律**：前端只调我们后端 `/plugin/shop-ops/*`；后端 `resolveAdapter(shop)` 后才决定读本地库、调平台 API、还是返回跳转计划。前端不直连任何平台。

## 3. 数据模型

### 3.1 扩展连接对象（`StoredConnection`，仍存 `plugin_storage.connections`）

只加字段，不改既有字段语义，老库读取时补默认值：

```ts
shopType?: 'demo' | 'test' | 'production'; // 默认 test；旧 demo:true → demo；旧 tag='生产' → production
supplyMode?: 'stocked' | 'dropship';        // 默认 stocked
platformShopId?: string;                    // 平台侧店铺 ID（API 同步用）
```

迁移规则（`activate()` 里幂等执行）：

- `demo === true` → `shopType = 'demo'`
- 否则 `tag === '生产'` → `shopType = 'production'`，其余 → `shopType = 'test'`
- `supplyMode` 缺省补 `'stocked'`
- 旧 `tag` 字段保留（写操作闸门仍读它做生产判定），新逻辑统一读 `shopType`

### 3.2 新增业务表（SQLite，真源）

DDL 同时加到 `packages/core/src/db/schema.ts` 与 `apps/server/src/db.ts` 的建表段（沿用现有 `CREATE TABLE IF NOT EXISTS` 风格）：

```sql
CREATE TABLE IF NOT EXISTS shop_product (
  id             TEXT PRIMARY KEY,
  shop_id        TEXT NOT NULL,              -- 对应 connection.id
  sku            TEXT NOT NULL,
  title          TEXT NOT NULL,
  image_url      TEXT,
  category       TEXT,
  supply_mode    TEXT NOT NULL DEFAULT 'stocked',
  source_ref     TEXT,                       -- 无货源：1688 链接/供应商货号
  cost_cents     INTEGER NOT NULL DEFAULT 0,
  price_cents    INTEGER NOT NULL DEFAULT 0,
  currency       TEXT NOT NULL DEFAULT 'CNY',
  stock          INTEGER NOT NULL DEFAULT 0, -- 无货源固定 0，不参与口径
  safety_stock   INTEGER NOT NULL DEFAULT 0,
  listing_status TEXT NOT NULL DEFAULT 'draft', -- draft|online|offline
  attrs_json     TEXT DEFAULT '{}',
  created_at     INTEGER NOT NULL,
  updated_at     INTEGER NOT NULL,
  UNIQUE(shop_id, sku)
);

CREATE TABLE IF NOT EXISTS shop_order (
  id          TEXT PRIMARY KEY,
  shop_id     TEXT NOT NULL,
  order_no    TEXT NOT NULL,
  buyer       TEXT,
  amount_cents INTEGER NOT NULL DEFAULT 0,
  currency    TEXT NOT NULL DEFAULT 'CNY',
  status      TEXT NOT NULL DEFAULT 'pending', -- pending|paid|sourcing|shipped|completed|refunded
  items_json  TEXT NOT NULL DEFAULT '[]',
  address_json TEXT DEFAULT '{}',
  created_at  INTEGER NOT NULL,
  paid_at     INTEGER,
  UNIQUE(shop_id, order_no)
);

CREATE TABLE IF NOT EXISTS shop_shipment (
  id           TEXT PRIMARY KEY,
  shop_id      TEXT NOT NULL,
  order_id     TEXT NOT NULL,
  carrier      TEXT,                          -- 对应 SHOP_PLATFORMS 的物流 id
  tracking_no  TEXT,
  status       TEXT NOT NULL DEFAULT 'pending', -- pending|shipped|in_transit|delivered|exception
  shipped_at   INTEGER,
  delivered_at INTEGER,
  note         TEXT,
  created_at   INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS shop_stock_move (
  id          TEXT PRIMARY KEY,
  shop_id     TEXT NOT NULL,
  product_id  TEXT NOT NULL,
  kind        TEXT NOT NULL,                  -- in|out|adjust|reserve
  qty         INTEGER NOT NULL,
  before_qty  INTEGER NOT NULL,
  after_qty   INTEGER NOT NULL,
  reason      TEXT,
  actor       TEXT NOT NULL DEFAULT 'human',  -- human|ai
  created_at  INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_shop_product_shop ON shop_product(shop_id, listing_status);
CREATE INDEX IF NOT EXISTS idx_shop_order_shop   ON shop_order(shop_id, status, created_at);
CREATE INDEX IF NOT EXISTS idx_shop_ship_shop    ON shop_shipment(shop_id, status);
CREATE INDEX IF NOT EXISTS idx_shop_stock_shop   ON shop_stock_move(shop_id, product_id, created_at);
```

**为什么换成 SQL 表**：商品/订单/发货/库存需要过滤、排序、分页、聚合（看板 KPI、低库存预警）；继续放 `plugin_storage` JSON 会每次全量读写，且无法做索引。连接对象保持 JSON（读写频率低、字段异构），两者以 `shop_id` 关联。

## 4. 后端分层

新增目录 `apps/server/src/shop/`，把业务从 1600 行的 `plugins/shop-ops.ts` 里拆出来（插件只保留 manifest + 路由挂载 + 工具注册）：

```
apps/server/src/shop/
  types.ts            领域类型（Shop, Product, Order, Shipment, StockMove, JumpPlan）
  store.ts            SQL 读写（products/orders/shipments/stock + dashboard 聚合）
  adapter.ts          适配器契约 + resolveAdapter()
  adapters/
    demo.ts           shopType=demo：全部读写本地库，平台动作只返回跳转计划
    local.ts          本地底座（有货源库存/发货），平台侧动作交给 sync
    amazon-sp.ts      包装 services/amazon-sp-api.ts（P1 扩展 products/orders）
    jump.ts           返回 JumpPlan（URL + 步骤 + 是否可由 pageAgent 代跑）
  actions.ts          runShopAction：闸门通过后按适配器执行 + 审计 + 回写
  seed.ts             演示数据种子（按店铺模板生成商品/订单/发货/库存）
```

### 4.1 适配器契约

```ts
export type ActionKind =
  | 'product.list' | 'product.create' | 'product.update'
  | 'product.publish' | 'product.price' | 'product.stock'
  | 'order.list' | 'order.ship' | 'shipment.track'
  | 'platform.open';

export interface JumpPlan {
  kind: 'jump';
  url: string;
  title: string;
  steps: string[];
  /** true = 可由 pageAgent 在登录态下代跑；false = 必须用户亲手操作（付款/验证码） */
  automatable: boolean;
}

export type ActionOutcome =
  | { kind: 'done'; summary: string; data?: unknown }        // 已落库/已调通
  | { kind: 'jump'; plan: JumpPlan }                         // 交给用户或 pageAgent
  | { kind: 'unsupported'; reason: string };                 // 该平台/该动作不支持

export interface ShopAdapter {
  readonly id: string;
  supports(action: ActionKind): boolean;
  run(shop: Shop, action: ActionKind, payload: Record<string, unknown>): Promise<ActionOutcome>;
}
```

`resolveAdapter(shop, action)` 判定顺序：

1. `shop.shopType === 'demo'` → `demo`（业务动作读写 SQLite，`done`；平台侧动作返回 `jump`，绝不真正执行）
2. 平台 `integration.client === 'ready'` 且有凭据 → `api`（目前仅亚马逊；其余平台 P2）
3. 动作属于**本地可完成**（`product.list/create/update/price/stock`、`order.list`、库存调整、`shipment.track`）→ `local`（写本地库，`done`）
4. 动作必须在平台侧发生（如把上下架同步到真实店铺）→ `jump`（`JumpPlan`，`automatable` 由平台风控口径决定）

> 这是本方案最关键的一步：**本地业务动作永远可用**（小店铺的商品/库存/发货管理本身就是我们应用的核心价值），平台同步是**可选的第二跳**。没有平台 API 不等于没有管理能力。

### 4.2 路由（沿用 `/plugin/shop-ops` 前缀，避免动前端与授权）

```
GET    /plugin/shop-ops/dashboard?shopId=           看板聚合（KPI、低库存、待发货）
GET    /plugin/shop-ops/products?shopId=&status=     商品列表（分页/搜索）
POST   /plugin/shop-ops/products                     新建商品
PATCH  /plugin/shop-ops/products/:id                 编辑商品
DELETE /plugin/shop-ops/products/:id                 删除（硬删 + 二次确认 + 审计）
POST   /plugin/shop-ops/products/:id/listing         上架/下架（body: online|offline）
POST   /plugin/shop-ops/products/:id/price           改价
POST   /plugin/shop-ops/products/:id/stock           改库存（写 stock_move）
POST   /plugin/shop-ops/products/batch               批量上下架/改价（生产店铺拒绝）
GET    /plugin/shop-ops/orders?shopId=&status=       订单列表
POST   /plugin/shop-ops/orders/:id/source            无货源：标记已采购
POST   /plugin/shop-ops/orders/:id/ship              创建发货（carrier/trackingNo）
GET    /plugin/shop-ops/shipments?shopId=            发货列表
POST   /plugin/shop-ops/shipments/:id/track          轨迹（复用 logistics 客户端）
GET    /plugin/shop-ops/stock/moves?shopId=          库存流水

POST   /plugin/shop-ops/shops/:id/open               返回 JumpPlan（打开平台后台）
```

写接口统一走 `runShopAction`：校验店铺类型与动作 → 执行适配器 → 写审计 → 返回结果。工作台模式通过请求头/参数携带（`actor='human'|'ai'`），只用于审计与界面回执，**不作为权限开关**。

## 5. 店铺类型语义（演示 / 测试 / 生产）

| 能力 | 演示 `demo` | 测试 `test` | 生产 `production` |
|---|---|---|---|
| 商品/订单/库存/发货 | 本地种子数据，可增删改查，立即生效 | 本地底座 + 平台同步 | 本地底座 + 平台同步 |
| 平台侧动作 | **只返回跳转计划，绝不真正触达平台** | API/浏览器/跳后台 | API/浏览器/跳后台 |
| 写操作确认 | 变更单 + 一次确认 | 变更单 + 一次确认 | 变更单 + 额外批准 |
| 批量操作 | 允许 | 允许 | **禁止** |
| 真实物流轨迹 | 只有合成运单；有真实凭据时可查真实接口，但需显式说明 | 可查 | 可查 |
| 数据标记 | 店铺、商品、订单、发货、AI 回复全部带「演示」前缀/角标 | 带「测试」角标 | 无（或「生产」红色角标） |
| 清空数据 | 只删 `shopType='demo'` 的店铺及其业务行 | 不允许一键清空 | 不允许一键清空 |
| 比价 / 选品 | **仍走真实网站** | 真实网站 | 真实网站 |

演示种子（`shop/seed.ts`）：沿用现有 `DEMO_PROJECTS` 的店铺模板，为每家演示店铺生成：

- 6–12 个商品（含成本/售价/库存/货源链接；无货源店库存为 0、带 `source_ref`）
- 8–20 条订单（不同状态：待付款/已付款/待发货/已发货/已完成）
- 对应发货单与运单号（合成）
- 近 14 天库存流水（用于看板与预警）

种子必须幂等：重复执行按 `shop_id` 覆盖更新，不重复插入。

**测试店铺**不自动种子，空库即空；用户自己建商品，或从演示店铺「复制为测试店铺」时复制种子。

顶部工具条：

- **店铺类型**（演示/测试/生产）：下拉切换，`PATCH /shops/:id`，写审计。演示→测试/生产需要确认（数据不迁移，只改类型与数据源）。
- **货源模式**（有货源/无货源）：分段切换，影响商品表单字段、看板口径、订单动作。切换只改口径，不删除已有库存数据（保留字段，界面隐藏）。
- **工作台模式**（人工/AI）：全局分段切换，复用现有 `lead` 形态：
  - `human`：表格/表单居中，对话靠边；写按钮直接调用后端。
  - `ai`：对话居中，工作台作为结果视图；写按钮改为「交给 AI 执行」，把动作与参数发到当前店铺会话。
  - 切模式不改变当前页签、不丢筛选与选中项（状态放 `shopSession.ts`）。

**商品表列**：图片、SKU、标题、货源（自营/1688 链接）、成本、售价、毛利、库存（无货源显示「不持库存」）、状态、更新时间。操作列：上架/下架、改价、改库存、编辑。

**订单页**：订单号、买家、金额、状态、下单时间、操作（无货源：标记已采购；有货源：发货）。

**发货页**：运单号、物流商、状态、轨迹（点开时间线，复用 `shop_track_query` 的渲染）。

## 7. 人工工作台 vs AI 工作台

| | 人工（human） | AI（ai） |
|---|---|---|
| 布局 | 工作台居中、对话靠边 | 对话居中、工作台为结果视图 |
| 商品管理 | 表格内新建/编辑/上下架/改价/改库存 | 对话下指令 → 变更单 → 确认 → 工具执行 → 表格刷新 |
| 订单发货 | 选订单 → 选物流商 → 填运单号 → 发货 | 对话下指令 → 同上链路 |
| 无货源采购 | 点「去 1688 采购」→ 打开后台 | AI 生成采购变更单 → 确认 → 跳转/代跑 |
| 数据和权限 | 完全一致 | 完全一致（仅执行者不同） |
| 审计 | `actor='human'` | `actor='ai'` |

- 两种模式共用同一套后端路由、同一份数据、同一套闸门；**不存在「AI 模式下 AI 才能改」的权限限制**，只是入口不同。
- AI 模式下若用户仍想手改，切回人工即可；人工模式下也可以随时问 AI（只读）。
- 工作台模式持久化在本地（`shopSession` / localStorage），重启保持。

## 8. 平台接入与「跳后台」

| 平台 | 现在能做 | 本方案 P0/P1 | 无 API 时 |
|---|---|---|---|
| 演示店铺 | 本地种子 | 全量本地闭环 | — |
| 亚马逊 | SP-API 凭据自检、GET | P1 用 SP-API 同步库存/订单（若账号权限允许） | 跳卖家中心，pageAgent 可代跑非资金动作 |
| 淘宝/天猫 | 无 | 本地管理 + 跳千牛后台 | `JumpPlan(url=myseller.taobao.com)`，风控强，优先用户操作 |
| 拼多多 | 无 | 同上 | 跳商家后台，短信验证码由用户完成 |
| 1688 | 无 | 无货源货源比价（真实网站），采购跳后台 | 跳 1688，**付款必须用户完成** |
| TikTok / Shopify | 无 | 本地管理 + 跳后台 | 同左 |
| 物流（顺丰/云途） | 轨迹查询已实现 | 发货单关联运单号 + 轨迹 | 未接的服务商只登记 |

**跳转协议**：后端 `POST /shops/:id/open` 返回：

```json
{ "kind": "jump", "url": "https://myseller.taobao.com/", "title": "淘宝卖家中心",
  "steps": ["确认已登录卖家账号", "进入商品管理", "..."], "automatable": true }
```

**内嵌打开（默认方式，2026-10-22 用户拍板）**：平台后台不弹外部浏览器，而是**内嵌在控制台页签里**——新增 `tabs/ShopPlatformView.vue`，内部复用 `<BrowserPanel scope="shop" />`（`packages/ui/src/components/BrowserPanel.vue:542` 支持 `scope` 参数，独立标签页与 store 隔离，不与主浏览器互相干扰）。JumpPlan 返回后直接切到该页签并导航到 `url`，登录态复用 `browser_login_saved`；面板顶部显示当前跳转任务的步骤条与「已处理」按钮（写审计）。也可一键切到独立浏览器面板（`/browser`）全屏操作。AI 的 pageAgent 代跑同样复用这套内嵌页面，不另开执行面。

**不做**：不存平台账号密码（凭据只存 API key/secret 密文）、不绕验证码、不代付款、不代签收。

## 9. 安全与数据一致性

1. 写操作闸门保留：变更单 → `confirmed` → 生产店铺 `approveProduction`；执行结果必须审计。
2. 生产店铺禁止批量操作；演示店铺的平台侧动作只返回跳转计划。
3. 所有涉及金额的字段用**整数分**（`*_cents`），避免浮点误差；展示层格式化。
4. 商品删除：P0 硬删 + 二次确认 + 审计；订单/发货不允许删除，只允许状态流转。
5. `shop_id` 必须存在于 connections，否则拒绝；跨店操作一律拒绝。
6. 连接对象中的 `secretEnc` 永不出库视图；业务表不含任何密钥。
7. 并发：better-sqlite3 同步事务；库存变更用 `UPDATE ... WHERE stock >= ?` + 事务内读旧值写流水，防超卖。
8. 演示数据不参与任何平台同步；测试/生产数据不允许「一键清空」。

## 12. 验收方式

1. `pnpm typecheck` 全绿；`pnpm --filter @yan-zhi/server test`、`--filter @yan-zhi/ui test` 全绿（新增 store 逻辑补单测：库存并发、状态流转、适配器路由、演示店铺不触达平台）。
2. 桌面端启动 → 店铺模式 → 创建演示项目 → 打开演示店铺：
   - 商品页有 6+ 商品；新建商品后列表出现；
   - 上架/下架、改价、改库存后，概览 KPI 与库存流水同步变化；
   - 订单页有不同状态订单；发货后发货页出现运单，轨迹可查（有凭据时真实接口，无凭据时明确提示）；
   - 切「无货源」后库存列消失、商品出现货源链接、订单出现「去采购」；
   - 切「AI 工作台」后在对话里说「把 SKU-001 价格改成 27.99」→ 出变更单 → 确认 → 数据库与界面更新；切回「人工工作台」同一动作在表格里直接完成。
3. 比价：在演示店铺发起「对比这个商品在淘宝/1688 的价格」→ 仍走真实浏览器，返回真实链接/价格（或如实报告抓取失败），不读演示库。
4. 演示店铺点「上架到平台」→ 只返回跳转计划，不触达任何真实平台；测试/生产店铺同理走适配器。
5. 「打开平台后台」：测试/生产店铺点按钮 → 浏览器面板打开对应卖家中心 URL；未登录时提示用户登录。
6. 审计：每笔人工/AI 写操作在操作日志有记录，含 actor、店铺类型与前后值。

## 13. 风险与边界

| 风险 | 级别 | 处理 |
|---|---|---|
| 业务表与连接 JSON 双存，可能出现孤儿数据 | medium | 所有查询以连接存在为前提；清空演示/删除店铺时级联删业务行；启动时清理孤儿（可选） |
| 真实平台同步误伤 | high | P1 前平台侧动作一律 `jump`；P2 接 API 时逐平台灰度，写操作仍走闸门；生产店铺禁批量 |
| 演示数据被误当成真实经营数据 | medium | 全链路「演示」角标 + AI 回复前缀 + 种子名称固定前缀；`shopType='demo'` 与平台动作硬隔离 |
| 店铺类型切换导致数据语义混淆 | medium | 演示→测试/生产只改类型不迁移数据，并显式提示；测试/生产不允许清空 |
| 无货源合规（侵权/授权） | high | 沿用 `skill_1688_sourcing` 的前置检查；采购/铺货变更单强制列合规结论 |
| 页面拆分导致状态丢失 | medium | 沿用 `shopSession.ts` 模块级状态（切页不销毁），与 `opsSession` 同模式 |
| 改动横跨 1600 行插件文件 | medium | 先抽 `shop/` 模块，再改插件挂载；每步保持 typecheck 绿 |

## 14. 边界确认（按本次口径）

- 店铺类型只有三档：**演示 / 测试 / 生产**。
- 模式只有两档：**有货源 / 无货源**。
- 人工 / AI 是**工作台切换**，不是店铺属性，不改变数据与权限，只改变「谁操作」与界面布局。
- 平台没有管理 API 时，后端返回跳转计划，界面打开平台后台，由用户自己登录操作；AI 可在允许的范围内代跑非资金动作。

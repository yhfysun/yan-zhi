# 桌面整理 v2 · 重做方案

> 2026-10-30 · 状态：待拍板
> 可交互原型：[desktop-organizer-v2-proto.html](./prototypes/desktop-organizer-v2-proto.html)（单文件，双击即开；底部可切「现状 / 新方案」对照）

---

## 0. 一句话结论

现在的实现**不是界面不好看，是承载方式选错了**：一个分组一个 Electron 窗口、每 1.5 秒轮询整块重绘、拖动靠 JS 每帧 `setBounds`、每次点击要 spawn 一个进程抬层。
功能缺失（不能跨分组拖、不能框选、不能搜索、不能卷起、没有文件夹传送门）也大多是被这套结构卡住的，不是没写。

**建议整体重写为「单个桌面层窗口 + 主进程命中测试」**，并沿用已经验证过的规则引擎、撤销、图标助手。

三条可以直接抄的技术结论：

1. **没有任何一家轮询文件系统。** 用 `ReadDirectoryChangesW` / shell 通知，空闲就是真空闲。
2. **拖拽是 OS 级拖放**，不是自己算坐标。这样跨分组、拖出到资源管理器、拖进 Word 全都免费拿到。
3. **同一个进程统管所有 fence**——跨分组动画、对齐参考线、框选、拖拽捕获才能成立。

## 3. 三个候选架构

### 方案 A：保留「一窗一分组」，把数据/渲染/交互三层重写

**好处**
- 改动面最小，`desktop-windows.js` 的窗口规划可以留；
- 空白桌面天然归系统管，命中边界不会错，不存在「窗口吃掉点击」的坑；
- 多显示器 / DPI / 分辨率变更最好处理，窗口本来就是独立矩形；
- 崩溃隔离：一个分组窗口挂了不影响其他。

**坏处**
- 内存降不下来：6 分组 + 3 组件 = **9 个 renderer ≈ 400MB 常驻**，这是结构性的；
- 跨分组拖拽只能靠 `webContents.startDrag`（OS 原生拖放）绕，虽然能用，但**插入位置动画、拖动中的对齐参考线做不了**（源窗口被 startDrag 阻塞到 drop 结束）；
- Peek 要把 N 个窗口同时抬到最前，每个都是一次 `--pin`，卡；
- 框选只能在一个分组内，跨分组的框选永远做不了；
- 窗口层叠顺序靠重复 `--pin` 维持，Win11 上 WorkerW 层不稳定时行为会飘。

### 方案 B：单个「桌面层」窗口 + 主进程命中测试（推荐）

一个和屏幕等大的桌面层窗口，所有分组、组件、搜索、命令面板都在**同一个 DOM** 里。空白区域由主进程把 `setIgnoreMouseEvents(true)` 打开，光标进入某个分组矩形时再关掉——点击就穿透到真正的桌面。

**好处**
- **一个 renderer**：内存从 ~400MB 降到 ~120MB；图标缓存、缩略图、字体、GPU 纹理都只一份；
- 跨分组拖拽 = 同一 DOM 内拖拽，可以做**幽灵 + 插入占位 + 目标高亮 + 磁吸参考线 + 边缘停顿自动滚动**，这些是手感的核心；
- 跨分组框选、全桌面搜索、Peek、分页全部变成小功能而不是架构难题；
- 分组之间不打架：不再有独立窗口的抬层问题，不需要每次点击 spawn 进程；
- 只有一个窗口要管，`syncChildren` 的整套 diff/开窗关窗逻辑直接删掉。

**坏处 / 风险**
- 命中测试要自己写：主进程 8~16ms 用 `screen.getCursorScreenPoint()` 算点是否落在分组矩形内（Electron 自带，不需要全局钩子），然后切 `setIgnoreMouseEvents`。**极端情况下光标刚跨过边界就点击可能丢一次**（人类反应 >80ms，实际基本不可能）；
- 拖动窗口/滚动时命中区域要冻结，否则会打断鼠标捕获；
- 全屏透明窗口的合成开销要实测（分层窗口全屏 per-pixel alpha）；
- 钉在 Progman 子层的窗口上 `setIgnoreMouseEvents` 是否真生效 **必须 spike 验证**（这正是上一轮踩过的坑：子窗口收不到转发的 mousemove；但这次不依赖转发，靠主进程主动算）。
  → **已部分排除**：上一轮实测「主进程 `screen.getCursorScreenPoint()` + 页面上报热区 + 切 `WS_EX_TRANSPARENT`」在 pinned 子窗口上是可行的。剩下要验的只是热区表的精度与拖动中的冻结策略。

### 方案 C：原生渲染（Rust/C#/Direct2D）+ Electron 只做设置页

**好处**
- 性能天花板：ZenDesktop 是 3MB 二进制、4MB 内存、0% CPU；
- 真实 Windows 右键菜单、OLE 拖放、缩略图全部原生，没有一处妥协；
- 不受 Electron 透明窗口、子窗口、DPI 那些坑影响。

**坏处**
- 等于新起一个项目：C++/Rust + Direct2D 渲染引擎、文本排版、输入法、滚动、无障碍，全要自己写；
- 与现有 Electron 生态割裂：插件系统、设置页、AI 编排都要跨进程重做一遍；
- 工期以「人月」计，不是这个插件该有的体量；
- 我们已有的 C# 助手只适合做辅助，不适合承载整个 UI。

## 4. 结论与降级路径

**推荐方案 B。** 理由排序：内存 1/4、手感上限最高、功能缺失基本被结构性问题一次性解决。

但 B 有两个必须先用半天验证的点，所以：

```
P0 spike（半天）
 ├─ ① 全屏 pinned 窗口的命中测试精度（★ 前置条件已验证：上一轮实测可切 WS_EX_TRANSPARENT；
 │     这轮只需验「热区表 + 16ms 轮询」的实际手感与边界误差）
 ├─ ② 全屏透明分层窗口的合成开销（拖动分组时帧率）
 └─ ③ Win32 助手常驻化后 --pin/--drag 的延迟
       ├─ 三项全过 → 走 B（主线）
       └─ ① 或 ② 不过 → 走 A（UI 层、数据层一字不改，只换承载方式）
```

**A 和 B 共享 P1（数据层）、P2（渲染层）、P4（功能）的 90% 工作量**，所以先做 spike 不会浪费。

## 5. 新的信息架构与交互设计

### 5.1 三套窗口合成一套

| 现在 | 之后 |
|---|---|
| `fence.html` 工具条窗口 | **删掉**。桌面右上角一个半透明入口（悬停才显现），点击出命令面板 |
| `fence.html?fence=` 分组窗口 | 桌面层内的一个卡片（方案 A 下仍是一窗，方案 B 下是 DOM 节点） |
| `widgets.html` 组件窗口 | **删掉**。组件 = 分组的一种视图：`view: grid \| portal \| todos \| clock \| memo \| metric` |
| `settings.html` | 保留，但重写（设置项从「窗口/组件」改为「分组/外观/规则/快捷键」） |
| 工具条放大窗口显示菜单 | **删掉**。所有弹层都在桌面层 DOM 内，不需要改窗口尺寸 |

### 5.2 手感清单（原型里都能摸到）

- **拖拽**：幽灵跟随（微旋转+放大 6%）、源项变淡、目标分组整块高亮 + 1px 蓝描边、**目标位置显示虚线插入格**、拖到分组外松手 = 移出到桌面。
- **卷起**：双击标题栏，220ms 缓动收起到 34px 标题条；**卷起后鼠标悬停自动展开**（Fences 的招牌手感）。
- **移动分组**：原生窗口拖动（不是 JS 每帧 setBounds），靠近其他分组边缘/桌面 40px 网格时**吸附并显示蓝色参考线**。
- **调整大小**：右下角手柄，最小 220×140，按 8px 网格。
- **框选**：分组空白处拖出橡皮筋，跨分组也成立（B 方案下）。
- **键盘**：`/` 搜索、方向键移动选中、`Enter` 打开、`Delete` 进回收站、`F2` 重命名、`Ctrl+Z` 撤销（已有后端能力）。
- **搜索**：一个覆盖层搜**所有分组**，输入即筛，回车打开第一条，点结果自动展开卷起的组并滚动定位 + 高亮脉冲。
- **Peek**（`Win+Space`）：分组浮到当前应用之上，可直接把文件拖进 Photoshop / 上传框，再按一次回到桌面。
- **右键**：调用**真实 Windows shell 菜单**（`IContextMenu`），不是自绘的「打开 / 移入分组」两条。

### 5.4 「一键整理」= 内容整理 + 布局整理

> 注：第一版方案只写了「把文件归到分组」，这是不完整的——用户点「一键整理」期望的是**整张桌面变整齐**，包括分组和组件卡片的摆放。这里补齐。

一键整理出的是**一份可审阅的方案**，不是立即执行：

```
一键整理
 ├─ ① 整理文件内容     散落文件 → 按规则/AI 归入分组（已在分组里的不动）
 ├─ ② 重排分组布局     卡片高度收缩到内容所需 + 列内紧排 + 列间对齐
 ├─ ③ 统一卡片尺寸     所有列拉成同一宽度、高度取整到 88px 图标行高（板正）
 └─ ④ 收掉空分组       没有内容的分组自动卷起（不删除）
        ↓
   预览（卡片动画到目标位 + 前后缩略对比）
        ↓
   执行 ── 整批可撤销（Ctrl+Z 恢复位置、尺寸 + 归属）
```

面板是桌面层 DOM 里的一个卡片，**不需要把窗口撑大**（现行实现的 `expandForDialog` 就删在这里）。每一条可单独勾选，所以「只想理文件，别动我摆好的位置」也成立。

### 5.5 布局引擎规则

布局整理的目标不是「最优装箱」，而是**在保住用户空间记忆的前提下，把空洞挤掉**：

| # | 规则 | 理由 |
|---|---|---|
| 1 | 工作区 = 屏幕可用区扣掉任务栏，四周留 40px | 不贴边、不被任务栏压 |
| 2 | 按当前 x 聚成「列」（阈值 120px），**列内保持用户原来的上下顺序** | 用户记住的是「左边那列放应用」，重排打乱顺序比留点空隙更糟 |
| 3 | 卡片高度 = 表头 34 + 行数 × 88 + padding（`todos` 等视图按行高算） | 现在的高度是手写的，所以每张卡都有一大片空白 |
| 4 | 列内纵向间距统一 12px，紧排 | 消除随机空隙 |
| 5 | **所有列统一到同一宽度**（= 全局最宽卡片），**卡片高度取整到 88px 的图标行高**；列间距 12px | 边缘对齐、行高成整数倍，整张桌面才「板正」；高度贴合内容会参差不齐 |
| 6 | 总高超出工作区 → 溢出的列折到下一行带 | 不硬压、不缩小 |
| 7 | 系统桌面图标还可见时，整块向右让出一个图标列宽（75px） | 不压到用户原有的桌面图标 |
| 8 | 「锁定位置」只锁**手动拖动**；一键整理是显式动作（有预览、可撤销），**仍然会重排锁定的卡片** | 布局不合理就得动，否则一键整理没意义 |
| 9 | 空分组 / 空的「待归类」自动卷起，不删除 | 腾空间，且随时可展开 |

可选的排序策略（默认关闭，避免擅自改变用户习惯）：按最近使用频率把高频分组放到左上；按内容类型分组。开启前会在预览里明确显示会怎么动。

「统一卡片尺寸」默认开启（板正）；关掉则退回紧凑模式——高度贴合内容、宽度各用各的，省空间但边缘不齐。两种都能在预览里直接对比。

**验收**：5 个分组、3 列的样例桌面，占用高度 654px → 536px，5 张卡宽度统一 404px、高度为 224/224/224/224/136（88px 整数倍），无重叠、无越界、列左缘对齐，全程 420ms 动画且可取消。



### 5.6 视觉

匹配 Win11 桌面：`backdrop-filter: blur(26px) saturate(1.35)` + `rgba(26,31,43,.58)`，12px 圆角，`inset 0 0 0 1px rgba(255,255,255,.07)`；图标单元格 76×88（48px 图标 + 两行 11px 标签），与 Explorer 桌面网格同尺寸，避免「插件里的图标和桌面上的对不齐」。

### 5.7 卡片（分组 / 组件）能力矩阵

组件就是卡片的一种视图，所以下面这些能力对 `clock / todos / memo / portal` 一样成立。

| 能力 | 触发 | 行为 | 原型 |
|---|---|---|---|
| 折叠 / 展开 | 标题栏双击，或标题栏 `⌃` 按钮 | 收到 34px 标题条；**卷起后鼠标悬停自动展开** | ✅ |
| 改宽度 / 高度 | 右下角手柄拖动（最小 220×140，8px 网格） | 落库；内容不够时高度可手动保留 | ✅ |
| 移动 | 拖标题栏（原生拖动，不是 JS 每帧 setBounds） | 吸附到其他卡片边缘 / 40px 网格，显示蓝色参考线 | ✅ |
| 锁定位置 | 右键 → 锁定位置 | **手动拖不动**（光标变禁止符号，防误碰）；一键整理不受影响，仍会把它摆到合理位置 | ✅ |
| 置顶显示 | 右键 → 置顶显示 | 常驻浮在其他应用之上（相当于一直开着的 Peek） | ✅ |
| 重命名 | 右键 → 重命名，或 `F2` | 标题内联编辑，Enter 提交 / Esc 取消 | ✅ |
| 删除分组 | 右键 → 删除分组 | 二次确认；**只取消分组，文件回桌面，不删文件** | ✅ |
| 新建文件夹 / 文本文档 | 右键 → 新建…，或空白桌面右键 → 新建 | 在桌面目录真建文件，再按规则归入分组 | ✅（原型造条目） |
| 单文件操作 | 右键图标 | 打开 / 重命名 / 资源管理器定位 / 移入分组 / 移到回收站 | ✅ |

### 5.8 空白桌面：原样交给系统

| 位置 | 谁处理 |
|---|---|
| 卡片内、图标上 | 我们（上表） |
| **空白桌面右击** | **Windows 自己**：查看、排序方式、刷新、新建、显示设置、个性化，一个不少 |
| 空白桌面左键拖动 | Windows（框选桌面图标） |

实现上：方案 A 下空白桌面本来就不属于任何窗口；方案 B 下由主进程命中测试，光标在空白处时把窗口设成穿透（`WS_EX_TRANSPARENT`），点击直接落到 Progman / DefView，**系统菜单原样弹出——我们不绘制也不拦截**。

唯一交互点是「新建 › 文件夹」：文件在桌面目录创建后会被我们的规则立刻归类，看起来像「刚建出来就进了某个分组」。这个行为可以在设置里关掉（关掉后新建的东西留在桌面散落状态）。

## 6. 技术方案要点

### 6.1 零轮询

- 首帧仍用 `/state`，之后**只用推送**：主进程 `fs.watch`（目录级 + 150ms 去抖）→ 计算 diff → IPC 推给桌面层窗口（`electronAPI` 已有通道）；
- 更彻底：把 Win32 助手改成**常驻 daemon**，用它跑 `ReadDirectoryChangesW`（`fs.watch` 在 Windows 上递归不可靠，且大目录开销高）；
- 验收：打开 3 小时，空闲 CPU 增量 < 1%，无 `setInterval`。

### 6.2 渲染增量

- 渲染层持 `Map<itemId, HTMLElement>`，按 `rev` 做 keyed diff；只有增删改的项动 DOM；
- 网格滚动用 `scrollTop` 保留，不重建容器；
- 图标 `<img>` 元素复用，`src` 不变就不重新 decode。

### 6.3 图标与缩略图

- 主进程统一出图，磁盘 LRU 缓存（键：`path + mtime + size + px`），目录在 `%LOCALAPPDATA%`；
- 大图标 256px（已有 `SHGetImageList` 能力）；
- 缩略图走 `IShellItemImageFactory`（助手加 `--thumb <path> <px>`），图片/视频/Office/PDF 自动有预览；
- 文件夹图标做「前三项堆叠」合成（Nimi Places 的做法）。

### 6.4 拖拽

- 图标拖动统一走 `webContents.startDrag({file, icon})`——**这是 OS 原生拖放**，一个 API 同时解决：
  - 跨分组移动（drop 在另一个分组的 `dragover/drop` 上 → 只改 `fenceId`，不动真实文件）；
  - 拖出到桌面（drop 落在 Explorer → 文件真移动，等同于「移出分组」);
  - 拖进其他应用（Word / 上传框），这是 Fences 用户最常用的路径；
- `dragover` 里算插入位置并显示占位格（原生拖放也能拿到 `clientX/Y`）；
- 从资源管理器拖入：`webUtils.getPathForFile`（preload 已暴露）。

### 6.5 窗口拖动与抬层

- 拖动：助手加 `--drag <hwnd>`，内部 `ReleaseCapture() + SendMessage(WM_NCLBUTTONDOWN, HTCAPTION)`，**真正的 OS 拖动**，60fps 且零 IPC；
- 助手常驻（`--daemon`，stdin/stdout 行协议），`--pin` / `--raise` / `--thumb` / `--drag` 全部走长连接，**消除每次 30~100ms 的进程启动**，也顺带干掉首次 csc 编译 3~5 秒；
- 抬层：B 方案下不需要（单窗口）；A 方案下用 daemon 即时 raise。

### 6.6 多显示器

`rect` 改成 `{ displayId, x, y, w, h }`，并**按显示器配置存一份布局**（接/拔外接屏自动回到上次的位置，Fences 5.50 同款）。

| 阶段 | 内容 | 工期 | 验收 |
|---|---|---|---|
| **P0** | spike 三项（见 §4） | 0.5 天 | 结论写进本文档，决定 B/A |

**硬指标**
- 空闲 CPU 增量 < 1%，无轮询定时器
- 拖动帧率 ≥ 55fps
- 点击到视觉响应 < 50ms
- 分组首帧 < 150ms
- 常驻内存 < 150MB（现状 ~400MB）
- 数据变更到界面 < 100ms（现状最多 1.5s）

## 9. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| `setIgnoreMouseEvents` 在 pinned 子窗口上不生效 | B 方案失败 | 上一轮已实测可切 `WS_EX_TRANSPARENT`；P0 只验热区精度，风险降为中 |
| 热区表漏报（弹层/滚动中） | 按钮点不动 | 热区由渲染层 `ResizeObserver` + 弹层打开事件主动上报；主进程侧兜底：光标进入窗口且 30ms 内无热区也临时放行 |
| 全屏分层窗口合成开销高 | 拖动掉帧 | P0 第②项；必要时窗口只覆盖分组包围盒 |
| `startDrag` 阻塞渲染进程 | 拖动期间源窗口无法动画 | 幽灵由 OS 画，源项在 `dragstart` 前就置灰，可接受 |
| Win11 无 WorkerW 层 | 桌面层钉不住 | 已有 DefView 父窗口兜底；B 方案下单窗口影响面更小 |
| `ReadDirectoryChangesW` 在超大桌面目录开销 | 文件监听卡顿 | 只监听桌面目录 + 150ms 去抖 + 一次最多推送 200 条变更 |

单文件、无依赖，双击即可：

```
docs/prototypes/desktop-organizer-v2-proto.html
```

或本地起静态服务：

```bash
python -m http.server 4217 --directory docs/prototypes
```

底部演示条：`新方案 / 现状` 切换对照，`Peek` 演示其他应用之上的浮出，`模拟应用窗口` 先放一个 Word 挡在前面。

右上角（悬停显现）的 **一键整理** 是重点：点开是一份可审阅的方案（整理文件内容 / 重排分组布局），带前后缩略对比；`预览布局` 让所有卡片动画到目标位，`开始整理` 应用并提示可撤销。

卡片本身能双击标题栏折叠（卷起后悬停自动展开）、拖右下角改尺寸、拖标题栏移动（带吸附参考线）；右键有重命名 / 锁定位置 / 置顶显示 / 新建文件夹 / 新建文本文档 / 删除分组；图标上右键有打开 / 重命名 / 移入分组 / 移到回收站；空白桌面右键弹出的是**模拟的系统菜单**（查看 / 排序 / 刷新 / 新建 / 显示设置），用来对照「这块不归我们管」。

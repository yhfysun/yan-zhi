# 目录任务模式（Project Task Mode）方案

> 目标：给**空间/目录**绑定一个「任务类型」，用户在该目录下创建任务时，系统按该类型的
> **固定流水线**引导用户：备资源 → 逐步产出 → 逐步确认 → 交付归档 → 形成可复用的任务记忆。
> 本文档只做方案与排期，**未动任何代码**（代码改动待确认后开干）。

---

## 一、先看现状（调研结论，均带源码依据）

### 1.1 目录/文件这条线已经有的基础

| 能力 | 现状 | 位置 |
|---|---|---|
| 空间（目录） | `Space{id,name,dirPath,...}`，`dirPath` 可选；`currentSpaceId` 持久化 | `shared/types/index.ts:109`、`stores/space.ts:27` |
| 会话归属空间 | `conversation.space_id`，建会话时取 `currentSpaceId` | `stores/chat.ts:622-633` |
| 工作目录同步 | `space.dirPath → settings.workspaceDir → POST /workspace/dir` 双向同步 | `ChatFileTab.vue:200-209`、`useChat.ts:1852-1859` |
| 产物目录 | `.yan-zhi/tasks/<convId>/<categoryDir>`，`categoryDir` = uploads / intermediate / deliverables | `shared/utils/artifact-paths.ts:26-30,83-96` |
| 文件登记 | 三分类 `upload / intermediate / deliverable`，表 `conversation_file` | `stores/file.ts`、`shared/types/index.ts:121` |
| 上传落盘 | **与产物目录同一个**（先问 `/artifact-dir?category=upload&ensure=1`） | `useChat.ts:2494-2522` |

**结论**：目录骨架是现成的，缺的是「目录 ↔ 任务类型」这一层绑定，以及「按类型组织资源」。

### 1.2 交互/计划/记忆这条线的真实能力（决定了方案要补什么）

| 能力 | 现状 | 缺口 |
|---|---|---|
| 反问 `ask_user` | 单选/多选/文本/补充说明 | **不持久化**：刷新/切会话即丢 |
| 确认向导 `confirm_user` | **多页**向导（pages[]） | 同上，不持久化 |
| 任务计划 `task_plan/step` | 按会话分桶，有卡片 UI | **纯内存、不落盘**，跨会话共享不了 |
| 记忆 | `memory` 表 + **空间级 `MEMORY.md`**（每空间一份，注入系统提示词） | 空间级记忆**已经能跨会话复用** ← 可直接利用 |
| 工作流 | DAG（nodes/edges），支持 debug 断点 | **无 human/ask 节点**，运行期不能暂停等确认 |
| 短剧流水线 | 已内置：主题→分镜表→loop 生图+配音→字幕→交付 | **缺「人物分析」节点**（现从主题直接出分镜） |
| Skill | 内置 skill 即「执行手册」，可按场景关键词自动挂载 | 可承载类型 SOP |

**关键判断**：
- ✅ **`space-memory.ts` 已经提供了跨会话的项目记忆**（`<dir>/MEMORY.md`），这是本方案「任务记忆」的天然落点，不用从零造。
- ❌ 但 `ask_user`/`confirm_user`/`task_plan` **全是内存态**，长任务一旦刷新或换会话就断 —— **这是必须补的第一块**。

### 1.3 办公文档渲染：我们和 WorkBuddy 的差距（明确可量化）

| 类型 | 我们 | 差距 |
|---|---|---|
| xlsx/xls | **真渲染**（exceljs 读样式→HTML 表格，可双击改值写回） | 不差 |
| pdf | pdf.js 栅格化成图（30 页上限，scale 1.6），失败降 unpdf 文本 | 中等，缺「矢量文本层」（可选中/搜索） |
| md / txt / 代码 | markdown-it + hljs | 够用，缺 KaTeX（katex 已装但零引用） |
| **docx/doc** | **不渲染**，提示「请用本机应用打开」 | ★★ **这是最大差距** |
| pptx | **不渲染**（不在白名单，落到"暂不支持"） | ★★ 第二大差距 |
| docx 导出 | 手写 OOXML 最小部件集，仅段落+图片，**无标题层级/列表/表格/加粗** | 导出质量弱 |

★ **讽刺点**：`packages/core` 里**已经装了 `mammoth ^1.8.0`** 且有 `extractDocxHtml`
（`packages/core/src/preview/index.ts:38-51`），但只被聊天**附件缩略浮层取前 N 字纯文本**用，
`FilePreview.vue` 根本没用。**即：能力已有，只是没接到预览面板。**

### 1.4 工具自动下载：我们基本没有

- **MCP**：纯手工填 command/args（`npx -y @xxx/server-filesystem` 靠用户自己写），
  系统**不识别、不预检、不代拉包**；命令不存在即连接失败。
- **插件**：只能**上传 .yzp 包**安装（`routes/plugins.ts:74`），**无远程市场**下载
  （现在那个"远程商城"是**智能体**源，不是插件）。
- **运行时**：只有 **ffmpeg** 一条是真的按需下载（`mcp/ffmpeg-runtime.ts`，带 3 次重试），
  但**需用户确认**（提示里明写"建议先向用户确认再下载"）。
  Python 是**打包期**预烤（含 python-docx/pptx/xlrd），dev 缺就回退系统 python，**不下载**。

★ **WorkBuddy 的做法**：工具缺失时自动拉取（npx/uvx 拉 MCP 包、自动装依赖），
我们缺的是这一层「**依赖探测 → 提示 → 一键/自动安装**」。

## 二、方案总览

分 **4 期**，每期可独立交付、独立验证：

```
P0 底座：让长任务"不断线"     ← 必须先做，否则后面全是空中楼阁
P1 任务类型 + 资源目录          ← 用户主诉求
P2 分步引导流水线              ← 短剧/小说/翻译/有声小说的执行形态
P3 文档渲染 + 工具自安装        ← 体验补齐（对标 WorkBuddy）
```

## 三、P0：长任务底座（必须先做）

### 3.1 交互状态持久化（关键）

把 `pendingQuestion` / `pendingConfirmation` / `pendingPlatformConfig` 从内存 ref 落到库：

- 新增表 `conversation_pending`（或复用 `conversation` 的 json 列）：
  `id / conversation_id / kind(ask|confirm|platform) / payload_json / created_at`
- 恢复时机：`loadMessages(convId)` 后顺带拉；有则渲染内联表单，
  **并把 Promise 重新挂上**（让 ReAct 循环能续跑）。
- 取消/过期：给 `expires_at`（建议 7 天）；会话删除时级联清理。

### 3.2 任务计划落盘（跨会话）

`plansByConv` 现在纯内存 → 落到 `conversation_plan` 表
（`conversation_id / title / steps_json / cursor / status`）。

- 这样「换一个会话继续同一个长任务」才成立（用户明确要求：*方便多次进行任务（多个会话）*）。
- UI：TaskPlanCard 增加「继续上次」「跳到第 N 步」。

### 3.3 任务记忆（复用现成的空间记忆）

**不新造轮子**，扩展 `space-memory.ts`：

```
<dir>/MEMORY.md              ← 已有的空间级记忆（项目画像）
<dir>/.yan-zhi/task-memory/  ← 新增：按任务类型分文件
    characters.md            ← 人物卡（文字+图片描述）
    scenes.md                ← 场景设定
    style-guide.md           ← 风格/格式约定（用户确认过的响应格式）
    decisions.md             ← 历次确认记录（决策日志）
    progress.md              ← 进度：做到第几段/第几镜
```

- 注入策略：系统提示词注入 **当前任务类型的 `progress.md` + `decisions.md` 摘要**，
  长任务时不全量注入（防爆窗），按需用工具读（`memory_read` 已存在）。
- 工作流已有 `memory_read / memory_write` 节点（`workflow-runner.ts:570,595`）→ 直接复用。

## 四、P1：任务类型 + 资源目录规划

### 4.1 给 Space 加任务类型字段

```sql
ALTER TABLE space ADD COLUMN task_type TEXT;      -- short_drama|novel_rewrite|translate|audiobook|custom
ALTER TABLE space ADD COLUMN task_config_json TEXT; -- 该类型在该目录下的覆盖配置
```

UI：空间编辑弹窗加「任务类型」下拉（默认「通用」）。
**目录首次设为某类型时**，生成该类型的默认目录骨架（见 4.2）。

### 4.2 资源目录规划（用户上传 vs 生成物）

原则：**目录结构自解释**，用户自己往里拷文件也能被识别；生成物与上传物**物理分离**但同级可见。

```
<空间目录>/
├─ MEMORY.md                       # 空间记忆（已有）
├─ .yan-zhi/
│  ├─ task.json                    # 任务类型 + 进度游标（P1 新增）
│  ├─ task-memory/                 # 任务记忆（P0.3）
│  └─ tasks/<convId>/              # 会话级产物（已有，保持不变）
│      ├─ uploads/  ├─ intermediate/  ├─ deliverables/
└─ <类型资源目录>/                  # ★ 新增：用户可见、可直接往里放东西
   ├─ 00-source/        # 用户上传的原始资源（小说 txt、剧本、待译原文、视频素材）
   ├─ 01-reference/     # 参考资料（人设图、风格参考、术语表）
   ├─ 02-work/          # 中间产物（人物卡、分镜草稿、逐段译文）
   └─ 03-output/        # 最终交付（成片、成稿、字幕文件）
```

**为什么这样分**：
- `00-source` / `01-reference` 是**用户负责**的（引导用户上传/拷贝）；
- `02-work` 是**过程**（对应现有 `intermediate`，可回退重做）；
- `03-output` 是**交付**（对应现有 `deliverable`）。
- 四段用数字前缀排序，在文件树里自然按流程顺序排列，**用户一眼看懂流程**。

★ **与现有机制的衔接**（不推翻重来）：
- 会话级产物**仍然**走 `.yan-zhi/tasks/<convId>/<category>`（后端既有逻辑不动）；
- `00~03` 是**目录级**的长期资源（跨会话共享，这才是"多次进行任务"的关键）；
- 登记时新增 `scope` 字段（`session` / `project`）区分两者，文件管理面板按 scope 分组显示。

### 4.3 文件管理面板的显示改造

现在三分类（上传/中间/交付）→ 改为**两段式**：

```
【本任务】upload / intermediate / deliverable    ← 会话级，跟随任务
【项目资源】00-source / 01-reference / 02-work / 03-output  ← 目录级，跨会话
```

上传入口按当前所处段自动归位（在"项目资源"里上传 → 落到对应 `0x-` 目录）。

## 五、P2：分步引导流水线

### 5.1 新增 `human_confirm` 工作流节点（核心补缺）

工作流现在**没有**「暂停等用户确认」节点 → 补一个：

```jsonc
{ "type": "human_confirm", "data": {
    "kind": "ask" | "confirm",        // 复用 ask_user / confirm_user
    "question": "...",
    "pages": [...],                    // 多页向导
    "artifact": "characters.md",       // 待确认的产物（可选，自动在预览窗打开）
    "onReject": "retry" | "abort"      // 用户打回后重做还是中止
}}
```

运行期：写 `conversation_pending` → 挂起 → 用户回答后恢复（依赖 P0.1）。
**这是"一步步让用户确认"的机械保证**，靠提示词约束不可靠。

### 5.2 默认任务类型与流水线

| 类型 | 流水线（每步都带确认） |
|---|---|
| **短剧**（short_drama） | ① 读 `00-source` 剧本 → ② **逐个人物分析**（文字描述 + 参考图，一人一卡，逐个确认）→ ③ 场景设定确认 → ④ **分镜脚本逐段产出（中英双语）** → ⑤ 用户确认响应格式（表格/JSON/Markdown）→ ⑥ 生图/配音（走已有 loop）→ ⑦ 字幕 + 交付清单 |
| **小说改写**（novel_rewrite） | ① 导入原文 → ② 确认改写目标（风格/人称/篇幅/受众）→ ③ 大纲确认 → ④ 逐章改写（每章确认）→ ⑤ 术语/人名一致性检查 → ⑥ 成稿导出 |
| **翻译**（translate） | ① 导入原文 → ② 确认语种/术语表/风格 → ③ 确认输出格式（对照/纯译文）→ ④ 分批翻译（每批确认）→ ⑤ 术语一致性校验 → ⑥ 导出 |
| **有声小说**（audiobook） | ① 导入视频素材+文本 → ② 确认配音/字幕参数 → ③ 分镜-配音-字幕 → ④ 时间轴校准确认 → ⑤ 合成导出 |

★ **短剧的「人物分析」节点是当前流水线缺的**（现从主题直接出分镜），本方案补上，
且明确要求**每个人物都要有文字 + 图片描述**并**逐个让用户确认**。

### 5.3 承载方式的选择

三种可选，建议**混用**：

| 方案 | 适用 | 说明 |
|---|---|---|
| **A. Skill 手册** | 主力 | 内置 skill 作为类型 SOP（已有先例：`skill_anime_storyboard`），改动小、可调优 |
| **B. 工作流 DAG** | 需要严格顺序/循环（如逐镜生图） | 补 `human_confirm` 节点后可用；已有短剧流水线可改造 |
| **C. 场景绑定** | 选类型即切智能体+挂 Skill | 复用 `scenes.ts` 的 `agentId + prompt + skillKeywords` 机制 |

**建议**：类型 = **场景（切智能体/挂 Skill）+ Skill 手册（SOP）+ 可选工作流（重环节用 DAG）**。
轻量类型（翻译、改写）用 A+C；重类型（短剧、有声小说）用 A+B+C。

## 六、P3：体验补齐（对标 WorkBuddy）

### 6.1 办公文档渲染（差距最大，收益最高）

**第一步（低成本、高收益）**：把**已装的 mammoth** 接到 `FilePreview.vue`
→ docx 走 `extractDocxHtml` 渲染成 HTML（带基本样式），而不是"请用本机应用打开"。

| 项 | 动作 | 成本 |
|---|---|---|
| docx 预览 | mammoth → HTML（已在 core/preview） | **低**（接线即可） |
| docx 保留图片 | mammoth 默认转内联图，需确认 data URI 策略 | 中 |
| pptx 预览 | 已有自写 XML 解析（`file-to-markdown.ts:57`）→ 先转**逐页 Markdown/缩略图**；真渲染需新增 PPTX 布局渲染器 | 中~高 |
| docx 导出增强 | 现手写 OOXML → 补 标题层级/列表/表格/加粗 | 中 |
| KaTeX | katex 已装但未用 → markdown-it 加插件 | 低 |
| pdf 文本层 | pdf.js text layer（可选中/搜索） | 中 |

**建议先做**：docx 预览（接线）+ 导出增强 + KaTeX。pptx 单独立项。

### 6.2 工具自动下载

分级实施（**都要有确认，不做静默下载**）：

1. **MCP 依赖预检**：保存 MCP 配置时探测 command 是否存在
   （`where`/`which`），不存在则提示「需要 npx/uvx 拉取，约 XX MB，是否安装？」
2. **一键安装**：对已知包（`@modelcontextprotocol/server-*` 等）提供
   「用 npx 安装 / 用 uvx 安装」按钮，复用 ffmpeg 那套下载+重试框架。
3. **远程插件市场**：现在只能上传 .yzp → 增加从 marketplace baseUrl 拉取安装
   （复用现有"远程智能体商城"的 baseUrl 配置模式）。
4. **运行时探测**：把 ffmpeg 的模式抽象成通用的 `runtime-installer`
   （ffmpeg / python / playwright chromium 共用一套：探测→提示→下载→校验→重试）。

### 8.1 权限默认只读（已实施 ✅）

用户拍板前发现的安全问题：`permissionMode` 默认 `default`（= 全部工具放行），太危险。
已改为**新任务默认 `readonly`**（后端拦截设计本就完善：写工具黑名单 + custom_/mcp_/wf_ 不可控前缀 + 工作流内容白名单，fail-safe 方向正确）：

- 前端 store 默认值 / 新建任务归零 → `readonly`
- 后端 `normalizePermissionMode` 未知值 fail-safe 收窄 → `readonly`（`default` 作为合法值保留，存量会话不受影响）
- `llm-task-manager` 查库异常兜底 + 4 处 `|| 'default'` 兜底 → `readonly`
- 建库列默认值（core schema + server 迁移，仅对新库生效）→ `readonly`
- UI 文案：`只读（默认）` / `标准权限` / `全部放行`
- 存量会话的 `permission_mode` **保持原值不动**（忠实保留当时选择；UI 与后端口径一致）
- 守门测试 6 条 + 变异验证 6/6 变红

**体验说明**：只读任务里模型撞到拦截会收到明确原因（`permissionModePrompt` 会先注入"本次只读"指令），
模型会主动提示用户放开权限；用户在权限胶囊（移动端在「+」菜单）一键切换即可。

### 8.2 ★ 硬性要求：用户确认过的内容必须落盘为任务记忆（用户 2026-09-27 强调）

> 「确认好的要记录到空间记忆里」—— 人物形象、场景设定、响应格式、风格选择、每批次的通过/打回，

落到 P0.3 的 `decisions.md`（决策日志）+ 各专项文件（`characters.md` / `style-guide.md`）：

- 每次用户确认（ask_user / confirm_user / human_confirm 节点的返回）→ 由工作流
  `memory_write` 节点或后端在任务收尾时**结构化追加**到 `<dir>/.yan-zhi/task-memory/decisions.md`，
  格式：`[日期] [类型] 决定内容（来源：第 N 轮确认）`。
- 下次同目录任务开始时，系统提示词注入 `decisions.md` 摘要 + `progress.md`，模型先复述
  已确认的设定再继续，避免重复追问。
- 判据（验收用）：同一目录下新开会话，模型**不再重复问**已确认过的人物/格式/风格。

## 十五、★ 方向校正：任务模式 ≠ 工作流（2026-09-27 用户澄清，必读）

> 用户原话：「**不是流水线啊，是任务模式规则啊，还是通过对话完成小说改写，翻译，脚本文案，短剧啊**」

**我上一轮把主路径搞错了。** 正确定位：

| | 任务模式规则（**主路径**） | 内置工作流（可选的重环节机械保证） |
|---|---|---|
| 用户在哪 | **对话里**（选目录类型 → 直接聊） | 工作台 `/workflow` 跑 DAG |
| 谁推进 | 模型按注入的 SOP **分步引导** | 引擎按图执行 |
| 怎么确认 | 模型调 **`confirm_user` / `ask_user`**（真实工具调用，挂起等回答） | `human_confirm` 节点（图上结构事实） |
| 适用 | **所有类型**（小说改写/翻译/脚本文案/短剧/配音…） | 只在"错了会很贵"的重环节（如短剧逐镜出图）加一道机械拦截 |

**结论**：P2 的 4 条（现 5 条）内置流水线**不是错**，但它不是用户要的主体验；
用户要的是**对话里的任务模式规则**。第 14 节那批工作流保留为"重环节可选加速器"，
主线工作应放在 **`task-types.ts` 的规则文本 + 对话注入**上。

### 本轮（第十五节）落地：把 SOP 升级成"对话可执行的规则"

`packages/shared/src/utils/task-types.ts`（前后端共用，后端注入提示词、前端做下拉）：

| 改动 | 说明 |
|---|---|
| ★★ 步骤写明**用哪个工具确认** | `confirmTool: 'confirm'\|'ask'` + `confirmAbout` → 注入文本变成「**必须用 confirm_user（多页向导）确认：风格、人称、篇幅…**」。理由：只写"让用户确认"时，模型会**在正文里问一句"可以吗"然后继续往下跑**（不阻塞、拿不到回答）——这正是"一步步确认"在纯提示词下的典型失效形态 |

### ★★ 真机抓到的不一致（已修）

`space-resources.ts` 的 `mergeTaskMeta` 是**合并写**（保留未传字段）。实测：

```
① 设 novel_rewrite → DB=novel_rewrite, task.json=novel_rewrite
② 改成 dubbing     → DB=dubbing,        task.json=dubbing
③ 改回通用(null)   → DB=null,           task.json=dubbing   ← ★ 文件里还留着旧类型
```

- **影响**：`task.json` 目前**只写不读**，故对功能暂无影响；但它的设计意图是
  「用户把整个目录拷到别的机器时一并带过去」—— 留着过期类型，届时就会误导
  （用户看文件以为还是配音任务，实际 DB 已是通用、不再注入 SOP）。
- **修法**：`setSpaceTaskType` 在 `prev` 有值而本次清空时调 `clearTaskMetaType(root)`，
  只删 `taskType / taskTypeLabel / taskConfig`，**保留其它机器状态**（`spaceId` / `resourceDirs` / 进度游标）——
  与「只 mkdir、不删用户文件」的底线上不冲突（`task.json` 是机器状态文件，不是用户资源）。

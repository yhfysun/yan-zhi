# 版本分档与授权分级方案

> 目标：把「一个代码库 → 三种能力档次的包」做成可签发的授权体系。
> 本轮范围（用户拍板）：**前端门禁 + 三版本打包**；后端代码不做裁剪，全量随包。

---

## 一、需求口径（已确认）

| 版本 | key | 放行的模式 | 随包默认授权码 |
| --- | --- | --- | --- |
| 阉割版 | `lite` | 仅办公模式 | lite 码 |
| 基础版 | `basic` | 办公 + 工作流 + 开发 | basic 码 |
| 高级版 | `pro` | 全部（办公/工作流/开发/运维/安全） | **basic 码**（可用 pro 码升级） |

- 「流水线」= **工作流模式（`wf`）**，不是 cicd-pipeline 插件。
- 高级版全量包拿到基础版码时，未授权的模式**完全隐藏**（不出现在模式下拉与左栏，不留置灰项、不留提示文字）。
- 授权码**可勾选版本**签发。

## 三、契约设计

### 3.1 版档字段写入授权码

`LicensePayload` 增加 `edition?: string`（参与签名，客户端改不了）：

```ts
{ expireAt: string | null, mac: string | null, machineId?: string | null, edition?: 'lite'|'basic'|'pro' }
```

**默认档 = `pro`**：老码（无 `edition`）与非法值都按 `pro` 处理 → 已发出的码行为不变（这是必须的，否则存量客户掉权限）。
> 注意：`DEFAULT_LICENSE` 预置试用码也要重新签发成 `basic`，否则高级包开箱即全量，与「默认携带基础版」不符。

### 3.2 唯一权威映射表（后端）

```ts
export const EDITION_MODES: Record<Edition, AppMode[]> = {
  lite:  ['office'],
  basic: ['office', 'wf', 'dev'],
  pro:   ['office', 'wf', 'dev', 'ops', 'sec'],
};
```

`VerifyResult` 增加两个字段：`edition: Edition`、`modes: AppMode[]`。
前端**不再自己写一份**模式清单 —— 只读后端下发的 `modes`，避免两处漂移。

### 3.3 两级上限：构建档 ∩ 授权档

生效模式 = `BUILD_EDITION 允许的模式` ∩ `授权码允许的模式`

为什么两级都要：
- **构建档**让「阉割版包里就没有别的模式的代码」成立（用户明确要求「打出来的包就相应内容的代码」）；
- **授权档**让高级全量包能按码升降（用户明确要求）。

`edition.json`（构建期由脚本写入，dev 下默认 `basic`）是**唯一构建期输入**，前端与主进程共用。

## 五、风险与对策

| 风险 | 等级 | 对策 |
| --- | --- | --- |
| 存量码无 `edition` 字段 → 若默认成 `lite`，客户直接掉权限 | **high** | 默认档定为 `pro`；专门写测试用例钉死「无字段 → 全量」 |
| 前端与后端各写一份模式清单 → 长期漂移 | medium | 模式清单只在后端定义，前端只消费 `modes` |
| 未授权模式仅靠前端隐藏 → 直连 `/api/workflow/*` 仍可达 | **high（已知）** | 用户已明确接受本轮「前端先禁」；后端裁剪列为下一轮（见「未做」） |
| 当前模式失权后 UI 停在空白工作台 | medium | 激活/降级后显式回落 `office` 并跳路由 |
| `main.cjs` 改动必须重启 Electron（主进程不热更） | medium | 改动后做打包版实测，不靠 dev 模式判断 |
| 打包脚本三份 yml 的 `files:` 需登记新增文件 | **high** | `edition.json` 与 `set-edition.cjs` 的归属需逐个核；漏登记 → 打包版启动即崩（已有前车之鉴：`keyring-crypto.cjs`） |

## 第一轮：分层 + 压缩落库 + 快照瘦身

用户原话：「检查下未完成的任务完成一下，单会话上下文过长，看看主流框架怎么处理，应该不是把所有消息
给到大模型吧，消息保存前端显示是一份，还有一份应该是跟大模型交互的，可以放文件里？多了还能压缩？」

**三条直觉全部成立** —— 尤其第二条正是 Roo Code 的 **dual message store**
（`ui_messages.json` / `api_conversation_history.json`）。言智当时的问题是**只有一份**，
且「未超阈值时把全量历史原样发」。

## 第二轮：有效上下文（标称 ≠ 可用）

用户原话：「好像最优的上下文就是 258K 啊，如果超出了是不是应该有优化策略？现在虽然很多大模型
号称支持 1M 但是上下文过多后效果就不好了，看看主流产品怎么优化的?」

### 一、用户判断成立，「258K」有确切出处

| 来源 | 结论 |
|---|---|
| **Chroma「Context Rot」(2026)** | 测 **18 个前沿模型**（含标称 1M 窗口的）→ **无一例外**随长度退化；**单靠长度掉 7.9%**（干扰全去掉也一样）；相关信息落在 20 篇文档**第 5–15 位**时掉 **30+ 个百分点**。生产建议：按标称窗口的 **25–30%** 设预算 |
| **RULER（NVIDIA, COLM 2024）** | 17 模型 × 13 任务：需要多跳推理/聚合时，**有效上下文只有标称的 50–65%** |
| **Lost in the Middle（Liu et al.）** | U 形曲线：首尾召回好、**中段掉 30%+**；不随窗口变大消失（注意力随序列长度二次方稀释） |
| **社区甜点区 (2026)** | GPT-4.1（标称 1M+）≈ **256K**；Llama 4 long（1M–10M）≈ **256K**；Gemini 2.5 Pro（2M）≈ 500K。**LongCodeBench：多数模型 256K 之后编程能力已崩** ← **正是用户说的 258K** |
| **Aider 作者经验值** | 25–30K 之后模型就开始"犯迷糊"（"能塞"与"该塞"差一个数量级） |

### 二、主流产品怎么做

- **Claude Code**：1M 原生窗口模型默认 **~967K** 才压缩（激进），但文档明确建议
  「delegate large reads to subagent」「/clear between tasks」「别让上下文变满」；
  压缩分**三档**：① microcompaction（持续裁老 tool 结果，含 cache-aware 模式直接改缓存前缀）
  ② session-memory compaction（**零 API 成本**，用已抽取的会话记忆当摘要）
  ③ full compaction（LLM 生成 9 段结构化摘要；摘要时**关闭工具**；用 **forked agent 复用父会话 prompt cache**）。
  触发：`threshold = contextWindow − 20K(摘要预留) − 13K(buffer)`。
- **LibreChat**：`trigger: {type: token_ratio, value: 0.8}` + `reserveRatio: 0.05` + `contextPruning` 两级。
- **Roo Code**：`allowedTokens = cw×(1−10%) − reservedTokens`；压缩后仍超限 → 强制滑窗。
- **社区实践（byteiota 汇总）**：**把 compaction 触发点从默认 95% 提前到 70%** ——
  ★ 关键洞察：**95% 才压缩时"损害早已发生"**。
- **Morph**：sub-agent 隔离搜索/探索，实测性能提升 **90%**。

| 位置 | 内容 |
|---|---|
| **新增** `packages/shared/src/utils/context-policy.ts` | `EFFECTIVE_CONTEXT_RATIO = 0.25`（Chroma 生产建议区间）／`EFFECTIVE_CONTEXT_FLOOR = 16K`（小窗口不被压太狠）／`MAX_SESSION_MESSAGES = 400`（治"很多条短消息"）／`effectiveContextLimit()`／`contextUsageLevel()`／`contextUsagePercent()` |

| `ChatInputArea.vue` | tooltip 同时展示「模型标称窗口」与「有效区」，让用户看出差距 |

### ★★ 踩坑：两层折扣**不能叠加**

`resolveContextWindow(1048576)` 会把"恰好等于建库默认 1M"判为**不可信** → 退回 **32K**（它自己的口径）。
若紧接着再乘 25% → 变 **8K** → 扣输出预留后可用区只剩 4K → **压缩触发得离谱地早**（双重保守）。

⇒ 修法：**只在"声明值被信任"时才叠有效性折扣**；已退回 `SAFE_CONTEXT_WINDOW` 时说明本就在按小窗口估算，
该值**本身就是**有效值。

★ 判据：**串联两个"保守兜底"会得到过度保守** —— 与「两层口径必须同源」是同一族问题的反面。

## 坑（已并入 `MEMORY.md`）

1. **★★★ `.gitattributes` 规定 `*.ts` 为 LF，但 `llm-task-manager.ts` 是 CRLF** →
   测试里多行 `indexOf('...{\n')` 锚点在 `{\r\n` 上落空 → `space-memory-progress` / `task-memory-and-pending`
   这类**源码结构断言集体假红**，表象像"改坏了源码"。
   ⇒ 定位手法：**`git show HEAD:<file>` 切回基线跑同一测试** → 立刻分清"既有红"与"本轮引入"。
2. **★★ 手写白名单 mock 的连锁失同步**：`vi.mock('../src/db.js'|'@yan-zhi/core', () => ({...}))` 是白名单 →
   生产代码每多用**一个导出**，所有踩到它的测试静默失同步 → 报 `No "X" export is defined on the mock`，
   而**表象是「任务 failed」**。本轮一次补齐 **12 个 db mock + 2 个 core mock**。
3. **★★ 变异脚本必须区分「跑了」与「没跑起来」**：本机 node spawn 被沙箱拦成 `EBUSY`，
   首版变异器把"进程启动失败"当成"测试变红" → 得出 **6/6 假捕获**结论。
4. **★★ 串联两个"保守兜底"会过度保守**（见第二轮踩坑）。

## ⏳ 仍未做

- **存量快照清理**：库内 226MB 旧快照仍在（瘦身只对新写入生效）→ 需一轮离线迁移。
- **压缩触发点**：当前 = `有效预算 × 0.5`；社区建议进一步提前到 ~70%（本轮已因有效窗口折算
  从"几乎不触发"变到"合理触发"，是否再提前需实测长任务表现后再定）。
- **子智能体摘要不落库**（`persist:false`，刻意避免主循环读到子智能体摘要而带偏）→
  子智能体每步仍重算增量摘要（`subSummaryCaches` 挡住 LLM 调用，但重算仍在）。要治需给
  `message_summary` 加 `parent_tool_call_id` 维度。
- **P5 可选**：非破坏性回滚前端接线（`deleteMessageSummariesAfter` API 已备好）／AST 文件折叠。
- **历史回放**时的压缩标记（当前 `context:compacted` 只对流式事件生效）。
- **动态模型能力表**：可用 API 的 `/models` 或 `capabilities_json` 自动判定每模型的**有效窗口**，
  而不是统一 25%（各厂商退化曲线不同）。

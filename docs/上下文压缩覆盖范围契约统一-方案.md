# 上下文压缩「覆盖范围」契约统一（A 方案·最彻底）

> 2026-10-03 · 修「安装版最近会话卡很久」的根因
> 关联：`packages/core/src/compress/window.ts`、`apps/server/src/services/context-view.ts`、
> `apps/server/src/services/context-snapshot.ts`

## 一、现象与实测

- 用户发消息 → 首条助手落库，慢时 **25–28s**；单步 assistant 生成 10–25s，一轮 50 步 > 10 分钟。
- 会话 `061202ec`（10-03）里用户自己打了「怎么卡了这么久？」。
- 服务端还原接口只要 86–168ms —— **不是**服务端/DB 慢。

## 二、根因（数据定案）

`message_summary` 同一会话落了 **111 条**摘要，且：
- 每一条 `messageIds[0]` 在 `message` 表里位置都是 **idx = 1**（起点偏移）；
- 覆盖条数 **721 → 959**（**全量**，不是分段）；
- 故**每步都在全量重压 + 写一条新摘要**，压缩从未「只生效一次」。

**机制**：写侧与读侧对「一次压缩覆盖了哪些消息」用了**两套坐标**：

| | 位置 | 起点 |
|---|---|---|
| 写侧 | `core/compress/window.ts` `onCompressed.coveredIds` = `toCompress`（**跳过了 keepFirst 头部**，头部每轮原文重发） | `raw[2]` |
| 读侧 | `server/services/context-view.ts` `stillValid` = 从 idx 0 起逐项比对 | 期望 `raw[0]` |

`keepFirst=2`（主循环/子智能体均传 2）→ 覆盖段从 idx=2 起 → 读侧第 0 条即 mismatch
→ `stillValid=false` → 旧摘要每轮判废 → 每步重算全量摘要。

> 触发条件：`keepFirst > 0`。默认 0 时头部不单独重发，两套坐标恰好一致，故此前未暴露。

## 三、修法（A 方案）：坐标收敛到 core 的唯一定义处 + 废除多余的「头部重发」

1. **core 新增并导出**（`compress/window.ts`）：
   - `SYNTHETIC_MESSAGE_IDS` / `isSyntheticMessageId(id)` —— 合成消息 id 的唯一清单。
   - `coveredIdsForCompression(consumed)` —— **写侧坐标**：覆盖段 id（连续、去合成）。
   - `isIdPrefix(prev, cur)` / `isCoveredPrefix(coveredIds, allIds)` —— **读侧判据**（唯一前缀实现）。
2. **core 压缩切分**：**取消「头部原文重发」**，切分只剩一处——保留最近 `keepRecent` 条，
   其余（**含头部**）全部并入被摘要段 → 覆盖段恒为「从会话首条起的连续前缀」。
   `keepFirst` 参数保留但不再影响切分（兼容既有调用）。
3. **server `context-view.ts`**：读侧 `isCoveredPrefix`；写侧落库前用 `isSyntheticMessageId` 过滤。
4. **server `context-snapshot.ts`**：合成 id 清单改为从 core 再导出（消掉第二份）。

**关键判断**：摘要指令**本就强制保留** `## 任务目标`（用户最初的原始问题）+ `## 已完成` / `## 待办`
——即「原始问题 / 处理了什么 / 还没处理什么」。既然如此，「每轮再原文重发头部」是**多余的第二套机制**，
正是它制造了两套坐标。→ 只保留摘要这一套。

## 四、验证（真实数据 + 编译产物）

- 契约测试 `packages/core/src/compress/context-coverage.test.ts` **21/21 通过**，
  覆盖「覆盖段从首条起」「合成 id 过滤」「多步复用」「keepFirst 不改变契约」。
- 真实生产库 300 条历史跑真实链路：**覆盖 293 条、起点 idx=0、读侧命中、增量无重叠**。
- 修复前对照：旧摘要起点 idx=1 / 旧写侧 idx=2 → 均判废。
- `tsc` 真编译 0 错误；产物含新导出。core 全量测试仅 `sandbox.test.ts` 1 项既有红（本机 spawn 受限，与本轮无关）。

## 五、附带项（未做，另议）

- 库内 336MB 中 `message` 表 312MB、`system_prompt_snapshot` 占 **234MB**（修复前旧快照存量）
  —— 是磁盘问题不是速度问题，可做一次性瘦身。
- `message_summary` 的 `message_ids_json` 每条复制整份 id 列表（111 条合计 ~2.36MB），属 O(n²) 复制，
  量大时可考虑只存"覆盖条数 + 首末 id"。

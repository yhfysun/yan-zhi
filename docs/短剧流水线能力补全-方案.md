## 2. 设计原则：模型为先、程序兜底

用户提的这个分层是对的，而且和现有 `resolveMediaPlatform()` 的思路一脉相承。把它固化成**统一的媒体能力路由**，三个模块共用一套骨架：

```
能力请求（capability: i2v | tts | compose）
  │
  ├─① 模型层（优先）
  │     查 model 表 → 有对应 capability 的模型 → 按平台协议发送
  │     成功 → 落盘 → 登记 → 返回
  │
  ├─② 程序层（兜底，模型缺失或调用失败时）
  │     TTS   → edge-tts → 系统语音（SAPI/say）
  │     合成  → 随包 ffmpeg
  │     图生视频 → 无本地模型，降级为「首帧描述 + 文生视频」（语义兜底）
  │
  └─③ 引导层（两层都不通）
        不静默失败：明确说清缺什么、在哪配、配完怎么重试
```

三条硬规矩：

1. **兜底不改变语义**：程序层产出要标注来源（`provider: 'edge-tts'` / `'sapi'`），让用户知道这是兜底音色还是模型音色。
2. **兜底不静默**：与现有代码一致，`catch` 必须留痕（参考 `api-tool-executor.ts:466`、`:1133` 的写法）。
3. **不做声音克隆**：配音只做「选音色」，不做「复刻某人声音」——版权与合规红线。

## 3. 模块一：图生视频

### 3.1 问题

不是「没写」，是**协议碎片化 + 上游未开放**两件事叠在一起：

- agnes：`first_frame` / `last_frame`，但 `mode` 只接受 `'text'`（`api-tool-executor.ts:597` 的 `MEDIA_NOT_OPEN_HINT`）
- OpenAI Sora 风格：`input_reference`
- 可灵 / 即梦 / 海螺 / Vidu：字段名各不相同

现在代码是**硬编码三分支**（`isAgnes` 与非 `isAgnes`），加平台就得改代码。

### 3.2 方案：协议 profile 化

在 `api-tool-executor.ts` 里把发送逻辑抽成一张表：

```ts
type VideoProtocol = {
  modeField?: 'text';                    // agnes: mode 固定 text
  firstFrameField: string;               // first_frame / input_reference / image
  lastFrameField?: string;               // last_frame
  extraFields?: Record<string, unknown>;
};
function resolveVideoProtocol(baseUrl: string, modelId: string): VideoProtocol
```

- 命中 agnes → `{ modeField:'text', firstFrameField:'first_frame', lastFrameField:'last_frame' }`
- 命中 openai/sora 家族（baseUrl 或 model 名匹配） → `{ firstFrameField:'input_reference' }`
- 其余 → `{ firstFrameField:'image' }`（通用兜底，失败时**原样透出上游报错**，不吞）

新增平台只加一行 profile，不动主流程。

### 3.3 降级链路（关键）

图生视频**无法用程序兜底生成画面**（本地没有扩散模型）。所以兜底只能降一档语义：

```
i2v 请求
 ├ 成功 → 返回视频
 ├ 上游报 invalid mode / not supported
 │    └ 自动降级：
 │        image_analyze(首帧图) → 得到画面描述
 │        → 拼接进原 prompt（主体/构图/光线锚点）→ 走文生视频
 │        → 返回结果，并注明「本平台不支持图生视频，已按首帧画面描述生成
 │          文生视频；如需严格一致性请改用支持 i2v 的平台」
 └ 连文生视频也不通 → 明确失败
```

用户体验从「报错」变成「拿到了一条视频，且知道它是什么档次」。降级开关建议做成工具参数 `allowFallback`（默认 `true`）。

### 3.4 能力可见化

`list_models` 已经支持按 `type` / `capability` 过滤（`llm-task-manager.ts:143-188`），但模型的能力标签是空壳。给视频模型补上能力标签：

- `t2v`（文生视频）、`i2v`（图生视频）、`kf`（首尾帧）
- 视频工具的 description 里写明「先用 list_models(type=video) 确认目标模型是否支持 i2v」

这样模型自己能做选型，不用人猜。

## 4. 模块二：文字转语音

### 4.1 现状

全项目零 TTS：

- 无 tts 工具（grep `tts|text_to_speech|speech_synth` 无实现）
- seed 的 agnes 模型只有 6 个 llm + 3 个 image + 3 个 video，**无 audio**（`apps/server/src/agens-platform/service.ts:99-112`）
- `list_models` 的文档提到 `audio/tts`（`list-models.ts:17`），但目录里没这类模型
- 前端 `MediaTarget.kind` 没有 `audio`，`ToolMediaPreview.vue` 没有 `<audio>` 分支
- `platform.ts:82` 的 `audio` 分类指的是 whisper 语音**转文字**（STT），不是 TTS

### 4.2 新增工具 `api_tts_speak`

```jsonc
{
  "text": "要说的话（或 dialogue 数组）",
  "role": "说话角色（用于多角色音色路由）",
  "voice": "音色 id（模型层：alloy/晓晓…；程序层：edge 音色名）",
  "model": "TTS 模型 id（默认按 platformId 或首次可用）",
  "platformId": "指定平台",
  "speed": 1.0,
  "format": "mp3 | wav",
  "outName": "输出文件名（默认按角色+序号）"
}
```

模型层请求（OpenAI 兼容，多数平台通用）：

```
POST {baseUrl}/v1/audio/speech
{ "model": "...", "input": "...", "voice": "...", "response_format": "mp3", "speed": 1.0 }
```

响应是音频二进制流 → 复用现有 `mediaTarget()` 落盘 + `MEDIA_TOOLS` 登记链路，只把 `kind` 扩成 `'audio'`、mime 用 `audio/mpeg`。

### 4.3 「内置语音包」怎么加：三个候选

用户问的「内置加个语音包」，本质是选**程序层默认引擎**。三条路都测过优劣：

| 方案 | 体积 | 离线 | 中文音色 | 音质 | 建议 |
|---|---|---|---|---|---|
| **A. edge-tts**（pip 预烤） | ~1MB | 否（走微软免费接口） | 几十个（晓晓/云希/晓伊，含多情感） | 很好 | **默认程序兜底** |
| **B. 系统语音**（Windows SAPI / macOS say） | 0 | 是 | 取决于系统装了啥（中文 Win 自带 Huihui） | 一般 | 离线兜底 |
| **C. sherpa-onnx + VITS 模型** | 60~120MB/音色 | 是 | 需挑模型，多数是单人 | 中等 | **可选语音包，按需下载** |

推荐组合：**A 默认 → B 离线兜底 → C 做成「语音包」可选下载**。

理由：项目已有 lite / full 两套打包配置（`apps/desktop/electron-builder.lite.yml` / `.full.yml`），正好承载 —— full 版内置 1~2 个中文语音包，lite 版首次使用时提示下载，避免主安装包膨胀。

接入方式与 Python 依赖一致：`scripts/build-python-runtime.mjs:125-137` 的 `DEPS` 数组加 `edge-tts`，走 `--force` 或指纹变化自动增量预烤。**注意**：新增依赖后本地重包必须带 `--force`，否则指纹一致会跳过安装。

### 4.4 短剧场景的关键设计：角色音色表

TTS 单独用只是「朗读」，短剧要的是「多角色分工配音」。做法：

1. 分镜 skill 的**设定集**（`00-设定集.md`）里增加「角色音色」字段：`角色 / 音色 id / 语速 / 音调 / 备注`
2. 分镜表的「台词或旁白」列已标明说话人（现有格式含此信息）
3. 配音工具接受 `dialogue: [{ role, text }]`，按 `voices[role]` 批量合成，输出多个音频 + 一个时间轴清单
4. 长文本按标点切句分段合成再合并（单次请求有长度上限）

这样「配音」从一次 API 调用变成一条流水线工序，且完全自动化。

## 5. 模块三：剪辑 / 合成

### 5.1 先明确一个判断

**短剧不需要 NLE（时间轴剪辑器）。** 拖时间轴、逐帧调是 CapCut / 剪映的活，在对话式产品里 ROI 极低，且做不过它们。

需要的是**合成器（composer）**：按分镜表**自动**拼装成片。因为——

> 分镜表里每镜都写了 `时长(s)`、`台词`、`BGM`、`转场`、`音效`。**时间轴是已知的，不需要人工剪。**

这是整个方案里最省力的一点：剪辑退化成一次纯计算 + 一次 ffmpeg 执行。

### 5.2 基础设施：随包 ffmpeg

- 载体：npm 的 `ffmpeg-static`（约 70MB，win/mac/linux 三平台齐全）
- 落点：`apps/desktop/resources/ffmpeg/`
- 解析：仿 `packages/core/src/tool/builtin/python-runtime.ts` 写 `ffmpeg-runtime.ts`
  - `getBundledFfmpegPath()` 读 `process.resourcesPath`
  - 缺失时回退系统 PATH 的 `ffmpeg`
  - 都没有 → 明确报错并给出安装指引（不静默）
- 打包：**三份 electron-builder yml 都要加 extraResources**（`.lite.yml` / `.full.yml` / `.mac.yml`）—— 这是本项目踩过的坑，加文件必须三处同步

### 5.3 新增工具 `media_compose`

一次调用执行一串操作（参数化，不做 UI 编辑器）：

```jsonc
{
  "ops": [
    { "op": "concat", "inputs": ["shot-01.mp4", "shot-02.mp4"], "transition": "fade", "fadeMs": 300 },
    { "op": "scale_pad", "width": 1080, "height": 1920 },
    { "op": "attach_audio", "video": "...", "audio": "voice-01.mp3", "mode": "replace" },
    { "op": "mix_bgm", "bgm": "bgm.mp3", "volume": 0.25, "ducking": true },
    { "op": "subtitle", "srt": "ep01.srt", "burn": true, "fontSize": 42 },
    { "op": "export", "out": "第一集-成片.mp4", "crf": 20, "fps": 24 }
  ]
}
```

各 op 映射到 ffmpeg：

| op | ffmpeg 手法 |
|---|---|
| `concat` | `-f concat -safe 0 -i list.txt -c copy`（同源同参可直接 copy，快） |
| `transition` | 需 `xfade` filter，转为重编码路径 |
| `attach_audio` | `-i video -i audio -c:v copy -map 0:v -map 1:a -shortest` |
| `mix_bgm` | `amix` / `sidechaincompress`（ducking 用旁链压缩，人说话时自动压低 BGM） |
| `subtitle` | `-vf subtitles=xx.srt:force_style=...`（烧字幕）；不烧则走 `-c:s mov_text` 软字幕 |
| `export` | `-c:v libx264 -crf -preset medium -pix_fmt yuv420p -movflags +faststart` |

### 5.4 字幕与音轨对齐：白送

分镜表已有每镜时长 + 台词，所以：

```
起始时间 = 前面所有镜头时长之和（含转场重叠扣减）
结束时间 = 起始 + 本镜时长
```

→ 直接生成标准 SRT，零 ASR 成本、零人工对齐。BGM 长度不足则 `-stream_loop -1` 循环。

### 5.5 交付

成片落 `deliverables/`，`conversation_file` 登记为 `video/mp4`，前端走已有交付卡片。**不新增任何按钮**（内部能力，符合项目既有约束）。

## 6. 短剧流水线编排

工作流引擎现成可用，缺的是「模板 + 接线」。

### 6.1 目标 DAG

```
input(题材 / 小说文件)
  └→ sub_agent(动漫脚本分镜助手)         → 设定集 + 分集大纲 + 分镜表 + 提示词
      └→ code(解析分镜 CSV)              → 每镜 { 序号, 时长, 提示词, 台词, 角色 }
          └→ loop(逐镜)
              ├→ tool(api_image_generate)     出首帧图
              └→ tool(api_video_generate)     图生视频（不可用则降级文生视频）
          └→ tool(api_tts_speak)             按角色批量配音
              └→ code(生成 SRT + 音轨时间轴)
                  └→ tool(media_compose)     拼接 + 混音 + 烧字幕
                      └→ output(成片 mp4)    交付登记
```

### 6.2 必须补的接线

在 `apps/server/src/workflow-runner.ts:402` 之前加一个分支：

```ts
if (toolSource === 'api') {
  const result = await executeApiTool(toolName, args, userId, undefined, undefined, conversationId);
  return { output: result };
}
```

约 5 行，低风险。改完必须重编 dist（`tsc -p tsconfig.json && node scripts/fix-esm-extensions.cjs`），否则跑的是旧逻辑。

### 6.3 顺手把分镜助手升级成端到端

现在 `storyboardAgent` 只产出文字。补两处：

1. `STORYBOARD_AGENT_BUILTIN_TOOLS`（`db.ts:1271`）加入三个媒体工具 + TTS + 合成工具
2. `SKILL_BODY_REFRESH_IDS`（`db.ts:2336`）—— 若改了 `skill_anime_storyboard` 的 body，**必须把 id 加进这个白名单**，否则库里旧 body 不会被刷新（本项目的已知坑）

这样分镜助手会从「脚本助手」变成「导演」，能一路到成片。

## 8. 分阶段落地

### P0 —— 纯接线 + 无新依赖（可立刻验证）— **已实施（2026-09-17）**

1. ✅ 媒体三工具挂载到默认助手 + 分镜助手（`db.ts` 两个挂载数组；种子分支每次启动同步 `builtin_tool_ids`，老库直接生效，无需迁移）
2. ✅ `api_tts_speak`：**双层引擎，与原设计有偏离** ——
   - 模型层：OpenAI 兼容 `POST /v1/audio/speech`（传 `model`/`platformId` 点名，或库里有 audio 型模型时自动尝试）
   - 程序层兜底：**系统语音（Windows SAPI / macOS say）而非 edge-tts**。偏离理由：edge-tts 依赖微软在线服务，断网即挂且要动 Python 打包；系统语音零依赖、离线可用，「有产出且标注来源」优先。edge-tts 语音质量更好，留作后续可选接入

**顺带修复的两个既有缺陷（都在 `services/media-fetch` 的代理隧道，通用收益 —— 图/视频/ffmpeg 下载同一条入口）**

1. **不跟随 3xx 重定向**：原先只在 200 时取 body。而 gyan.dev / GitHub releases / evermeet 等下载源普遍先回 303/302 → 表现为「下载失败 HTTP 303」。已加重定向跟随（限 5 跳，支持相对 Location）。
2. **CONNECT 响应头之后的字节被丢弃**：响应头与 **TLS ServerHello 常在同一 TCP 包到达**，丢掉剩余字节 = 丢 TLS 握手数据 → **小文件偶尔能过、大文件必然 ECONNRESET**。已提取纯函数 `splitConnectResponse()` 统一处理（Buffer 累积 + `socket.unshift(leftover)`），并加 6 例单测钉住。

> **定位教训**：114MB 经代理跑 20 分钟 ECONNRESET，而 `curl -x` 同源 3m22s 下完 106MB → **一对照就知道是自家实现的问题，不是网络**。别急着归因网络环境。

**下载稳健性**：`installFfmpeg` 带 3 次重试（大文件经隧道瞬时断连是常态）。**不做断点续传**（需服务端 Range 支持且实现复杂）—— 靠重试覆盖瞬时故障，持续不可用时明确报错而非无限重试。

配套：`generated-files` 产物目录 + `/api/generated/files/...`；SRT 显式 UTF-8（Windows 默认编码会导致中文乱码）；`MEDIA_TOOLS` / `guessMime` 纳入新工具（`.srt → application/x-subrip`）。

## 十、智能体流程优化：动漫分镜助手 → AI 短剧导演（2026-09-17）

### 问题诊断

媒体工具挂载后存在一个**静默断链**：工具在 `builtin_tool_ids` 里，但**提示词零提及** → LLM 不知道要调，

### 决策：改造而非新建

链路重叠 ~70%（取材/设定/分集/分镜/提示词完全一致），新建会有大量重复维护；
且「短剧」本就是「分镜」的天然延伸。故原地升级为**策划 + 生产两段式**。

### 改造内容

| 项 | 改动 |
|---|---|
| 人设 | 「动漫脚本分镜助手」→「**AI 短剧导演**」，明确**两段职责** |

### 生产段的三个关键设计

1. **默认不做，做了要先讲代价**：必须 `confirm_user` 说明「每镜出图/配音都是真实 API 调用、按镜数线性增长」。
   一集 30 镜 = 30 次生图 + 30 次配音 —— 不让 LLM 闷头烧额度。
2. **先做 1 镜试片**：跑通「图 → 配音 → 合成」全链路给用户看，样式不对就重跑这一镜，
   **不要**先把 30 镜跑完再发现风格错。
3. **不撞注定失败的路**：`api_video_generate` 上游只开放文生视频，图生视频参数会被拒 ——
   提示词明确要求「被拒就告知上游限制并改为交付图+配音+字幕」，而不是反复重试。

### ️ 踩坑：提示词是模板字符串，正文不能有反引号

在提示词里写工具示例时用了 `` `api_image_generate` `` 这种反引号包裹 —— 而提示词本身就是反引号模板字符串，

```
      → 系统语音（离线兜底，3 个中文音色）
```

engine 字段如实回传：model / local / edge / winrt / sapi / say。
**任何一层失败都不会导致没声音** —— 逐层降级是硬性要求。

### 角色 → 说话人映射
⚠️ **aishell3 的 174 个说话人无官方性别/年龄标注**（编号形如 SSB0005）。
因此 AISHELL3_ROLE_MAP 是**「可区分性优先」的默认值，不是声学结论**：
按常见角色给分散编号，保证不同角色拿到不同声音；用户可用 voice: "local:88" 覆盖。
表外角色用**名字散列**分配（同角色恒定同编号，避免声音忽变）。

### 关键实现点（踩坑）
1. **原生二进制不在 npm 包里**：sherpa-onnx-node 只是 JS 包装（0.1MB），真二进制在同名平台包
   sherpa-onnx-win-x64（win32 上游刻意改名成 win 避 spam 过滤）。故引擎也**按需下载**
   （与 ffmpeg 同策略）——在 Windows 上无法准备 mac/linux 构建。
2. **resolveSherpaLib 与 localSpeak 的定位必须一致**：曾出现「状态显示可用、合成报 Cannot find module」
   —— 前者支持按需下载位/手动目录，后者却按**包名** require。已统一到 loadSherpaModule()。
3. **模块不许依赖 db**：tts-packs.ts 初版从 ../db.js 取 dataDir → 把 better-sqlite3 拖进来，
   裸跑直接崩（ABI 不匹配）。改为只读 DATA_DIR 环境变量（与 ffmpeg-runtime 同一个教训，**又犯了一次**）。
4. **阿拉伯数字会被 lexicon 当 OOV 忽略**（实测日志 OOV 0. Ignore it!）→ 加 normalizeForTts() 转汉字。

### 网络容错（重要）
实测 GitHub Releases **时通时不通**（有整段时间直连超时 + 代理 TLS 失败，而 npm 镜像 287ms 正常）。
应对：**多源候选 + 重试**（4 个加速镜像 → 官方源），全部失败时**明确告知手动放置目录**：
<dataDir>/tts-models/manual/<id>，用户可自行下载解压，系统会识别（isInstalled / installedDir 双路径探测）。

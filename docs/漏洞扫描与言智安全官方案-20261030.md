## 一、结论先行

**不新造一个扫描器，造一个扫描编排层。**

现有安全模式已经有 56 个工具 / 60 余条命令，URL 扫描能力（recon / webprobe / crawl / dirsearch / poc_scan / verify_xss / headers / tls / baseline / nuclei）其实**已经齐了**。真正缺的是四件事：

| 缺口 | 现状 | 影响 |
|---|---|---|
| 没有统一「扫描作业」 | 要人记住十几条命令、按顺序拼 | 普通用户根本跑不起来完整扫描 |
| 源码审计太浅 | `sast.ts` 只有 10 条正则，无依赖审计、无 Electron 配置检查、无基线抑制 | 只能发现最表面的问题，报告没法长期用 |
| 安装包扫描完全没有 | 无 APK / asar / EXE 解析 | 「上线前体检」这条线是断的 |
| 没有「看自家」的智能体 | 安全助手面向外部授权目标 | 扫言智自己的 app 反而最别扭（要登记 scope、却不知道自家资产在哪） |

对应方案四件事：

1. **一个 `scan` 工具 + 四个命令**（`/scan-source` `/scan-url` `/scan-package` `/scan-self`），背后是统一的 `ScanJob` 作业模型与扫描剖面（profile）。
2. **源码扫描升级为三层**：L0 规则包（零依赖）/ L1 结构化解析与依赖审计 / L2 LLM 语义审计（由智能体承接）。
3. **安装包扫描新增**：APK / AAB / IPA / asar / EXE-MS I，零依赖优先，检测到 apktool / jadx 自动增强。
4. **新增内置智能体「言智安全官」**：只扫自有资产（言智源码仓库、本机运行的言智 Web/Electron、构建产物），默认不需要人工登记 scope，但审计、黑名单、审批一个不少。

## 四、架构

```
/scan-source ┐
/scan-url    ├─→ scan 工具 ─→ ScanOrchestrator ─→ ScannerRegistry
/scan-package┤                                  ├─ source  (sast 升级)
/scan-self   ┘                                  ├─ url     (编排既有工具，不重复实现)
                                                └─ package (新建)
                                                         │
                                         Finding 归一 + fingerprint + baseline 抑制
                                                         │
                                     finding_status 状态机 → sec_report(MD/HTML/SARIF)
                                                         │
                                              前端运行卡 / 扫描面板（SSE 进度）
```

### 4.1 ScanJob 模型

```ts
interface ScanJob {
  id: string;
  kind: 'source' | 'url' | 'package' | 'self';
  target: string;              // 目录 / URL / 文件 / self 资产 id
  profile: string;             // quick | standard | deep | api
  status: 'queued' | 'running' | 'done' | 'failed' | 'canceled';
  stages: ScanStage[];         // 每个阶段：name / status / startedAt / durationMs / count
  findings: Finding[];         // 复用现有 Finding 类型
  artifacts: { path: string; kind: string }[];  // 报告、解包目录、原始输出
  baselineId?: string;         // 抑制基线
  createdAt: number;
  createdBy: 'human' | 'agent';
}
```

- 作业落 `plugin_storage`，重启后可查（与 `expstore` 同套存储习惯）。
- 进度复用现有 SSE 协议，事件粒度：`stage:start` / `stage:progress` / `stage:done` / `scan:done`。
- 每个作业有硬上限：`maxFiles` / `maxBytes` / `maxDurationMs` / `maxFindings`，超限截断并在报告里写明。

### 4.2 剖面（profile）

| 剖面 | 内容 | 风险级 | 典型耗时 |
|---|---|---|---|
| `quick` | 仅被动项：recon / headers / tls / baseline / poc_scan（源码：规则包） | passive~active | 秒级 |
| `standard` | quick + 爬虫 / JS 接口 / 目录 / WAF / 依赖 | active | 分钟级 |
| `deep` | standard + XSS 反射验证 +（交战模式）SQLi/SSRF + OAST | 含 intrusive | 十分钟级 |
| `api` | 读 OpenAPI / 抓包记录 → 端点枚举 → 鉴权矩阵（只读 GET 优先） | active | 分钟级 |

`deep` 里的侵入级步骤**必须**走既有闸门：交战模式 + `confirm_user` + ExecutionGate，编排层不得绕过。

### 4.3 Scanner 接口

```ts
interface Scanner {
  id: string;                       // 'source-rules' | 'package-apk' ...
  kinds: ScanJob['kind'][];
  stages: string[];                 // 供进度展示
  run(ctx: ScanContext): Promise<Finding[]>;
}
```

新增能力 = 注册一个 Scanner + 一条命令，**控制台界面零改动**（沿用现有设计原则）。

## 五、三个引擎

### 5.1 源码扫描（升级）

**文件布局**

```
sec-lab-tools/scan/source/
  engine.ts        # 遍历 + 规则调度 + 结果归一
  rules/
    secrets.ts     # 硬编码凭据（含高熵字符串、私钥块、云 key）
    injection.ts   # SQL / 命令 / 模板 / 反序列化
    web.ts         # XSS / 路径遍历 / SSRF / CORS / 开放重定向
    crypto.ts      # 弱哈希 / 弱随机 / 关闭证书校验
    electron.ts    # nodeIntegration / contextIsolation / webSecurity / 未校验 IPC
    config.ts      # 调试路由 / 默认口令 / 目录列表 / 上传限制
  deps.ts          # package.json + pnpm-lock 解析；可选 npm audit
  baseline.ts      # fingerprint 生成与抑制
```

**规则升级要点**

- 规则从「单行正则」升级为「规则包 + 上下文窗口」：`secrets` 需要看前一行的赋值、`injection` 需要看 sink 附近的变量来源。
- 新增**高熵字符串**检测（Shannon 熵 ≥ 4.5 且长度 ≥ 20），弥补固定 key 名的漏报。
- 新增**依赖审计**：解析 `pnpm-lock.yaml` / `package-lock.json`，与内置的「已知高危包-版本区间」快照比对；可选调用 `npm audit --json`（明确标注需要联网，默认关闭）。
- 新增 **Electron 配置审计**（言智自身最关键的一类问题）：
  - `nodeIntegration: true`
  - `contextIsolation: false`
  - `webSecurity: false`
  - 未设置 CSP / CSP 含 `unsafe-eval`
  - `preload` 暴露过宽（`ipcRenderer` 整体透传）
  - `setPermissionRequestHandler` 缺失
- **fingerprint 与基线抑制**：`fingerprint = hash(ruleId + 相对路径 + 规范化行内容)`。`/scan-baseline accept <jobId>` 后，下次只报**新增**问题。这是让扫描能进日常流程的关键。
- **默认排除**：`node_modules` / `.git` / `dist` / `build` / `release` / `coverage` / `vendor` / `android/**/build`；`.env` 单独规则（只报键名，不回显值）。

**与现有 `/code-scan` 的关系**：保留 `sast` 工具与命令（向后兼容），新引擎作为 `source` Scanner 接入，规则为其超集。

### 5.2 URL 扫描（编排，不重写）

不新增探测实现，只把既有工具编排成剖面，并统一结果：

| 阶段 | 复用工具 | 备注 |
|---|---|---|
| 授权核对 | `scope_list` / `scope_add` | 目标必须先登记；未登记直接终止 |
| 画像 | `recon` | 被动，DNS/TLS/头/子域 |
| 基线 | `headers_audit` / `tls_audit` / `baseline_scan` | 只读 |
| 内容面 | `crawl` / `js_endpoint` / `dirsearch` / `waf_detect` | active |
| 模板 POC | `poc_scan` / `nuclei`（外部） | active |
| 验证 | `verify_xss`（active）/ `verify_sqli`·`verify_ssrf`（intrusive） | intr 需交战模式 |
| 情报 | `cve_intel` / `attack_map` | 收尾映射 |

**新增一块：接口鉴权矩阵（`api` 剖面）**
- 输入：OpenAPI/Swagger、HAR、或 `/proxy` 已有的抓包记录。
- 做三件事：① 同族端点横向对比（`/api/user/1` vs `/api/user/2`）判断 IDOR 嫌疑；② 去掉鉴权头重放，看是否返回同等数据（**只做 GET/HEAD**，写操作一律不试）；③ 记录每个端点的鉴权结论，输出矩阵。
- 风险级 active；写操作探测列为 intrusive 且默认关闭。

> 落地记录（2026-10-30，`sec-lab-tools/scan/api/`）：
> 三路枚举（`--input` 的 OpenAPI/HAR、代理内存抓包、目标上的 OpenAPI 文档探测，仅 JSON），
> 端点只收目标 host；矩阵三列（匿名 / 普通 / 管理员），未提供凭证的列记 `—` 而不是猜；
> 写方法只进矩阵标 `not_tested_write`，不发请求；IDOR 优先用同族端点横向对比，
> 没有同族才做 ID 替换（数字 1↔2 / UUID 改末位），只给「疑似」结论。
> 凭证作为工具参数 `auth` / `adminAuth` 传入，**不落作业、不回显**，审计 `argsSummary` 按键打码
> （`redact.maskSensitiveArgs`）。测试：`scan-url` / `scan-api-matrix` / `scan-export` / `scan-self`。

### 5.3 安装包扫描（新建，重点）

**支持格式**

| 格式 | 解析方式 | 覆盖 |
|---|---|---|
| `.apk` / `.aab` | ZIP 解包 + aapt2（本机 SDK）+ DEX 字符串 + 资源 | 清单 / 权限 / 导出组件 / 明文流量 / 密钥 / 签名 |
| `.ipa` | ZIP + `Info.plist` + 二进制字符串 | ATS 配置 / 权限声明 / 硬编码域名与密钥（不做反编译） |
| `.asar` / Electron 产物 | asar 头解析 + 内置 JS 走源码规则 | 打包后的 JS / 硬编码密钥 / 调试开关 |
| `.exe` / `.msi` | 提取内嵌 asar + Authenticode 签名校验 | 签名主体 / 是否未签名 / 打包内容 |
| `.zip` / `.tar.gz` | ZIP 解包后按内容识别 | 通用兜底 |

**三层降级**

- **L0 零依赖（默认）**
  - ZIP 用已有依赖 `adm-zip`；解包前做 zip-slip / zip-bomb 防护。
  - APK 清单：优先 `aapt2 dump xmltree`（本机 Android SDK 已有，见文末风险）；没有则用内置 AXML 解析器兜底（P3.5 视情况）。
  - DEX：自研纯 JS **字符串池解析器**（DEX 头 → string_ids → 字符串表），抽取类名、URL、密钥、加密算法特征，不做指令级反编译。
  - 签名：`apksigner verify`（SDK 自带）；检测 debug 证书。
- **L1 外部工具增强**：检测到 `apktool` / `jadx` 才用，未装给出安装建议，不自动下载（与 `toolchain` 策略一致）。
- **L2 LLM 语义审计**：对反编译出的关键类（登录、支付、网络层、WebView、密钥管理）做复核，成本可控地抽样。

**APK 检查项（首批）**

| 类别 | 检查项 | 严重度参考 |
|---|---|---|
| 清单 | `android:debuggable="true"` | high |
| 清单 | `android:allowBackup="true"` | medium |
| 清单 | `usesCleartextTraffic="true"` / 无 network-security-config | high |
| 组件 | 导出组件（`exported=true`）且无权限保护 | high |
| 组件 | 导出 Activity 缺 `intent-filter` 校验 | medium |
| 权限 | 危险权限（短信、定位、通讯录、悬浮窗）清单与用途 | info~medium |
| 签名 | 未签名 / debug 签名 / v1-only | high |
| 密钥 | DEX / 资源里的云 key、私钥块、JWT 密钥 | high |
| 网络 | 明文 http 端点、可疑第三方域名 | medium |
| WebView | `setJavaScriptEnabled(true)` + `addJavascriptInterface` | high |
| 存储 | 明文写入外部存储 / SharedPreferences 存 token | medium |
| 组件 | 硬编码 IP / 测试环境地址 | low~medium |
| 依赖 | 已知高危 SDK 版本特征（如旧版 OkHttp/WebView 封装） | medium |

**安全边界（硬性）**
- 解包到系统临时目录下的独立目录，**不执行包内任何代码**、不安装、不启动。
- zip-slip：条目路径解析后必须仍在解包根内；zip-bomb：压缩比 > 200 或解压总量 > 上限即中止。
- 产物（解包目录、原始输出）作业结束后按配置清理；报告只留证据摘要。
- 所有解包内容视为**不可信数据**，不进入提示词原文，只把结构化结果交给模型。

## 六、言智安全官（新内置智能体）

### 6.1 定位

- id：`a_builtin_yanzhi_sec_officer`，名称「言智安全官」
- 只做**自有资产**：言智源码仓库、本机运行的言智 Web/Electron、构建产物（APK / EXE / asar）
- 与「安全助手」的分工：
  - 安全助手：外部授权目标（域名/IP/网段），必须先登记 scope。
  - 安全官：自家资产，默认放行，但仍然受黑名单、审批、审计约束；**对外部目标一律拒绝并转交安全助手**。

### 6.2 自有资产模型（关键设计）

`guard` 目前只认 `domain/ip/cidr`，本地路径走白名单。新增一个 `self` 目标类型：

```ts
interface SelfAsset {
  id: string;
  kind: 'repo' | 'build' | 'runtime';
  value: string;        // 仓库根路径 / 产物路径 / localhost origin
  discoveredBy: 'auto' | 'manual';
}
```

自动发现来源：
- 仓库根：从 `package.json` + `pnpm-workspace.yaml` 向上定位
- 构建产物：`dist/`、`release/`、`android/**/build/outputs/**`、`*.asar`
- 运行时：本机 server 默认端口（3001）、Vite dev 端口、Electron 本地服务

**不可伪造**：`self` 判定在服务端根据 target 计算，**不接受调用方传 `self: true`**。外部 URL / 任意外部路径永远匹配不上自有资产，模型无法借这个口子越权。

### 6.3 工具面与子体

主智能体工具（精简，只做编排）：

```
plugin_sec-lab__scan            # 统一扫描入口
plugin_sec-lab__self_assets     # 列出/刷新自有资产
plugin_sec-lab__sec_report      # 报告
plugin_sec-lab__finding_status  # 状态机
plugin_sec-lab__sec_skill       # 技能参考
call_agent / list_sub_agents / task_plan / task_step / ask_user / confirm_user
```

三个子体（各挂最小工具面，延续现有子体纪律）：

| 子体 | 职责 | 工具 |
|---|---|---|
| 源码审计子体 | 规则扫描 + 依赖 + Electron 配置 | `scan`(source) / `sast` / `sec_report` |
| 运行时审计子体 | 本机 URL、CSP、渲染进程配置、IPC 面 | `scan`(url/self) / `recon` / `headers_audit` / `browser_*`（只读） |
| 制品审计子体 | APK / asar / EXE | `scan`(package) / `sec_report` |

### 6.4 输出

- 「言智安全体检报告」模板：执行摘要 → 按资产分类（源码 / 运行时 / 制品）→ 严重度分布 → 合规映射（等保 2.0 三级 / OWASP Top 10 2021 子集）→ 修复清单（按文件:行号 / 清单属性 / 端点）→ 复测项。
- `/watch` 定时体检：目标是自有资产（仓库路径 / 本机固定端口）时按 interval 跑 `scan_self`，
  增量复用编排层指纹基线（每轮 `upsertBaseline` 滚动），只报新增；其他目标仍做端口/子域 diff。
- 结果默认脱敏（token / 密钥只留前后 4 位）。

> 落地记录（2026-10-31，`sec-lab-tools/scan/self/report.ts`）：
> 体检模板已实现并接入导出链路——`buildReportExport` 遇 `job.kind === 'self'` 自动切换，
> 控制台「导出本次扫描」零改动即得体检报告（文件名 `self-health-report-*.md`）。
> 分类按 ruleId：源码规则/依赖 → 「源码」、`self-electron-*` → 「Electron 配置」、
> `self-runtime-*` → 「运行时」；package/url 作业退化为单分类报告。结论三分支
> （高危→优先处理 / 仅中危→排期 / 空→健康），基线抑制项不进正文但在复测项说明；
> 出口再过一遍 `maskSecrets`（输出层脱敏硬约束）。测试：`scan-self-report` 10 例。

> 落地记录（2026-10-31，`sec-lab-tools/watch.ts` + `sec-lab.ts`）：
> `/watch` 已接入自有资产体检。`/watch start <仓库路径|本机固定端口>` 由服务端 `matchSelfAsset`
> 判定为自有资产后，每轮跑 `scan_self`（kind='self'）；`runScan` 自动用 `activeBaseline`
> 抑制老指纹，watch 只把未抑制项写入 onFindings 与审计，轮末用 `upsertBaseline` 滚动基线，
> 保证同一问题只报一次、已修复项不复活（首轮无基线时只建立基线、报 0 条新增，
> 避免一开巡检就刷出全量老问题；需要全量结果用 `/scan-self`）。
> `list` 显示上次体检摘要（新增 X / 共 Y）与下次时间；其他目标仍走 recon+portscan 端口/子域 diff。
> **重启语义（硬约束）**：定时器在进程内，应用重启后巡检列表清空，需重新 `/watch start <target>`
> 恢复；体检基线落在 plugin_storage，恢复后老问题不会重报。输出统一经 `jobToOutput` + `maskSecrets`
> 脱敏。测试：`sec-lab-watch-self` 5 例（滚动基线增量 / list 摘要 / tick 只报新增 / 重启提示）。

> 落地记录（2026-10-31，`scan/compliance.ts`）：
> 体检报告新增「合规映射」段：按 ruleId 对照等保 2.0 三级（GB/T 22239-2019 8.1.4.x：
> 身份鉴别 / 访问控制 / 入侵防范 / 数据完整性 / 数据保密性）与 OWASP Top 10 2021 子集，
> 按「标准 → 控制项 → 命中规则/条数」聚合，一条发现可对应多个控制项。

> 安装包 `-asset` 资源命中按主规则映射；未登记规则在报告里显式列为「未映射规则」，不静默略过。
> 映射是启发式对照，报告内注明不替代测评机构结论。测试：`scan-compliance` 5 例 + 报告新增 1 例。

## 七、护栏与合规（不能松）

| 项 | 设计 |
|---|---|
| 新工具风险分级 | `scan` 按 kind 映射：source/package → passive；url/self → 继承子步骤最高风险 |
| 无目标白名单 | `scan` 在 kind=source/package 时进 `NO_TARGET_TOOLS`；kind=url 时仍走 scope |
| 自有资产 | `self` 目标服务端计算，不可由参数伪造 |
| 人工闸门 | `deep` 剖面里的 intrusive 步骤继续走 `engagementMode` + `confirm_user` + ExecutionGate |
| 解包安全 | zip-slip / zip-bomb / 条目数 / 总大小四道上限；不执行、不安装 |
| 审计 | 每次扫描记：谁发起、kind、目标、剖面、耗时、findings 数、是否被护栏拒绝 |
| 报告脱敏 | 沿用 `redactReport`，密钥/token/内网 IP 打码 |
| 外部工具 | 只跑 `TOOLCHAIN` 白名单（新增 `apktool` / `jadx` / `apksigner` / `aapt2` 条目），参数数组化，不经 shell |

## 九、方案对比（为什么这么选）

### 9.1 自研轻量 vs 引入成熟扫描器

| 方案 | 好处 | 坏处 |
|---|---|---|
| **自研 + 外部工具可插拔（推荐）** | 与现有 Finding/报告/护栏/审计完全统一；零部署；可控误报；能扫自家 Electron/言智特有面 | 深度不如专职工具；规则要自己维护 |
| 引入 MobSF（APK 动态） | APK/动态分析最全 | Python + Django 重依赖；报告与现有体系割裂；动态分析要起模拟器 |
| 引入 semgrep | AST 规则强、社区规则多 | Python 运行时；规则语法另一套；结果要二次归一 |
| 引入 gitleaks | 密钥扫描强，单二进制 | 只覆盖密钥一类，仍需自研其余 |

**结论**：默认自研，`toolchain.ts` 里把 semgrep / gitleaks / apktool / jadx 加成可选增强项，谁装了谁生效，不强制。

### 9.2 编排层 vs 每类一个独立扫描器

| 方案 | 好处 | 坏处 |
|---|---|---|
| **统一编排（推荐）** | 一次点击跑完整剖面；结果可去重、可比对、可抑制；前端只认一种作业 | 编排层要处理阶段失败与超时 |
| 每类独立 | 实现简单 | 报告碎片化；用户要自己拼；无法做基线抑制 |

### 9.3 安全官独立智能体 vs 安全助手加技能

| 方案 | 好处 | 坏处 |
|---|---|---|
| **独立智能体（推荐）** | 职责清晰；默认自有资产、不逼用户登记 scope；提示词可专注 | 多一个内置智能体要维护 |
| 安全助手加技能 | 改动最小 | 外部目标与自家资产的纪律冲突，提示词会互相打架 |

## 十、分期与验收

### P1：扫描作业模型 + 源码扫描升级 + 安全官（只做源码）

- `scan` 工具、`ScanJob`、ScannerRegistry、剖面定义
- `source` 引擎：规则包、熵检测、Electron 配置、依赖清单、fingerprint 基线
- 命令：`/scan-source`、`/scan-status`、`/scan-report`、`/scan-baseline`
- 言智安全官主智能体 + 源码审计子体 + `skill_sec_source_audit` / `skill_sec_self_app_audit`
- 自有资产自动发现（repo 一类）
- 验收：
  - 对本仓库跑 `/scan-source` 30 秒内完成，产出 SARIF 且通过 schema 校验
  - 同一仓库连跑两次，fingerprint 一致、结果一致
  - 接受基线后，第二次只报新增
  - 安全官能自主跑完，不需要人工登记 scope

### P2：URL 扫描剖面 + API 鉴权矩阵

- `url` 引擎：quick/standard/deep 编排既有工具
- `api` 剖面：OpenAPI/HAR/抓包记录 → 端点 → 鉴权矩阵（只读）
- 命令：`/scan-url`
- 验收：
  - 对靶场（dvwa）跑 `standard`，findings 全部进 finding_status
  - `deep` 在未开交战模式时**拒绝** intrusive 步骤并说明原因
  - 未登记 scope 的目标被拒，审计有记录

### P3：安装包扫描

- `package` 引擎：ZIP 安全解包、APK（aapt2 + DEX 字符串 + 资源 + 签名）、asar、EXE 签名
- 外部工具增强：apktool / jadx（检测到才用）
- 命令：`/scan-package`
- 制品审计子体 + `skill_sec_package_audit`
- 验收：
  - 对自构建 APK 扫出清单项（debuggable / cleartext / 导出组件 / 签名）
  - zip-slip 与 zip-bomb 用例被拦截且有测试
  - 解包目录在作业结束后被清理
  - 未安装 apktool 时走 L0 不报错，提示增强项

### P4：安全官扩容 + 巡检 + 报告模板

- 运行时审计子体（本机 URL / CSP / Electron 渲染进程 / IPC 面）
- 自有资产覆盖 build + runtime
- `/scan-self` 一键体检 + `/watch` 定时巡检
- 「言智安全体检报告」模板 + 合规映射（等保/O WASP 子集）
- 验收：
  - `/scan-self` 能一次覆盖源码 + 运行时 + 制品
  - 巡检重启后可手动恢复，文档写明限制
  - 报告可与 `sec_report` 的 MD/HTML/SARIF 三种格式互通

> 落地记录（2026-10-30，`sec-lab-tools/scan/self/`）：
> `scan_self` 改走 `kind='self'` 的独立引擎——路径资产 = 源码规则 + Electron 结构审计
> （`webPreferences` 的 nodeIntegration/contextIsolation/webSecurity、主窗口 CSP、权限处理器、
> webview 钩子），本机 3001/5173/3000 有服务在听时再补只读运行时探测（CORS 回源、
> 本地接口匿名可读）；URL 资产只跑运行时探测。CSP 不做响应头判定——Electron 的 CSP 由主进程
> 注入，查 HTTP 头只会稳定假阳性。体检报告模板已于 2026-10-31 补齐（见 6.4 落地记录）；
> `/watch` 定时巡检已于 2026-10-31 接入（自有资产跑体检、指纹基线只报新增、重启需重新 start，见 6.4 落地记录）；
> 合规映射（等保 / OWASP 子集）亦已落地（`scan/compliance.ts`，见 6.4 落地记录）。

**工作量粗估**：P1 3–4 人日，P2 2–3 人日，P3 4–5 人日，P4 2–3 人日。可并行的是 P2 与 P3。

## 十一、风险与未决

| 风险 | 说明 | 缓解 |
|---|---|---|
| aapt2 依赖 | 依赖本机 Android SDK；不同机器版本不一 | 探测 `ANDROID_HOME` + 常见路径；缺失降级到内置 AXML 解析，并在结果里标注「清单解析为降级模式」 |
| DEX 解析深度 | 只做字符串池，不做指令级反编译 | 明确写成「线索发现」而非「确认漏洞」；深度靠 jadx L1 |
| 误报 | 规则扫描天然有误报 | fingerprint 基线 + `finding_status` 人工确认 + 报告只列 confirmed |
| LLM 成本 | L2 语义审计按文件抽样可能很贵 | 抽样上限（默认每类 ≤ 20 个文件）、只送关键片段 |
| iOS / EXE | Windows 上无法完整分析 | 明确为「有限检查」，报告里写清能力边界 |
| 扫描他人资产 | 安全官可能被引导去扫外部目标 | 服务端 self 匹配 + 外部目标硬拒 + 审计 |
| 解包磁盘占用 | 大 APK 解包可能几百 MB | 总量上限 + 作业结束清理 + 可配置临时目录 |

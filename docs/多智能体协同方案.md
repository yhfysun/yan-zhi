# 多智能体协同优化方案（小说视频推文长任务场景）

> 2026-10-08 立项方案 · 只做设计，未动代码 · 确认后实施

## 一、目标场景

小说视频推文类长任务，主智能体负责规划，子智能体负责执行：

```
主智能体（规划者）
 ├─ T1 获取章节全文        → pageAgent（≤10 步约束）→ 产出文件，只回「路径+描述」
 ├─ T2 写文件/字幕分词     → 文案智能体（依赖 T1 的产物路径）
 ├─ T3 视频下载            → 下载智能体（无依赖，与 T1 并行）
 ├─ T4 音频生成            → TTS 智能体（依赖 T2 字幕或独立文案）
 └─ T5 合成                → 依赖 T3+T4
```

核心诉求：
1. 主智能体动态规划 DAG，无依赖任务**异步并行**
2. 大数据产物**只传路径+描述**，不回流主智能体上下文
3. 失败由主智能体**重新分配任务**（换执行者/重试），不是整条链报废
4. 整个任务在一个会话内闭环，上下文不被过程数据污染

## 二、业界方案调研结论

| 框架 | 范式 | 可借鉴点 | 不照搬原因 |
|---|---|---|---|
| LangGraph | 显式状态图 + Checkpointer | Checkpointer 断点恢复、conditional edges、parallel branches | 图是**静态预定义**的；我们要的是运行时动态规划 |
| CrewAI | 角色分工 + Task context 链 | Task 只声明 `context=[上游task]` 即自动传依赖产物 | 串行为主，层级模式就是「manager 逐个派活」，无真并行调度 |
| AutoGen/MAF | 对话驱动群聊 | 终止条件、发言策略 | 群聊式协作 token 成本爆炸，且上下文共享与我们的隔离目标相反 |
| 生产实践共识（2026） | Orchestrator–Worker | ① **canonical handoff schema**（task_id/goal/state/constraints，禁自然语言传状态）② 每个 handoff 有 trace ID ③ 每步超时预算 ④ 接收方需回 ACCEPTED/REJECTED ⑤ fan-out 用最小够用模型 | — |

**结论**：不引入任何框架。yan-zhi 已有 call_agent / spawn_subagent / workflow DAG / 自动接力四块地基，业界模式的可取之处归结为三件事——**结构化任务单（替代自然语言传值）、工件注册表（路径引用协议）、计划层并发调度**。这三件事自建成本远低于引入 Python 框架（我们是 TS monorepo，框架均为 Python 生态）。

## 三、现状与缺口（已核实源码）

### 已具备
- ✅ 子智能体上下文隔离：消息带 `parent_tool_call_id`，`loadSubAgentMessages` 分支过滤，摘要缓存隔离且 `persist:false` —— 主上下文只见最终返回值
- ✅ 同批 `call_agent` 可并发（`YANZHI_MAX_CONCURRENT_AGENTS` 默认 2，上限 8）
- ✅ 后台子智能体 `startBackgroundSubAgent`（上限 3）+ 结果经 `injectUserMessage` 投递回原会话
- ✅ workflow 引擎有 DAG 拓扑（入度 `buildExecutionPlan`）、产物落盘登记（`persistRunArtifacts`）、`workflow_run` 表 + SSE 断线续传
- ✅ 自动接力：预算边界「总结 → critic → 决策续批」+ `maybeReplanOnContinue` 重规划

### 缺口
| 缺口 | 现状 |
|---|---|
| ① 无动态任务规划 | 主智能体是扁平 ReAct；`task_plan` 只是文本清单；workflow 图是静态预定义 |
| ② 工作流引擎严格串行 | `executePlan` 是 `while(pending)` 单条循环，无 fan-out/join 并发节点 |
| ③ 返回值全文回流 | `runSubAgent` 返回全文（48K 截断），无「只回路径+描述」协议；`browser_get_page_content` 上限 20K，长章节抓取会被截 |
| ④ 后台子智能体不持久化 | 上限 3、无队列、重启即丢；失败只回一条错误文本 |
| ⑤ 无失败重分配 | 无「失败 → 检测 → 换执行者重派」机制 |
| ⑥ 任务不可断点续跑 | `llm_task` 重启标中断不可恢复 |

## 四、设计方案

### 4.1 核心抽象：TaskPlan + Artifact（新增两件事）

**① 动态任务单（TaskPlan）** —— 对应业界 canonical handoff schema

新增 `task_plan_item` 表（复用现有 sqlite），结构：

```
task_plan_item:
  id, conversation_id, task_id
  seq                 -- 计划序号
  title               -- 任务名，如「获取第3章全文」
  agent_id            -- 指定执行者（pageAgent / 业务智能体 / spawn 现场生成）
  instruction         -- 结构化任务指令
  depends_on          -- 依赖的 plan_item id 列表（JSON）→ DAG 边
  max_steps           -- 步数预算（如 pageAgent 抓全文限 10）
  status              -- pending / running / done / failed / skipped
  attempts            -- 已尝试次数
  artifact_ids        -- 产出的工件 id 列表（JSON）
  error_summary       -- 失败摘要（供重分配决策）
```

主智能体新增工具 `plan_tasks(items)`：一次调用把整批任务写成结构化计划落库，引擎按 DAG 自动调度。主智能体只在**两种时刻被唤醒**：① 全部完成 → 汇总；② 有节点失败且重试耗尽 → 重分配决策。

**② 工件注册表（Artifact）** —— 对应「大数据只传路径+描述」

新增 `artifact` 表：

```
artifact:
  id, conversation_id, plan_item_id
  kind          -- file / text / snapshot / url
  path          -- 磁盘路径（file 类必填）
  description   -- 一句话描述（LLM 生成，给主智能体看）
  summary       -- 摘要（可选，如章节字数、视频时长）
  meta          -- JSON（大小、格式、来源等）
```

- 子智能体执行完，**落库登记产物**（复用现有 `conversation_file` 登记与 `deliverWorkflowFile` 落盘逻辑），返回给主智能体的统一是 `artifact_id + path + description + summary` 的短文本（几百字符封顶）
- 主智能体给下游任务传参时只引用 `{{artifact:xxx}}`，由引擎在**任务启动时**把真实路径解析注入该子智能体的 instruction —— 大文件从头到尾不进任何主/规划上下文
- 子智能体内部需要读内容时用自己的工具（file_read 等）按路径自取

### 4.2 并行调度器：PlanRunner（新增，server 侧）

新文件 `apps/server/src/services/plan-runner.ts`：

```
入口 runPlan(taskId, planItems):
  loop:
    ready = status==pending && depends_on 全部 done
    并发派发 ready 中可运行的（信号量上限 = 现有 YANZHI_MAX_CONCURRENT_AGENTS，建议默认提到 4）
    每个任务 = 一个子 ReAct 循环（复用 runSubAgent，已有隔离机制）
    任务完成 → 登记 artifact → 更新 status → 解锁下游
    任务失败 → attempts+1：
       attempts < maxRetries(默认2) → 重新入队（同执行者，instruction 附加失败原因）
       attempts 耗尽 → status=failed，唤醒主智能体做重分配决策
    全部 done → 汇总产物清单投递主智能体
```

关键点：
- **复用而非重写**：任务执行体就是现有 `runSubAgent`（上下文隔离、步数预算、截断、摘要缓存全部继承），PlanRunner 只做 DAG 就绪判定 + 并发闸 + 状态机
- **步数约束**：`max_steps` 直接映射到现有子智能体批预算机制（pageAgent 场景设 10，超限触发 `summarizeOnMaxSteps` 返回已获内容或失败）
- **每步超时预算**：沿用现有任务墙钟预算机制，per-item 可配

### 4.3 主智能体协议改动（提示词 + 3 个工具）

新增/改造工具（走现有 builtin 白名单三段注册，见记忆坑①）：

| 工具 | 作用 |
|---|---|
| `plan_tasks` | 提交结构化任务计划（含依赖关系、执行者、步数预算） |
| `get_plan_status` | 查看计划执行状态（哪完成/失败、产物列表） |
| `reassign_task` | 失败重分配：换 agent_id / 改 instruction / 重派 |
| `read_artifact` | 主智能体确实需要看某个产物内容时按 id 读取（默认不需要） |

提示词侧给主智能体新增「规划者协议」块：
1. 拆任务 → 判依赖 → `plan_tasks` 一次提交
2. 无依赖的任务必须在同一批提交（让引擎并行跑）
3. 等待期间**不轮询**（PlanRunner 完成后主动唤醒）
4. 子智能体返回的只会有路径+描述，需要细节用 `read_artifact`

### 4.4 与现有机制的关系

| 现有机制 | 处置 |
|---|---|
| `call_agent async:true` 后台子智能体 | 保留，作为**单发后台任务**入口；PlanRunner 是编排层，二者不冲突 |
| workflow 静态 DAG | 保留，服务确定性流程；PlanRunner 服务**运行时动态规划**。后续可在 workflow 引擎加 parallel 分支节点作为二期 |
| 自动接力（预算边界续批） | 保留，PlanRunner 在接力点接手等待并行分支，属于互补 |
| `maybeReplanOnContinue` | 失败重分配逻辑与其对齐：失败唤醒 = 一次注入「任务 X 失败，原因 Y，产物状态 Z」的 user 消息 |

### 4.5 可观测性

- PlanRunner 每个状态迁移写 `task_plan_item`（事实表）+ SSE `plan:item_update` 事件推前端
- 前端聊天流里计划以轻量清单卡片展示（内部优化，不加用户侧按钮）——是否做 UI 先挂起，接口先具备
- 每个 handoff 用现有 task_id + plan_item_id 做跨智能体 trace，排查不用翻全量消息

## 五、实施步骤（分四期，每期可独立验证）

**P1 工件协议（最小闭环，风险 low）**
- 建 `artifact` 表 + 登记接口；`runSubAgent` 返回值改为「产物优先」：子智能体产出了文件 → 自动登记并返回路径+描述短文本
- `browser_get_page_content` 增加「超长内容直接落盘为工件」路径（解决 20K 截断，pageAgent 抓全文的前置条件）
- 验证：跑一次「抓全文 → 写文件」，确认主上下文只收到路径

**P2 任务计划表 + 串行 PlanRunner（风险 low）**
- `task_plan_item` 表 + `plan_tasks` / `get_plan_status` 工具
- PlanRunner 先按拓扑序串行执行（DAG 语义先立住），失败重试
- 验证：小说推文链路「抓章节 → 字幕分词 → 写文件」全链一计划跑通

**P3 并行调度 + 失败重分配（风险 medium）**
- ready 集并发派发（信号量闸）；`reassign_task` 工具 + 失败唤醒主智能体
- 验证：构造「视频下载 + 音频生成」双分支并行，计时对比串行；人为制造 pageAgent 失败验证重派

**P4 持久化与断点续跑（风险 medium）**
- PlanRunner 状态全部在表里，天然支持重启恢复：启动时扫描 conversation 内未完成 plan → 续跑
- 后台子智能体注册表落库（解决重启即丢）

## 六、风险与代价

| 风险 | 等级 | 对策 |
|---|---|---|
| 并行子智能体挤占本地模型/并发额度 | medium | 信号量上限 + 现有 token 预算机制共享 |
| 子智能体产物路径失效（用户移动/清理） | low | 登记时校验存在性；`read_artifact` 时二次校验 |
| 主智能体计划质量差（依赖标错） | medium | `plan_tasks` 提交时引擎做环检测（复用 workflow `callStack` 环检测逻辑）；主智能体可随时追加/改计划 |
| 新工具又造「多入口」漂移 | high（历史坑） | 三个新工具严格走三段注册：`api-tools/*.ts` + 挂载 + `buildToolsForBackend`，核验打第三段 |
| token 成本翻倍 | medium | fan-out 子任务路由到小模型（现有 platformId/modelId 参数已支持） |

## 七、不做什么

- 不引入 LangGraph/CrewAI/AutoGen（Python 生态，与 TS monorepo 不兼容，且其抽象与现有地基重复）
- 不做群聊式多智能体对话（token 爆炸 + 上下文污染，与目标相反）
- 不改 workflow 静态引擎的串行内核（二期再议 parallel 节点）
- 不新增用户侧按钮/提示（UI 展示先挂起）

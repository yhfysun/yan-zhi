# 视频剪辑与特效能力（media_edit）方案

> 2026-09-28。用户诉求原话：「现在有声小说能搞定了？还有短剧合成？有没有视频剪辑工具啊提供啊，还有字幕工具？能加效果的」
>
> 结论：**基础都在（ffmpeg 早已集成），缺的是「剪辑操作层」** —— 补一组 op 即可，不必另装软件。

## 一、改造前的现状盘点

| 类别 | 状态 |
|---|---|
| 有声小说 | ✅ 分段配音 + 字幕 + 合成（上一轮修复了 maxTokens 驼峰、空参数 id、误导提示三个真 bug） |
| 短剧合成 | ⚠️ 有「AI 短剧导演」智能体 + 「短剧流水线」工作流，但"合成"只是**组装**（混音/拼接/烧字幕），**不是剪辑** |
| 视频剪辑 | ❌ 无。`media_compose` 只有 dub / concat / subtitle 三个 op |
| 字幕工具 | ⚠️ 有 SRT 生成 + 烧录，但样式**写死**（白字黑边、底部居中），不可配 |
| 加效果 | ❌ 裁剪/变速/转场/滤镜/画中画/水印/关键帧/BGM 全无 |

## 二、新增：`media_edit`（12 个 op）

一次调用做一件事，按需点名；每个 op 都是**一次确定性的 ffmpeg 加工**，与时间轴解耦。

| 分组 | op | 作用 | 关键参数 |
|---|---|---|---|
| 剪辑基础 | `trim` | 裁剪取片段 | `start` / `end`\|`duration`（支持 `MM:SS`） |
| | `speed` | 变速、慢动作 | `factor` 0.25~4（音轨自动同步变速） |
| | `snapshot` | 抽帧成图（做封面） | `time` |
| | `transform` | 翻转/旋转/裁切 | `ops[]`、`cropW/cropH/cropX/cropY` |
| | `fade` | 画面+声音淡入淡出 | `fadeIn` / `fadeOut` |
| 视觉特效 | `color` | 调色 | `preset`（warm/cool/bw/vintage/vivid/film/fade）或 brightness/contrast/saturation/gamma/hue |
| | `transition` | 两段间转场 | `video2`、`type`（19 种）、`duration` |
| | `overlay` | 画中画/贴图/水印 | `overlay`、`position`、`opacity`、`overlayWidth/overlayScale` |
| | `kenburns` | 静态图片做推拉运镜成视频 | `image`、`duration`、`size`、`direction` |
| 音频增强 | `bgsound` | 加 BGM 并压低原声 | `audio`、`volume`、`duck`（侧链压缩） |
| | `volume` | 音量调整 | `db` 或 `factor` |
| | `loudnorm` | EBU R128 响度归一 | `target`（默认 -16 LUFS） |

## 三、字幕样式增强（`media_compose` op=subtitle 新增参数）

`subtitleColor` / `subtitleOutlineColor` / `subtitleOutline` / `subtitlePosition` / `subtitleMarginV` / `safeArea` / `titleColor` / `titleFade`

`safeArea=true` 专为竖屏短视频（抖音/快手/视频号）设计：字幕上抬到画面上方约 78% 处，避开底部进度条与账号信息遮挡。

## 四、★★ 最关键的坑：libass 的单位不是像素

**现象**：把 `subtitleFontSize` 设成 34（以为是"34 像素"，很小），实际渲染出 **170px 高的字**——用户反馈的"字幕有点大"就是这个原因。

**实测反推**（生成帧 + PIL 量像素）：

| FontSize | 画面 | 渲染字高 | 占画面高 |
|---|---|---|---|
| 8 | 1080×1920 | 39px | 2.03% |
| 17 | 1080×1920 | 85px | 4.43% |
| 34 | 1080×1920 | 168~171px | 8.75% |
| 68 | 1080×1920 | 345px | 17.97% |
| 34 | 1280×720 | 63px | **8.75%** |
| 34 | 720×1280 | 112px | **8.75%** |

**结论**：
1. ffmpeg 的 `subtitles` 滤镜生成的 ASS 头**恒定**为 `PlayResX: 384 / PlayResY: 288`，与输出分辨率无关；`original_size` 参数**实测完全无效**（os=1080×1920 与 os=384×288 渲染结果一模一样）。
2. 换算公式：`渲染字号px = FontSize × frameH / 384`，`渲染边距px = MarginV × frameH / 288`。
3. 即 **FontSize/MarginV 是「以画面高度为分母的比例值」**，跨画幅视觉占比恒定 → **不需要按分辨率缩放**。
4. 实现里统一换算：对外按**像素（以 1920 高成片为基准）**暴露 → `FontSize = px × 384/1920`、`MarginV = px × 288/1920`。默认字号 120px（≈ libass 24 ≈ 9 字/行）。

**对比 drawtext（标题）**：`drawtext` 的 `fontsize` 与 `y` 是**绝对像素**（真实视频坐标系），所以标题**必须按高度缩放**——两者规则相反，不能混用同一套换算。

## 五、实跑验证中抓到的缺陷（每条都是"命令成功但结果错"）

| # | 缺陷 | 症状 | 修复 |
|---|---|---|---|
| 1 | `bgsound` 非 duck 分支 `asplit` 输出 `v2` 悬空 | ffmpeg 直接失败：`Filter 'asplit' has output 0 (v2) unconnected` | 两条分支的图结构**不同**：duck 才需要 asplit（原声要喂 amix + sidechain 两路） |
| 2 | 安全区/边距写死 180px | 横屏 854×480 上 180px 占 37.5% 高，字幕被顶到画面中央（抽帧肉眼确认） | 改为按 libass 单位换算（本质是比例值，跨画幅一致） |
| 3 | 默认值 34 被当像素 | 实际渲染 170px，6.4 字/行（"字幕有点大"的真因） | 换算 + 默认 120px（9 字/行） |

**验证方式**：不是"编译通过就算"，而是**逐条实跑 ffmpeg 命令 + ffprobe 校验产物 + 抽帧肉眼核验**。
覆盖：有音轨 / 无音轨两类素材、竖屏/横屏/方形三种画幅、12 个 op、5 个调色预设、3 种转场。

## 八、使用示例

```
# 压时长：把 3 分钟素材压到 1 分钟
media_edit { op: "speed", video: "C:/.../raw.mp4", factor: 3 }

# 转场（两段需先统一规格）
api_media_normalize { videos: ["a.mp4","b.mp4"], size: "1080x1920" }
media_edit { op: "transition", video: "a.mp4", video2: "b.mp4", type: "dissolve", duration: 0.8 }

# 右上角半透明水印
media_edit { op: "overlay", video: "main.mp4", overlay: "logo.png", position: "tr", opacity: 0.6, overlayWidth: 160 }

# 加 BGM 并说话时自动压低
media_edit { op: "bgsound", video: "main.mp4", audio: "bgm.mp3", volume: 0.25, duck: true }

# 竖屏成片 + 安全区字幕
media_compose { op: "subtitle", video: "main.mp4", srt: "sub.srt", title: "驭兽斋·第1章", safeArea: true }
```

## 九、只读会话下的媒体工具：明确放行（用户决策）

**决策（2026-09-29，用户原话「那就放行啊」）**：媒体生成/加工类工具**一律放行**，不被只读模式拦截。

| 工具 | 只读会话 |
|---|---|
| `api_image_generate` / `api_video_generate` / `api_tts_speak` / `api_srt_generate` | ✅ 放行 |
| `media_compose` / **`media_edit`** / `api_media_normalize` / `api_media_fetch` | ✅ 放行 |
| `media_install_ffmpeg` / `media_install_ytdlp` | ✅ 放行 |
| `file_write` / `file_edit` / `cmd_exec` / `python_exec` 等 | ❌ 仍拦截 |

**理由（已写进 `tool-permission.ts` 注释，防后人"顺手加回去"）**：
这批工具不是「改用户文件」，而是「按用户要求生产新素材」——产物写进**会话交付目录**，
本质与 `file_read` 同类：用户要的就是这份产出，不存在"偷偷改了用户的东西"。
`media_edit` 即便输入指向用户已有文件，也只是**读**它、产物落新路径，不写回原文件。

**边界仍然保留**：只读会话里**不能**用 `file_write` / `file_edit` 改用户已有文件。

⚠️ 遗留口径不一致（本次未动）：**工作流**（`wf_*`）侧走的是 `READONLY_SAFE_TOOLS` **白名单**，
媒体工具不在该白名单里 → 只读会话下**工作流里的媒体节点仍会被拒**。
即"对话会话放行、工作流会话拦截"。如需一致，需另行调整工作流侧白名单。

# 记忆治理与「任务执行不了」归因 —— 实证报告与修复方案

> 2026-10-09 · 全部结论带 `文件:行号` + 实测计数。**纠正一处用户归因、抓出两个确凿缺陷。**
> 触发问题：「同一工作目录下任务会话太多了后面的任务都执行不了；上下文管理要优化；空间记忆要有最大上限字数，参考 WorkBuddy」

## 一、★ 先纠偏：「任务执行不了」不是会话太多造成的

### 实测：16 次中断里 13 次是「服务重启」

```

10-07 16:35   5.7min  interrupted  服务重启，任务被中断
10-07 17:24  16.9min  interrupted  服务重启，任务被中断
10-07 18:01   9.7min  interrupted  服务重启，任务被中断
10-07 18:14   1.0min  interrupted  服务重启，任务被中断

10-09 19:41  20.8min  interrupted  服务重启，任务被中断   ← ★ 见下
```
- **10-07 一天 9 次** —— 那天是重度开发日（反复改源码）。
- **10-09 19:41 那条 20.8 分钟的任务** —— 正是**本轮修复过程中改 `llm-task-manager.ts` 触发 dev 热重载**，把用户刚跑起来的任务杀掉了。

### 结论
| 归因 | 是否成立 | 证据 |
|---|---|---|
| ① 同一目录会话太多 → 后面的任务执行不了 | **不成立** | 中断与"会话数"无时间相关性；同空间会话数期间没变。真正的失败模式是**服务重启**，与目录/会话数无关 |
| ② **dev 模式 tsx watch 热重载杀任务** | ★ **成立且是主因（13/16）** | 时间聚集在开发日；`interrupted` 文案由 `markOrphanTasksInterrupted()`（启动时回收）产生 |
| ③ 数据库损坏（`malformed`） | 成立但**独立**（2 次） | 已在 10-09 修复（`services/db-integrity.ts` 启动自愈） |
| ④ 墙钟 15 分钟 | 成立但**已修** | 本轮引入等待抵扣 + 有限接力 |

★ 判据：**"后面的任务跑不了"要按 `llm_task.status + error` 归因，不要按"用起来的感觉"归因。**
本次用户的因果假设（会话多 → 跑不了）与实测（服务重启）是**相关而非因果** —— 与记忆里"用户对现象的归因常是相关而非因果"完全一致。

### 修法（消除最大来源）
| # | 项 | 说明 |
|---|---|---|
| R1 | **dev 模式改代码不应杀运行中任务** | 现状：`tsx watch` 一重启 → `markOrphanTasksInterrupted()` 把所有 running 标记 interrupted。改法：① 回收时**判定是否为"优雅重启"**，是则**保留任务可续跑**（已有 `plan.md`/`progress.md` 接力链，重启后由用户一条"继续"就能接上）；② 或在 dev 下改用**不 kill 任务的增量重启**（只重载改动的模块）；③ 至少把文案改清楚：「服务重启（开发热重载）→ 任务中断，可点继续」 |
| R2 | 改代码前提示 | 若检测到有 running 任务，改动前的重启应**先落一次进度**（写 progress.md），保证重启后能接上 |

## 二、★ 确凿缺陷 1：`progress.md` 读取取到**最旧**内容 → 模型不知道最新进度

### 缺陷
```ts
// apps/server/src/services/space-memory.ts:575
const content = readFileSync(filePath, 'utf-8').slice(0, PROGRESS_READ_MAX_CHARS);
//                                                          ^^^^^^^^^^^^^^^^^^^^^^^ 取【头部】
```
- 但 progress.md 是**追加写**（`appendLineWithHeader` 末尾追加）→ **最新在文件尾部**。
- ⇒ 取头部 = **取最旧的内容**，把最新进度全部丢掉。

### 实测（空间「小说推文」progress.md）
```
文件总长 = 14840 字符
slice(0,8000) 覆盖到的最后一条任务行：
    - 2026-10-07 13:04 任务【失败中断】...            ← 只到 10-07
文件里实际最新一条：
    - 2026-10-09 19:38 任务【达最大步数中断】(200 步)... 第3章推文出片
★ 最新条目在 slice 窗口内吗 = False
★ 漏掉的任务行数 = 8
```
⇒ **模型通过 `api_space_memory_read` 看到的进度停在 10-07，今天（10-09）的第3章进度完全看不到。**

### ★ 根因是「同一语义两处不一致」（正是项目记忆里记过的那类坑）
| 位置 | 语义 | 做法 | 对错 |
|---|---|---|---|
| 注入侧 `selectMemoryLines`（`space-memory.ts:264-306`） | 超限时选哪些 | `take(arr, newestFirst=true)` **从新到旧** | ✅ 对（注释里还专门写了"第一版写错被自检抓到"） |
| 读取侧 `readTaskProgressForConversation`（`:575`） | 超限时读哪段 | `slice(0, MAX)` **从旧到新** | ❌ **错** |

- ★ 判据：**"超限时保留哪一端"必须只有一处定义**。注入侧想到了（注释写得很清楚），读取侧漏了 —— 说明当时的自检只覆盖了注入侧。

### 修法
- `readTaskProgressForConversation` 改为**取尾部**（或复用 `selectMemoryLines` 的 newestFirst 逻辑）；
- ★ 更彻底：把"截断/选取"抽成**唯一函数**，注入侧与读取侧共用，消除第二处实现（避免再漂移）。

## 三、★ 确凿缺陷 2：记忆文件**没有字数上限治理**（对比 WorkBuddy）

### 实测现状（空间「小说推文」）
| 文件 | 实际 | 预算 | 状态 | 写入侧淘汰 |
|---|---|---|---|---|
| `MEMORY.md` | 3036 | 6000 | 未满 | ✅ 任务进展行滚动淘汰（`PROGRESS_ENTRY_KEEP=8`） |
| `decisions.md` | 3484 | 3000 | **超 1.16x** | ❌ 决策行**永不淘汰** |
| `progress.md` | 14840 | 8000 | **超 1.85x** | ❌ **完全没有 prune** |
| 注入侧合计 | — | — | **约 14036 字符 ≈ 7000 tokens/任务**（固定成本） | — |

### 根因（三层）
1. **写入侧**：`appendTaskProgress`（`:533-559`）里——
   - 明细分支（progress.md）`appendLineWithHeader(...)` **没传 `keepPerMark`**（代码注释自认"文件本身有界由读取侧 8000 字兜底"）→ **文件无限增长**；
   - 而注释说的"读取侧兜底"**恰恰就是上面那个取错方向的 `slice`** → 双重失效。
2. **读取侧**：只有"截断"，**没有 WorkBuddy 式的 30 天蒸馏 + 删除**。
3. **闸门错配**：`MAX_SESSION_MESSAGES = 400`（`context-policy.ts:71`）是**会话内消息条数**闸门，**不是记忆文件闸门** → 记忆文件**真正无上限**。

★ 这正是项目记忆里那条：「token 之外还要**条数闸门**」—— 会话有闸门，**记忆文件没有**。

### 对比 WorkBuddy（已查证）
| 项 | WorkBuddy | yan-zhi 现状 | 差距 |
|---|---|---|---|
| 工作区长期记忆 | **MEMORY.md ≤ 3000 字符** | 6000 | 上限偏大一倍 |
| 每日日志 | 单独 `YYYY-MM-DD.md`，**注入时只取"今天"的** | 无日期分文件（用滚动淘汰代偿） | 缺"只注入今天" → 旧流水靠淘汰，易漏 |
| 长期治理 | **超 30 天 → LLM 蒸馏进 MEMORY.md → 删原文件** | **无蒸馏、无删除** | ★★ 核心差距：只截断不蒸馏，信息要么丢要么堆积 |
| 用户级记忆 | ≤ 4000 字符/会话 | 4000（一致） | ✅ |

★ WorkBuddy 的关键设计不是"限额"本身，而是**"蒸馏 + 删除"**：既控制体积，又不丢信息（把有价值的部分提炼进 MEMORY.md）。yan-zhi 只有"截断"——**信息要么被静默丢掉，要么堆在文件里永不清理**。

### 修法
| # | 项 | 做法 |
|---|---|---|
| M1 | **修 progress 读取方向** | 见 §二（取尾部 / 复用 selectMemoryLines） |
| M2 | **给 progress.md 加写入侧淘汰** | `appendTaskProgress` 明细分支补 `{ mark: PROGRESS_ENTRY_MARK, keep: N }`（如 20 条）；文件有界才谈得上"读取正确" |
| M3 | **给 decisions.md 加上限 + 淘汰** | 决策行也永不淘汰 → 加 `DECISION_ENTRY_KEEP`（如 15 条）或按 `DECISIONS_INJECT_MAX_CHARS` 做滚动 |
| M4 | **抽唯一"记忆截断/选取"函数** | 注入侧与读取侧共用，消除第二处实现（本次漂移的根因） |
| M5 | **补"蒸馏"机制** | 对齐 WorkBuddy：超 N 天的 progress 明细 → LLM 蒸馏成要点写进 MEMORY.md → 删原条目。★ 比单纯截断更符合用户"要好好优化"的诉求 |
| M6 | **MEMORY.md 上限对齐 WorkBuddy 3000？** | ⚠️ 需拍板：3000 更省注入预算，但 yan-zhi 的 MEMORY.md 同时承载"空间长期记忆 + 任务进展要点"两类，压到 3000 可能挤掉要点。建议 **4000**（折中）或**维持 6000 但加强淘汰** |
| M7 | **记忆文件条数/体积闸门可见** | 前端/日志暴露"当前 MEMORY.md 用了 X/上限"（对齐已有 `ContextUsagePill` 的做法） |

### 验收
- **M1**：`api_space_memory_read` 返回的 progress **包含当天最新条目**（断言：最新条目 in 返回内容）。

- **R1**：改一行源码触发重载后，运行中任务**不被标记 interrupted**（或标记为"可续跑"）。
- **M5**：超期明细被蒸馏后，原条目消失且 MEMORY.md 新增要点。

## 六、一句话总结

- 「会话太多导致任务跑不了」**不成立** —— 主因是 **dev 热重载杀任务**（13/16），本轮我自己就触发了一次。
- 真正坏掉的是两处：**progress 读取取错方向**（模型看到的进度停在 10-07）、**记忆文件没有上限治理**（decisions 超 1.16x、progress 超 1.85x，且写入侧不淘汰、没有蒸馏）。
- 对齐 WorkBuddy 的关键**不是限额数字**，而是它的 **"蒸馏 + 删除"** 治理闭环 —— 我们目前只有"截断"。

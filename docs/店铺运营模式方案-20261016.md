# 店铺运营模式（亚马逊 / 淘宝 / 1688 / 跨境中转仓）方案

> 2026-10-16 ｜ 状态：**待评审，未开工** ｜ 方案范围：新增「店铺运营模式」= 一个插件 + 一个独立控制台 + 一个专属智能体 + 5 个技能 + 1 组任务类型。
> **不动**：会话/空间/任务三条既有机制（只加行，不改语义）、番茄小说推文发布流水线、抖音运营能力（只撤了它的模式位，岗位卡+智能体+技能+任务类型保留）。
> 决策口径（用户已拍板）：① 做成**重模式**（插件 + 独立控制台）；② 允许**代操作店铺**，但每步二次确认；③ 「中间站」= **跨境中转仓 / 海外仓**；④ 平台含 **1688**。

### 3.2 后端插件 `shop-ops`

照 `ops-shell` 的三件套：**manifest（声明能力）+ 工具集（给模型用）+ `/plugin/shop-ops/*` 路由（给控制台用）**，数据落 `plugin_storage`（`plugin_id='shop-ops'`）。

| 层 | 内容 |
|---|---|
| manifest | `id='shop-ops'`、`contributes.permissions`（新增 `shop-write`：店铺写操作权限，与 ops-shell 的 `remote-shell` 同范式）、`contributes.routes`（`/shop`，desktopOnly）、`contributes.sidebar` |
| 工具族（只读） | `shop_conn_list` / `shop_conn_create` / `shop_conn_update` / `shop_conn_delete` / `shop_product_search` / `shop_product_detail` / `shop_orders_list` / `shop_metrics_pull` / `shop_review_pull` |
| 工具族（写，**全部强制二次确认**） | `shop_listing_create` / `shop_listing_update` / `shop_price_update` / `shop_stock_update` / `shop_coupon_apply` / `shop_reply_send` |
| 控制台路由 | `GET/POST /plugin/shop-ops/connections`、`GET /plugin/shop-ops/groups`、`POST /plugin/shop-ops/metrics`、`GET /plugin/shop-ops/audit`、`POST /plugin/shop-ops/:connId/probe`（连通性自检） |

**关键约束（照 ops-shell 既有做法，不发明新写法）**：
- 密钥加密一律走 `apps/server/src/utils/crypto.ts` 的 `encrypt/decrypt`（与运维连接同一把主密钥）；
- 连接对象**只存密文**，出库必经 `toClientView` 剥离 `secretEnc`；
- 每次写操作 `pushPluginAudit`（照 `ops-shell.ts:547`，保留 500 条环形缓冲）；
- **登录态不落库**：平台登录交给 pageAgent 用 `browser_login_saved` 复用浏览器 cookie，插件不存账号密码（与抖音运营「不代发布、不碰用户登录态」同一条硬边界——本模式的差别只是「用户自己登录后，允许 agent 代操作」）。

### 3.4 智能体与技能

**专属智能体** `a_builtin_shop_agent`（声明在 `apps/server/src/builtin-shop-agents.ts`，字段照 `builtin-douyin-agents.ts`：`id/name/description/type='harness'/is_builtin=1/builtin_tool_ids/skill_ids/sub_agent_ids/system_prompt/force_sync/agent_kind='main'/category/config_json`）。

- `type: 'harness'`、`agent_kind: 'main'`、`config_json: { maxReActSteps: 50 }`
- `sub_agent_ids: ['a_builtin_page_agent']`（浏览器操作全部委派 pageAgent）
- `skill_ids`: 下列技能
- `system_prompt` 要点：**先对齐口径再算数**（站点/币种/含税/佣金/头程）；**只读优先**；**写操作一律先出变更单**（改什么、从什么改成什么、影响面、回滚方式），经确认才执行；**不做平台规则的口头断言**（费率/政策一律 pageAgent 现查）；合规红线（禁刷单、禁违规改价、禁虚假宣传）。

**技能**（落 `db.ts` 的 `builtinSkillDefaults` + `.claude/skills/<name>/SKILL.md`）：

### 3.6 写操作闸门与审计（本次新增的核心安全件）

「允许代操作 + 每步二次确认」落到三条硬约束，缺一不可：

1. **工具层闸门**：所有 `shop_*` 写工具在执行前必须调用既有 `confirm_user`（`TaskStep.confirmTool='confirm'`），把**变更单**（对象 / 现值 / 新值 / 影响面 / 回滚方式）交给用户确认；未确认一律不执行。
2. **生产店铺强确认**：连接的 `tag === '生产'` 时，二次确认文案额外高亮「生产店铺」，并禁止批量（照 ops-shell 对生产标签的处理口径）。
3. **审计留痕**：每次写操作 `pushPluginAudit` 记录 动作 / 店铺 / 对象 / 前后值摘要 / 是否确认通过，控制台「操作日志」页签可回看（复用 `OpsConsole` 的审计页签形态）。

另有一层既有兜底可直接复用：会话级 `permissionMode='readonly'` 时后端拦截写类工具（`packages/shared/src/types/index.ts:112-113`）——建议控制台为「诊断/分析」类会话默认给 `readonly`。

### 3.7 平台能力矩阵

| 平台 | 只读分析（P0/P1） | 写操作（P2） | 登录态 | 主要难点 |
|---|---|---|---|---|
| **Amazon** | 竞品/关键词/评论/BSR、后台订单与广告报表 | 改价、改库存、上下架、A+ 提交 | 卖家中心登录（pageAgent + `browser_login_saved`）；有 SP-API 时优先 API | 重页面与风控；报表导出格式多变；费率口径需现查 |
| **淘宝/天猫** | 标题关键词、主图/详情、DSR、竞品价格 | 改价、库存、活动报名、回消息 | 千牛/卖家中心登录 | 反爬强；数据多在后端接口而非 DOM，**优先走 `browser_get_network_log` 找接口** |
| **1688** | 同款比价、阶梯价、起订量、供货能力 | 建议**不开放**下单/铺货（风险高于收益） | 登录后可看阶梯价 | 与亚马逊同款匹配是核心，直接复用 `compare_products` |
| **跨境中转仓 / 海外仓** | 头程报价、时效、库存台账、周转与滞销 | 入库预约、调拨单 | 多为自有台账/服务商系统 | 数据以表格为主 → `skill_xlsx_data_processing` |

## 4. 影响面与风险

| 项 | 级别 | 说明 |
|---|---|---|
| 平台风控与验证码 | **high** | 淘宝/亚马逊对自动化敏感。已明确：**不设绕过**，遇验证码即停下让用户人工处理；抓数优先走页面自身接口而非高频点击 DOM |
| 写操作误伤真实店铺 | **high** | 三道闸门（二次确认 + 生产强确认 + 审计）+ 建议默认 `readonly` 会话。仍建议 P2 才开放，且首个写操作只做「改价」单一动作打样 |
| 重页面导致动作超时 | medium | 有历史实据（抖音创作者中心单步吃满 18s）。方案要求 pageAgent 侧对重页面走「先找接口再取数」，不逐元素抓 |
| 平台规则口径过期 | medium | 所有费率/政策一律现查，不在提示词里写死数字（与既有约定一致） |
| 授权档位选择 | medium | 建议与 `ops`/`sec` 同放 `pro`：涉及真实账号与资金动作，不宜在基础档放开 |
| 控制台壳重复 | low | `ops`/`sec`/`shop` 三套同形态页面目前是复制粘贴，没有基类。本方案**接受这份重复**（先落地，择机再抽）——抽基座会让这次改动横跨三个既有模式，风险大于收益 |
| 白名单漂移 | **high（但已有守门）** | `AppMode` / `Conversation.mode` / `VALID_MODES` / `api-tool-executor` 的 `MODES` / `license.ts` 必须同改；漏一处表现为「会话静默落成 office 或从列表消失」。既有守门测试会在漏改时变红：`conversation-mode.test.ts` 从源码抽 `VALID_MODES`、`conversation-self-config.test.ts` 正则匹配白名单字面量、`mode-edition.test.ts` 从 `MODE_DEFS` 推导期望 |

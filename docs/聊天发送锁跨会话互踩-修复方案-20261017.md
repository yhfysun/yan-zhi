# 聊天发送锁「跨会话互踩」修复方案

日期：2026-10-17 ｜ 分支：dev0.1-mobile ｜ 风险等级：medium ｜ 状态：待确认

## 一、现象与根因（已确认）

- 现象：会话 A 跑长任务期间，在**别的会话**按回车/点发送 → 毫无反应、零反馈；刷新后恢复。
- 根因：`useChat()` 是单例（`useChat.ts:4002-4010`），其中的防重入锁 `sending`（`:413`）
  因此是**全局一把锁**。锁在 `send()` 置位（`:2587`）、`finally` 释放（`:2591`），
  而 `sendInner` 尾部 `await store.sendMessage` 等**整个任务 SSE 全程** → 任务跑多久锁挂多久。
- 吞没点：`send()` 开头的「任务运行中入队」分支（`:2568-2581`）只对**当前会话**生效；
  切到会话 B 时 `isConvStreaming(B)=false`，直接落到 `:2586` `if (sending.value) return`
  → **静默吞掉**。
- 放大因素：发送按钮 disabled 只看 `canSubmit`（`ChatInputArea.vue:1050`，不看 sending）
  → 按钮亮着、回车也放行，用户以为「回车坏了」。
- 注释与实现分裂：`ChatInputArea.vue:1916` 注释明写「切到别的会话则正常发送」，
  实现上被全局锁挡住 —— 本修复就是把实现拉回注释宣称的行为。

## 二、影响点盘点（sending 的全部消费方）

| 位置 | 用法 | 改动影响 |
|---|---|---|
| `useChat.ts:413` | `const sending = ref(false)` 声明 | 重写为内部 Set + computed 导出 |
| `useChat.ts:2586-2591` | 锁判定位/释放 | 改为按会话 key 判定 |
| `useChat.ts:3977` | return 导出 `send, sending` | 导出名不变，UI 零改动 |
| `ChatInputArea.vue:803` | 解构 `sending`（模板未实际使用） | 无需改动 |
| `send-reentry-lock.test.ts` | **锚点测试**，正则断言源码形状 | **必须同步改写**（见 §四） |
| `input-send-affordance.test.ts` | 断言 disabled 只看 canSubmit、canSubmit 不含 sending | 语义保持，不破坏 |
| `ChatHub.vue` / `Peers.vue` | 各自局部 `sending` ref，与 useChat 无关 | 不受影响 |

## 三、修复设计（最小改动，锁粒度从「全局」改「按会话」）

只动 `useChat.ts` 一个文件 + 一个锚点测试：

```ts
// 1. 声明处（:413）：
const sendingConvs = ref<Set<string>>(new Set());
//   语义：key = 会话 id；草稿态（尚无会话 id）用 '__draft__'，防连发语义不变。
//   对 UI 的导出名保持 sending：「当前会话是否在发送中」——UI 侧语义完全不变：
const sending = computed(() => sendingConvs.value.has(store.currentConvId || '__draft__'));

// 2. send() 内（:2586-2592）：
const lockKey = store.currentConvId || '__draft__';
if (sendingConvs.value.has(lockKey)) {
  ElMessage.warning('该会话正在发送中，请稍候');   // ★ 不再静默吞掉
  return;
}
sendingConvs.value.add(lockKey);
try { await sendInner(); }
finally { sendingConvs.value.delete(lockKey); }
```

设计取舍：

- **锁 key 在进入时冻结**：`sendInner` 建会话后 `currentConvId` 会变，但锁仍挂
  `__draft__` 直到 finally —— 草稿态并发连发仍被互斥（与旧行为一致，不退化）。
- **入队分支保持锁前**：现有 `:2568-2581`（同会话运行中 → 入队）顺序不动，
  它不受本改动影响。
- **`sending` 导出名/语义不变**：`input-send-affordance.test.ts` 的断言
  （disabled 只看 canSubmit、canSubmit 不含 sending）继续成立。

## 四、测试计划

1. **改写锚点** `send-reentry-lock.test.ts`：正则改为断言新形状
   （`sendingConvs` Set 声明、`sendingConvs.value.has(`、`add(`/`delete(`、finally 释放、
   导出仍为 `send, sending`），并保留「锁在任何 await 之前置位」的顺序断言
   （`:47` 的 lockAt 早于首个 await 的检查逻辑照搬）。
2. **新增行为测试**（同文件或新文件）：
   - 会话 A 锁住时，切到会话 B 调 `send()` → 不被拦（核心回归用例，对应用户实报）。
   - 同一会话并发第二次 `send()` → 被拦且有 `ElMessage.warning`（断言不再静默）。
   - 草稿态（`currentConvId=''`）并发两次 → 第二次被拦（防重入不退化）。
3. 跑 `vitest` 相关文件 + `vue-tsc`（packages/ui）。

## 五、风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 核心发送链路改动 | medium | 锚点测试 + 行为测试双保险；`sending` 导出语义不变，UI 侧零改动 |
| 草稿态并发发送 | low | `__draft__` key 保持互斥，不退化 |
| 多会话同时发送对后端的压力 | low | 后端本就支持多会话并行（`runningConvIds` 即为 Set），前端只是不再假性互斥 |

## 六、验收口径（用户视角）

会话 A 跑任务时切到会话 B 发消息 → 立即正常发送，互不影响；
在 A 自己里发 → 照旧入队；同会话连点发送 → 提示「正在发送中」而非无声无息。

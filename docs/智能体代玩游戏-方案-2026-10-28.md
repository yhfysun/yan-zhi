# 智能体代玩游戏 · 方案（2026-10-28）

> 目标：让智能体能在**浏览器里真的把网页游戏玩下去**，而不是"点两下就断片"。
> 原型：`docs/prototypes/game-mode-proto.html`（可直接玩，两种驱动模式实时对比）

## 一、结论先说

能做，但不能一把梭。现有链路（`截图 → LLM 决策 → 点击`）在**回合制、放置挂机、棋类、每日签到**上已经够用；**实时动作类**必须把执行层从"每步一次 LLM 往返"换成"主进程确定性循环"。

不做的事：常驻的全自动视觉闭环（截屏→小视觉模型→坐标点击，完全绕开对话）。模型成本与误判率都不划算，等前两步跑顺再评估。

## 二、为什么现在玩不了实时游戏

一次"看一眼动一下"在当前实现里是**三次工具调用**：

1. `browser_screenshot` —— 拿图（`packages/core/src/tool/builtin/browser/index.ts:545`）
2. `image_analyze` —— 真的让模型看图（`packages/ui/src/stores/chat.ts:2723` 拦截，`2832` 执行）
3. `browser_click` —— 执行（`browser/index.ts:331`，支持 `x/y` 坐标，`:340-341`）

工具回执里还写着"你本身看不到画面，请继续调用 image_analyze"（`browser/index.ts:574`），等于强制多一跳。加上 LLM 往返，单步落在 **1–2 秒**；动作游戏要求 100 毫秒级，差两个数量级。

原型里把两个口径实测出来了：

| 口径 | 回合制（LLM 慢通道） | 实时（主进程循环） |
|---|---|---|
| 平均单步 | ~700–1400 ms | 2–33 ms |
| 6 秒得分 | 4 分，屏上堆 5 个没接住 | 9 分，屏上一个不漏 |
| LLM 调用 | 每步 1 次 | 开局 1 次 |
| 6 秒 token | ~10.9k | ~2.2k |

## 三、架构：三层 + 两种驱动

```
感知 ── 截屏 / canvas 像素采样
决策 ── LLM（开局定策略 / 卡住时回问）  或  确定性脚本（像素条件分支）
执行 ── sendInputEvent / CDP Input（真实鼠标键盘）
```

**两种驱动方式共用同一套工具，差别只在"决策"这一层谁干活：**

- **回合制**：每步都问 LLM。慢、贵、泛化好，适合状态复杂但节奏慢的游戏。
- **实时**：LLM 只在开局（读目标 → 生成循环脚本）和"卡住"时介入；执行与条件判断留在主进程，30Hz 跑。

关键洞察：**游戏状态判断用像素采样，而不是视觉模型**。血条颜色、目标区域有没有出现，读几个像素就能判定，毫秒级且零成本。原型里实时模式就是真读 canvas 像素（`getImageData`）判定金币是否还在，回执里的 `#f2bb49 → 命中` 是实测值。

## 四、落地切片

### P0 · 让回合制真能玩（约 1–2 天）

1. **截图一次进模型**：`browser_screenshot` 的回执改为多模态内容（图像块 + 一句摘要），不再强制二次调用 `image_analyze`。复用 `chat.ts` 已有的图片压缩链路（`:2924` 那段），避免长截图把上下文打爆。
2. **游戏模式开关**：面板/会话级 `gameMode` 标志，打开后跳过动作后的页面稳定等待与冗余回执，只保留"是否发生变化"的最小信号。
3. **动作合批**：连续坐标点击合并成一次调用（一帧内多个动作）。

验收：在真实回合制/挂机页游上，20 步内不漏关键操作，单步 < 1.5 秒。

### P1 · 实时循环 `browser_run_loop`（约 3–5 天）

新工具，跑在主进程（`apps/desktop/main.cjs`），不经过渲染层往返：

```ts
browser_run_loop({
  steps: [{ type: 'click', x: 420, y: 310 }, { type: 'key', key: 'Space' }],
  condition: { type: 'pixel', x: 420, y: 310, expect: '#f0b43c', tol: 24 },  // 可选
  hz: 30,            // 循环频率，上限 60
  maxSeconds: 30,    // 时长闸
  maxSteps: 300,     // 步数闸
  onMiss: 'skip' | 'stop',
})
```

- 执行用 `wc.sendInputEvent`（`main.cjs:3244` / `:3316`）或 CDP `Input.dispatchKeyEvent`（`:4607`），拿到的是真实按键，`isTrusted` 与手动操作一致。
- 像素条件在主进程读帧判定（`capturePage` + `nativeImage` 取像素），不产生 LLM 调用。
- **急停三件套**：Esc 热键、`maxSeconds`、`maxSteps`，任一触发即冻结并返回现场（末 N 步日志 + 最后一张截图）。
- 回执只回摘要（跑了多少步、命中率、终止原因），不回每一步。

前置：`capturePage()` 在面板隐藏时必失败（`main.cjs:236-245` 的注释就是踩这个坑写的）→ 实时模式要求浏览器可见窗口，见 P2。

验收：在一个真实的动作小游戏上连续跑 60 秒不中断，急停能在 200ms 内生效。

### P2 · 游戏会话窗（约 2–3 天）

- 独立置顶窗口承载浏览器，复用 `child-window:open`（`main.cjs:2072`），需要时加 `alwaysOnTop` 与"缩到角落"。
- 执行条：目标输入、运行状态、采样色值、步数、急停按钮（原型里那一整条就是它的形态）。
- 与宠物联动：宠物播"游戏中"动作；智能体卡住时宠物切"思考"态（`usePetBridge` 已在推状态，增量很小）。

## 五、风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 页游禁止脚本 | 多数页游 ToS 明确禁止自动化，封号是真实后果 | 只做用户自己已登录的本地会话；不做批量刷号、不做多开；界面上明示"账号风险自担" |
| 误操作扩散 | 实时循环点错位置可能触发付费/删档 | 坐标点击默认限制在游戏 iframe/canvas 区域内；`maxSteps` 与急停常驻 |
| 可见性依赖 | 隐藏面板截不到图 | 实时模式强制可见窗口；不可见时直接拒绝并提示，不静默降级 |
| computer-use 抢通道 | 它有 200 次/10 分钟限流，且默认禁止点本应用窗口 | 代玩一律走浏览器内部通道，不经过 computer-use |
| 上下文被打爆 | 长截图 + 多步日志很快撑满窗口 | 截图压缩 + 回执只回摘要 |

## 六、待拍板

1. **P0 先行还是 P1 并做**：P0 能马上验证"到底有没有人想用"，我建议先 P0。
2. **首批目标游戏**：需要你指定 1–2 个真实站点，否则验收标准没法量化。
3. **是否给宠物开"观战"**：代玩时宠物在屏上播反应动作（成本极低，但会分散注意力）。

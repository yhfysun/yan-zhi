# 固定脚本 RPA 调研与融合方案

> 日期：2026-11-13
>
> 状态：P0/P1 已实施，P2/P3 基础闭环已接通
>
> 范围：浏览器固定操作、桌面键鼠脚本、文件处理、网页挂机循环与定时执行

> 实施更新（2026-11-13）：已落地独立 `rpa` 模式、`AutomationWorkbench` 工作台、脚本 CRUD/不可变版本/发布/运行记录、浏览器步骤执行器、浏览器事件录制与敏感字段脱敏、桌面窗口激活和窗口相对坐标点击/输入/按键、文件存在/等待/复制/移动、RPA 定时任务固定发布版本执行、`rpa_*` 工具、`a_builtin_rpa_builder` 智能体，以及办公助手挂载。
>
> 当前明确边界：桌面全局键鼠录制、UIA/图像/OCR 定位、图像等待、暂停/恢复、运行事件 SSE、定时任务控制台里的独立 RPA 创建页签尚未接入；桌面固定点击仍以窗口相对坐标执行为主。这些能力已有的 schema 预留不会伪装成可运行能力。

## 0. 结论先行

这个需求不应该做成“每一步都让模型看着屏幕思考”的 Agent，而应该做成：

> **固定脚本 RPA 为主，AI 只负责生成脚本、修补失效步骤和异常诊断。**

用户演示或手动配置一次，系统把它保存成版本化脚本。以后执行时不再调用大模型，直接按脚本快速重放。遇到页面或窗口变化时，先走稳定的元素定位和图像/OCR 兜底；仍然失败，再让 AI 给出局部修复建议，用户确认后更新脚本。

| 方案 | 结论 | 原因 |
|---|---|---|
| 只给 pageAgent 加提示词，每次让模型现场点 | 不推荐 | 慢、贵、不可复现，同一流程仍会每次“现场发挥” |
| 直接嵌入 UiPath / Power Automate / OpenRPA | 不推荐作为主路线 | 部署重、Windows/授权依赖强，难以和当前智能体、工具、权限和 UI 融合 |
| 只复用现有 Workflow DAG | 不够 | 适合复杂编排，不适合用户录制“十次点击”后直接回放 |
| **新增原生 RPA Script 层** | **推荐** | 快速、确定、可审计、可版本化，并能复用现有浏览器、桌面、文件、定时和后台任务能力 |

一句话产品定义：

> 在现有应用里增加“自动化脚本”：录一次，存成流程，随时一键重放；复杂时再升级为工作流，失败时由智能体协助修。

## 1. 外部调研

### 1.1 Power Automate Desktop：录制器 + UI 元素仓库 + 图像兜底

Microsoft 的 desktop flow recorder 会记录鼠标和键盘活动，并把它转换成独立动作。录制完成后，页面或桌面控件会进入 UI elements 仓库。

官方文档明确写到：

- recorder 会跟踪 mouse/keyboard 活动与 UI elements 的关系，并分别记录每个动作。
- 桌面和网页自动化优先使用 UI elements，不需要依赖图像识别或绝对坐标。
- 对于不暴露 accessibility API 的应用，可以用 image-based recording，通过图像识别和 OCR 定位元素、提取文字。
- 网页自动化需要浏览器扩展或受支持的浏览器连接，再执行 click、extract 等动作。

这说明成熟的固定脚本产品通常有三层定位：

1. UI 元素/选择器。
2. 图像或 OCR。
3. 最后的坐标定位。

来源：

- <https://learn.microsoft.com/en-us/power-automate/desktop-flows/introduction>
- <https://learn.microsoft.com/en-us/power-automate/desktop-flows/recording-flow>
- <https://learn.microsoft.com/en-us/power-automate/desktop-flows/ui-elements>
- <https://learn.microsoft.com/en-us/power-automate/desktop-flows/automation-web>

### 1.2 UiPath：多种录制模式 + 稳定选择器

UiPath 把录制类型分为 Basic、Desktop、Web、Image、Citrix 等：

- Desktop/Web 录制会生成容器和较稳定的元素定位。
- Image 录制面向虚拟桌面、远程桌面、Citrix、SAP 等难以读取控件树的场景。
- Image 录制允许图像点击、文本/OCR、键盘和快捷键动作。

UiPath 的 selector 文档直接指出：用屏幕位置识别 UI 元素不可靠，因此应保存控件及其父级属性。它还强调应优先选择不会在每次启动时变化的属性。

这对我们的启发很直接：

- 浏览器脚本优先 `role + accessible name`、`label`、稳定属性、相对 DOM。
- 桌面脚本优先 Windows UI Automation 的属性。
- 坐标只能作为最后一层兜底，并应绑定窗口相对位置，而不是屏幕绝对位置。

来源：

- <https://docs.uipath.com/activities/other/latest/ui-automation/about-recording-types>
- <https://docs.uipath.com/activities/other/latest/ui-automation/about-selectors>
- <https://docs.uipath.com/activities/other/latest/ui-automation/computer-vision-recorder>

### 1.3 Playwright：录制生成、语义定位、Trace 证据链

Playwright 的 Codegen 可以在用户点击页面时自动生成动作，并优先使用 role、text、test id 等定位方式。它的 Locator 文档建议优先使用用户可感知的属性和明确契约，而不是脆弱 CSS/XPath。

Playwright 的 Trace Viewer 则把一次运行记录成可回看的 trace，适合定位失败步骤和网络/页面状态。

来源：

- <https://playwright.dev/docs/codegen>
- <https://playwright.dev/docs/locators>
- <https://playwright.dev/docs/best-practices>
- <https://playwright.dev/docs/trace-viewer>
- <https://playwright.dev/docs/auth>

### 1.4 Windows：UIAutomation 负责“找控件”，SendInput 负责“真输入”

Windows UI Automation 是 Windows 的无障碍和程序化 UI 访问框架，可以读取大部分桌面控件、属性和 control patterns，也可以执行控件支持的操作。它比看截图找坐标更稳定。

对于没有 UIA 暴露的游戏或自绘界面，最终仍然需要：

- 截图/图像匹配/OCR 识别状态。
- `SendInput` 注入鼠标与键盘事件。
- 低层鼠标/键盘 hook 用于录制。

需要注意：`SendInput` 受 UIPI 限制，权限较低的进程不能向权限更高的进程注入输入。因此普通权限的应用不能可靠操作管理员权限窗口。

来源：

- <https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-uiautomationoverview>
- <https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput>
- <https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw>

### 1.5 Electron：应用内浏览器可直接录制和回放

当前应用桌面端已经使用 Electron `<webview>` 和 CDP 操作浏览器。Electron 提供：

- `webContents.executeJavaScript`：注入录制器、读取 DOM。
- `webContents.sendInputEvent`：发送真实点击和键盘输入。
- `webContents.capturePage`：截图留证。
- `webContents.debugger`：使用 Chromium DevTools Protocol 完成更底层的输入、上传和截帧。

来源：

- <https://www.electronjs.org/docs/latest/api/web-contents>
- <https://chromedevtools.github.io/devtools-protocol/>

### 1.6 可靠性边界

Power Automate 的无人值守桌面流文档说明：无人值守运行依赖独立的 Windows/RDP 会话，锁定用户会话会阻止桌面流运行；录制和无人值守运行的分辨率不同，也可能造成元素找不到或键鼠点错。

因此产品上不能承诺：

- 电脑锁屏后仍能操作当前用户桌面。
- 不同分辨率、缩放、系统主题和软件版本下永远无需维护。
- 对任何游戏都能长期挂机。

可以承诺：

- 脚本可版本化、可审计、可暂停/恢复。
- 正常执行不依赖模型。
- 元素定位有明确降级顺序。
- 失败时留下可诊断证据。
- 用户确认后可局部修复，不必整条重录。

来源：

- <https://learn.microsoft.com/en-us/power-automate/desktop-flows/run-unattended-desktop-flows>
- <https://learn.microsoft.com/en-us/power-automate/desktop-flows/errors>

## 2. 当前仓库已有基础

当前仓库并不缺底层动作，缺的是一层把“固定流程”保存、编辑、运行和管理起来的产品层。

| 能力 | 当前实现 | 可直接复用 | 主要缺口 |
|---|---|---|---|
| 浏览器确定性配方 | `browser_run_recipe` + `recipes.ts` | 步骤执行、验证码阻断、续跑、备用选择器、回读验证 | 只有工具入口，没有录制/编辑/运行中心 |
| 浏览器文件配方 | `<工作目录>/recipes/*.json` | 可将固定步骤保存为数据 | 步骤类型有限，仅 navigate/upload/fill/clickText/waitText |
| 浏览器重复操作 | `browser_run_loop` | 键鼠循环、条件、until、轮数/时间/步数上限、Esc 中止 | 只覆盖浏览器页内，不是通用脚本管理 |
| pageAgent | `packages/shared/src/page-agent.ts` | 页面读取、点击、输入、上传、下载、配方、循环 | 由模型调用，不是固定脚本回放入口 |
| 桌面键鼠 | `computer-use` 插件 | 截图、点击、输入、快捷键、窗口枚举/激活、应用启动 | 目前是工具调用粒度，缺录制器和步骤时间线 |
| 桌面能力桥 | `desktop-capability` | 远程后端把 desktop-input 送回用户本机执行 | 缺 RPA 运行状态与脚本上下文 |
| 工作流引擎 | input/output/code/condition/loop/tool/LLM/sub_agent/human_confirm | 适合复杂编排与人工确认 | 不适合作为简单点击脚本的第一编辑界面 |
| 运维 Runbook | 版本、参数、审批、回滚、定时 | 可借鉴版本化、审批和固定版本执行 | 绑定 SSH 连接，步骤只有 exec/http/wait |
| 定时任务 | cron/interval + 工作流/Runbook | 可作为 RPA 触发器 | 需要增加 `task_type=rpa_script` |
| 后台长任务 | `background_job` 状态机与唤醒 | 可承载长时间脚本执行与 UI 进度 | 需要增加 automation 运行关联 |

- pageAgent 工具面：`packages/shared/src/page-agent.ts:23`
- 浏览器循环：`packages/core/src/tool/builtin/browser/index.ts:727`
- 桌面工具清单：`apps/server/src/plugins/computer-use.ts:49`

## 3. 产品方案

### 3.1 产品命名

建议对用户使用“自动化脚本”或“固定流程”，不要把所有功能都叫“RPA 智能体”。

“智能体”容易让用户误解为每次都要推理；“脚本”则准确表达：

- 步骤固定。
- 每次执行一致。
- 可手动编辑。
- 可定时运行。
- AI 可以协助，但不是执行前置条件。

### 3.2 三类脚本

| 类型 | 适用场景 | 主要执行器 |
|---|---|---|
| 浏览器脚本 | 登录、签到、搜索、填表、下载、上传、页面巡检 | 现有 `browser_run_recipe` / `browser_run_loop` |
| 桌面脚本 | 本地客户端点击、快捷键、窗口切换、导出、保存 | `computer-use` + 本地桌面能力桥 |
| 混合脚本 | 浏览器下载后交给桌面软件处理，再上传/归档 | 统一 Runner 调度多个 adapter |

文件处理不单独强调成第四种用户心智，而是作为脚本步骤：

- 文件存在/非空/哈希校验。
- 重命名、移动、复制、压缩、解压。
- Excel/CSV/PDF/图片处理。
- Python 批处理。

### 3.3 用户主流程

1. 新建自动化脚本。
2. 选择“录制浏览器”“录制桌面”或“手动添加步骤”。
3. 用户正常操作一次。
4. 系统自动归并输入、去掉无意义鼠标移动，生成步骤时间线。
5. 用户填写参数、设置成功判据和危险动作确认。
6. 在一个隔离环境中试运行。
7. 发布为固定版本。
8. 手动运行、定时运行、聊天调用或热键触发。
9. 失败时查看步骤截图、页面快照和修复建议。

### 3.4 页面结构

自动化首页：

```text
┌──────────────────────────────────────────────────────────────┐
│ 自动化脚本                     [录制浏览器] [录制桌面] [新建] │
├──────────────┬───────────────────────────────┬───────────────┤
│ 搜索/标签     │ 脚本列表                       │ 最近运行       │
│ 全部          │ 每日报表同步   浏览器  09:00   │ 成功 23        │
│ 浏览器        │ 客户资料整理   混合    手动    │ 失败 2         │
│ 桌面          │ 游戏签到       浏览器  已暂停  │ 平均 46 秒     │
│ 定时          │                               │               │
└──────────────┴───────────────────────────────┴───────────────┘
```

脚本详情：

```text
┌──────────────────────────────────────────────────────────────┐
│ 每日报表同步 v3        [试运行] [运行] [暂停] [停止] [发布]   │
├───────────────────────┬──────────────────────┬───────────────┤
│ 步骤时间线             │ 当前页面/窗口预览     │ 参数与定位     │
│ 1 打开系统             │                      │ 账号：已绑定    │
│ 2 点击“报表中心”       │  截图 / 页面预览      │ 日期：{{today}}│
│ 3 选择日期             │                      │ 成功判据       │
│ 4 点击“导出”           │                      │ 文件存在       │
│ 5 等待文件完成         │                      │               │
│ 6 打开本地 Excel       │                      │               │
└───────────────────────┴──────────────────────┴───────────────┘
```

运行态只显示当前步骤、进度和必要控制，不把整条脚本和全部日志同时铺开。点击某一步再查看详情。

### 3.5 步骤编辑方式

默认使用线性时间线，而不是让用户先画 DAG：

- 支持拖动排序。
- 单步启用/禁用。
- 单步修改参数。
- 单步试跑。
- 从任意安全步骤继续。
- 插入等待、条件、循环、文件处理、人工确认。

复杂脚本再提供“升级为工作流”，转换成现有 Workflow DAG。不要让十次固定点击先进入 Vue Flow 画布。

### 3.6 智能体分工与统一入口

这个需求不仅是一个录制器，还需要一个统一负责“把业务需求变成固定脚本”的智能体。

但必须把三种能力拆开：

| 能力层 | 负责什么 | 谁拥有 |
|---|---|---|
| **RPA Builder 智能体** | 问需求、设计流程、选择定位策略、生成草稿、校验、试跑、解释失败 | 自动化模式主智能体；也可作为其他主智能体的子智能体 |
| **脚本编辑工具** | create/update/validate/test/record/publish | RPA Builder；必要时按权限挂给办公、开发等主智能体 |
| **脚本运行工具** | list/get/run/getRun/cancel | 所有业务主智能体，按工具权限放行 |

建议新增内置智能体：

```text
id: a_builtin_rpa_builder
name: 自动化脚本设计师
type: harness
agent_kind: main
```

它有两种使用形态：

1. **自动化模式主智能体**：可以直接调用 pageAgent，边看页面边设计、录制和试跑脚本。
2. **其他智能体的子智能体**：办公助手等通过 `call_agent` 把业务目标交给它，由它生成脚本草稿。

当前运行时的子智能体只允许一层，子智能体不能再调用子智能体。因此第二种形态下，RPA Builder 不能再委派 pageAgent。调用方需要：

- 先让 pageAgent 采集页面结构、截图或现有配方证据，再交给 RPA Builder。
- 或者让用户进入自动化模式，由主形态的 RPA Builder 自己调用 pageAgent。

这不是缺陷，而是当前 agent depth 契约下的明确边界。不要为了一个功能贸然把全局嵌套深度改成多层。

#### RPA Builder 的工具面

```text
rpa_script_list
rpa_script_get
rpa_script_create_draft
rpa_script_update_draft
rpa_script_validate
rpa_script_test
rpa_script_get_run
rpa_recording_start
rpa_recording_stop
rpa_repair_suggest
```

发布不直接依赖模型自证：

```text
rpa_script_publish
```

该工具必须带后端生成的用户确认凭证，或由自动化模式 UI 的“发布”按钮调用。模型只能提出发布建议，不能静默替换正式版本。

#### 其他业务智能体的工具面

所有适合自动化能力的主智能体默认只挂运行类工具：

```text
rpa_script_list
rpa_script_get
rpa_run_script
rpa_get_run
rpa_cancel_run
```

办公、开发、运维等有明确授权的主智能体可以额外挂：

```text
rpa_script_create_draft
rpa_script_update_draft
rpa_script_validate
rpa_script_test
```

但即使挂了编辑工具，也不能直接修改已发布版本。编辑只能产生草稿或新版本。

办公助手建议挂载：

```json
{
  "builtin_tool_ids": [
    "rpa_script_list",
    "rpa_script_get",
    "rpa_run_script",
    "rpa_get_run",
    "rpa_cancel_run"
  ],
  "sub_agent_ids": [
    "a_builtin_page_agent",
    "a_builtin_data_agent",
    "a_builtin_rpa_builder"
  ]
}
```

这样办公助手的典型路径是：

```text
用户：把每天导出报表再上传到财务系统的流程做成自动化
  -> 办公助手判断这是自动化脚本创作任务
  -> call_agent { agentId: "a_builtin_rpa_builder", input: "<完整业务目标、系统、输入输出和验收标准>" }
  -> RPA Builder 生成脚本草稿
  -> 用户在自动化模式检查步骤、试跑、补充选择器或参数
  -> 用户发布
  -> 后续任何有权限的智能体通过 rpa_run_script 调用
```

RPA Builder 的系统提示词应强制：

- 先问清目标系统、输入、输出、触发方式、成功判据和危险动作。
- 优先使用录制步骤和稳定元素定位，不把坐标当第一选择。
- 优先少步骤、可重放、可验证的脚本，不生成“让模型现场看着办”的步骤。
- 密码、验证码、支付信息不进入脚本明文。
- 任何选择器、窗口或模板不能凭空编造；缺证据时要求补充或进入录制模式。
- 生成后必须执行 schema 校验和安全预检。
- 试跑成功后还要用户确认才能发布。
- 失败时只提出局部修复建议，不静默重写整条脚本。

#### 统一创建入口

统一入口不等于只能从一个页面创建。建议同时提供四个入口：

| 入口 | 使用方式 |
|---|---|
| 自动化模式 | 脚本库 → 新建/录制，最完整的管理与编辑入口 |
| 任意智能体聊天 | 用户直接描述业务目标，智能体委派 RPA Builder 生成草稿 |
| 成功任务后保存 | 一个已经跑通的工具流程提供“保存为自动化脚本” |
| 高级编辑 | 用户直接编辑 JSON/YAML，或导入脚本文件 |

其中“成功任务后保存”很重要：用户本来就在聊天里完成了一次真实操作，系统可以把已经验证过的动作序列转成脚本草稿，而不是让用户重新录一遍。

### 3.7 是否单独增加“自动化模式”

**建议单独增加。**

建议模式元数据：

```text
key: rpa
label: 自动化模式
route: /automation
fallbackAgent: a_builtin_rpa_builder
lead: human
chatPlacement: right
```

不建议把它塞进现有工作流模式，原因如下：

| 维度 | 工作流模式 `wf` | 自动化模式 `rpa` |
|---|---|---|
| 核心对象 | DAG 工作流 | 固定步骤脚本 |
| 主要编辑方式 | Vue Flow 节点画布 | 录制 + 线性时间线 |
| 执行语义 | 节点/分支/LLM 编排 | 确定性重放、低延迟 |
| 典型任务 | 生成报告流水线、多节点 AI 流程 | 每日签到、导出上传、桌面点击 |
| 调试重点 | 节点输入输出 | 失败步骤、元素定位、截图证据 |
| Agent 角色 | 工作流运行助手 | 自动化脚本设计师 |

合并会增加用户认知负担：用户只是要录十个点击，不应该先理解 DAG、LLM 节点和节点连线。

自动化模式建议采用“人主导、对话在右”的形态：

```text
┌──────────────────────────────────────────────────────────────┐
│ 脚本库                  [录制浏览器] [录制桌面] [新建脚本]    │
├──────────────┬───────────────────────────────┬───────────────┤
│ 脚本/文件夹   │ 步骤时间线 / 脚本编辑器 / 运行台 │ RPA Builder   │
│ 最近运行      │ 当前步骤、截图、定位、成功判据   │ 需求整理      │
│ 模板          │                               │ 修复建议      │
└──────────────┴───────────────────────────────┴───────────────┘
```

AI 主导形态可以保留，但默认不要让聊天抢占脚本库和步骤编辑器。用户来这个模式主要是管理、录制和运行固定流程。

工作流模式和自动化模式应互相跳转：

- 自动化脚本变复杂时，“升级为工作流”。
- 工作流里某一段是固定点击/文件操作时，“提取为自动化脚本”。

## 4. 总体架构

```text
┌──────────────────────────────────────────────────────────────┐
│ 自动化中心 UI                                                 │
│ 录制器 / 步骤编辑器 / 运行控制 / 运行历史 / 修复建议           │
└──────────────────────────────┬───────────────────────────────┘
                               │ HTTP / WS / SSE
┌──────────────────────────────▼───────────────────────────────┐
│ AutomationRunner                                             │
│ 参数校验 / 步骤调度 / 暂停停止 / 重试 / 证据 / 审批 / 检查点    │
└───────────────┬──────────────────┬───────────────────────────┘
                │                  │
      ┌─────────▼────────┐ ┌──────▼─────────┐ ┌───────────────┐
      │ BrowserAdapter   │ │ DesktopAdapter │ │ FileAdapter   │
      │ 现有 recipe/CDP  │ │ computer-use   │ │ fs/Python     │
      └─────────┬────────┘ └──────┬─────────┘ └───────────────┘
                │                 │
      ┌─────────▼────────┐ ┌──────▼───────────────────────────┐
      │ Electron webview │ │ 本机桌面能力桥 / Windows helper  │
      │ Playwright/CDP   │ │ UIA + image/OCR + SendInput      │
      └──────────────────┘ └──────────────────────────────────┘

持久化：automation_script / script_version / automation_run / run_event / artifact
触发：手动 / 聊天 / 定时任务 / 热键 / 文件夹监听 / 内部事件
```

关键边界：

- `AutomationRunner` 不依赖 LLM。
- Browser、Desktop、File 分别实现 adapter。
- 正式执行只接受已发布版本的脚本。
- AI 只读取失败证据并生成候选补丁，不直接接管正式运行。

## 5. 脚本契约

### 5.1 脚本结构


### 5.2 步骤类型

首版建议收敛为以下集合：

| 分类 | 步骤 |
|---|---|
| 浏览器 | navigate / click / type / pressKey / select / upload / download / waitFor / extract / screenshot |
| 桌面 | activateWindow / click / doubleClick / rightClick / move / drag / scroll / type / pressKey / screenshot / waitForImage / waitForText |
| 文件 | read / write / copy / move / rename / deleteToTrash / exists / wait / hash |
| 流程 | wait / condition / loop / subflow / humanConfirm / setVariable |
| 证据 | screenshot / pageSnapshot / windowSnapshot / assert |

不要在第一版开放“任意按键序列”或“任意 PowerShell”作为可导入脚本步骤。需要命令执行时使用已有受控工具，不要绕过权限和审计。

### 5.3 目标定位

浏览器目标：

```ts
type BrowserTarget =
  | { by: 'role'; role: string; name: string; exact?: boolean }
  | { by: 'label'; label: string }
  | { by: 'placeholder'; placeholder: string }
  | { by: 'testId'; testId: string }
  | { by: 'text'; text: string; exact?: boolean }
  | { by: 'css'; selector: string }
  | { by: 'frame'; frameUrl: string; target: BrowserTarget }
  | { by: 'point'; x: number; y: number };
```

桌面目标：

```ts
type DesktopTarget =
  | { by: 'uia'; processName: string; windowTitle?: string; automationId?: string; name?: string; role?: string }
  | { by: 'image'; template: string; threshold: number; region?: Rect }
  | { by: 'ocr'; text: string; region?: Rect; language?: string }
  | { by: 'windowPoint'; x: number; y: number }
  | { by: 'screenPoint'; x: number; y: number };
```

优先级固定：

1. 可访问性语义。
2. 稳定属性和相对结构。
3. 图像/OCR 锚点。
4. 窗口相对坐标。
5. 屏幕绝对坐标。

每个目标都可以保存 fallback 列表。录制器自动生成，用户可以手动调整顺序。

## 6. 录制器设计

### 6.1 浏览器录制

在应用内 `<webview>` 或受控浏览器页面注入 capture-phase 事件监听：

- `click` / `dblclick` / `contextmenu`
- `input` / `change`
- `keydown` 中的 Enter、Tab、Esc 和组合键
- `scroll` 结束后的汇总
- 导航、下载开始、文件选择器、弹窗

录制器只记录高层意图，不记录每一次 mousemove：

- 同一输入框 1.5 秒内的键入合并为一个 type 步骤。
- 仅当 click 后确实出现导航/弹窗/下载时，自动补一个 wait/verify。
- 密码框、验证码、支付字段默认不记录值，只记录“需要人工输入”占位。
- 使用稳定 selector 生成规则，并保留备用定位。

生成顺序建议：

1. `role + accessible name`
2. `label` / `placeholder`
3. `data-testid` / 稳定 `name` / 稳定 `id`
4. 可见文本
5. 相对 CSS
6. 坐标兜底

### 6.2 桌面录制

桌面录制通过本机 helper 的低层键鼠 hook 获取事件，同时读取：

- 当前前台窗口的进程名、标题、窗口矩形和 DPI。
- 鼠标位置下的 UI Automation 元素。
- 可选的小区域截图和 OCR 文本。

同样只记录高层动作：

- 左/右/双击。
- 键盘输入合并。
- 快捷键。
- 窗口切换。
- 滚动和拖拽。

录制期间必须有明显的全局提示“正在录制”，并提供停止热键。不能静默长期监听键盘。

### 6.3 录制后的自动整理

录制结束先进入“草稿”，不要直接发布：

- 删除无意义移动和重复点击。
- 合并连续输入。
- 将固定等待改为优先等待条件。
- 标注可能的危险动作：提交、发布、删除、支付、发送消息。
- 提示补充成功判据。
- 用户在时间线里手动确认。

## 7. 运行时设计

### 7.1 状态机

```text
queued
  -> preparing
  -> running
  -> waiting_user
  -> paused
  -> retrying
  -> completed
  -> failed
  -> cancelled
```

规则：

- 暂停和停止发生在步骤边界，不强杀正在执行的短动作。
- 桌面脚本暂停后立即释放输入锁。
- 浏览器脚本可以继续保留页面，恢复时从下一条安全步骤开始。
- 每一步可选择“可安全重试”或“执行结果未知时必须人工确认”。
- 完成后必须运行确定性断言，不能仅凭“点击成功”标记完成。

### 7.2 执行流程

```text
加载脚本固定版本
  -> 校验参数、权限、窗口和页面前置条件
  -> 创建 automation_run
  -> 为本次运行创建独立浏览器标签/桌面上下文
  -> 逐步执行
      -> 选目标
      -> 执行动作
      -> 等待条件
      -> 运行断言
      -> 写步骤结果和证据
  -> 执行后置校验
  -> completed / failed / paused
```

正常回放不调用 LLM。这样速度由动作本身决定，不会被模型延迟放大。

### 7.3 检查点和副作用

需要区分三类步骤：

| 类型 | 示例 | 重启/失败后策略 |
|---|---|---|
| 可重试 | 等待、读取、截图、查询 | 自动重试 |
| 可核对 | 填表、普通本地保存 | 先读当前状态，再决定是否重做 |
| 不可盲目重试 | 发布、发送、支付、删除、外部提交 | 进入人工确认，不自动重放 |

这与后台长任务现有的“结果未知时先核对，再决定”原则一致。

## 8. 三类执行适配器

### 8.1 BrowserAdapter

直接复用：

- `browser_run_recipe` 的步骤执行和验证码阻断/续跑。
- 文件配方 `<工作目录>/recipes/*.json`。
- `browser_run_loop` 的 rounds、until、if、maxSeconds、maxSteps、Esc 中止。
- 页面读取、截图、上传、下载和网络日志工具。

建议新增：

- `automation.runBrowserStep`：将统一脚本步骤映射为现有 browser action。
- 每个 run 使用独立 `runId` 对应的标签页，避免和用户当前页面互相抢控制权。
- 执行后自动生成 Trace 式证据包：URL、标题、关键 DOM、下载记录、截图和失败步骤。

第一版浏览器脚本可以直接编译为现有 `PublishRecipe` 的扩展格式，减少新执行器数量。

### 8.2 DesktopAdapter

直接复用：

- `computer-use` 的截图、鼠标、键盘、窗口枚举/激活。
- 桌面能力桥，把远程后端的 computer 工具送回用户本机执行。
- 现有急停、操作上限、自窗点击拒绝和审计。

建议新增：

- UIA 元素定位和控件操作。
- 窗口绑定与前台校验：目标窗口不在前台时先激活，激活失败就暂停。
- 图像模板/OCR 目标定位。
- 相对窗口坐标。
- 录制器与窗口快照。

现有 `computer-use` 每次动作启动 PowerShell 的模式适合办公操作，不适合几十毫秒级游戏循环。游戏场景应走后续的常驻桌面 helper。

### 8.3 FileAdapter

复用现有文件工具和 Python 能力：

- 文件读写、列表、搜索。
- Excel/CSV/PDF/图片处理。
- 输出验证：存在、非空、大小、哈希、行数、字段数。
- 产物登记、失败截图和日志。

所有路径必须限制在工作区或用户明确授权的目录内。删除默认进入回收站或先备份。

## 9. 挂机游戏场景

### 9.1 浏览器游戏

现有 `browser_run_loop` 已经覆盖：

- 点击、移动、拖拽、按键、长按。
- 多键组合。
- 页面内读取状态。
- 条件分支。
- until 停止条件。
- 轮数、总时长、总步数硬上限。
- Esc 中止。

固定挂机脚本可以把它产品化为“循环步骤”，无需模型每轮参与。

### 9.2 桌面游戏

桌面游戏通常不暴露 UIA，需要单独执行档：

- 目标窗口绑定。
- 快速截图。
- 图像模板匹配或 OCR 识别状态。
- 键鼠输入。
- 固定 tick 循环。
- 状态不确定时暂停，而不是盲点。

`SendInput` 受 UIPI 限制，管理员权限游戏或受保护进程可能无法操作。不同分辨率、DPI、窗口大小和游戏版本都会影响坐标/模板，脚本必须保存窗口信息、DPI 和模板版本。

图像模板匹配的官方概念可参考 OpenCV：

- <https://docs.opencv.org/4.x/d4/dc6/tutorial_py_template_matching.html>

### 9.3 产品边界

- 不承诺绕过游戏反作弊或平台风控。
- 不承诺锁屏状态下的桌面挂机。
- 游戏脚本默认使用独立窗口和明确停止热键。
- 用户离开电脑时应锁定目标窗口；目标窗口失焦立即暂停。
- 目标识别置信度不足时宁可不点，不猜坐标。

游戏应该被定义为“桌面快速执行档”，而不是第一版办公固定脚本的核心验收场景。

## 10. AI 的边界

AI 适合做四件事：

1. 根据自然语言生成脚本草稿。
2. 把一次录制整理成可读步骤。
3. 失败后根据 DOM/截图生成局部修复候选。
4. 解释失败原因并建议下一步。

AI 不适合做三件事：

1. 正常回放的每一步都参与决策。
2. 自己判断“任务完成”。
3. 未确认就修改正式脚本版本。

修复流程：

```text
步骤失败
  -> 确定性 fallback 尝试
  -> 收集页面/窗口/截图/定位证据
  -> AI 输出候选补丁
  -> 对比旧定位和新定位
  -> 用户确认
  -> 写入新版本
```

AI 生成的补丁只允许修改目标定位、等待条件或参数映射，不允许悄悄扩大权限或新增外部提交动作。

## 11. 安全与权限

固定脚本比聊天工具更需要严格权限，因为它可以在无人值守时连续操作。

必须遵守：

- `desktop-input` 明确授权，首次启用和首次录制分别确认。
- 录制状态全局可见，提供停止热键。
- 密码、验证码、支付信息默认不录制明文。
- 脚本保存浏览器域、桌面进程、文件根目录白名单。
- 禁止点击本应用自身窗口，现有 `computer-use` 已有该护栏。
- 禁止操作高于本应用权限级别的窗口，并给出 UIPI 原因。
- 提交、发布、删除、支付、群发等动作设置审批门。
- 每次运行、每步结果和危险动作写审计日志。
- 脚本导入先校验 schema、步骤类型、路径和域名，不执行任意代码。
- 运行中的脚本可以暂停、停止和人工接管。

### 13.2 智能体工具

```text
rpa_list_scripts  列出用户可运行的固定脚本
rpa_run_script    按 scriptId + params 启动脚本，返回 runId
rpa_get_run       读取运行状态和当前步骤
rpa_cancel_run    取消运行
rpa_repair_script 读取失败证据并生成修复建议，不直接发布
```

`rpa_run_script` 只允许调用已发布、已授权版本。模型不能直接传任意步骤或任意脚本代码执行。

## 14. 与现有模块的接入方式

| 现有模块 | 接入方式 | 不做什么 |
|---|---|---|
| `browser_run_recipe` | 作为 BrowserAdapter 的首选执行器 | 不复制第二套浏览器动作 |
| `browser_run_loop` | 作为浏览器循环步骤执行器 | 不让模型每轮重新规划 |
| `computer-use` | 作为桌面动作执行器 | 不重新写 PowerShell 键鼠层 |
| `desktop-capability` | 保证桌面动作在用户本机执行 | 不静默回落到后端机器 |
| Workflow | 高级编排和“升级为工作流” | 不强迫简单脚本使用 DAG |
| Ops Runbook | 复用版本、审批、固定版本、运行历史思路 | 不把 SSH 连接模型硬套到浏览器/桌面 |
| 定时任务 | 新增 `task_type=rpa_script` | 不新建第二套定时器 |
| 后台任务 | 长脚本关联 `background_job` | 不让模型持续轮询 |
| 权限系统 | 复用工具权限、插件权限和审批门 | 不新增绕过路径 |
| 产物系统 | 复用 `conversation_file`/artifact | 不把文件散落在临时目录 |
| 内置智能体系统 | 新增 `a_builtin_rpa_builder`，复用 `agent_kind/sub_agent_ids/call_agent` | 不新建第二套 Agent 协议 |

## 15. 分阶段落地

### P0：自动化模式 + RPA Builder + 浏览器固定脚本闭环，5-7 人日

交付：

- 自动化脚本 schema 和序列执行器。
- 新增 `rpa` 模式和自动化工作台骨架。
- 新增 `a_builtin_rpa_builder`。
- 办公助手挂载 RPA Builder 与运行类脚本工具。
- 运行类工具按权限挂给其他主智能体。
- 浏览器 click/type/press/select/wait/upload/download 步骤。
- 复用 `browser_run_recipe`。
- 简单脚本列表和步骤时间线。
- 手动创建、试运行、运行、停止、运行历史。
- `rpa_run_script` 工具。

验收：

- 用户可在自动化模式创建脚本，也可在办公聊天里让 RPA Builder 生成草稿。
- 其他智能体可以列出并运行有权限的脚本，但不能修改已发布版本。
- 录制或手写一个 10 步浏览器流程，成功执行 20 次。
- 正常回放不产生模型调用。
- 失败时保存失败步骤、URL 和截图。

### P1：浏览器录制器，4-6 人日

交付：

- 在应用内浏览器录制 click/input/keydown/navigation/download。
- 自动生成 role/label/testid/text/CSS 定位和 fallback。
- 密码与敏感字段脱敏。
- 录制草稿编辑与发布。

验收：

- 普通后台表单操作录制后无需手写 JSON。
- 动态 class 变化后优先命中 role/text，不因 hash class 失效。

### P2：桌面固定脚本，5-8 人日

交付：

- 桌面录制器。
- UIA 优先定位。
- 图像/OCR 兜底。
- 窗口相对坐标。
- 窗口激活、失焦暂停、自窗点击拒绝。
- 文件处理步骤。

验收：

- 完成“打开本地应用 → 点击 → 输入 → 保存 → 校验文件”。
- 100% 和 125% DPI 下均可通过窗口相对定位执行。
- 权限不足时明确提示 UIPI，而不是静默失败。

### P3：流程能力和触发，4-6 人日

交付：

- 参数、变量、条件、循环、子脚本。
- 定时任务、文件夹监听、热键触发。
- 审批门槛和暂停/恢复。
- 失败修复建议。

验收：

- 同一个脚本可按日期、文件路径、客户名等参数重复运行。
- 定时任务固定使用已发布版本。
- 发布/发送/删除动作未审批时物理上无法执行。

### P4：桌面快速执行档，5-10 人日

交付：

- 常驻桌面 helper。
- 快速截图与窗口绑定。
- 图像模板匹配/OCR 状态识别。
- 固定 tick 循环。
- 游戏/自绘应用测试样本。

验收：

- 目标窗口移动后仍能通过模板锚点定位。
- 失焦、锁屏、分辨率变化时立即暂停并说明原因。
- 不依赖模型持续参与。

## 16. 推荐首个演示

最稳妥的首个演示是“浏览器下载 → 文件校验 → 本地处理 → 上传/归档”，因为仓库已有下载、上传和文件处理能力。

示例：

1. 打开财务/客服/ERP 页面。
2. 点击导出。
3. 等待下载完成并校验文件非空。
4. 用 Python 校验行数或按要求重命名。
5. 上传到另一个系统。
6. 回读成功提示并记录回执。

第二个演示：

1. 打开本地桌面软件。
2. 激活指定窗口。
3. 点击固定位置或图像锚点。
4. 输入变量。
5. 快捷键保存。
6. 校验输出文件。

游戏挂机演示放到 P4，先在浏览器游戏中使用现有 `browser_run_loop` 验证，再决定是否投入桌面快速执行器。

## 17. 验收标准

- [ ] 固定脚本正常回放全程不调用 LLM。
- [ ] 脚本有不可变版本，定时任务锁定已发布版本。
- [ ] 浏览器定位优先语义属性，坐标只作兜底。
- [ ] 桌面定位优先 UIA，图像/OCR 次之，坐标最后。
- [ ] 每一步都有成功判据或明确的人工验收。
- [ ] 失败时保存截图、页面/窗口信息和失败步骤。
- [ ] 暂停/停止在步骤边界生效，停止后释放键鼠输入锁。
- [ ] 不可逆动作支持审批和“结果未知时人工确认”。
- [ ] 密码、验证码和敏感字段不进入脚本明文。
- [ ] 脚本导入有白名单校验，不执行任意代码。
- [ ] 页面刷新或应用重启后，运行历史和证据仍可查看。
- [ ] 桌面脚本在目标窗口失焦时暂停，不向错误窗口输入。
- [ ] 锁屏/无人值守边界在 UI 中明确说明。

## 18. 关键决策建议

| 决策 | 推荐值 |
|---|---|
| 是否新增自动化模式 | 是，独立 `rpa` 模式，工作台居中、对话在右 |
| 是否新增专属创建智能体 | 是，`a_builtin_rpa_builder` |
| Builder 能否被其他智能体调用 | 能，通过 `sub_agent_ids + call_agent` |
| 办公助手是否挂载 Builder | 是 |
| 其他智能体默认能力 | 运行/查询/取消脚本；编辑能力按权限另开 |
| 脚本发布权限 | 只允许用户确认或自动化模式 UI 发布 |
| 第一版是否让 AI 每步参与 | 否 |
| 简单脚本主界面 | 线性步骤时间线 |
| 复杂流程 | 可升级为 Workflow DAG |
| 浏览器执行器 | 复用 `browser_run_recipe` / `browser_run_loop` |
| 桌面执行器 | 复用 `computer-use`，新增 UIA/图像定位与录制器 |
| 文件处理 | 作为脚本步骤，复用文件工具和 Python |
| 定时入口 | 复用 `scheduled_task` |
| 长任务 | 复用 `background_job` |
| 正式执行版本 | 只运行已发布版本 |
| AI 修复 | 生成补丁候选，用户确认后发新版本 |
| 目标平台 | Windows 先做完整桌面能力，macOS 保持基础能力 |
| 游戏挂机 | P4 独立快速执行档，不进第一版通用脚本 |
| 锁屏运行 | 不承诺；需要独立 Windows/RDP 会话时再设计远端执行节点 |

## 19. 待拍板问题

1. 首个真实流程选浏览器、桌面，还是混合流程？
2. 桌面录制是否默认只允许当前用户本机运行，还是允许企业远程节点？
3. 游戏挂机是否是明确产品方向；如果只是内部试验，建议先不进正式产品界面。
4. 是否需要脚本分享、导入导出和模板市场；如果要，需先确定签名和权限审查。

## 20. 最终建议

1. **先把“固定脚本”产品化，不要把主体验做成每次问模型的 Agent。**
2. **浏览器先落地，因为现有 recipe、pageAgent、CDP 和下载上传链路最完整。**
3. **桌面第二步落地，优先 UIA，图像/OCR 和坐标作为兜底。**
4. **文件处理作为统一步骤，复用现有工具和 Python，不另起文件引擎。**
5. **单独增加自动化模式，作为脚本库、录制、运行历史和人工编辑的统一工作台。**
6. **新增 `a_builtin_rpa_builder`，办公助手和其他主智能体通过 `call_agent` 统一委派脚本创作。**
7. **所有业务智能体默认只拿运行类脚本工具，编辑和发布权限单独收敛。**
8. **智能体只负责起草、整理、修复和解释，正式回放保持确定性。**
9. **游戏挂机单独做快速执行档，先验证浏览器循环，再决定桌面高频执行器。**

最终产品形态可以概括为：

> 用户像录宏一样录一次固定流程，系统像 RPA 一样稳定重放；页面改版或窗口变化时，智能体先给修复建议，而不是每次重新思考怎么点。

# UI 设计规范 · 数据工作台

> 本文是 `design.md` / `design-addendum.md` 的 UI 层配套。高保真原型见同目录 `ui-prototype.html`（单文件，浏览器直接打开，左侧导轨切 5 个视图）。
> 冲突时：**功能语义**以 `design-addendum.md` 为准，**视觉与交互**以本文与原型为准。

---

## 0. 设计取向

题材是「数据治理 + 语义编译」，不是通用 SaaS 仪表盘。所以刻意避开了 AI 工具的默认长相（渐变文字、玻璃拟态、圆角投影卡片网格、hero 大数字）。

定的方向是 **「编目卡片 + 仪器面板」**：

| 概念 | 视觉手段 | 为什么 |
|---|---|---|
| 编目 | 发丝线分隔 + 等宽 code 列 + 小圆角（3/5/8px） | 本体是数据字典，气质接近档案卡而非营销卡片 |
| 仪器 | 浅色工作台里嵌一块 `--void #14161A` 深色 SQL 面板 | SQL 是「读数」区域，深底给它仪器感与专注边界 |
| 编译 | 签名元素「编译轨道」：意图 → 关系路径 → 物理 SQL → 结果 | 把「AI 到底在干什么」可视化，是本产品区别于通用 BI 的核心叙事 |

**唯一允许花哨的地方是编译轨道**。其余一切从简：全局只留 2 级阴影、0 个 pill 圆角、0 处渐变。

## 1. 设计令牌

沿用言智品牌紫 `#7C3AED`（既有产品约定），其余全部具名而非 `primary/secondary`——因为这套页面里颜色承担**功能语义**，抽象命名会立刻失效。

### 1.1 表面与文本

| Token | 值 | 用途 |
|---|---|---|
| `--canvas` | `#FBFAFD` | 工作台底色（比全局 `--color-bg #f8fafc` 更冷更浅，形成「另一个工作面」的暗示） |
| `--surface` | `#FFFFFF` | 卡片 / 面板 |
| `--ink` | `#14161A` | 主文本（带蓝调近黑，非纯黑） |
| `--ink-2` | `#5B6070` | 次要文本 |
| `--ink-3` | `#8E93A6` | 弱文本 / 占位 / 元信息 |
| `--rule` | `#E7E5EE` | 发丝分隔线 |
| `--rule-strong` | `#D3D0DE` | 表头下边 / 输入框边 |

### 1.2 状态色

| Token | 值 | 语义 |
|---|---|---|
| `--brand` | `#7C3AED` | 品牌 / 度量 / 主行动 |
| `--signal` | `#0E9F8F` | 成功 / 已连接 / 数值正向 |
| `--caution` | `#B4710A` | 草稿 / 待复核 / **AI 建议未采纳** |
| `--danger` | `#D6336C` | 拒绝 / 敏感 / **写操作** |

每个状态色配 `-soft`（底）与 `-line`（边）两个衍生值，禁止直接用主色铺底。

### 1.3 语义角色色（本体字段角色）

这不是装饰，是**功能编码**——用户扫一眼表格就要能分辨字段是维度还是度量：

| 角色 | Token | 值 |
|---|---|---|
| 实体 entity | `--role-entity` | `#334155` slate |
| 维度 dimension | `--role-dim` | `#0E9F8F` teal |
| 度量 measure | `--role-measure` | `#7C3AED` 品牌紫 |
| 时间维度 time | `--role-time` | `#4F7DF3` blue |
| 过滤器 filter | `--role-filter` | `#B4710A` amber |
| 行级策略 policy | `--role-policy` | `#D6336C` rose |

### 1.4 深色仪器面板

| Token | 值 | 用途 |
|---|---|---|
| `--void` | `#14161A` | **派生产物**（编译出的 SQL、只读） |
| `--void-2` | `#1C1F27` | **源文件态**（YAML、可改）+ 面板顶栏 |
| `--void-3` | `#2A2E38` | 深色内分隔线 |
| `--void-ink` / `--void-ink-2` | `#E6E8EE` / `#8B91A3` | 深色区主/次文本 |

> **关键规则**：源文件态与派生产物必须一眼可分。源文件用 `--void-2` + 紫色 `源文件 · 可改` 角标；派生产物用 `--void` + 灰色 `派生 · 只读` 角标。否则用户会去改错地方——而在 text2sql 场景里，改错口径就是事故。

### 1.5 字体三角色

| 角色 | 字体栈 | 用在哪 |
|---|---|---|
| Display | `Space Grotesk` → 苹方/雅黑 | 页面标题、分段标签（大写 + `.1em` 字距） |
| Body | `IBM Plex Sans` → 苹方/雅黑 | 正文、标签、说明，基准 **13px / 1.55** |
| Mono | `JetBrains Mono` → Consolas | code、SQL、YAML、枚举 key、**所有数值**（`font-variant-numeric: tabular-nums`） |

> 中文标题会 fallback 到苹方/雅黑，效果可接受。但**中英混排标题**（同一按钮内）会出现字形断层，落地时需为中文标题单独声明 `PingFang SC` 600 字重。

### 1.6 尺度

- 间距：4 基准 → `4 / 8 / 12 / 16 / 20 / 24 / 32 / 40`
- 圆角：`3 / 5 / 8 / 12`px。**数据工具用小圆角，拒绝 pill**
- 阴影：只两级。`--sh-1` 卡片静置，`--sh-2` 浮层。**其余一律用发丝线代替阴影**

## 2. 五个页面规格

### 2.1 数据源（`v-ds`）

**布局**：顶部固定筛选条（搜索 + 同步结构 + 新建）→ 下方独立滚动的卡片网格。遵循项目既有约定：*筛选固定顶部、列表区独立滚动，禁止整页滚动遮挡筛选*。

**类型选择器分三组**，而非 8 个 chip 平铺：

- 关系型 · 支持自动 JOIN → MySQL / PostgreSQL / 达梦 DM / Oracle / SQLite
- 内置 → 言智项目库
- 文档型 · 无 JOIN 下推 → MongoDB / Elasticsearch（虚线边 + 弱化文字，暗示能力受限）

> 分组不是为了好看，是把「8 个选项」切成 3 个 ≤5 的语块降认知负荷，同时**把能力差异写进分组标题**——用户选 MongoDB 前就知道没有自动 JOIN。

**新建表单是临时态**，视觉重量必须**低于**常态卡片：白底 + 左侧 2px 品牌色竖线，不铺紫色底。

**四种连接态**：已连接（teal 点）/ 未同步（琥珀）/ 连接失败（玫红）/ 文档型（标注不支持 JOIN 下推）。

**失败态必须带诊断**。只给一个「重新测试」等于让用户盲查十几分钟。折叠展开给错误码解释：

```
ORA-12170 是什么？如何排查
  1. 防火墙 / 安全组未放通 1521
  2. 监听未启动：目标机执行 lsnrctl status
  3. 服务名写错：ORCLPDB1 与实际 PDB 不一致
  [复制错误码与连接串]
```

**写操作**：`允许写操作` 默认关闭，且文案明确「需在会话中限时开启」。

### 2.2 本体管理（`v-ont`）

**三栏**：左 264px 本体列表（筛选固定顶部）｜中 主编辑区（5 子页签）｜右 360px 编译预览。

**5 个子页签**，各带计数徽标：语义 / 字段（12）/ 关系（3）/ 示例问答（4）/ YAML。

#### 语义页 — 必须分三段

7 个字段一字排开是一堵墙。切成：

| 分段 | 含什么 | 段说明（写给用户的风险提示） |
|---|---|---|
| **标识** | code、名称 | 改 code 会断开引用它的智能体 |
| **语义** | 业务描述、同义词、业务域 | 大模型只看这一段来决定选不选它 |
| **物理** | 来源 SQL | 大模型看不到这一段，只有编译器用 |

同义词用 **chip 输入**而非 textarea——「一组短标签」的心智不该用多行文本框表达。

来源 SQL 区顶栏显示 `7 输出列 · 全部已别名`，直接把 addendum 里的 **H2 别名校验**做成可见状态。

#### 字段页 — 一行内表达四件事

表格列：角色徽标 / 名称 / 描述 / 表达式 / 聚合 / 枚举与单位 / **置信度** / **锁**。

- 置信度 < 0.70 的行浅黄底（`#FFFEFA`），且**未复核不允许发布**
- 锁图标 = 人工已确认，结构同步永不覆盖（对应 addendum 的 `locked=1`）
- `AI 草稿` 徽标用 `--caution`，与人工确认的字段视觉分离

#### 关系页 — 大模型不写 JOIN

关系图 SVG + 关系表（左/右/基数/ON/状态）。底部**扇出风险警示卡**（琥珀）：

> 检出 1 处扇出风险（chasm trap）：路径 `order → order_item → refund` 同时取 `pay_amount_sum` 与 `refund_amount_sum` 会让金额按明细行数翻倍。引擎将**直接拒绝**，并提示先建聚合本体。

这张卡是关系页的实质内容，不是填白——它把 addendum 里最容易出事故的规则前置暴露。

#### YAML 页 — 源文件态

`--void-2` 底 + 紫色 `源文件 · 可改` 角标 + 版本号。页脚一句话说清四态分工：

> 存关系表 → 导出 YAML → 喂大模型用裁剪后的 YAML 片段（不含物理 SQL）→ 大模型回 JSON 意图 → 引擎吃编译后的 manifest。

#### 右栏 · 编译轨道（签名元素）

四阶：`1 意图 → 2 关系路径 → 3 物理 SQL → 4 结果`，已完成态实心、当前态描边高亮。下方是编译出的 SQL（`派生 · 只读`）+ 页脚 `路径 order → user · 2 JOIN · 耗时 6 ms` + 四级诊断行（OK / WARN / ERR + 定位到 `measures`、`relations` 等段）。

> 建议把编译轨道升格为**全局进度规范**，其他多阶段流程（结构同步、AI 富化）复用同一语言。

#### 底部动作条

四个动作，**文案自带一行说明**（不用 tooltip）：

| 动作 | 说明 | 对应 addendum |
|---|---|---|
| 预览定义 | 看编译结果，不执行 | 本体预览 |
| 预览数据 | 裸跑前 50 行 | 数据预览 |
| 试跑查询 | 套上选择器与过滤器 | 本体数据预览 |
| **发布 v3** | 当前生效 v2 · 草稿对智能体不可见 | 发布 |

再加 **`3 处未保存改动` + 撤销**——切页签前必须能看见改动没落地。

**发布必须过预检**。发布改变智能体取数口径，等同写操作：

```
发布预检 · order v2 → v3
  口径变更（3）
    − pay_amount: 订单金额（含优惠）
    + pay_amount: 实付金额（已扣优惠，不含退款）
    + measures.avg_order_value: non_additive
  影响范围 · 3 个智能体正在引用
    经营日报智能体   用于 GMV 口径
    客服查单助手     仅用状态维度
    数据分析师       金额口径将变化   ← 玫红警示
  发布后 24 小时内可一键回滚到 v2，历史版本永久留存。
              [取消] [确认发布]
```

### 2.3 标准属性（`v-attr`）

左列表（每项显示 `被 N 个本体引用`）+ 右详情。

**枚举表格四列即 addendum 的四要素**：`key`（mono）/ `value` / **`def` 业务口径** / **`next` 下一状态**，外加同义词。

- `def` 是**写给大模型判断用的口径**，不是给人看的备注
- `next` 用 mono + `→` 表达状态流转，支撑漏斗分析与非法流转校验
- **语义分组**单独一块：`已完结 = [3, -1]`、`未完结 = [0,1,2]`，直接消解「未完结订单」这类歧义提问
- **三种录入方式**并列可见：表格手填 / JSON 粘贴（表格⇄JSON 双模式切换）/ **SQL 取字典表**（`SELECT dict_code AS key, dict_name AS value, remark AS def FROM sys_dict` → 预览映射 → 入库 → 一键刷新）
- 改标准属性时提示`将影响 N 个本体`，可选同步或断开转副本

### 2.4 SQL 控制台（`v-con`）

**三段**：左 schema 树（可折叠到表→列，列带类型标签）｜中 深色编辑器｜下 结果网格。

- 顶栏左侧固定 **只读护栏** 徽标 + `上限 500 行 · 超时 30s · 单语句`——护栏是常驻状态而非提示语
- 按钮带键位：`格式化 ⇧⌥F` / `运行选中 ⌃↵` / `全部运行 ⌃⇧↵`
- 编辑器顶栏显示 `3 条语句 · 光标在第 2 条`，选中段高亮，未选中段灰化——直接回答用户的「选中执行 / 多条执行都支持」
- 结果网格：行号列 + 表头带类型 + NULL 显示为弱化 `NULL` 而非空白 + 底部 `耗时 / 行数 / 是否截断`

### 2.5 查询结果面板（`v-res`）

智能体右栏形态，接入既有 `ChatPreviewPane` 多 tab 体系（新增一种 `kind`）。

自上而下：**本体来源标注**（`order · 数据源 言智项目库`）→ **过滤器条**（chip 可增删，映射本体过滤器）→ 迷你趋势图 → 数据网格 → 分页（页大小 + 总行数 + 是否截断）→ 底部 `导出 CSV` / `用 Python 分析` / `生成报告`。

> 底部三个动作正是能力链出口：查数 → python 分析 → doc 报告，对应挂 `skill_data_analysis` 与 `skill_report_doc` 两级。

## 5. 待拍板的开放问题

评审提出三个需要产品决策的问题，**UI 层无法自行消解**：

1. **首次上手成本**：不会写 SQL 的人打开本体页，看到三栏 + 5 子页签 + 编译轨道，第一眼知道该干什么吗？还是以为这是给 DBA 的工具？→ 建议补一个**引导态**：本体数为 0 时，中栏不显示空表单，而显示「从数据源同步 → AI 生成草稿 → 你只需复核」三步引导。
2. **心智模型**：用户第一周能否建立「本体 = 我和 AI 之间的取数合同」这个认知？还是会把 YAML 当成又一个配置文件？→ 建议在 `发布预检` 里持续强化「改的是智能体的口径」这个因果。
3. **角色分离**：`预览定义 / 预览数据 / 试跑查询 / 发布` 是给**写本体的人**还是**审本体的人**用的？两种角色需要的动作不同，目前只有一套。→ 若后续要做协作，需拆出「提交复核」与「批准发布」。

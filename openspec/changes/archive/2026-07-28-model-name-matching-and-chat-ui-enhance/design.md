## Context

当前系统在对模型的管理中存在以下问题：

1. **模型 ID 漂移**：`fetchRemoteModels` 中每次拉取远程模型都会用 `uid('m_')` 生成新 ID，即使模型已存在本地。虽然后续通过 `modelId` 在 Map 中查找并更新已有条目，但新增模型总用新 ID。当远程 API 返回的模型列表有增删时，本地模型列表与远程之间的关系依赖 ID 和 `modelId` 两个维度，容易产生不一致。

2. **会话引用不稳定**：`Conversation` 通过 `modelId` 字段存储的是模型的内部 ID（`m.xxx`），而非实际的模型名称（如 `gpt-4o`）。当模型被删除后重新拉取，内部 ID 变化导致会话找不到对应模型。

3. **聊天输入区缺少快捷入口**：当前 input toolbar 中间区域有智能体选择、模型选择、MCP、Skill 入口，右侧仅有一个发送按钮。用户需要频繁去侧边栏新建会话，体验不佳。工作目录切换也没有直观入口。

## Goals / Non-Goals

**Goals:**
- 模型匹配逻辑统一改用 `modelId`（模型名称/标识符，如 `gpt-4o-mini`）作为唯一标识，在同一平台内模型名称天然唯一
- `fetchRemoteModels` 按 `modelId` 做 insert-or-update，不再产生重复记录
- 会话中存储的模型引用通过 `modelId + platformId` 交叉定位，而非依赖易变的内部 ID
- 聊天输入区工具栏新增"新建会话"图标和一键入口
- 聊天输入区工具栏新增"工作目录选择"图标，实现目录浏览和切换

**Non-Goals:**
- 不改变 `Model` 接口的数据库表结构（内部 `id` 仍是主键）
- 不改变服务端 API 的模型管理逻辑
- 工作目录选择不支持自定义输入路径文本（仅文件树浏览）

## Decisions

### Decision 1: 模型匹配以 `(platformId, modelId)` 为逻辑唯一键

**选择**：在本地客户端（离线模式）的 `fetchRemoteModels` 中，以 `modelId` 为查找 key，而非内部 `id`。

**理由**：同一平台下 `modelId` 是 API 提供商定义的模型名称（如 `gpt-4o`、`claude-sonnet-4-20250514`），天然唯一且不变。现有逻辑已用 `Map<modelId, Model>` 做查找，但新增模型时强制用 `uid()` 生成新 ID，导致即使同一 `modelId` 已有记录也会被新 ID 覆盖。改为：已有则更新（保留原 ID），无则新增。

**替代方案**：
- 只用 `modelId` 作为主键去掉内部 `id` → 影响范围太大，数据库迁移风险高，不采纳
- 在服务端做幂等去重 → 需要同时改服务端和客户端，不在本次范围

### Decision 2: 会话存储模型引用使用 `modelId` 而非内部 `id`

**选择**：会话创建/更新时直接存储 `modelId`（字符串）而非内部 `id`，查询时通过 `modelId + platformId` 交叉查找 Model 对象。

**理由**：当前 `Conversation.modelId` 字段存的是 `Model.id`（内部 UUID），这导致模型重新拉取后 ID 变化，会话就无法定位模型。改为存 `modelId`（模型名称）后，只要模型存在于同平台下就能匹配。

**迁移**：存量会话的 `modelId` 字段存的是内部 ID 格式（如 `m_xxx`），需要在加载时兼容老格式——先尝试按 `modelId` 精确匹配，匹配不到则回退到内部 ID 查找。

### Decision 3: 新建会话图标放在输入区 toolbar-right 区域

**选择**：在 toolbar-right 区域发送按钮左侧添加一个新建会话图标按钮（`Plus` 图标），点击后执行 `startNewChat()`。

**理由**：用户自然操作路径是"在聊天框附近新建会话"，放在发送按钮旁边是最接近操作焦点的位置。同时保留侧边栏的"新建"按钮，保持一致。

### Decision 4: 工作目录选择器作为独立弹窗组件

**选择**：在 toolbar-center 区域添加工作目录选择图标，点击弹出 Dialog 展示文件系统树，用户选择目录后更新工作目录状态。

**理由**：工作目录是影响 AI 助手上下文的重要设置，用 Dialog 弹窗提供完整的浏览体验更直观。目录路径持久化到 keyring 设置中。

## Risks / Trade-offs

- **存量数据兼容**：已有会话中 `modelId` 存的是内部 ID（如 `m_xxx`），需要在 modelId 解析时做兼容处理 → 在 Chat 组件中增加回退查找逻辑
- **`modelId` 名称重复**：理论上同一平台不会有相同名称的模型，但需在拉取时做防御性检查 → 拉取时如发现同一 `modelId` 有多条记录，保留第一条，其余禁用
- **服务端模式**：在线模式下模型通过 API 管理，`modelId` 冲突由服务端处理 → 客户端仅处理离线模式的去重逻辑

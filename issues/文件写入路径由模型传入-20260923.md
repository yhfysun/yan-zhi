# 文件写入路径由大模型传入 —— 文件散落 + 预览必 404

- **状态**：**已修复**（2026-09-23）
- **严重度**：high
- **发现方式**：用户反馈「文件写入还是不对啊。。。。路径不应该方法里面自己判断？还用大模型传？」

## 现象

1. agent 写出的文件**散落在工作区各处**，不在会话产物目录里（用户看到"文件写得到处都是"）；
2. 文件管理里点开 / 预览这些文件**打不开**（404）；
3. 与另一条台账 [产物根目录漂移导致媒体404-20260919.md](产物根目录漂移导致媒体404-20260919.md)
   的"生成图片能看到但预览不行"是**同一个病根**。

## 根因

`packages/core/src/tool/builtin/file-write.ts` 的 `inputSchema`：

```ts
required: ['path', 'content']        // ← path 必填，模型只能自己编
path: { description: 'The absolute or relative path to write the file to.' }
```

而**产物位置在本系统里是确定性可推导的**：
`<根>/.yan-zhi/tasks/<conversationId>/{intermediate,deliverables}`
（见 `@yan-zhi/shared` 的 artifact-paths，以及 `services/artifact-dir.ts` 的单一出口）。

调用方 `llm-task-manager.executeTool()` 手里就有 `task.conversationId`，
**完全可以在代码层算好目录传进去**，却让模型去猜位置 →
① 落点随机、散落各处；② 不在规范目录内，服务端静态媒体路由定位不到 → 预览 404；
③ 登记进 `conversation_file.path` 的是一个"模型以为存在"的位置。

## 影响面

- 所有经 `file_write` 落盘的文本产物（报告、代码、CSV…）。
- 与媒体产物（图片/视频）同源：媒体走 `mediaTarget()` 是**服务端自己定目录**（正确），
  文本走 `file_write` 是**模型定目录**（错误）—— 两条路径口径不一致，是问题的结构性成因。

## 修复（用户明确要求：**不做回调抽象，代码层面直接传入**）

### 1. 工具侧：不再推导路径

- `required` 改为 `['content']`；新增 `file_name`（只要文件名，不要路径）；
  `path` 保留但语义收敛为「仅当用户明确点名要某个落点时才填」。
- 新增可选第二参数 `ctx: ToolContext`（`packages/core/src/tool/types.ts`）：

```ts
export interface ToolContext {
  conversationId?: string;
  userId?: string;
  /** 本会话各分类产物目录的**绝对路径**，调用方直接传入 */
  artifactDirs?: { intermediate?: string; deliverable?: string; upload?: string };
}
```

- 工具只做：`ctx.artifactDirs[category]` + 文件名 → 落盘。
  **不做路径推导、不查库、不注回调**（core 是平台无关层，路径怎么算属边缘层知识）。
- 文件名来源：`file_name` → 退化取模型传的 `path` 的 basename → 再退化按内容首个标题/时间戳生成。
  文件名里的路径分隔符一律清理（防越界）。

### 2. 调用点：算好直接传

`llm-task-manager.ts` 的内置工具分支里，用**与媒体同一个单一出口**
`resolveArtifactDirFor()` 算出三个分类目录，组成 `toolCtx` 传给 `registry.execute(toolName, args, toolCtx)`。

### 3. 登记：用工具回传的**实际路径**

工具在 `_meta` 里回传 `{ path, name, category, bytes, beforeContent }`；
`executeTool` 通过 `metaOut` 出参把它交给主循环，`conversation_file` 一律登记 `_meta.path`
（不再用 `args.path`）。

★ 顺带修掉 Diff 快照：`file_write` 的落盘路径只有工具自己知道（调用方执行前无法预知），
故 `beforeContent` 由**工具在落盘前自己读**并回传（`file_edit` 仍走调用方预读）。
此前用 `args.path` 取原内容会读到错误位置 → diff 面板显示"整篇新增"。

## 复现与验证

验证脚本直接调 `FileWriteTool`（带 ctx），7 项断言全过：

| # | 场景 | 期望 | 实测 |
|---|---|---|---|
| ① | `required` 内容 | 只含 content、有 file_name | ✓ |
| ② | 只给 content + category | 落到 ctx 给的交付目录；文件名由内容首行推导 | ✓ `销售分析.md` |
| ③ | 给 file_name | 尊重文件名，目录仍由 ctx 决定 | ✓ `数据表.csv` |
| ④ | **仍按旧习惯传了 path（含目录）** | 目录被忽略、只取 basename | ✓ 落在中间目录，未随模型路径跑 |
| ⑤ | `file_name: '../../escape.txt'` | 分隔符被清理、不越界 | ✓ `_.._escape.txt` |
| ⑥ | 无 ctx（desktop/web/单测） | 退回旧行为、不崩 | ✓ |
| ⑦ | beforeContent 回传 | 读到旧内容（供 Diff） | ✓ |

守门测试：`packages/ui/src/composables/fileWriteAndPreviewFix.test.ts`
（15 例覆盖"工具侧不推导 + 调用点确实算好传了 + 登记用实际路径"），
**变异测试 14/14 全部有效**。

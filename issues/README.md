# issues/ — 已知问题台账

本目录记录**项目当前存在、尚未解决**的问题。

## 用法

- 一个问题一个 Markdown 文件，文件名用 `简述-日期.md`（如 `产物路径漂移-20260919.md`）。
- 每条问题必须写清：**现象 → 根因 → 影响面 → 复现步骤 → 修复方向**。
- **问题修复并验证通过后，把对应文件从本目录删除。**
  本目录里应该只剩下「还没做完的事」；文件越少越好，全是空目录说明状态健康。
- 若某个问题长期挂着（超过一个迭代周期）无法推进，在文件里加一行
  「阻塞原因」说明为什么动不了，而不是让它悄悄烂在那里。

## 为什么单独开一个目录

排障结论散落在聊天记录、临时脚本、代码注释里，下一次接手的人（或几个月后的自己）
很难找全。集中成台账后：
- 有明确的「收件箱」可以逐条消化；
- 解决了就删除，天然形成「剩余工作量」的可见度量；
- 避免同一个坑被反复重新分析（本目录的第一个问题就是这样被查了两遍）。

方案类文档（打算怎么做）仍放 `docs/`；本目录只放**问题本身**。

# 工具历史参数被清洗成 `{}`，导致模型模仿空参并陷入退化循环

- 日期：2026-09-29
- 严重度：**high**
- 状态：已定位根因，**已修复**（见下方「修复记录」）

> ★ 关于「为什么会有两份 core」：源码只有一份，另一份是**构建副产物**。
> `server/node_modules/@yan-zhi/core/package.json` 的 `main` 指向
> `../../../dist/packages/core/src/index.js`，即运行时实际加载的是
> `server/dist/packages/core/`；而 `server/node_modules/@yan-zhi/core/dist/core/`
> 是构建时连带产出、无人引用的冗余副本（两者差异仅 3 行 import 的 `.js` 后缀）。
> → 修复只需改源码并重新构建，无需手工同步两份。

## 现象

工具调用频繁出现 `arguments` 为空（`{}`），框架据此拦截并回提示：

> 工具 python_exec 未执行：arguments 缺少必填参数（code）。可能原因：输出被长度上限截断（如 max_tokens 偏小或未生效）、流中断，或模型本身不擅长工具调用。请重试并一次性给出**完整且简短**的 JSON 参数……

该提示把原因归给「max_tokens 偏小 / 模型不行」。

**实测数据（生产库 687 条含 tool_calls 的消息）**：

| 工具 | 调用数 | 空参 | 空参率 |
|---|---|---|---|
| python_exec | 480 | 374 | **77.9%** |
| browser_get_page_info | 5 | 5 | 100% |
| browser_get_page_content | 27 | 21 | 77.8% |
| browser_navigate | 68 | 29 | 42.6% |
| file_read | 49 | 13 | 26.5% |

## 根因（两条互补链路）

### 主因：`toApiMessage` 回放历史时清空 `arguments`

`packages/core/src/llm/client.ts:49-64`

```ts
if (m.toolCalls?.length) {
  out.tool_calls = m.toolCalls.map(tc => ({
    id: tc.id,
    type: 'function',
    function: {
      name: tc.toolName || (tc as any).function?.name,            // ← name 有兜底
      arguments: typeof tc.arguments === 'string'
        ? tc.arguments
        : JSON.stringify(tc.arguments || {}),                     // ← arguments 没有兜底 ✗
    },
  }));
}
```

**数据结构不匹配**：主循环落库的是 `DeltaToolCall` 形态（参数在 `function.arguments`），
而这里只读顶层 `tc.arguments`（那是内部 `ToolCall` 的形态，两者不同构）。

实测（真实库 220 个 tool_call 样本）：

```
有顶层 arguments   = 0
有 function.arguments = 220
```

→ 命中率 **100%**：每一次历史回放，assistant.tool_calls 的参数都被洗成 `{}`。

后果链：

1. 模型看到的「自己上一轮调用工具的记录」参数全为 `{}`（例：
   `{"function":{"name":"python_exec","arguments":"{}"}}`，尚未被 sanitize 剥离，因为配对 id 完整）；
2. 模型模仿历史格式，继续输出空参；
3. 空参被 `missingRequiredArgs` 拦截 → tool 回一条无参数的错误说明；
4. 模型再模仿 → **自我强化的退化循环**，直到 `consecutiveArgFailures >= 3` 断路。

### 结构性缺陷：`ContextWindow` 只认 `content`

`packages/core/src/compress/window.ts`（已接在主链路 `llm-task-manager.ts:1211-1227`）

- `tokenCount()` 只累加 `content + reasoningContent`，**完全不计 `toolCalls`**；
  实测该字段占总字符 **13%**，且长任务里工具参数（尤其 `code`）往往是最长的那部分。
- `summarize()` 用 `messages.map(m => \`${m.role}: ${m.content || ''}\`)` 生成摘要输入，
  **直接丢弃 `toolCalls`** —— 压缩后历史里连「用正常参数调用过工具」的样本都不剩，
  模型只能模仿 keepRecent 窗口内残留的空参样本。
- 阈值口径不一致：判据用 `tokenCount`（保守低估，实测低估约 **2 倍**），
  而 `maxTokens` 传的是 `model.contextWindow`（100 万级），
  二者不是同一个量纲 → 压缩几乎永不触发，上下文无限膨胀（实测单会话 1156 条消息 /
  真实 prompt ≈ 22 万 token），模型同时被「参数全空的历史」持续污染。

### 同类遗漏（一并核对）

- `packages/core/src/llm/anthropic.ts:107-108`：`name: tc.toolName` + `input: parseInput(tc.arguments)`
  同样只读顶层 → Claude 协议下同样丢参。

**仓库内已有正确先例**（说明这是遗漏而非设计）：
`apps/server/src/workflow-runner.ts:447` 写的是
`parseToolCallArgs(tc.arguments ?? tc.function?.arguments)`。

## 影响面

- 所有走 ReAct 主循环、依赖**历史回放**的模型调用；会话越长越严重。
- 实测空参率随会话内调用序号单调攀升，与根因吻合：

| 会话内第几次调用 | 空参率 |
|---|---|
| 1-5 | 26.5% |
| 6-20 | 36.6% |
| 21-50 | 33.0% |
| 51-100 | 63.0% |
| 100+ | **75.4%** |

- 首次调用 12.5% vs 后续调用 63.2%；
  「首调用参数正常且总调用 ≥2」的会话里，**83%** 后续出现空参。
- 任何**不支持 tools、被迫走文本模式**的模型更是必踩（无 id 时上下文丢失时文本确实是唯一来源）。
- **与 max_tokens 无关**：实测 `file_read` 的必填参数 `path` 只需几十字符，同样出现空参；
  且多轮空参发生时 `completion_tokens` 很小、`reasoning_len = 0`，不存在上限压力。

## 复现步骤

1. 打开任意长会话（调用过数十次工具）；
2. 触发一次工具调用；
3. 在「LLM 交互日志」中确认发往上游的 `messages` 里，历史 assistant 的
   `tool_calls[].function.arguments` 全为 `"{}"`，而库里 `message.tool_calls_json` 参数完好。

静态复现（构建期即可）：

```sql
SELECT COUNT(*) FROM message
WHERE tool_calls_json NOT LIKE '%"function":{"name"%';   -- 顶层 arguments 的行数 → 0
```

## 修复方向

1. **`toApiMessage` 补兜底**（一行，主因）：
   `arguments: tc.function?.arguments ?? (typeof tc.arguments === 'string' ? tc.arguments : JSON.stringify(tc.arguments || {}))`
   同样给 `name` 补 `tc.function?.name ?? tc.toolName`。**注意顺序**：顶层与嵌套都要兼容。
2. **`anthropic.ts` 同步**：`name: tc.function?.name ?? tc.toolName`、
   `input: parseInput(tc.function?.arguments ?? tc.arguments)`。
3. **`ContextWindow` 修正**：
   - `tokenCount()` 计入 `toolCalls`（序列化后估算）；
   - `summarize()` 保留 `toolCalls`（至少保留工具名与参数摘要，避免丢掉「正常调用」样本）；
   - 阈值口径统一：要么按 `contextWindow × 安全系数`，要么用真实 token 估算。
4. 补回归测试：断言「`DeltaToolCall` 形态经 `toApiMessage` 后 `arguments` 不丢」。
5. 稳定后，把 `missingRequiredArgs` 的提示文案从「怀疑 max_tokens / 模型能力」
   改为优先提示「历史参数回放异常」，避免继续误导排查方向。

## 阻塞原因

无。改动集中、影响面清晰，可直接修。

## 备注

框架那条提示文案（`llm-task-manager.ts:1849-1852`）按「输出被长度上限截断」引导用户换模型 / 调大 tokens，
在本次实测中**方向是错的**：干净上下文下同一模型同一工具能稳定吐出 ~2000 字符的完整参数。
建议修复后一并修正文案，否则下次仍会把人带到错的方向。

## 补充实验（2026-09-29 深夜）：修复有效，但暴露两个**独立**的新问题

用真实会话（`aaa84c6c`，取最近 200 条）直连上游做三组对照：

| 组 | 历史 tool_call 空参占比 | 实际结果 |
|---|---|---|
| `old`（复刻旧 bug，只读顶层） | **100%**（104/104） | `finish=length`，**一个工具都不调** |
| `new`（修复后，两种形态都认） | **33%**（34/104） | `finish=length`，**仍不调工具** |
| `new` + 剔除历史残留空参样本 | **0%** | ✅ 正常调用 `python_exec`，代码 508 字符 |

### 结论 1：修复确实生效，但**只修回放还不够**
历史里只要有 **1/3** 的空参样本，模型就跟着空 —— 修复把 100% 降到 33%，
但**旧会话里已落库的空参调用记录依然在污染**。
→ 所以已同时修正 `ContextWindow` 阈值口径（`forContextWindow`）：让压缩真正开始工作，
   把老历史摘要化（摘要保留工具名+参数），空参样本才会被压出上下文。
   **旧会话不必删，但需要压缩真正触发；最干净仍是新会话。**

### 结论 2（新发现）：`finish_reason` **完全没被读取** —— 截断信号被静默丢弃
`grep -c finishReason apps/server/src/llm-task-manager.ts` = **0**。
`parseSSE` 明明解析并返回了 `finishReason`，主循环却从不读它。
→ 后果：因输出上限被截断时（`finish=length`，`arguments` 是**半截 JSON**），
   代码无法区分「模型没生成」与「生成到一半被切断」，
   统一走 `missingRequiredArgs` 并给出「怀疑 max_tokens / 模型能力」的**错误归因**。
→ 修复方向：读 `finish_reason`；为 `length` 走独立分支 ——
   保留已收到的 JSON **片段作预览**（例如 `{"code":"import os, subprocess\\nF=r"C:/...`），
   明确告知模型「本次因输出上限被截断，**不要重试同样长度**，改用 `file_write` 把代码落盘后执行」。
   ★ 这才是"下一轮补全"真正有效的形式：**不是补你这次没发的参数，而是换个工具让它能表达完**。

### 结论 3：为什么**不适合**做「工具参数补全子智能体」
- `arguments` 是模型在**同一次生成**里吐出来的，代码层拿到时它已经定型；
  子智能体无法"补"一个模型根本没生成完的东西（它拿不到那次生成的中间态）。
- 要补只能**让模型重新生成** —— 而框架本来就会把提示作为 `tool` 结果喂回去触发重试，
  **这个机制已经是"补全"**。加一层子智能体只是给同一次重试多包一层，不产生新信息。
- 内置智能体也解决不了：`builtin_tool_ids` 非空的智能体不走兜底工具集；
  且子智能体按 `parentToolCallId` 隔离消息，**看不到父任务的上下文**（这是刻意的隔离设计）。
- 隐藏同理不需要：它是正常工具，按现有机制正常显示即可。
- ★ 真要"辅助"，方向应是**换工具**（长参数用 `file_write` 分步落盘，而不是塞进一个巨大 `code` 字段），
  这靠提示词 + 截断感知即可，不需要新增智能体。


**判定口径（刻意保守，避免误判）**：
- 「空」= 空串 / 纯空白 / 空的 `{}`；**半截 JSON 不算空**（它是截断信号，两者不能混）。
- 「截断」= `finish_reason === 'length'` **或** 以 `{` 开头且 `JSON.parse` 失败。
  不以 `{` 开头的一律不算（否则老模型的纯文本参数会被误判）。
- 非截断场景走普通缺参提示，**不再臆测"截断 / max_tokens"**，避免重复误导排查方向。

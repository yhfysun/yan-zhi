# 代码审查（code-review）

对代码进行系统化审查，按严重度分级输出问题与改进建议。结合静态工具 + 人工检查清单，覆盖质量/可读性/性能/错误处理/命名/重复/安全。

## 何时触发

- 用户说"审查代码""review 一下""代码走查""帮我看看代码"等
- 用户提交 PR / 合并请求，要求审查
- 用户要求检查某文件/目录/函数的代码质量

## 标准流程

1. **确定范围**：明确审查的文件/目录/PR diff/语言
2. **静态扫描**（可选）：运行 linter 捕获机械问题
3. **逐项审查**：按检查清单逐类排查
4. **分级报告**：按 阻塞/重要/建议/表扬 分类输出，每项给位置 + 问题 + 修复建议 + 代码示例

## 静态工具辅助

```bash
# JS/TS
npx eslint <file> --ext .js,.ts,.tsx
npx prettier --check <file>
# Python
ruff check <file>
pyright <file>
# Go
golangci-lint run <file>
# 通用复杂度
npx cr --file <file>   # 圈复杂度
```

## 检查清单

### 1. 正确性
- 边界条件是否处理（空值/0/负数/越界/空集合）
- 异步是否正确等待（漏 await、竞态、未处理的 Promise）
- 错误是否被吞掉（空 catch、catch 后不记录不抛出）
- 资源是否释放（文件/连接/锁/订阅未关闭）

### 2. 可读性
- 命名是否达意（`data`/`tmp`/`x` 等无意义名）
- 函数是否过长（> 80 行需拆分）
- 嵌套是否过深（> 4 层用提前返回/提取函数）
- 注释是否解释"为什么"而非"是什么"

### 3. 重复与抽象
- 是否有复制粘贴的重复块（提取公共函数）
- 是否过度抽象（只用一次的泛化封装）

### 4. 性能
- 循环内是否有不必要的重复计算/IO
- 大列表是否用了低效查找（O(n²) 可改 Map/Set）
- 是否在热路径做重复序列化/正则编译

### 5. 错误处理
- 外部调用（网络/文件/DB）是否处理失败分支
- 错误信息是否对调试有用（带上下文）
- 是否区分"可重试"与"不可重试"错误

### 6. 安全（简要）
- 输入是否校验、是否信任了用户输入
- 是否有硬编码密钥/凭证
（详细安全审计见 code-security-audit skill）

### 7. 测试
- 关键分支是否有对应测试
- 测试是否覆盖失败路径，不只 happy path

## 报告格式

```
## 代码审查报告

### 阻塞（必须修改）
- [正确性] src/foo.ts:42 — async 函数漏 await，Promise 未等待
  修复：const res = await fetch(...)

### 重要（强烈建议）
- [错误处理] src/bar.ts:18 — catch 块为空，错误被吞
  修复：catch (e) { logger.error(e); throw e }

### 建议（可选优化）
- [可读性] src/baz.ts:30 — 变量名 `d` 不达意
  修复：改为 `deadline`

### 表扬
- src/qux.ts 抽象清晰，测试覆盖完整
```

## 注意事项

- 优先看正确性和错误处理，再谈风格
- 给修复建议时附最小代码示例
- 区分"必须改"和"锦上添花"，不要把风格问题标成阻塞
- 大改动建议拆成多个小 PR
- 安全问题深挖请转用 code-security-audit skill
